<a name="section-01"></a>
## HTTP 버전별 발전

<a name="q1"></a>
### Q1. [대표 질문] HTTP/1.1, HTTP/2, HTTP/3의 차이는 무엇인가요?

> "HTTP/1.1은 지속 연결을 지원하지만 하나의 연결에서 여러 응답을 효율적으로 병렬 처리하는 데 한계가 있습니다.
>
> HTTP/2는 바이너리 프레이밍과 멀티플렉싱을 통해 하나의 TCP 연결에서 여러 스트림을 처리합니다.
>
> HTTP/3는 UDP 기반 QUIC을 이용하여 스트림 간 HOL Blocking을 완화하고 연결 관리 기능을 개선했습니다."

| 구분 | HTTP/1.1 | HTTP/2 | HTTP/3 |
| --- | --- | --- | --- |
| 전송 기반 | TCP | TCP | QUIC/UDP |
| 메시지 전송 | 텍스트 | 바이너리 프레임 | QUIC 기반 프레임 |
| 멀티플렉싱 | 일반적으로 미지원 | 지원 | 지원 |
| 헤더 압축 | 기본 미지원 | HPACK | QPACK |

**핵심 요약**

HTTP/1.1은 지속 연결, HTTP/2는 멀티플렉싱, HTTP/3는 QUIC 기반 스트림 독립성이 핵심이다.

<a name="q2"></a>
### Q2. HOL Blocking이란 무엇인가요?

> "HOL Blocking(헤드 오브 라인 블로킹)은 앞선 데이터나 작업의 지연 때문에 뒤에 있는 작업까지 진행이 지연되는 현상입니다.
>
> HTTP/1.1에서는 응답 순서에 따른 지연이 발생할 수 있으며, HTTP/2에서는 TCP 계층의 데이터 손실로 여러 스트림이 함께 지연될 수 있습니다."

**핵심 요약**

HOL Blocking은 앞선 데이터나 작업의 지연이 뒤의 작업까지 영향을 주는 현상이다.

<a name="q2-1"></a>
#### ↳ Q2-1. HTTP/1.1에서는 HOL Blocking을 어떻게 완화했나요?

> "브라우저는 여러 TCP 연결을 이용해 요청을 병렬로 처리하기도 했으며, 개발자는 리소스 번들링, 이미지 스프라이트, 도메인 샤딩 등의 방법을 활용했습니다.
>
> HTTP Pipelining도 있었지만 실제로는 여러 제약이 있었습니다."

**핵심 요약**

HTTP/1.1에서는 여러 연결과 리소스 최적화로 HOL Blocking의 영향을 줄였다.

<a name="q3"></a>
### Q3. HTTP/2의 멀티플렉싱이란 무엇인가요?

> "멀티플렉싱(Multiplexing, 멀티플렉싱)은 하나의 TCP 연결에서 여러 요청과 응답을 독립적인 스트림으로 구분하고, 프레임을 교차 전송하는 방식입니다.
>
> 이를 통해 여러 요청을 효율적으로 처리하고 반복적인 연결 수립 비용을 줄일 수 있습니다."

**핵심 요약**

멀티플렉싱은 하나의 연결에서 여러 스트림의 데이터를 교차 전송하는 기술이다.

<a name="q3-1"></a>
#### ↳ Q3-1. HTTP/2는 왜 성능이 개선되었나요?

> "하나의 TCP 연결에서 여러 스트림을 처리해 여러 연결을 관리하는 비용을 줄이고, HPACK으로 반복되는 헤더의 전송 크기를 줄일 수 있기 때문입니다.
>
> 다만 실제 성능은 네트워크 상태와 요청 특성에 따라 달라집니다."

**핵심 요약**

HTTP/2는 멀티플렉싱과 헤더 압축으로 통신 효율을 높인다.

<a name="q3-2"></a>
#### ↳ Q3-2. 멀티플렉싱과 멀티스레딩은 같은 개념인가요?

> "아닙니다. 멀티플렉싱은 하나의 통신 연결에서 여러 데이터 스트림을 효율적으로 전송하는 방식입니다.
>
> 멀티스레딩은 하나의 프로세스에서 여러 스레드를 이용해 작업을 실행하는 방식입니다.
>
> 따라서 멀티플렉싱은 네트워크 데이터 전송, 멀티스레딩은 프로그램 실행과 동시성 처리에 관한 개념입니다."

**핵심 요약**

멀티플렉싱은 데이터 전송 방식이고 멀티스레딩은 프로그램 실행 방식이다.

<a name="q3-3"></a>
#### ↳ Q3-3. 멀티플렉싱을 사용하면 모든 요청이 동시에 완료되나요?

> "아닙니다. 여러 요청의 프레임을 교차 전송할 수 있다는 뜻이지 모든 요청의 처리 시간이 같다는 뜻은 아닙니다.
>
> 각 요청의 서버 처리 시간, 데이터 크기, 네트워크 상태 등에 따라 완료 시점이 달라집니다."

**핵심 요약**

멀티플렉싱은 동시 전송을 지원하지만 모든 요청의 동시 완료를 보장하지 않는다.

<a name="q4"></a>
### Q4. HTTP/2에서도 HOL Blocking이 발생하나요?

> "그렇습니다. HTTP/2는 HTTP 계층의 응답 순서 대기 문제를 개선했지만 TCP 위에서 동작합니다.
>
> TCP 패킷 손실이 발생하면 순서 있는 바이트 전달을 위해 같은 TCP 연결의 여러 스트림이 함께 지연될 수 있습니다."

**핵심 요약**

HTTP/2는 HTTP 계층의 HOL Blocking을 완화했지만 TCP 계층의 HOL Blocking은 남아 있다.

<a name="q5"></a>
### Q5. HTTP/3는 왜 UDP 기반 QUIC을 사용하나요?

같은 질문의 다른 회차 답변 · [tcp-udp-handshake](../tcp-udp-handshake.md#q11)

> "HTTP/3는 QUIC을 통해 독립적인 스트림을 제공하고 TCP 수준의 HOL Blocking 문제를 완화합니다.
>
> UDP 자체에는 TCP 같은 신뢰성 기능이 없지만 QUIC이 손실 복구, 재전송, 흐름 제어, 암호화 등을 구현합니다."

**핵심 요약**

HTTP/3는 QUIC을 이용해 신뢰성과 스트림 독립성을 함께 제공한다.

<a name="q5-1"></a>
#### ↳ Q5-1. HTTP/3의 연결 수립이 빠른 이유는 무엇인가요?

> "QUIC은 TLS 1.3을 통합하여 일반적인 새 연결을 1-RTT로 수립할 수 있고, 조건에 따라 재방문 시 0-RTT 데이터를 사용할 수 있습니다.
>
> 단, 0-RTT는 재전송 공격 위험 등을 고려해야 합니다."

**핵심 요약**

QUIC은 TLS 통합과 0-RTT 재개로 연결 지연을 줄일 수 있다.

<a name="q5-2"></a>
#### ↳ Q5-2. Connection Migration이란 무엇인가요?

> "Connection Migration(커넥션 마이그레이션)은 클라이언트의 IP 주소나 포트가 변경되어도 연결 ID를 이용해 기존 QUIC 연결을 이어갈 수 있도록 하는 기능입니다.
>
> Wi-Fi에서 모바일 네트워크로 전환하는 상황이 대표적인 사례입니다."

**핵심 요약**

Connection Migration은 네트워크가 바뀌어도 QUIC 연결을 유지할 수 있게 한다.

<a name="q6"></a>
### Q6. HTTP/2는 텍스트 기반인가요?

> "아닙니다. HTTP/1.x는 텍스트 기반 메시지 형식을 사용하지만 HTTP/2는 바이너리 프레이밍을 사용합니다.
>
> 이를 통해 메시지의 구조적 처리와 멀티플렉싱을 지원합니다."

**핵심 요약**

HTTP/1.x는 텍스트 기반이고 HTTP/2는 바이너리 프레이밍 기반이다.

<a name="q7"></a>
### Q7. HTTP/2를 사용하면 번들링이 필요 없나요?

> "과도한 리소스 번들링의 필요성은 줄어들지만 완전히 불필요해지는 것은 아닙니다.
>
> 압축 효율, 파일 크기, 브라우저 캐시 전략 등을 고려해 적절한 번들링을 사용할 수 있습니다."

**핵심 요약**

HTTP/2는 번들링의 필요성을 줄이지만 성능 최적화에는 여전히 유용할 수 있다.

<a name="section-02"></a>
## HTTP와 HTTPS, TLS

<a name="q8"></a>
### Q8. [대표 질문] HTTP와 HTTPS의 차이는 무엇인가요?

> "HTTP는 기본적으로 통신 내용이 암호화되지 않지만, HTTPS는 TLS를 사용하여 HTTP 통신을 보호합니다.
>
> TLS는 통신 데이터의 기밀성, 무결성, 서버 인증 등을 제공하며, 로그인 정보나 개인정보를 전송하는 서비스에서는 HTTPS를 사용해야 합니다."

**핵심 요약**

HTTPS는 HTTP 통신에 TLS를 적용하여 기밀성, 무결성, 서버 인증을 제공한다.

<a name="q9"></a>
### Q9. HTTPS에서 TLS는 어떤 역할을 하나요?

> "TLS(Transport Layer Security)는 안전한 네트워크 통신을 위한 보안 프로토콜입니다.
>
> TLS 핸드셰이크에서 서버 인증과 키 합의 등을 수행하고, 이후 실제 데이터를 대칭키 기반의 인증된 암호화 방식 등으로 보호합니다."

**핵심 요약**

TLS는 인증과 암호화 키 설정을 통해 통신 내용의 기밀성과 무결성을 보호한다.

<a name="q9-1"></a>
#### ↳ Q9-1. 대칭키와 비대칭키 암호화의 차이는 무엇인가요?

> "대칭키 암호화는 암호화와 복호화에 동일한 비밀키를 사용하는 방식입니다.
>
> 비대칭키 암호화는 공개키와 개인키의 쌍을 사용하는 방식입니다.
>
> 일반적으로 대칭키 암호화는 대용량 데이터 전송에 효율적이며, 현대 TLS는 공개키 기반 인증과 키 합의 기법을 이용하여 통신 키를 안전하게 설정합니다."

| 구분 | 대칭키 암호화 | 비대칭키 암호화 |
| --- | --- | --- |
| 키 | 동일한 비밀키 | 공개키·개인키 |
| 특징 | 일반적으로 빠름 | 키 쌍을 활용 |
| TLS에서 | 실제 애플리케이션 데이터 보호 | 인증·키 합의 관련 기술 |

**핵심 요약**

대칭키는 같은 비밀키로 암복호화하고 비대칭키는 공개키와 개인키를 사용한다.

<a name="q9-2"></a>
#### ↳ Q9-2. HTTPS에서 인증서는 왜 필요한가요?

> "서버 인증서는 클라이언트가 접속한 서버의 신원을 검증하는 데 사용됩니다.
>
> 인증서에는 서버의 공개키와 도메인 관련 정보 등이 포함되며, 브라우저는 인증서 신뢰 체인, 유효 기간, 도메인 일치 여부 등을 확인합니다.
>
> 이를 통해 공격자가 정상 서버를 사칭하는 위험을 줄일 수 있습니다."

**핵심 요약**

HTTPS 인증서는 클라이언트가 서버의 신원을 검증하도록 돕는다.

<a name="q10"></a>
### Q10. TLS Handshake란 무엇인가요?

같은 질문의 다른 회차 답변 · [tcp-udp-handshake](../tcp-udp-handshake.md#q22)

> "TLS Handshake(핸드셰이크)는 클라이언트와 서버가 암호화 통신을 시작하기 전에 보안 매개변수를 협상하고, 서버를 인증하며, 사용할 암호화 키를 설정하는 과정입니다."

**핵심 요약**

TLS Handshake는 서버 인증과 암호화 키 설정을 수행하는 과정이다.

<a name="q11"></a>
### Q11. HTTPS를 사용하면 모든 데이터가 안전한가요?

> "아닙니다. HTTPS는 주로 통신 구간의 데이터를 보호합니다.
>
> SQL Injection, XSS, CSRF, 서버 내부의 취약점, 잘못된 접근 권한 설정 등 애플리케이션 보안 문제까지 자동으로 해결하지는 못합니다."

**핵심 요약**

HTTPS는 전송 구간을 보호하지만 애플리케이션의 모든 취약점을 해결하지는 않는다.

<a name="q12"></a>
### Q12. HTTPS에서는 URL의 경로와 쿼리도 암호화되나요?

> "HTTPS는 HTTP 요청의 경로, 쿼리, 헤더, 본문을 TLS로 보호합니다.
>
> 하지만 연결 대상 IP와 일부 연결 메타데이터는 노출될 수 있으며 URL은 브라우저 기록이나 서버 로그에 남을 수 있습니다.
>
> 따라서 비밀번호 같은 민감한 값을 쿼리 파라미터에 넣는 것은 피해야 합니다."

**핵심 요약**

HTTPS는 경로와 쿼리를 암호화하지만 로그 등 다른 경로의 정보 노출까지 막지는 못한다.

<a name="q13"></a>
### Q13. HTTPS는 왜 HTTP보다 추가적인 연결 과정이 필요한가요?

> "안전한 통신을 위해 TLS 핸드셰이크를 수행하고 서버 인증서와 암호화 키 등을 검증·설정해야 하기 때문입니다.
>
> 다만 TLS 1.3, 세션 재개, 연결 재사용 등으로 이러한 비용을 줄일 수 있습니다."

**핵심 요약**

HTTPS에는 TLS 인증과 키 설정 과정이 필요하지만 최신 프로토콜로 비용을 줄일 수 있다.

<a name="q14"></a>
### Q14. HTTPS를 사용하면 성능이 무조건 떨어지나요?

> "암호화와 연결 설정에 비용이 발생할 수 있지만 TLS 1.3, 하드웨어 가속, 연결 재사용 등의 최적화가 가능합니다.
>
> 따라서 HTTPS가 항상 체감 성능이 느리다고 단정할 수는 없습니다."

**핵심 요약**

HTTPS에는 암호화 비용이 있지만 연결 재사용과 최적화로 부담을 줄일 수 있다.

<a name="section-03"></a>
## CORS와 브라우저 보안

<a name="q15"></a>
### Q15. [대표 질문] CORS란 무엇이고 왜 필요한가요?

> "CORS(Cross-Origin Resource Sharing)는 서버가 다른 출처의 브라우저 요청에 대해 응답 접근을 허용할 범위를 HTTP 헤더로 알려주는 메커니즘입니다.
>
> 브라우저는 동일 출처 정책을 적용하며, 서버가 적절한 CORS 응답 헤더를 제공하면 허용된 교차 출처 요청의 응답에 접근할 수 있습니다."

**핵심 요약**

CORS는 서버가 다른 출처의 브라우저 요청에 대한 응답 접근 범위를 알려주는 메커니즘이다.

<a name="q16"></a>
### Q16. 동일 출처 정책(Same-Origin Policy)이란 무엇인가요?

> "동일 출처 정책은 브라우저가 서로 다른 출처 사이의 데이터 접근을 제한하는 보안 정책입니다.
>
> 출처는 스킴, 호스트, 포트의 조합으로 구분합니다."

예를 들어:

```
http://localhost:3000
http://localhost:8080
```

포트가 다르므로 서로 다른 출처입니다.

**핵심 요약**

동일 출처 정책은 스킴·호스트·포트가 다른 출처 간 데이터 접근을 제한한다.

<a name="q17"></a>
### Q17. CORS 오류는 서버에서 발생하는 건가요?

> "CORS에 따른 응답 접근 제한은 기본적으로 브라우저에서 적용합니다.
>
> 서버가 정상적으로 응답했더라도 적절한 CORS 헤더가 없다면 브라우저가 JavaScript에서 응답을 읽지 못하도록 제한할 수 있습니다.
>
> 따라서 Postman 같은 API 클라이언트에서는 호출되지만 브라우저에서는 CORS 오류가 발생할 수 있습니다."

**핵심 요약**

CORS 오류는 주로 브라우저가 교차 출처 응답 접근을 제한하는 과정에서 나타난다.

<a name="q18"></a>
### Q18. Preflight Request란 무엇인가요?

> "Preflight Request(프리플라이트 리퀘스트)는 실제 교차 출처 요청을 전송하기 전에 브라우저가 OPTIONS 요청으로 서버의 허용 여부를 확인하는 과정입니다.
>
> 특정 메서드나 헤더를 사용하는 요청에서 발생하며, 서버는 허용하는 Origin, Method, Header 등의 정보를 응답합니다."

**핵심 요약**

Preflight는 실제 요청 전에 OPTIONS로 교차 출처 요청의 허용 여부를 확인하는 과정이다.

<a name="q19"></a>
### Q19. Spring Boot에서 CORS는 어떻게 처리하나요?

> "Spring MVC에서는 `@CrossOrigin`이나 `WebMvcConfigurer`를 이용해 CORS를 설정할 수 있습니다.
>
> Spring Security를 사용하는 경우 Security Filter Chain에서도 CORS를 올바르게 처리하도록 설정하는 것이 중요합니다.
>
> 특히 인증 정보를 포함하지 않는 Preflight 요청이 인증 필터에서 부적절하게 차단되지 않도록 주의해야 합니다."

예를 들어 Controller 단위로 허용할 수 있습니다.

```
@CrossOrigin(origins = "http://localhost:3000")
@RestController
public class ProductController {
    // ...
}
```

**핵심 요약**

Spring MVC는 @CrossOrigin이나 전역 설정을 사용하고 Spring Security 환경에서는 보안 필터와 CORS 처리를 함께 고려해야 한다.

<a name="q20"></a>
### Q20. [핵심 질문] CORS 오류가 나면 서버가 요청을 처리하지 않았다는 뜻인가요?

> "반드시 그렇지는 않습니다.
>
> Preflight가 실패하면 실제 요청이 보내지지 않을 수 있지만, 요청이 이미 서버에서 처리되었는데 브라우저가 응답 접근만 차단하는 경우도 있습니다."

**핵심 요약**

CORS 오류는 서버가 요청을 전혀 처리하지 않았다는 뜻은 아니다.
