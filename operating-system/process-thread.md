## Process

<a name="q1"></a>
### Q1. [대표 질문] 프로세스란 무엇인가요?

> "프로세스는 실행 중인 프로그램을 의미합니다. 운영체제로부터 독립된 메모리 공간과 CPU 시간, 파일 등의 자원을 할당 받아 실행되는 작업의 단위입니다."

**핵심 요약**

**프로세스 = 실행 중인 프로그램**

---

<a name="q1-1"></a>
#### ↳ Q1-1. 프로그램과 프로세스의 차이는 무엇인가요?

> "프로그램은 디스크에 저장되어 있는 정적인 실행 파일이고, 이 프로그램이 메모리에 올라가 실행되기 시작하면 프로세스가 됩니다."

**핵심 요약**

**프로그램은 파일, 프로세스는 실행 중인 상태**

---

<a name="q2"></a>
### Q2. 프로세스의 메모리 구조를 설명해주세요.

> "프로세스의 메모리는 일반적으로 Code, Data, Heap, Stack 영역으로 구성됩니다. Code 영역에는 실행할 명령어가 저장되고, Data 영역에는 전역 변수와 static 변수가 저장됩니다. Heap에는 동적으로 할당한 데이터가 저장되고, Stack에는 지역 변수와 함수 호출 정보가 저장됩니다. 전형적인 메모리 구조에서는 Heap과 Stack이 서로 반대 방향으로 확장되도록 배치됩니다."

**핵심 요약**

**Code는 명령어, Data는 전역·static 변수, Heap은 동적 데이터, Stack은 함수 호출 정보·지역 변수**

---

<a name="q2-1"></a>
#### ↳ Q2-1. 힙과 스택이 서로 마주 보게 배치한 이유는?

> "Heap과 Stack은 프로그램 실행 중 크기가 동적으로 변할 수 있습니다. 전형적인 메모리 구조에서는 두 영역을 반대 방향으로 확장하게 해서, 사용 가능한 메모리 공간을 보다 유연하게 활용할 수 있도록 합니다."

**핵심 요약**

**전통적인 단순 주소 공간 모델에서는 힙과 스택의 반대 방향 성장을 예로 든다. 실제 배치는 OS, 할당기, 스레드 구성에 따라 달라진다.**

---

<a name="q3"></a>
### Q3. PCB(Process Control Block)란 무엇인가요?

> "PCB는 운영체제가 각 프로세스를 관리하기 위해 사용하는 자료구조입니다. 프로세스 ID, 프로세스 상태, 프로그램 카운터, 레지스터 값, 메모리 관리 정보, 열린 파일 정보, 스케줄링 정보 등을 저장합니다. 운영체제는 PCB를 이용해 여러 프로세스를 식별하고 관리합니다."

**핵심 요약**

**PCB = OS가 관리하는 프로세스의 상태 정보**

---

<a name="q3-1"></a>
#### ↳ Q3-1. PCB는 언제 사용되나요?

> "대표적으로 컨텍스트 스위칭 시 사용됩니다. 현재 실행 중인 프로세스의 CPU 상태를 PCB에 저장하고, 다음에 실행할 프로세스의 상태를 PCB에서 복원합니다. 이를 통해 프로세스가 중단된 지점부터 다시 실행될 수 있습니다."

**핵심 요약**

**PCB는 멈출 때 저장하고 다시 실행할 때 복원**

---

<a name="q3-2"></a>
#### ↳ Q3-2. TCB는 어떤 역할을 하나요?

> "TCB(Thread Control Block)는 스레드의 실행 상태를 관리하기 위한 자료구조입니다. 스레드 ID, 프로그램 카운터, 레지스터 값, 스택 포인터, 스레드 상태 등의 정보를 저장합니다. 프로세스의 자원은 같은 프로세스의 스레드들이 공유하지만, 각 스레드의 실행 상태는 서로 다르기 때문에 TCB가 필요합니다."

**핵심 요약**

**PCB는 프로세스 상태, TCB는 스레드 실행 상태**

---

<a name="q4"></a>
### Q4. 프로세스의 상태에는 어떤 것들이 있나요?

> "프로세스의 주요 상태는 New, Ready, Running, Waiting 또는 Blocked, Terminated의 5가지입니다.
>
> 프로세스가 생성되면 New에서 Ready 상태로 이동하고, 스케줄러가 CPU를 할당하면 Running 상태가 됩니다.
>
> 실행 중 I/O를 요청하거나 특정 이벤트를 기다려야 하면 Waiting 상태로 이동하고, I/O나 이벤트가 완료되면 다시 Ready 상태로 이동합니다. 또한 타임 슬라이스가 만료되거나 다른 프로세스에 의해 선점되면 Running에서 Ready 상태로 이동하며, 실행을 마치면 Terminated 상태가 됩니다."

**핵심 요약**

**New → Ready → Running → Waiting → Ready, 끝나면 Terminated**

---

<a name="q4-1"></a>
#### ↳ Q4-1. Ready와 Waiting의 차이는?

> "Ready 상태는 CPU만 할당 받으면 바로 실행할 수 있는 상태입니다. 반면 Waiting 상태는 I/O 완료나 특정 이벤트를 기다리고 있기 때문에 CPU를 할당해도 바로 실행할 수 없습니다."

**핵심 요약**

**Ready는 CPU를 기다리고, Waiting은 이벤트를 기다린다**

---

<a name="q4-2"></a>
#### ↳ Q4-2. 자식 프로세스가 제대로 종료되지 않으면 어떤 문제가 생기나요?

> "자식 프로세스가 종료됐는데 부모 프로세스가 wait() 등을 통해 종료 상태를 회수하지 않으면 좀비 프로세스가 됩니다. 실행에 사용하던 대부분의 자원은 해제되지만, 종료 상태 등의 정보가 프로세스 테이블에 남습니다.
>
> 반대로 부모 프로세스가 먼저 종료되면 자식 프로세스는 고아 프로세스가 됩니다. 이런 경우 시스템의 PID 1 프로세스나 서브리퍼가 부모 역할을 이어받아 관리할 수 있습니다."

**핵심 요약**

**좀비 = 자식은 끝났는데 부모가 회수 안 함 / 고아 = 부모가 먼저 종료됨**

---

<a name="q5"></a>
### Q5. 프로세스 간 통신(IPC)에는 어떤 방법이 있나요?

> "대표적인 IPC 방식에는 Pipe, Message Queue, 공유 메모리, Socket 등이 있습니다. 각 방식은 통신 범위와 성능, 구현 방식에 따라 적절한 상황에서 사용합니다."

**핵심 요약**

**IPC = 서로 독립된 프로세스끼리 데이터를 주고받는 방법**

---

<a name="q5-1"></a>
#### ↳ Q5-1. IPC가 필요한 이유는?

> "프로세스는 각각 독립된 주소 공간을 사용하기 때문에 다른 프로세스의 메모리에 직접 접근할 수 없습니다. 하지만 여러 프로세스가 협업하려면 데이터를 주고받거나 상태를 동기화해야 하기 때문에 IPC가 필요합니다."

**핵심 요약**

**프로세스는 메모리가 분리되어 있어서 IPC가 필요하다**

---

<a name="q5-2"></a>
#### ↳ Q5-2. 공유 메모리가 빠른 이유는?

> "공유 메모리는 여러 프로세스가 같은 메모리 영역을 매핑해서 직접 데이터를 읽고 쓸 수 있기 때문에, 통신할 때마다 데이터를 복사하는 방식보다 빠를 수 있습니다. 다만 여러 프로세스가 동시에 같은 데이터에 접근하면 Race Condition이 발생할 수 있으므로 Semaphore나 Mutex 등의 동기화가 필요합니다."

**핵심 요약**

**공유 메모리는 복사를 줄여 빠르지만 동기화가 필요하다**

- **Mutex(뮤텍스)**: 한 번에 **한 스레드만** 공유 자원에 들어가게 하는 잠금입니다.
→ **“1명만 들어가세요.”**
- **Semaphore(세마포어)**: 동시에 들어갈 수 있는 **개수를 정해두는 방식**입니다.
→ 예: 값이 3이면 **최대 3개 스레드까지 동시에 접근 가능**
→ **“3명까지 들어가세요.”**
- **synchronized(싱크로나이즈드)**: Java에서 사용하는 **동기화 키워드**입니다. 특정 코드나 메서드를 한 번에 하나의 스레드만 실행하도록 보호할 수 있습니다. **synchronized = Java에서 Mutex처럼 상호 배제를 구현할 때 쓰는 키워드**
→ **Java에서 락을 쉽게 거는 방법**

→ “세마포어를 1로 설정하면 한 번에 하나의 스레드만 접근할 수 있어서 뮤텍스와 비슷하게 동작합니다. 하지만 뮤텍스는 락의 소유권 개념이 있고, 세마포어는 접근 가능한 개수를 제어하는 것이 본래 목적이라는 차이가 있습니다.”

**핵심 요약**

> **Mutex = 1개만 접근 / Semaphore = N개까지 접근 / synchronized = Java에서 동기화하는 문법**

---

<a name="q6"></a>
### Q6. 멀티 프로세스의 장단점은?

> "장점은 각 프로세스의 메모리가 독립되어 있기 때문에 하나의 프로세스에 문제가 생겨도 다른 프로세스로 장애가 전파될 가능성이 낮다는 점입니다.
>
> 단점은 프로세스마다 별도의 주소 공간을 사용하므로 메모리 사용량이 크고, 프로세스 생성과 컨텍스트 스위칭 비용이 상대적으로 크며, 프로세스 간 통신도 스레드보다 복잡하다는 점입니다."

**핵심 요약**

**멀티 프로세스 = 안정적이지만 무겁다**

---

<a name="q6-1"></a>
#### ↳ Q6-1. 실제 서비스에서 멀티 프로세스를 사용하는 사례는?

> "Chrome 브라우저가 대표적인 사례입니다. 브라우저는 탭이나 렌더러 등을 별도의 프로세스로 격리하여, 하나의 탭이나 렌더링에 문제가 생겨도 다른 부분으로 장애가 전파되는 것을 줄입니다."

**핵심 요약**

**Chrome은 프로세스 격리로 장애 전파를 줄인다**

---

<a name="section-02"></a>
## Thread

<a name="q7"></a>
### Q7. [대표 질문] 스레드란 무엇이며 프로세스와 어떻게 다른가요?

> "스레드는 프로세스 내부에서 실행되는 작업의 흐름 단위입니다. 같은 프로세스의 스레드들은 Code, Data, Heap 등의 자원을 공유하지만, 각자 Stack과 CPU 실행 상태를 따로 가집니다. 프로세스끼리는 주소 공간이 독립되어 있지만, 같은 프로세스의 스레드들은 메모리를 공유하기 때문에 통신이 빠르고 상대적으로 가볍습니다."

**핵심 요약**

**프로세스는 자원의 단위, 스레드는 실행의 단위**

---

<a name="q8"></a>
### Q8. 스레드끼리 스택을 따로 갖는 이유는 무엇인가요?

> "Stack에는 함수 호출 정보와 지역 변수가 저장됩니다. 각 스레드는 서로 다른 함수를 실행하고 서로 다른 실행 흐름을 가지기 때문에 Stack을 독립적으로 가져야 합니다.
>
> 프로그램 카운터와 레지스터 값도 스레드마다 실행 위치와 CPU 상태가 다르기 때문에 각각 따로 관리됩니다."

**핵심 요약**

**각 스레드의 실행 흐름이 다르기 때문에 Stack과 CPU 상태도 따로 가진다**

---

<a name="q8-1"></a>
#### ↳ Q8-1. 스레드마다 별도로 갖는 것이 스택뿐인가요?

> "아닙니다. Stack뿐 아니라 프로그램 카운터, 레지스터 값, 스택 포인터 등 각 스레드의 실행 상태도 별도로 관리합니다. 이런 정보들은 TCB 등에 저장됩니다."

**핵심 요약**

**스레드는 Stack + PC + Register를 따로 가진다**

---

<a name="q9"></a>
### Q9. 멀티 스레드의 장단점은 무엇인가요?

> "장점은 같은 프로세스의 메모리와 자원을 공유하기 때문에 생성과 전환 비용이 상대적으로 작고, 스레드 간 데이터 공유가 쉽다는 것입니다.
>
> 반면 공유 자원에 여러 스레드가 동시에 접근하면 Race Condition 같은 동기화 문제가 발생할 수 있고, 하나의 스레드에서 잘못된 메모리 접근 등 치명적인 오류가 발생하면 프로세스 전체에 영향을 줄 수도 있습니다."

**핵심 요약**

**멀티 스레드 = 빠르고 가볍지만 공유 때문에 위험하다**

---

<a name="q9-1"></a>
#### ↳ Q9-1. 동기화 문제란 무엇인가요?

> "여러 스레드가 하나의 공유 자원에 동시에 접근할 때 실행 순서에 따라 결과가 달라지는 Race Condition이 발생할 수 있습니다. 이를 방지하기 위해 Mutex, Semaphore, synchronized 같은 동기화 방법을 사용합니다."

**핵심 요약**

**Race Condition = 실행 순서에 따라 결과가 달라지는 문제**

---

<a name="q9-2"></a>
#### ↳ Q9-2. 동기화를 하면 항상 좋은가요?

> "동기화를 사용하면 공유 자원을 안전하게 보호할 수 있지만 비용도 발생합니다. 락을 획득하고 기다리는 과정에서 성능이 떨어질 수 있고, 락을 잘못 설계하면 서로 상대방의 락을 기다리는 Deadlock이 발생할 수도 있습니다."

**핵심 요약**

**동기화는 안전성을 얻는 대신 성능 비용과 데드락 위험이 있다**

---

<a name="q10"></a>
### Q10. 멀티 프로세스와 멀티 스레드 중 무엇을 선택하나요?

> "장애 격리와 안정성이 중요하면 멀티프로세스가 유리하고, 메모리 효율과 빠른 데이터 공유가 중요하면 멀티스레드가 유리합니다. 다만 실제 시스템에서는 작업 특성과 구조에 따라 두 방식을 함께 사용하기도 합니다."

**핵심 요약**

**안정성은 프로세스, 효율성은 스레드**

---

<a name="q10-1"></a>
#### ↳ Q10-1. 웹 서버에서 스레드를 사용하는 이유는?

> "요청마다 새로운 프로세스를 생성하는 것은 메모리와 생성 비용이 큽니다. 스레드는 상대적으로 가볍고 같은 프로세스의 자원을 공유할 수 있기 때문에 여러 요청을 효율적으로 처리할 수 있습니다. 다만 현대 웹 서버는 스레드뿐 아니라 이벤트 루프나 비동기 I/O 등 다양한 모델을 사용합니다."

**핵심 요약**

**스레드는 가볍고 자원을 공유하므로 여러 요청 처리에 유리하다**

---

<a name="q11"></a>
### Q11. 스레드 풀(Thread Pool)은 왜 사용하나요?

> "스레드를 생성하고 제거하는 작업에도 비용이 발생하기 때문입니다. 미리 일정 수의 스레드를 만들어두고 작업이 들어올 때 재사용하면 반복적인 생성 비용을 줄일 수 있습니다. 또한 동시에 실행되는 스레드의 수를 제한하여 과도한 자원 사용도 방지할 수 있습니다."

**핵심 요약**

**스레드 풀 = 미리 만들어 재사용하고 개수를 제한한다**

---

<a name="q11-1"></a>
#### ↳ Q11-1. 스레드 풀 크기는 어떻게 정하나요?

> "작업의 성격에 따라 달라집니다. CPU-bound 작업은 CPU를 계속 사용하기 때문에 일반적으로 CPU 코어 수를 기준으로 스레드 수를 조정합니다.
>
> 반면 I/O-bound 작업은 I/O를 기다리는 시간이 많기 때문에 CPU-bound 작업보다 더 많은 스레드를 둘 수 있습니다. 정확한 크기는 I/O 대기 시간, CPU 사용량, 작업 특성 등을 측정하면서 결정하는 것이 좋습니다."

**핵심 요약**

**CPU 작업은 코어 수 중심, I/O 작업은 대기 시간이 많아 더 많은 스레드를 둘 수 있다**

---

<a name="q12"></a>
### Q12. 스레드는 많을수록 좋은가요?

> "아닙니다. 스레드가 많아지면 스레드마다 Stack 등의 메모리를 사용하고, CPU가 여러 스레드를 자주 전환하면서 컨텍스트 스위칭 오버헤드가 증가합니다. 또한 락 경합도 증가할 수 있기 때문에 일정 수준을 넘으면 오히려 성능이 떨어질 수 있습니다."

**핵심 요약**

**스레드는 많을수록 좋은 게 아니라 적절할수록 좋다**

---

<a name="q12-1"></a>
#### ↳ Q12-1. 스레드가 지나치게 많으면 어떤 문제가 발생하나요?

> "스레드 수가 지나치게 많으면 CPU가 실제 작업보다 스레드 전환에 많은 시간을 사용할 수 있습니다. 그러면 CPU 사용률은 높은데 실제 처리량은 떨어지는 상황이 발생할 수 있습니다.
>
> 일반적으로 이를 컨텍스트 스위칭 오버헤드가 과도해졌다고 표현하는 것이 정확합니다. 운영체제에서 Thrashing은 원래 메모리 부족으로 인해 페이지 폴트와 페이지 교체가 과도하게 발생하는 현상을 의미합니다."

**핵심 요약**

**스레드가 너무 많으면 일보다 교체에 시간을 더 쓰게 된다**

---

<a name="q12-2"></a>
#### ↳ Q12-2. 이런 문제를 줄이기 위한 방법에는 무엇이 있나요?

> "스레드 풀을 사용해 OS 스레드 수를 제한하거나, 이벤트 기반 비동기 처리 방식을 사용할 수 있습니다. 또한 Go의 Goroutine이나 Java의 Virtual Thread처럼 OS 스레드보다 가벼운 실행 단위를 활용할 수도 있습니다.
>
> Coroutine 역시 실행 흐름을 중단하고 재개할 수 있는 가벼운 추상화이지만, Virtual Thread나 Goroutine과 완전히 같은 개념은 아닙니다."

**핵심 요약**

**OS 스레드를 무작정 늘리지 말고 더 가벼운 실행 모델을 활용한다**

---

<a name="q12-3"></a>
#### ↳ Q12-3. 이벤트 루프 방식은 컨텍스트 스위칭과 어떤 관계인가요?

> "이벤트 루프 방식은 적은 수의 스레드에서 비동기 I/O를 처리하기 때문에, 요청마다 많은 스레드를 사용하는 방식보다 OS 스레드 간 컨텍스트 스위칭을 줄일 수 있습니다.
>
> 하지만 이벤트 루프를 실행하는 스레드에서 CPU 연산을 오래 수행하면 다른 작업을 처리하지 못하고 전체 응답이 지연될 수 있습니다."

**핵심 요약**

**이벤트 루프 = 스레드 전환은 줄이지만 CPU 작업이 길면 전체가 막힌다**

---

<a name="q13"></a>
### Q13. 사용자 수준 스레드와 커널 수준 스레드의 차이는?

> "사용자 수준 스레드는 사용자 공간의 라이브러리나 런타임에서 스케줄링하기 때문에 전환 비용을 줄일 수 있습니다.
>
> 커널 수준 스레드는 운영체제가 직접 스케줄링하기 때문에 여러 CPU 코어에서 병렬 실행하거나, 하나의 스레드가 블로킹되어도 다른 스레드를 실행하는 데 유리합니다.
>
> 다만 사용자 수준 스레드가 하나 블로킹됐다고 반드시 프로세스 전체가 멈추는지는 스레드 매핑 방식과 런타임 구현에 따라 달라집니다."

**핵심 요약**

**사용자 스레드는 런타임이 관리하고, 커널 스레드는 OS가 관리한다**

---

<a name="section-03"></a>
## Context Switching

<a name="q14"></a>
### Q14. [대표 질문] 컨텍스트 스위칭이란 무엇이며 왜 비용이 발생하나요?

> "컨텍스트 스위칭은 CPU가 현재 실행 중인 프로세스나 스레드를 멈추고 다른 실행 대상으로 전환하는 과정입니다.
>
> 이 과정에서 현재 작업의 프로그램 카운터, 레지스터 값 등 실행 상태를 저장하고, 다음 작업의 실행 상태를 복원해야 합니다.
>
> 또한 새로운 작업이 사용하는 데이터가 CPU 캐시에 충분히 없을 경우 캐시 미스가 증가할 수 있고, 주소 공간이 바뀌는 프로세스 전환에서는 TLB와 메모리 관리 측면에서도 추가 비용이 발생할 수 있습니다."

**핵심 요약**

**컨텍스트 스위칭 = 실행 대상을 바꾸면서 상태를 저장하고 복원하는 과정**

---

<a name="q14-1"></a>
#### ↳ Q14-1. 여기서 말하는 컨텍스트란 무엇인가요?

> "컨텍스트는 프로세스나 스레드가 나중에 실행을 이어가기 위해 필요한 현재 실행 상태를 의미합니다. 프로그램 카운터, CPU 레지스터 값, 스택 포인터 등이 대표적입니다.
>
> 이런 정보를 저장하지 않으면 나중에 다시 실행될 때 어디서부터 작업을 이어가야 하는지 알 수 없기 때문에 컨텍스트 스위칭 시 저장과 복원이 필요합니다."

**핵심 요약**

**컨텍스트 = 나중에 이어서 실행하기 위한 현재 상태**

---

<a name="q14-2"></a>
#### ↳ Q14-2. 캐시 미스가 왜 큰 비용인가요?

> "CPU 캐시에 필요한 데이터가 없으면 더 느린 하위 메모리 계층에서 데이터를 가져와야 하기 때문입니다.
>
> 컨텍스트 스위칭 후 새로 실행되는 작업이 사용하는 데이터가 캐시에 충분히 남아 있지 않으면 캐시 미스가 증가할 수 있습니다. 따라서 단순히 레지스터를 저장하고 복원하는 직접 비용뿐 아니라 캐시 적중률이 떨어지는 간접 비용도 발생할 수 있습니다."

**핵심 요약**

**새 작업 데이터가 캐시에 없으면 느린 메모리에서 다시 가져와야 한다**

---

<a name="q15"></a>
### Q15. 프로세스 전환과 스레드 전환 중 어느 쪽이 더 비싼가요?

> "일반적으로 서로 다른 프로세스 간 컨텍스트 스위칭이 같은 프로세스의 스레드 간 전환보다 비용이 큽니다.
>
> 프로세스가 바뀌면 주소 공간도 변경되기 때문에 페이지 테이블과 메모리 관리 관련 상태를 변경해야 하고, 기존 TLB 엔트리의 활용도가 떨어질 수 있습니다. 또한 새로운 프로세스의 데이터 때문에 캐시 적중률이 떨어질 수도 있습니다.
>
> 반면 같은 프로세스의 스레드들은 주소 공간을 공유하기 때문에 이러한 메모리 관리 관련 비용이 상대적으로 적습니다."

**핵심 요약**

**주소 공간까지 바뀌는 프로세스 전환이 더 무겁다**

---

<a name="q15-1"></a>
#### ↳ Q15-1. TLB란 무엇인가요?

> "TLB는 가상 주소를 물리 주소로 변환한 결과를 빠르게 재사용하기 위해 CPU가 사용하는 캐시입니다.
>
> 프로세스가 바뀌면 사용하는 주소 공간이 달라지기 때문에 기존 TLB 정보 중 일부를 그대로 사용할 수 없게 될 수 있습니다. 현대 CPU에서는 ASID나 PCID 같은 기능을 이용해 TLB 전체를 항상 비우지 않고도 서로 다른 프로세스의 주소 변환 정보를 구분하기도 합니다."

**핵심 요약**

**TLB = 가상 주소 → 물리 주소 변환 결과를 저장하는 캐시**

---

<a name="q16"></a>
### Q16. 컨텍스트 스위칭은 언제 발생하나요?

> "대표적으로 실행 중인 프로세스의 타임 슬라이스가 만료됐을 때, I/O를 요청해 대기 상태로 들어갈 때, 더 높은 우선순위의 작업이 실행되어야 할 때 등에 발생합니다.
>
> 인터럽트나 시스템 콜이 발생했다고 해서 항상 컨텍스트 스위칭이 일어나는 것은 아닙니다. 처리 후 원래 프로세스로 돌아갈 수도 있고, 그 과정에서 스케줄러가 다른 프로세스나 스레드를 선택했을 때 컨텍스트 스위칭으로 이어질 수 있습니다."

**핵심 요약**

**CPU를 다른 작업에게 넘겨줘야 할 때 컨텍스트 스위칭이 발생한다**

---

<a name="q16-1"></a>
#### ↳ Q16-1. 타임 슬라이스가 너무 짧거나 길면 어떻게 되나요?

> "타임 슬라이스가 너무 짧으면 프로세스가 자주 전환되어 컨텍스트 스위칭 오버헤드가 커집니다. 반대로 너무 길면 한 프로세스가 CPU를 오래 사용하게 되어 다른 작업의 응답 시간이 길어질 수 있습니다. 따라서 스케줄러는 처리량과 응답성 사이에서 적절한 균형을 잡아야 합니다."

**핵심 요약**

**짧으면 전환 비용 증가, 길면 응답성 저하**

---

<a name="q17"></a>
### Q17. 컨텍스트 스위칭 비용을 줄이는 방법이 있나요?

> "불필요하게 많은 프로세스나 OS 스레드를 생성하지 않고 적절한 수를 유지하는 것이 중요합니다. 스레드 풀을 활용하거나, I/O 중심 작업에서는 이벤트 기반 비동기 처리 방식을 사용할 수 있습니다.
>
> 또한 Virtual Thread나 Goroutine 같은 가벼운 실행 단위를 사용하면 많은 작업을 처리하면서도 OS 스레드 간 컨텍스트 스위칭을 줄일 수 있습니다."

**핵심 요약**

**불필요한 OS 스레드와 전환 횟수를 줄이는 것이 핵심**

---

<a name="q17-1"></a>
#### ↳ Q17-1. 경량 스레드는 왜 전환 비용이 상대적으로 적나요?

> "경량 실행 단위는 런타임이 여러 작업을 소수의 OS 스레드 위에 스케줄링할 수 있기 때문입니다. 따라서 작업이 바뀔 때마다 반드시 OS 스레드 컨텍스트 스위칭이 발생하지 않아도 되고, 저장하고 관리해야 하는 상태도 상대적으로 작을 수 있습니다."

**핵심 요약**

**런타임이 사용자 공간에서 많은 작업을 관리해 OS 스레드 전환을 줄인다**

---

<a name="q18"></a>
### Q18. 컨텍스트 스위칭이 많아지면 서버에 어떤 문제가 생기나요?

> "CPU가 실제 요청을 처리하는 것보다 실행 대상을 전환하는 데 많은 시간을 사용할 수 있기 때문에 처리량이 떨어지고 응답 지연이 증가할 수 있습니다.
>
> 또한 캐시 적중률 저하와 락 경합 등이 함께 발생하면 서버 성능이 더욱 나빠질 수 있습니다."

**핵심 요약**

**전환이 많아지면 CPU가 일보다 교체에 시간을 쓴다**

---

<a name="q18-1"></a>
#### ↳ Q18-1. 이런 상황을 어떻게 진단하나요?

> "Linux에서는 vmstat, pidstat 같은 도구를 이용해 컨텍스트 스위칭 횟수와 CPU 사용 상태를 확인할 수 있습니다.
>
> CPU 사용률은 높은데 실제 처리량이 낮고 컨텍스트 스위칭 횟수가 지나치게 많다면, 과도한 스레드 수나 락 경합 등을 의심해볼 수 있습니다."

**핵심 요약**

**CPU는 바쁜데 처리량이 낮고 전환이 많다면 컨텍스트 스위칭을 의심한다**

---

<a name="q19"></a>
### Q19. 인터럽트와 컨텍스트 스위칭은 어떻게 다른가요?

> "인터럽트는 하드웨어나 소프트웨어가 CPU에 처리해야 할 일이 생겼다는 것을 알리는 신호입니다.
>
> 반면 컨텍스트 스위칭은 CPU가 실행 중인 프로세스나 스레드를 다른 실행 대상으로 교체하는 과정입니다.
>
> 인터럽트가 발생해도 처리 후 원래 작업으로 돌아가면 컨텍스트 스위칭은 발생하지 않습니다. 하지만 인터럽트 처리 과정에서 스케줄러가 다른 작업을 선택하면 컨텍스트 스위칭으로 이어질 수 있습니다."

**핵심 요약**

**인터럽트는 알림, 컨텍스트 스위칭은 실행 대상 교체**

---

<a name="section-04"></a>
## 연관 종합 질문

<a name="q20"></a>
### Q20. Process, Thread, Context Switching을 한 문장으로 연결한다면?

> "프로세스는 독립된 자원을 가진 실행 환경이고, 스레드는 그 프로세스 안에서 실행되는 흐름이며, 컨텍스트 스위칭은 CPU가 이러한 실행 흐름을 번갈아 처리하기 위해 실행 상태를 저장하고 교체하는 과정입니다."

**핵심 요약**

**Process = 자원 / Thread = 실행 흐름 / Context Switching = 실행 대상 교체**

---

<a name="q21"></a>
### Q21. 동시성(Concurrency)과 병렬성(Parallelism)의 차이는?

> "동시성은 여러 작업을 일정 시간 동안 함께 진행할 수 있도록 구조화하는 개념이고, 병렬성은 여러 작업이 실제로 같은 순간에 실행되는 것을 의미합니다.
>
> 싱글코어에서는 여러 작업을 빠르게 번갈아 실행해 동시성을 구현할 수 있고, 멀티코어에서는 여러 작업을 실제로 동시에 실행해 병렬성을 구현할 수 있습니다."

**핵심 요약**

**동시성 = 여러 작업을 함께 다루기 / 병렬성 = 여러 작업을 실제로 동시에 실행하기**

---

<a name="q21-1"></a>
#### ↳ Q21-1. 싱글코어에서도 동시성이 가능한 이유는?

> "하나의 CPU 코어가 여러 작업을 짧은 시간 단위로 번갈아 실행할 수 있기 때문입니다. 예를 들어 작업 A를 조금 실행한 뒤 B를 실행하고 다시 A로 돌아오는 식으로 진행하면 여러 작업이 동시에 진행되는 것처럼 보일 수 있습니다."

**핵심 요약**

**싱글코어는 여러 작업을 빠르게 번갈아 실행해서 동시성을 만든다**

---

<a name="q22"></a>
### Q22. 멀티스레드가 항상 성능을 높이나요?

> "아닙니다. 스레드 수가 지나치게 많으면 컨텍스트 스위칭이 증가하고, 공유 자원에 대한 락 경합도 심해질 수 있습니다.
>
> 특히 CPU-bound 작업에서는 CPU 코어 수보다 지나치게 많은 스레드가 성능을 오히려 떨어뜨릴 수 있기 때문에 작업 특성과 CPU 코어 수를 고려해 적절한 스레드 수를 정해야 합니다."

**핵심 요약**

**멀티스레드는 많을수록 좋은 것이 아니라 작업과 코어 수에 맞게 써야 한다**

---

<a name="section-05"></a>
## 복습 요약

**Process**

→ **독립된 자원을 가진 실행 중인 프로그램**

**Thread**

→ **프로세스 안의 실행 흐름**

**PCB**

→ **프로세스 상태 저장**

**TCB**

→ **스레드 상태 저장**

**IPC**

→ **프로세스끼리 통신**

**Ready**

→ **CPU 기다림**

**Waiting**

→ **I/O나 이벤트 기다림**

**Zombie**

→ **자식은 끝났는데 부모가 회수 안 함**

**Orphan**

→ **부모가 먼저 종료됨**

**Race Condition**

→ **실행 순서에 따라 결과가 달라짐**

**Synchronization**

→ **공유 자원을 안전하게 사용하도록 제어**

**Thread Pool**

→ **스레드를 미리 만들어 재사용**

**Context Switching**

→ **실행 대상 교체 + 상태 저장·복원**

**Cache Miss**

→ **필요한 데이터가 캐시에 없음**

**TLB**

→ **주소 변환 결과를 저장한 캐시**

**Interrupt**

→ **CPU에게 보내는 알림**

**Concurrency**

→ **여러 작업을 함께 진행**

**Parallelism**

→ **여러 작업을 실제 동시에 실행**

**이벤트 루프**

→ **OS 스레드 전환을 줄이지만 CPU 작업이 길면 막힘**

**멀티프로세스**

→ **안정적이지만 무겁다**

**멀티스레드**

→ **가볍지만 공유 때문에 동기화가 필요하다**

---

<a name="section-06"></a>
## 핵심 요약

**Process = 독립된 자원을 가진 실행 단위**

**Thread = 프로세스 안에서 자원을 공유하는 실행 흐름**

**Context Switching = CPU가 실행 대상을 바꾸면서 상태를 저장하고 복원하는 과정**
