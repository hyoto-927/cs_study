## Hash

<a name="q1"></a>
### Q1. [대표 질문] 해시 함수란 무엇이고, 왜 사용하나요?

> "해시 함수는 입력 데이터를 일정한 크기의 해시값으로 변환하는 함수입니다. 해시 기반 자료구조에서는 Key의 해시값을 이용해 저장할 버킷의 위치를 빠르게 결정합니다. 배열은 인덱스로 바로 접근할 수 있기 때문에, 해시가 적절히 분산된다면 조회·삽입·삭제를 평균 O(1)에 수행할 수 있습니다."

**핵심 요약**

**Hash = Key를 빠르게 찾아갈 수 있는 값으로 변환하는 것**

---

<a name="q1-1"></a>
#### ↳ Q1-1. 해시 자료구조가 평균 O(1)의 빠른 속도를 내는 원리는?

> "Key를 해시 함수를 통해 해시값으로 변환하고, 그 값을 이용해 배열의 버킷 인덱스를 결정합니다. 배열은 인덱스를 알고 있으면 바로 접근할 수 있기 때문에 처음부터 모든 데이터를 하나씩 비교하지 않아도 됩니다. 충돌이 심하지 않다면 원하는 데이터가 있는 위치를 빠르게 찾아갈 수 있어 평균 O(1)의 성능을 냅니다."

**핵심 요약**

**Key → Hash → Index → 바로 접근**

---

<a name="q1-2"></a>
#### ↳ Q1-2. 해시 테이블의 조회·삽입·삭제 시간 복잡도는 얼마인가요?

> "일반적으로 조회, 삽입, 삭제 모두 평균 O(1)입니다. 하지만 해시 충돌이 심해져 많은 데이터가 같은 버킷에 몰리면 해당 버킷 내부에서 추가 탐색이 필요하기 때문에 성능이 저하될 수 있습니다. 구현 방식에 따라 최악의 시간 복잡도는 달라질 수 있습니다."

**핵심 요약**

**평균 O(1), 충돌이 심하면 느려진다**

---

<a name="q1-3"></a>
#### ↳ Q1-3. 해시 테이블이 범위 검색이나 정렬에 취약한 이유는?

> "해시 테이블은 Key를 해시값에 따라 여러 버킷에 분산해 저장하기 때문에 Key의 크기나 순서와 저장 위치 사이에 직접적인 관계가 없습니다. 따라서 '10 이상 20 이하의 Key를 찾아라' 같은 범위 검색이나 정렬된 순회에는 적합하지 않습니다. 이런 기능이 중요하다면 TreeMap 같은 정렬 기반 자료구조가 더 적합합니다."

**핵심 요약**

**Hash는 순서를 버리고 빠른 조회를 얻는다**

---

<a name="q1-4"></a>
#### ↳ Q1-4. Hash Table과 Java의 HashMap, Hashtable은 어떤 관계인가요?

> "Hash Table은 해시를 이용해 Key-Value를 저장하는 자료구조의 개념입니다. Java의 HashMap과 Hashtable은 이러한 해시 테이블 개념을 구현한 구체적인 클래스입니다.
>
> 참고로 Java 클래스 이름은 `HashTable`이 아니라 `Hashtable`입니다."

**핵심 요약**

**Hash Table은 개념, HashMap과 Hashtable은 Java 구현체**

---

<a name="q1-5"></a>
#### ↳ Q1-5. Hash Table이 데이터를 저장하고 조회하는 과정을 설명해주세요.

> "저장할 때는 Key의 해시값을 구하고, 그 값을 이용해 버킷 인덱스를 결정한 뒤 해당 위치에 Key와 Value를 저장합니다.
>
> 조회할 때도 동일하게 Key의 해시값으로 버킷을 찾아갑니다. 만약 같은 버킷에 여러 Key가 있다면 equals() 등의 비교를 통해 실제로 원하는 Key인지 추가로 확인합니다."

**핵심 요약**

**hashCode로 버킷을 찾고, equals로 진짜 Key를 찾는다**

---

<a name="q2"></a>
### Q2. 좋은 해시 함수의 조건은 무엇인가요?

> "좋은 해시 함수는 같은 입력에는 항상 같은 해시값을 반환해야 하고, 입력 데이터를 가능한 한 여러 버킷에 고르게 분산시켜 충돌을 줄여야 합니다. 또한 해시값을 계산하는 비용 자체도 너무 크지 않아야 합니다."

**핵심 요약**

**같은 입력은 같은 값, 데이터는 고르게 분산, 계산은 빠르게**

---

<a name="q2-1"></a>
#### ↳ Q2-1. 균등 분산이 안 되면 어떤 문제가 생기나요?

> "특정 버킷에 데이터가 집중되어 해시 충돌이 많아집니다. 그러면 해당 버킷 내부에서 여러 데이터를 추가로 비교해야 하기 때문에 해시 테이블의 평균 O(1)이라는 장점을 제대로 활용하지 못하고 성능이 저하됩니다."

**핵심 요약**

**한 버킷에 몰리면 O(1)의 장점이 사라진다**

---

<a name="q2-2"></a>
#### ↳ Q2-2. 실제 서비스에서 충돌 편중을 악용한 공격도 가능한가요?

> "가능합니다. 이를 Hash Collision DoS와 같은 형태로 악용할 수 있습니다. 공격자가 충돌이 많이 발생하는 Key를 대량으로 입력하면 서버가 한 버킷 내부를 반복적으로 탐색하는 데 많은 CPU 시간을 사용할 수 있습니다.
>
> 그래서 실제 구현에서는 해시 분산을 개선하거나, 충돌이 심한 버킷의 자료구조를 변경하는 등의 방법으로 피해를 완화하기도 합니다."

**핵심 요약**

**의도적으로 충돌을 만들면 해시의 성능 저하를 공격에 이용할 수 있다**

---

<a name="q2-3"></a>
#### ↳ Q2-3. 모든 객체의 hashCode()가 같은 값을 반환하면 HashMap은 정상 동작하나요?

> "기능적으로는 동작할 수 있습니다. HashMap은 hashCode()만 보고 Key가 같은지 판단하지 않고 equals()까지 확인하기 때문입니다.
>
> 하지만 모든 Key가 같은 해시값을 가지면 같은 버킷에 데이터가 집중되므로 성능이 크게 저하됩니다."

**핵심 요약**

**동작은 하지만 모두 같은 버킷에 몰려 매우 비효율적이다**

---

<a name="q3"></a>
### Q3. 해시 충돌은 왜 발생하나요?

> "서로 다른 입력이 같은 해시값이나 같은 버킷 인덱스로 매핑될 수 있기 때문입니다. 가능한 Key의 종류는 매우 많지만 실제 해시값과 버킷의 수는 한정되어 있으므로 충돌을 완전히 없애는 것은 일반적으로 불가능합니다."

**핵심 요약**

**입력은 많은데 저장 위치는 한정되어 있어서 충돌이 생긴다**

---

<a name="q3-1"></a>
#### ↳ Q3-1. 충돌을 해결하는 방법에는 어떤 것들이 있나요?

> "대표적으로 Separate Chaining과 Open Addressing이 있습니다.
>
> Separate Chaining은 충돌한 데이터를 같은 버킷 내부의 별도 구조에 함께 저장하는 방식이고, Open Addressing은 충돌이 발생하면 다른 빈 슬롯을 찾아 저장하는 방식입니다.
>
> Open Addressing에는 선형 탐사, 이차 탐사, 이중 해싱 등의 방법이 있습니다. Java의 HashMap은 버킷 안에서 노드들을 관리하는 Chaining 계열의 방식을 사용하고, 충돌이 심해지면 일부 버킷을 트리 구조로 바꿀 수 있습니다."

**핵심 요약**

**Chaining은 같은 버킷 안에 저장, Open Addressing은 다른 빈칸을 찾는다**

---

<a name="q3-2"></a>
#### ↳ Q3-2. Chaining과 Open Addressing 중 어느 것이 더 좋은가요?

> "무조건 한쪽이 더 좋다고 할 수는 없습니다. Chaining은 저장 공간이 버킷 배열에만 제한되지 않고 충돌 처리도 비교적 유연하지만 추가 노드와 포인터 등의 메모리 비용이 있습니다.
>
> Open Addressing은 배열 내부에 데이터를 저장해 메모리 지역성이 좋을 수 있지만, Load Factor가 높아지면 충돌과 탐사 횟수가 크게 증가할 수 있습니다. 따라서 데이터 크기와 메모리 특성, 구현 목적에 따라 선택합니다."

**핵심 요약**

**둘 다 장단점이 있어서 상황에 따라 선택한다**

---

<a name="q3-3"></a>
#### ↳ Q3-3. 해시 충돌이 발생하면 왜 성능이 저하되나요?

> "원래는 계산된 인덱스로 바로 접근하는 것이 해시의 장점인데, 충돌이 발생하면 같은 위치에 있는 여러 후보 중 원하는 Key를 추가로 찾아야 하기 때문입니다. 충돌이 많아질수록 비교 횟수도 증가합니다."

**핵심 요약**

**충돌이 나면 바로 못 찾고 추가 탐색을 해야 한다**

---

<a name="q3-4"></a>
#### ↳ Q3-4. 개방 주소법의 클러스터링이란 무엇인가요?

> "충돌한 데이터를 주변의 빈 슬롯에 저장하다 보니 특정 영역에 데이터가 연속적으로 몰리는 현상입니다. 특히 선형 탐사에서는 큰 덩어리의 군집이 만들어질 수 있고, 군집이 커질수록 빈 공간을 찾거나 데이터를 조회하는 탐사 횟수가 증가합니다.
>
> 이차 탐사나 이중 해싱 등을 이용해 이러한 현상을 완화할 수 있습니다."

**핵심 요약**

**충돌 때문에 데이터가 한 구역에 뭉쳐 탐사가 길어지는 현상**

---

<a name="q3-5"></a>
#### ↳ Q3-5. Open Addressing에서 삭제할 때 왜 단순히 슬롯을 비우면 안 되나요?

> "Open Addressing에서는 충돌 때문에 원래 위치보다 뒤쪽에 저장된 데이터가 있을 수 있습니다. 탐색 과정에서 빈 슬롯을 만나면 검색을 종료하는 방식이라면, 중간 데이터를 그냥 삭제해 빈칸으로 만들 경우 뒤에 있는 데이터를 찾지 못할 수 있습니다.
>
> 그래서 일반적으로 삭제되었다는 별도의 표시인 Tombstone을 사용하거나, 구현에 맞는 삭제 처리를 합니다."

**핵심 요약**

**중간을 그냥 비우면 뒤에 있는 데이터를 못 찾을 수 있다**

---

<a name="q3-6"></a>
#### ↳ Q3-6. 비어 있는 슬롯을 찾는 방법은?

> "이를 Probing이라고 합니다. 선형 탐사는 일정하게 한 칸씩 이동하고, 이차 탐사는 이동 폭을 제곱 형태로 변화시키며, 이중 해싱은 두 번째 해시 함수를 이용해 이동 간격을 결정합니다."

**핵심 요약**

**Probing = 충돌이 나면 다른 빈 슬롯을 찾아가는 방법**

---

<a name="q3-7"></a>
#### ↳ Q3-7. hashCode()는 같지만 equals()가 다른 객체를 HashMap에 넣으면 어떻게 되나요?

> "같은 버킷의 후보가 될 수 있지만 equals() 결과가 false라면 서로 다른 Key로 판단하므로 둘 다 저장할 수 있습니다. HashMap은 hashCode()만 같다고 해서 같은 Key라고 판단하지 않습니다."

**핵심 요약**

**hashCode가 같아도 equals가 다르면 다른 Key다**

---

<a name="q4"></a>
### Q4. 해시와 암호화의 차이는 무엇인가요?

> "암호화는 Key를 이용해 데이터를 변환하고, 적절한 Key를 가지고 있으면 다시 원본으로 복호화할 수 있도록 설계됩니다.
>
> 반면 암호학적 해시는 일반적으로 해시값에서 원본을 복원하기 어렵도록 만든 단방향 함수입니다. 따라서 비밀번호는 보통 복호화 가능한 형태로 저장하지 않고 비밀번호 전용 해시 또는 Key Derivation Function을 이용해 검증합니다."

**핵심 요약**

**암호화는 키로 복호화할 수 있다. 암호학적 해시는 역상 탐색이 어렵도록 설계하며 일반 해시 함수에는 그런 보장이 없다.**

---

<a name="q4-1"></a>
#### ↳ Q4-1. 비밀번호를 SHA-256으로 해싱해서 저장하면 안전한가요?

> "SHA-256을 한 번 적용하는 것만으로는 비밀번호 저장 방식으로 충분하지 않습니다. SHA-256은 빠르게 계산되도록 설계되어 있기 때문에 공격자도 많은 비밀번호 후보를 빠르게 대입할 수 있습니다.
>
> 비밀번호 저장에는 bcrypt, scrypt, PBKDF2, Argon2처럼 공격 비용을 높이도록 설계된 비밀번호 해싱 방식이나 KDF를 사용하는 것이 적절합니다."

**핵심 요약**

**비밀번호 해시는 일부러 느려야 무차별 대입 공격에 강하다**

---

<a name="q4-2"></a>
#### ↳ Q4-2. Salt는 왜 필요한가요?

> "비밀번호마다 서로 다른 임의의 값을 추가해 같은 비밀번호라도 서로 다른 해시 결과가 나오게 하기 위해 사용합니다.
>
> Salt가 없으면 같은 비밀번호를 사용하는 계정의 해시값도 같아질 수 있고, 미리 계산해둔 해시 목록을 이용한 공격에도 더 취약해질 수 있습니다."

**핵심 요약**

**Salt = 같은 비밀번호도 다른 해시값이 나오게 한다**

---

<a name="q5"></a>
### Q5. 백엔드에서 해시는 어디에 활용되나요?

> "Key 기반 빠른 조회를 위한 Map이나 Set, 비밀번호 검증, 파일이나 데이터의 무결성 확인, 캐시 Key 생성, 중복 데이터 탐지 등 다양한 곳에서 사용됩니다. 다만 사용 목적에 따라 일반 해시 함수와 암호학적 해시 함수를 구분해서 사용해야 합니다."

**핵심 요약**

**해시는 빠른 조회·중복 확인·무결성 검증 등에 활용된다**

---

<a name="section-02"></a>
## Hashtable

<a name="q6"></a>
### Q6. [대표 질문] Hashtable과 HashMap의 차이는 무엇인가요?

> "둘 다 Java에서 Key-Value를 해시 기반으로 저장하는 Map 구현체이지만 중요한 차이가 있습니다.
>
> Hashtable의 주요 메서드는 동기화되어 있어 여러 스레드가 개별 연산을 호출할 때 스레드 안전성을 제공합니다. 반면 HashMap은 자체적인 동기화를 제공하지 않습니다.
>
> 또한 Hashtable은 null Key와 null Value를 허용하지 않지만, HashMap은 null Key 하나와 null Value들을 허용합니다. Hashtable은 오래된 레거시 클래스이기 때문에 현대 Java 코드에서는 일반적으로 HashMap이나 ConcurrentHashMap을 상황에 맞게 사용합니다."

**핵심 요약**

**Hashtable은 동기화된 옛 구현, HashMap은 비동기화된 일반 구현**

---

<a name="q7"></a>
### Q7. Hashtable이 멀티스레드에서 안전한데도 요즘 잘 사용되지 않는 이유는?

> "Hashtable은 주요 연산을 synchronized 방식으로 보호하기 때문에 단순한 개별 연산의 스레드 안전성은 제공하지만, 동시에 여러 스레드가 접근할 때 병렬 처리 효율이 떨어질 수 있습니다.
>
> 동시 접근이 많은 환경에서는 ConcurrentHashMap이 더 높은 동시성을 제공하기 때문에 일반적으로 더 적합합니다."

**핵심 요약**

**멀티스레드라고 무조건 Hashtable이 아니라 보통 ConcurrentHashMap을 고려한다**

---

<a name="q7-1"></a>
#### ↳ Q7-1. ConcurrentHashMap은 어떻게 더 높은 동시성을 제공하나요?

> "ConcurrentHashMap은 전체 Map에 하나의 전역 락을 걸어 모든 작업을 직렬화하는 방식이 아니라, 조회와 갱신을 더 세분화해서 처리합니다.
>
> 현대 Java 구현에서는 조회는 일반적으로 락 없이 수행할 수 있고, 갱신 과정에서는 CAS나 필요한 버킷 단위의 동기화 등을 이용합니다. 그래서 서로 관련 없는 위치에 대한 작업은 더 높은 동시성으로 처리할 수 있습니다."

**핵심 요약**

**ConcurrentHashMap = 전체를 잠그지 않고 필요한 부분만 조정해 동시성을 높인다**

---

<a name="q7-2"></a>
#### ↳ Q7-2. HashMap을 Collections.synchronizedMap()으로 감싸면 ConcurrentHashMap과 같은가요?

> "아닙니다. synchronizedMap은 Map에 동기화 기능을 추가할 수 있지만, ConcurrentHashMap과 내부 구현이나 동시성 특성이 동일하지는 않습니다.
>
> synchronizedMap은 많은 연산을 하나의 동기화된 Map을 기준으로 보호하는 반면, ConcurrentHashMap은 높은 동시 접근을 고려해 별도로 설계되었습니다."

**핵심 요약**

**synchronizedMap과 ConcurrentHashMap은 둘 다 안전할 수 있지만 동시성 구조가 다르다**

---

<a name="q8"></a>
### Q8. Hashtable이 null을 허용하지 않는 이유는 무엇인가요?

> "Hashtable의 API 자체가 null Key와 null Value를 허용하지 않도록 설계되어 있습니다. 특히 get()이 null을 반환했을 때 'Key가 없는 것인지'와 'Value 자체가 null인 것인지'를 명확하게 구분해야 하는 문제도 있습니다.
>
> ConcurrentHashMap 역시 동시성 환경에서 이러한 모호성을 피하기 위해 null Key와 null Value를 허용하지 않습니다."

**핵심 요약**

**Hashtable과 ConcurrentHashMap은 null을 허용하지 않는다**

---

<a name="q8-1"></a>
#### ↳ Q8-1. HashMap의 null Key는 내부적으로 어떻게 저장되나요?

> "HashMap은 null Key를 허용합니다. null Key는 내부적으로 해시값 0에 해당하도록 처리되므로 현재 일반적인 HashMap 구현에서는 0번 버킷의 후보가 됩니다.
>
> null Key는 하나만 존재할 수 있고, null Value는 여러 Key에 대해 저장할 수 있습니다."

**핵심 요약**

**HashMap은 null Key 하나와 null Value 여러 개를 허용한다**

---

<a name="section-03"></a>
## HashMap

<a name="q9"></a>
### Q9. [대표 질문] HashMap은 내부적으로 어떻게 동작하나요?

> "HashMap은 Key의 hashCode()를 기반으로 내부 해시값을 만들고, 이를 이용해 버킷 인덱스를 결정합니다.
>
> 데이터를 저장할 때 해당 버킷에 Key-Value를 저장하고, 조회할 때도 같은 방식으로 버킷을 찾습니다. 같은 버킷에 여러 Key가 존재한다면 hash와 equals() 등을 이용해 실제 Key를 구분합니다.
>
> 해시가 적절히 분산되어 있다면 조회·삽입·삭제는 평균 O(1)입니다."

**핵심 요약**

**hashCode로 위치를 찾고 equals로 정확한 Key를 확인한다**

---

<a name="q9-1"></a>
#### ↳ Q9-1. HashMap의 Capacity는 왜 보통 2의 제곱수인가요?

> "Java HashMap 구현에서는 테이블 크기를 2의 제곱수 형태로 유지합니다. 그러면 버킷 인덱스를 계산할 때 `hash & (capacity - 1)`과 같은 비트 연산을 사용할 수 있고, 해시값의 비트를 이용해 효율적으로 버킷을 분배할 수 있습니다.
>
> 또한 용량을 두 배로 늘릴 때 기존 데이터의 새 위치를 효율적으로 결정할 수 있다는 장점도 있습니다."

**핵심 요약**

**2의 제곱수면 비트 연산으로 버킷 계산과 리사이징이 효율적이다**

---

<a name="q9-2"></a>
#### ↳ Q9-2. HashMap의 기본 초기 Capacity와 Load Factor는 얼마인가요?

> "기본 초기 Capacity는 16이고 기본 Load Factor는 0.75입니다.
>
> 따라서 테이블 용량이 16이라면 임계값은 16 × 0.75 = 12가 됩니다. 엔트리 수가 이 임계값을 초과하면, 일반적으로 다음 삽입 과정에서 용량을 늘리는 리사이징이 발생합니다."

**핵심 요약**

**기본 Capacity 16, Load Factor 0.75, 임계값은 12**

---

<a name="q10"></a>
### Q10. HashMap의 조회가 항상 O(1)인가요?

> "아닙니다. 평균적으로 O(1)이지만 해시 충돌 상태에 따라 탐색 비용이 증가할 수 있습니다.
>
> 현대 Java HashMap은 하나의 버킷에 충돌한 데이터가 지나치게 많아지고 테이블 크기도 충분히 크면 버킷을 연결 구조에서 Red-Black Tree 기반 구조로 변경하여 충돌이 심한 상황의 탐색 성능을 개선합니다."

**핵심 요약**

**HashMap은 평균 O(1)이지만 충돌이 심하면 느려진다**

---

<a name="q10-1"></a>
#### ↳ Q10-1. 특정 버킷에 데이터가 많이 몰리면 Java HashMap은 어떻게 처리하나요?

> "Java 8 이후 HashMap에서는 한 버킷의 노드 수가 트리화 기준에 도달하고, 전체 테이블 크기도 일정 기준 이상이면 해당 버킷을 Red-Black Tree 기반 구조로 변환할 수 있습니다.
>
> 대표적인 기준은 노드 수 8과 테이블 크기 64입니다. 이를 통해 충돌이 심한 버킷에서 선형적으로 탐색하는 비용을 줄일 수 있습니다."

**핵심 요약**

**충돌이 너무 많으면 리스트 형태의 버킷을 트리로 바꾼다**

---

<a name="q10-2"></a>
#### ↳ Q10-2. 왜 하필 8개인가요?

> "트리는 노드 자체의 구조와 연산이 연결 구조보다 복잡하기 때문에 데이터가 적을 때부터 사용하는 것이 항상 효율적인 것은 아닙니다.
>
> 그래서 Java HashMap 구현은 충돌 노드가 충분히 많아졌다고 판단되는 임계값을 두고 그 이상일 때 트리화를 고려합니다. 현재 구현의 대표적인 TREEIFY_THRESHOLD가 8입니다."

**핵심 요약**

**적을 때는 리스트가 가볍고, 충돌이 충분히 많아졌을 때만 트리로 바꾼다**

---

<a name="q10-3"></a>
#### ↳ Q10-3. 트리 전환에는 다른 조건도 있나요?

> "있습니다. 버킷의 노드가 8개 이상이더라도 전체 테이블 용량이 충분히 크지 않으면 바로 트리화하지 않고 리사이징을 우선할 수 있습니다.
>
> Java HashMap의 대표적인 MIN_TREEIFY_CAPACITY는 64입니다. 작은 테이블에서는 버킷 수 자체를 늘려 충돌을 분산시키는 것이 더 효율적일 수 있기 때문입니다."

**핵심 요약**

**8개만 넘는다고 바로 트리가 아니라 테이블 크기도 충분히 커야 한다**

---

<a name="q10-4"></a>
#### ↳ Q10-4. 트리에서 다시 작은 구조로 돌아가는 기준은 왜 6인가요?

> "Java 구현에는 트리화 기준과 다시 축소하는 기준 사이에 차이를 둡니다. 대표적으로 트리화 기준은 8, UNTREEIFY_THRESHOLD는 6입니다.
>
> 이렇게 간격을 두면 데이터 수가 경계값 근처에서 증가와 감소를 반복할 때 자료구조가 계속 변환되는 현상을 줄일 수 있습니다."

**핵심 요약**

**OpenJDK 21의 6은 리사이징으로 나뉜 버킷의 리스트 전환 기준이다. 일반 삭제 경로에서는 트리 모양도 고려한다**

---

<a name="q10-5"></a>
#### ↳ Q10-5. 왜 처음부터 트리를 사용하지 않나요?

> "데이터가 적은 경우에는 트리보다 단순한 노드 구조가 메모리 사용량과 연산 비용 측면에서 더 가볍기 때문입니다. 충돌이 많아져 선형 탐색 비용이 문제가 되는 경우에만 트리를 사용하는 것이 효율적입니다."

**핵심 요약**

**데이터가 적을 때는 단순한 구조가 더 가볍다**

---

<a name="q10-6"></a>
#### ↳ Q10-6. 데이터가 많아져도 HashMap 조회가 무조건 O(n)이 되지 않는 이유는?

> "데이터가 증가하면 일정 기준에서 테이블의 Capacity도 함께 증가하기 때문입니다. 해시값이 고르게 분산된다면 데이터 수가 늘어도 버킷 수도 함께 늘어나므로 하나의 버킷에 데이터가 과도하게 몰리는 것을 줄일 수 있습니다."

**핵심 요약**

**데이터가 늘면 버킷도 늘려 충돌을 분산한다**

---

<a name="q11"></a>
### Q11. Load Factor와 Resizing에 대해 설명해주세요.

> "Load Factor는 HashMap이 어느 정도 차면 Capacity를 늘릴지 결정하는 기준입니다. Java HashMap의 기본값은 0.75입니다.
>
> 예를 들어 Capacity가 16이면 임계값은 12이고, 저장된 엔트리 수가 이 값을 초과하면 보통 테이블 크기를 더 크게 늘리는 리사이징이 발생합니다.
>
> 리사이징 과정에서는 기존 엔트리들을 새 테이블의 적절한 버킷에 다시 배치해야 하기 때문에 비용이 발생합니다."

**핵심 요약**

**Load Factor = 얼마나 차면 테이블을 키울지 정하는 기준**

---

<a name="q11-1"></a>
#### ↳ Q11-1. 리사이징 비용을 줄이려면 어떻게 해야 하나요?

> "저장할 데이터의 개수를 어느 정도 예측할 수 있다면 처음부터 적절한 초기 용량을 지정하는 것이 좋습니다. 그러면 데이터가 증가하면서 테이블을 여러 번 확장하고 재배치하는 비용을 줄일 수 있습니다.
>
> 다만 초기 용량을 지나치게 크게 잡으면 불필요한 메모리를 사용할 수 있으므로 적절한 크기를 정해야 합니다."

**핵심 요약**

**데이터 수를 안다면 초기 Capacity를 적절히 잡아 리사이징을 줄인다**

---

<a name="q11-2"></a>
#### ↳ Q11-2. 대용량 데이터를 다룰 때 초기 용량이 중요한 이유는?

> "초기 테이블이 지나치게 작으면 데이터가 증가할 때마다 여러 번 리사이징이 발생할 수 있습니다. 리사이징 때는 새로운 테이블을 만들고 기존 엔트리들을 새 위치에 배치해야 하므로 데이터가 많을수록 누적 비용이 커집니다."

**핵심 요약**

**대용량인데 Capacity가 작으면 리사이징이 반복되어 비싸다**

---

<a name="q11-3"></a>
#### ↳ Q11-3. Load Factor를 1.0으로 높이면 어떻게 되나요?

> "Load Factor를 높이면 같은 데이터 수에 대해 테이블 크기를 상대적으로 작게 유지할 수 있어 공간 사용량을 줄일 수 있지만, 하나의 버킷에 데이터가 몰릴 가능성이 높아져 조회 비용이 증가할 수 있습니다.
>
> 반대로 Load Factor를 낮추면 충돌 가능성은 줄일 수 있지만 더 큰 테이블이 필요해 메모리 사용량이 증가합니다.
>
> 기본값 0.75는 시간과 공간 사이의 일반적인 균형값입니다."

**핵심 요약**

**Load Factor가 높으면 메모리 절약·충돌 증가, 낮으면 그 반대**

---

<a name="q12"></a>
### Q12. HashMap의 Key로는 어떤 객체를 사용하는 것이 좋나요?

> "가능하면 Key의 equals()와 hashCode() 계산에 사용되는 값이 변경되지 않는 객체가 좋습니다.
>
> Key를 저장한 뒤 해당 값이 변경되어 hashCode()가 달라지면, 조회할 때 저장 당시와 다른 버킷을 탐색할 수 있어 정상적으로 데이터를 찾지 못할 수 있기 때문입니다. 따라서 불변 객체를 Key로 사용하는 것이 안전합니다."

**핵심 요약**

**HashMap Key는 저장 후 hashCode가 변하지 않는 객체가 좋다**

---

<a name="q12-1"></a>
#### ↳ Q12-1. HashMap의 Key로 String이 많이 사용되는 이유는?

> "String은 불변 객체이기 때문에 생성된 후 문자열 값이 바뀌지 않습니다. 따라서 Key로 사용한 뒤 hashCode가 바뀌는 문제가 없습니다.
>
> 또한 equals()와 hashCode()가 값 기반으로 올바르게 구현되어 있어 Key로 사용하기 편리합니다."

**핵심 요약**

**String은 불변이고 equals/hashCode가 잘 구현되어 있어 Key로 안전하다**

---

<a name="q12-2"></a>
#### ↳ Q12-2. 가변 객체를 Key로 사용하고 값이 바뀌면 어떻게 되나요?

> "Key의 변경으로 hashCode()가 바뀌면 get()이나 containsKey()가 저장 당시의 버킷과 다른 위치를 찾아가면서 기존 엔트리를 찾지 못할 수 있습니다.
>
> 엔트리 자체는 Map 내부에 남아 있을 수 있으므로 매우 찾기 어려운 상태가 됩니다. 그래서 hashCode와 equals에 영향을 주는 필드는 Key로 저장한 뒤 변경하지 않는 것이 좋습니다."

**핵심 요약**

**Key가 바뀌면 저장은 돼 있는데 조회를 못 하는 문제가 생길 수 있다**

---

<a name="q12-3"></a>
#### ↳ Q12-3. 커스텀 객체를 Key로 사용할 때 반드시 해야 할 것은?

> "객체의 논리적인 동일성을 기준으로 사용하려면 equals()와 hashCode()를 서로의 규약에 맞게 함께 구현해야 합니다.
>
> 그리고 가능하면 두 메서드의 계산에 사용하는 필드는 변경되지 않도록 불변 객체로 설계하는 것이 안전합니다."

**핵심 요약**

**커스텀 Key는 equals와 hashCode를 함께 구현하고 가능하면 불변으로 만든다**

---

<a name="q12-4"></a>
#### ↳ Q12-4. equals()와 hashCode()는 각각 어떤 역할을 하나요?

> "hashCode()는 HashMap이 데이터를 저장하거나 찾을 버킷의 후보를 빠르게 결정하는 데 사용되고, equals()는 같은 버킷의 후보들 중 실제로 같은 Key인지 판단하는 데 사용됩니다."

**핵심 요약**

**hashCode는 버킷 찾기, equals는 진짜 Key 확인**

---

<a name="q12-5"></a>
#### ↳ Q12-5. equals()만 오버라이딩하고 hashCode()를 재정의하지 않으면 어떤 문제가 생기나요?

> "논리적으로 같은 객체인데 서로 다른 hashCode()를 반환할 수 있습니다. 그러면 HashMap이 두 객체를 서로 다른 버킷에서 찾게 되어 equals()를 비교할 기회조차 생기지 않을 수 있습니다.
>
> 따라서 Java의 equals/hashCode 규약에 따라 equals()가 true인 두 객체는 반드시 같은 hashCode()를 반환하도록 구현해야 합니다."

**핵심 요약**

**equals를 재정의하면 hashCode도 같이 맞춰야 한다**

---

<a name="q12-6"></a>
#### ↳ Q12-6. equals()가 true면 hashCode()도 같아야 하는데 반대도 성립하나요?

> "아닙니다. equals()가 true인 객체들은 반드시 같은 hashCode()를 가져야 하지만, hashCode()가 같다고 해서 equals()가 반드시 true일 필요는 없습니다.
>
> 서로 다른 객체가 같은 hashCode()를 갖는 것이 바로 해시 충돌입니다."

**핵심 요약**

**equals 같음 → hashCode 같음 / hashCode 같음 → equals 같음은 아님**

---

<a name="q13"></a>
### Q13. HashMap은 Thread-safe한가요?

> "아닙니다. HashMap 자체는 동기화를 제공하지 않습니다. 여러 스레드가 동시에 같은 HashMap을 구조적으로 수정한다면 외부에서 동기화를 적용하거나 ConcurrentHashMap 같은 동시성 자료구조를 사용해야 합니다.
>
> 따라서 멀티스레드라고 무조건 HashMap을 사용할 수 없는 것은 아니지만, 아무런 동기화 없이 동시에 수정하는 것은 안전하지 않습니다."

**핵심 요약**

**HashMap은 기본적으로 Thread-safe하지 않다**

---

<a name="q14"></a>
### Q14. HashMap, TreeMap, LinkedHashMap은 각각 언제 사용하나요?

> "순서가 중요하지 않고 Key 기반의 빠른 조회가 필요하다면 HashMap이 적합합니다.
>
> Key를 정렬된 상태로 유지하거나 범위 검색이 필요하다면 TreeMap이 적합하고, 삽입 순서나 접근 순서를 유지할 필요가 있다면 LinkedHashMap을 사용할 수 있습니다."

**핵심 요약**

**빠른 조회는 HashMap / 정렬은 TreeMap / 순서 보존은 LinkedHashMap**

---

<a name="q14-1"></a>
#### ↳ Q14-1. LinkedHashMap으로 LRU Cache를 만들 수 있는 원리는?

> "LinkedHashMap은 삽입 순서뿐 아니라 접근 순서를 기준으로 엔트리를 관리하는 모드를 지원합니다.
>
> accessOrder를 true로 설정하면 최근에 접근한 엔트리가 순서상 뒤쪽으로 이동하므로 가장 앞쪽의 엔트리가 가장 오래 사용되지 않은 항목이 됩니다.
>
> 여기에 크기 초과 시 가장 오래된 엔트리를 제거하도록 구현하면 LRU Cache를 만들 수 있습니다."

**핵심 요약**

**접근한 데이터를 뒤로 보내고 맨 앞의 오래된 데이터를 제거하면 LRU**

---

<a name="q14-2"></a>
#### ↳ Q14-2. HashMap은 어떤 상황에서 적합한가요?

> "회원 ID로 회원을 찾거나 상품 ID로 상품 정보를 찾는 것처럼 특정 Key를 이용한 조회가 자주 발생하면서 정렬된 순서가 필요하지 않은 경우에 적합합니다."

**핵심 요약**

**순서보다 Key 기반 빠른 조회가 중요할 때 HashMap**

---

<a name="q15"></a>
### Q15. 백엔드에서 HashMap은 어디에 활용되나요?

> "요청 처리 중 데이터를 Key별로 묶거나 빠르게 조회할 때, 중복 여부를 확인할 때, 설정값이나 동적으로 구성된 필드를 Key-Value 형태로 관리할 때, 간단한 메모리 내 lookup 구조를 만들 때 등 다양한 곳에서 사용합니다.
>
> 다만 여러 스레드가 동시에 수정하는 공유 데이터라면 HashMap 대신 적절한 동기화 방식이나 ConcurrentHashMap 등을 고려해야 합니다."

**핵심 요약**

**백엔드에서 Key로 데이터를 빠르게 찾고 관리할 때 자주 사용한다**

---

<a name="section-04"></a>
## 연관 종합 질문

<a name="q16"></a>
### Q16. HashMap과 HashSet은 어떤 관계인가요?

> "Java의 HashSet은 내부적으로 HashMap을 이용해 구현됩니다. Set에 추가하는 객체를 내부 HashMap의 Key로 사용하고, Value에는 내부적으로 사용하는 공통 더미 객체를 저장합니다.
>
> 따라서 HashSet 역시 hashCode()와 equals()를 이용해 중복 여부를 판단합니다."

**핵심 요약**

**HashSet은 값을 HashMap의 Key로 넣어 중복을 제거한다**

---

<a name="q16-1"></a>
#### ↳ Q16-1. HashSet에 equals/hashCode를 제대로 구현하지 않은 객체를 넣으면 어떻게 되나요?

> "논리적으로는 같은 값을 가진 두 객체라도 equals()와 hashCode()가 그 의미에 맞게 구현되어 있지 않다면 HashSet이 서로 다른 객체라고 판단해 둘 다 저장할 수 있습니다.
>
> 따라서 사용자 정의 객체를 값 기준으로 중복 제거하려면 equals()와 hashCode()를 올바르게 구현해야 합니다."

**핵심 요약**

**HashSet의 중복 판단도 equals + hashCode다**

---

<a name="q17"></a>
### Q17. Hash, Hash Table, HashMap의 관계를 한 문장으로 설명한다면?

> "Hash는 입력을 해시값으로 변환하는 개념이고, Hash Table은 그 해시값을 이용해 데이터를 빠르게 저장하고 조회하는 자료구조이며, HashMap은 Java에서 이를 Key-Value 형태로 구현한 대표적인 클래스입니다."

**핵심 요약**

**Hash = 변환 / Hash Table = 자료구조 / HashMap = Java 구현체**

---

<a name="q18"></a>
### Q18. HashMap 대신 배열이나 리스트를 사용하면 안 되나요?

> "사용 목적에 따라 다릅니다. 배열이나 ArrayList는 인덱스를 알고 있다면 O(1)에 접근할 수 있고 순차 순회에도 적합합니다.
>
> 반면 '회원 ID가 5832인 회원을 찾아라'처럼 특정 Key를 기준으로 데이터를 탐색해야 한다면 일반 리스트는 처음부터 비교하면서 찾기 때문에 O(n)이 될 수 있지만, HashMap은 평균 O(1)에 찾을 수 있습니다."

**핵심 요약**

**Index로 찾으면 배열·리스트, Key로 찾으면 HashMap**

---

<a name="q18-1"></a>
#### ↳ Q18-1. HashMap이 ArrayList보다 조회가 무조건 빠른가요?

> "아닙니다. 무엇을 기준으로 조회하느냐가 다릅니다.
>
> ArrayList는 인덱스를 알고 있을 때 O(1)로 접근할 수 있고, HashMap은 Key를 기준으로 평균 O(1)에 탐색하는 데 강점이 있습니다. 따라서 자료구조의 성능은 사용 목적에 맞춰 비교해야 합니다."

**핵심 요약**

**ArrayList는 Index 조회, HashMap은 Key 조회에 강하다**

---

<a name="q19"></a>
### Q19. Hash 기반 자료구조의 트레이드오프는 무엇인가요?

> "빠른 Key 조회를 얻는 대신 추가적인 메모리 공간과 충돌 관리 비용이 필요합니다.
>
> 충돌을 줄이기 위해 실제 데이터 수보다 여유 있는 버킷 배열을 유지해야 하고, 데이터가 증가하면 리사이징 비용도 발생할 수 있습니다. 또한 기본적으로 정렬된 순서를 제공하지 않습니다.
>
> 그 대신 적절한 해시 분산이 이루어진다면 조회·삽입·삭제에서 평균 O(1)의 높은 성능을 얻을 수 있습니다."

**핵심 요약**

**Hash = 메모리와 순서를 어느 정도 포기하고 빠른 조회를 얻는 구조**

---

## 복습 요약

**Hash**

→ **Key를 빠르게 찾아가기 위한 값으로 변환**

**Hash Table**

→ **해시를 이용해 데이터를 저장하는 자료구조**

**HashMap**

→ **Java의 대표적인 Key-Value 해시 자료구조**

**Hashtable**

→ **동기화된 레거시 Map 구현체**

**ConcurrentHashMap**

→ **멀티스레드에서 높은 동시성을 위한 Map**

**Hash Collision**

→ **서로 다른 Key가 같은 위치의 후보가 되는 것**

**Chaining**

→ **충돌 데이터를 같은 버킷 안에서 관리**

**Open Addressing**

→ **충돌하면 다른 빈 슬롯을 찾음**

**Probing**

→ **빈 슬롯을 찾아 이동하는 과정**

**Clustering**

→ **충돌 때문에 데이터가 특정 영역에 뭉치는 현상**

**Tombstone**

→ **삭제됐지만 탐색은 계속하라는 표시**

**hashCode()**

→ **버킷 위치 후보를 찾는 데 사용**

**equals()**

→ **실제로 같은 Key인지 확인**

**equals가 true**

→ **hashCode는 반드시 같아야 함**

**hashCode가 같음**

→ **equals가 같다는 뜻은 아님**

**HashMap 평균 시간 복잡도**

→ **조회·삽입·삭제 평균 O(1)**

**Capacity**

→ **버킷 배열의 크기**

**기본 Capacity**

→ **16**

**Load Factor**

→ **얼마나 차면 크기를 늘릴지 정하는 기준**

**기본 Load Factor**

→ **0.75**

**Capacity 16의 Threshold**

→ **12, 이를 초과하면 리사이징 대상**

**Resizing**

→ **테이블을 키우고 데이터를 새 버킷에 재배치**

**Treeify**

→ **충돌이 심한 버킷을 트리 구조로 변경**

**대표 Treeify 기준**

→ **OpenJDK 21의 일반 put 경로에서는 기존 노드 8개인 버킷에 새 키를 추가할 때 트리화를 시도하며, 테이블 용량이 64 미만이면 먼저 확장**

**Immutable Key**

→ **hashCode가 바뀌지 않아 안전**

**String Key**

→ **불변 + equals/hashCode가 값 기반으로 구현됨**

**HashMap Thread-safe?**

→ **아니요**

**HashMap**

→ **빠른 Key 조회**

**TreeMap**

→ **Key 정렬·범위 검색**

**LinkedHashMap**

→ **순서 유지**

**HashSet**

→ **내부적으로 HashMap을 이용해 중복 제거**

**Password Hash**

→ **빠른 SHA-256 한 번보다 비밀번호 전용 느린 해시/KDF**

**Salt**

→ **같은 비밀번호도 다른 해시 결과가 나오게 함**

<a name="section-06"></a>
## 핵심 요약

**Hash = Key를 빠르게 찾아갈 값으로 변환**

**HashMap = hashCode로 버킷을 찾고 equals로 정확한 Key를 확인**

**Collision = 서로 다른 Key가 같은 버킷에 몰리는 것**

**Resize = 데이터가 많아지면 버킷 수를 늘려 충돌을 줄이는 것**

**equals()가 true면 hashCode()는 반드시 같아야 하지만, hashCode()가 같다고 equals()가 true인 것은 아니다**

---

<a name="section-07"></a>
## 구분해서 이해할 개념

**HashMap 평균 O(1) ≠ 항상 O(1)**

**hashCode가 같음 ≠ 같은 객체**

**equals가 같음 → hashCode는 같아야 함**

**HashMap ≠ Thread-safe**

**Hashtable ≠ Hash Table 개념 자체**

**ConcurrentHashMap ≠ Hashtable에 단순히 락을 조금 덜 거는 것**

**Capacity 16, Load Factor 0.75 → 12개가 되자마자 무조건 Resize가 아니라 임계값 12를 초과할 때 Resize**

**Treeify는 단순히 노드 8개만 보면 안 되고 테이블 Capacity 조건도 존재**

**Chaining과 Open Addressing 중 하나가 무조건 더 좋은 것은 아님**

**가변 객체를 Key로 쓰면 hashCode가 바뀌어 조회에 실패할 수 있음**
