<a name="section-01"></a>
## Memory (JVM 메모리 구조)

<a name="q1"></a>
### Q1. JVM의 메모리 영역은 어떻게 구성되나요?

> JVM의 Runtime Data Area는 Heap, Method Area, JVM Stack, PC Register, Native Method Stack으로 구분됩니다.
>
> Heap은 객체와 배열을 주로 저장하고, Method Area는 클래스 관련 정보를 관리합니다.
>
> 이 두 영역은 스레드 간 공유됩니다.
>
> 반면 JVM Stack, PC Register, Native Method Stack은 스레드별로 생성되어 관리됩니다.

**핵심 요약:** JVM 메모리는 Heap과 Method Area 등의 공유 영역, Stack과 PC Register 등의 스레드별 영역으로 구분된다.

<a name="q1-1"></a>
#### ↳ Q1-1. Method Area와 Metaspace는 같은 개념인가요?

> 완전히 같은 개념은 아닙니다.
>
> Method Area는 JVM 명세에서 정의하는 논리적인 메모리 영역입니다.
>
> Metaspace는 HotSpot JVM에서 클래스 메타데이터를 관리하기 위해 사용하는 구현 영역입니다.
>
> Java 8부터 HotSpot JVM은 기존 PermGen을 제거하고 Metaspace를 도입했습니다.

**핵심 요약:** Method Area는 JVM의 논리적 영역이고 Metaspace는 HotSpot JVM의 클래스 메타데이터 저장 구현이다.

<a name="q1-2"></a>
#### ↳ Q1-2. PC Register는 어떤 역할을 하나요?

> PC Register는 각 스레드가 실행 중인 JVM 명령어의 위치를 관리하는 영역입니다.
>
> 스레드마다 독립적으로 존재하며, 각 스레드의 실행 흐름을 관리하는 데 필요한 정보를 제공합니다.

**핵심 요약:** PC Register는 스레드별 JVM 명령어의 실행 위치를 관리한다.

<a name="q1-3"></a>
#### ↳ Q1-3. [심화 질문] Native Method Stack은 무엇인가요?

> Native Method Stack은 Java가 아닌 네이티브 메서드의 실행을 지원하는 메모리 영역입니다.
>
> 예를 들어 JNI를 통해 C나 C++ 등의 네이티브 코드를 호출할 때 관련 실행 정보를 관리하는 데 사용될 수 있습니다.

**핵심 요약:** Native Method Stack은 네이티브 메서드 실행을 지원하는 영역이다.

<a name="q1-4"></a>
#### ↳ Q1-4. [심화 질문] Heap과 Metaspace는 모두 GC의 영향을 받나요?

> Heap에 있는 일반 객체는 GC를 통해 메모리가 회수될 수 있습니다.
>
> Metaspace의 클래스 메타데이터도 클래스 언로딩이 가능한 조건이 충족되면 회수될 수 있습니다.
>
> 다만 두 영역의 저장 대상과 메모리 관리 방식은 서로 다릅니다.

**핵심 요약:** Heap의 객체와 Metaspace의 클래스 메타데이터는 각각의 조건에 따라 회수될 수 있다.

<a name="q2"></a>
### Q2. Stack과 Heap의 차이는 무엇인가요?

> Stack은 메서드 호출 시 생성되는 Stack Frame을 관리하며, 지역 변수와 메서드 실행에 필요한 정보를 저장합니다.
>
> 스레드마다 독립적으로 존재하고, 메서드가 종료되면 해당 Stack Frame이 제거됩니다.
>
> 반면 Heap은 객체와 배열이 주로 저장되는 영역으로 여러 스레드가 공유하며 GC를 통해 불필요한 객체의 메모리를 회수합니다.

**핵심 요약:** Stack은 메서드 실행 정보를 관리하고 Heap은 객체와 배열을 주로 저장한다.

<a name="q2-1"></a>
#### ↳ Q2-1. Java의 지역 변수는 항상 Stack에 저장되나요?

> 반드시 그렇지는 않습니다.
>
> JVM 명세에서 메서드의 지역 변수는 Stack Frame의 지역 변수 영역에서 관리됩니다.
>
> 하지만 실제 JVM 구현에서는 JIT 최적화에 따라 일부 값이 CPU 레지스터에 저장되거나 객체 할당이 최적화될 수 있습니다.
>
> 따라서 모든 지역 변수가 물리적으로 Stack 메모리에 저장된다고 단정할 수 없습니다.

**핵심 요약:** 지역 변수는 논리적으로 Stack Frame에서 관리되지만 실제 저장 위치는 JVM 최적화에 따라 달라질 수 있다.

<a name="q2-2"></a>
#### ↳ Q2-2. 객체와 참조 변수는 각각 어디에 저장되나요?

> 일반적으로 객체는 Heap에 생성됩니다.
>
> 참조 변수의 저장 위치는 선언된 위치에 따라 달라집니다.
>
> 메서드 내부의 지역 참조 변수는 Stack Frame에서 관리되고, 객체의 인스턴스 필드로 선언된 참조 변수는 해당 객체의 일부로 저장됩니다.
>
> 다만 실제 저장 방식은 JVM 최적화에 따라 달라질 수 있습니다.

**핵심 요약:** 객체는 주로 Heap에 생성되며 참조 변수는 선언 위치에 따라 관리되는 영역이 달라진다.

<a name="q2-3"></a>
#### ↳ Q2-3. StackOverflowError와 OutOfMemoryError는 어떻게 다른가요?

> StackOverflowError는 주로 재귀 호출 등이 지나치게 반복되어 스레드의 Stack 공간이 부족할 때 발생합니다.
>
> OutOfMemoryError는 JVM이 필요한 메모리를 확보하지 못할 때 발생합니다.
>
> OutOfMemoryError는 Heap뿐 아니라 Metaspace 등 다른 메모리 부족 상황에서도 발생할 수 있습니다.

**핵심 요약:** StackOverflowError는 스택 한도 초과, OutOfMemoryError는 메모리 확보 실패를 의미한다.

<a name="q2-4"></a>
#### ↳ Q2-4. [심화 질문] 여러 스레드가 같은 Heap 객체에 접근하면 어떤 문제가 발생할 수 있나요?

> Heap은 여러 스레드가 공유할 수 있으므로 동일한 변경 가능한 객체에 여러 스레드가 동시에 접근할 수 있습니다.
>
> 동기화 없이 같은 데이터를 수정하면 Race Condition이 발생할 수 있습니다.
>
> 이를 방지하기 위해 synchronized, Lock, Atomic 클래스, 불변 객체 등의 방법을 사용할 수 있습니다.

**핵심 요약:** 공유된 변경 가능한 객체에 여러 스레드가 동시에 접근하면 동시성 문제가 발생할 수 있다.

<a name="q3"></a>
### Q3. Java에서 객체가 생성되면 메모리에 어떻게 저장되나요?

> 일반적인 HotSpot JVM에서는 new 키워드로 객체를 생성할 때 주로 Heap에 객체를 위한 메모리를 할당합니다.
>
> 객체에는 인스턴스 필드와 객체 헤더 등의 정보가 포함되며, 생성된 객체를 가리키는 참조값이 반환됩니다.
>
> 메서드 내부의 지역 참조 변수는 일반적으로 Stack Frame에서 관리됩니다.
>
> 다만 실제 할당 방식은 JVM 최적화에 따라 달라질 수 있습니다.

**핵심 요약:** 객체는 일반적으로 Heap에 생성되며 참조 변수를 통해 접근한다.

<a name="q3-1"></a>
#### ↳ Q3-1. 객체를 생성하면 무조건 Heap에 할당되나요?

> 일반적인 Java 메모리 모델에서는 객체를 Heap에 생성한다고 설명합니다.
>
> 하지만 HotSpot JVM의 JIT 컴파일러는 Escape Analysis나 Scalar Replacement 등의 최적화를 통해 실제 객체 할당을 제거할 수 있습니다.
>
> 따라서 new 키워드가 항상 물리적인 Heap 할당으로 이어지는 것은 아닙니다.

**핵심 요약:** new는 논리적으로 객체를 생성하지만 JVM 최적화로 실제 Heap 할당이 생략될 수 있다.

<a name="q3-2"></a>
#### ↳ Q3-2. [심화 질문] 객체를 생성할 때 생성자보다 먼저 수행되는 작업은 무엇인가요?

> 객체 생성 시 필요한 클래스가 초기화되어 있는지 확인하고, 객체를 위한 메모리를 할당합니다.
>
> 이후 인스턴스 필드에 기본값을 설정하며, 객체 초기화 과정에서 명시적인 필드 초기화와 생성자 실행이 이루어집니다.
>
> 상속 관계가 있다면 상위 클래스의 초기화 순서도 고려해야 합니다.

**핵심 요약:** 객체 생성에서는 클래스 준비, 메모리 할당, 기본값 설정, 초기화 및 생성자 실행이 이루어진다.

<a name="q3-3"></a>
#### ↳ Q3-3. [심화 질문] 객체가 GC 대상이 되는 것과 실제 메모리가 회수되는 것은 같은 의미인가요?

> 아닙니다.
>
> GC 대상이 되었다는 것은 객체가 더 이상 도달 가능하지 않아 회수될 수 있는 상태라는 의미입니다.
>
> 실제 메모리가 회수되는 시점은 GC 알고리즘과 메모리 상황 등에 따라 달라집니다.

**핵심 요약:** GC 대상이 되는 시점과 실제 메모리가 회수되는 시점은 다를 수 있다.

<a name="q4"></a>
### Q4. Java는 Call By Value인가요, Call By Reference인가요?

> Java는 항상 Call By Value 방식으로 메서드 인자를 전달합니다.
>
> 기본형 변수를 전달하면 해당 값이 복사되고, 참조형 변수를 전달하면 객체 자체가 아니라 객체를 가리키는 참조값이 복사됩니다.
>
> 따라서 참조값을 통해 객체 내부의 필드를 수정하면 원본 객체에 영향을 줄 수 있지만, 메서드 내부에서 매개변수에 새로운 객체를 할당해도 호출자의 참조 변수는 바뀌지 않습니다.

**핵심 요약:** Java는 기본형과 참조형 모두 값을 복사하여 전달하는 Call By Value 방식이다.

<a name="q4-1"></a>
#### ↳ Q4-1. 참조값을 전달하는데 왜 Call By Reference가 아닌가요?

> Call By Reference는 호출자의 변수 자체에 접근하여 해당 변수에 저장된 값을 변경할 수 있는 방식입니다.
>
> 하지만 Java는 참조값 자체를 복사하여 전달합니다.
>
> 따라서 메서드 내부에서 매개변수에 다른 객체를 할당하더라도 호출자의 참조 변수는 변경되지 않습니다.

**핵심 요약:** Java는 객체의 참조값을 복사할 뿐 호출자의 참조 변수 자체를 전달하지 않는다.

<a name="q4-2"></a>
#### ↳ Q4-2. [심화 질문] 메서드 내부에서 객체의 필드를 수정하면 원본 객체가 변경되는 이유는 무엇인가요?

> 메서드에 전달된 참조값은 복사된 값이지만, 그 참조값이 호출자와 같은 객체를 가리킬 수 있기 때문입니다.
>
> 따라서 복사된 참조값을 이용해 객체의 필드를 변경하면 동일한 객체의 상태가 변경됩니다.
>
> 이는 Call By Reference이기 때문이 아니라 두 참조가 같은 객체를 가리키기 때문입니다.

**핵심 요약:** 참조값은 복사되지만 같은 객체를 가리키면 객체 내부 상태의 변경이 공유된다.

<a name="q5"></a>
### Q5. static 변수와 인스턴스 변수의 차이는 무엇인가요?

> static 변수는 클래스에 속하는 필드로, 동일한 클래스를 사용하는 여러 객체가 값을 공유합니다.
>
> 인스턴스 변수는 객체에 속하므로 객체마다 독립적인 필드 값을 가집니다.
>
> static 필드는 클래스 초기화 과정에서 초기화되며 인스턴스 필드는 객체 생성 과정에서 초기화됩니다.

**핵심 요약:** static 변수는 클래스에 속하고 인스턴스 변수는 각 객체에 속한다.

<a name="q5-1"></a>
#### ↳ Q5-1. static 변수는 Method Area에 저장되나요?

> JVM 명세에서 정적 필드는 클래스와 연관된 정보로 관리됩니다.
>
> 그러나 실제 저장 방식은 JVM 구현에 따라 달라집니다.
>
> HotSpot JVM에서는 static 필드의 값이 Heap에 있는 Class 미러 객체와 연관되어 저장됩니다.
>
> 따라서 모든 static 변수가 Metaspace에 저장된다고 설명하는 것은 정확하지 않습니다.

**핵심 요약:** static 필드는 클래스에 속하지만 실제 저장 위치는 JVM 구현에 따라 달라질 수 있다.

<a name="q5-2"></a>
#### ↳ Q5-2. static 변수가 참조하는 객체는 GC 대상이 되나요?

> 클래스가 살아 있고 static 필드가 객체를 계속 참조한다면 일반적으로 해당 객체는 GC Root에서 도달 가능한 상태이므로 회수되지 않습니다.
>
> 하지만 static 필드의 참조를 제거하거나 클래스가 언로딩되는 등의 상황에서는 객체가 GC 대상이 될 수 있습니다.

**핵심 요약:** static 필드의 참조가 유지되면 객체가 GC 대상에서 제외될 수 있다.

<a name="q5-3"></a>
#### ↳ Q5-3. [심화 질문] static 변수와 Spring Singleton Bean은 같은 개념인가요?

> 아닙니다.
>
> static 변수는 Java 언어 차원에서 클래스에 속하는 필드입니다.
>
> Spring Singleton Bean은 Spring IoC 컨테이너가 일반적으로 Bean 정의당 하나의 인스턴스를 생성하고 공유하도록 관리하는 객체입니다.
>
> 따라서 static은 클래스 차원의 개념이고 Spring Singleton은 객체 관리 범위에 관한 개념입니다.

**핵심 요약:** static은 클래스에 속하는 필드이고 Spring Singleton은 컨테이너가 관리하는 객체 범위이다.
