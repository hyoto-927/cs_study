<a name="section-01"></a>
## Garbage Collection (GC)

<a name="q1"></a>
### Q1. Garbage Collection이란 무엇이며, 왜 필요한가요?

> GC는 JVM이 더 이상 사용하지 않는 객체의 메모리를 자동으로 회수하는 기능입니다.
>
> Java에서는 개발자가 일반적인 객체 메모리를 직접 해제하지 않아도 되므로 메모리 관리 부담을 줄일 수 있습니다.
>
> GC는 일반적으로 GC Root에서 객체에 도달할 수 있는지를 기준으로 회수 대상을 판단합니다.
>
> 다만 GC에도 CPU와 메모리 자원이 필요하며, 일부 단계에서는 애플리케이션 실행이 일시적으로 중단될 수 있습니다.

**핵심 요약:** GC는 도달할 수 없는 객체의 메모리를 자동으로 회수하여 메모리 관리를 돕는다.

<a name="q1-1"></a>
#### ↳ Q1-1. Java에서는 메모리 누수가 발생하지 않나요?

> 아닙니다. Java에서도 메모리 누수가 발생할 수 있습니다.
>
> 예를 들어 더 이상 사용하지 않는 객체가 static 컬렉션이나 캐시에서 계속 참조되고 있다면 GC가 해당 객체를 회수하지 못할 수 있습니다.
>
> 따라서 GC가 자동으로 메모리를 관리하더라도 불필요한 객체 참조를 제거해야 합니다.

**핵심 요약:** Java도 불필요한 객체의 참조가 유지되면 메모리 누수가 발생할 수 있다.

<a name="q1-2"></a>
#### ↳ Q1-2. GC는 객체가 사용되지 않으면 즉시 실행되나요?

> 아닙니다.
>
> 객체가 GC Root에서 더 이상 도달할 수 없는 상태가 되면 회수 대상이 될 수 있지만 즉시 삭제되는 것은 아닙니다.
>
> 실제 GC 수행 시점은 GC 알고리즘과 메모리 상황 등에 따라 JVM이 결정합니다.

**핵심 요약:** 객체가 GC 대상이 되어도 실제 메모리 회수 시점은 보장되지 않는다.

<a name="q1-3"></a>
#### ↳ Q1-3. [심화 질문] System.gc()를 호출하면 GC가 즉시 실행되나요?

> 반드시 그렇지는 않습니다.
>
> System.gc()는 JVM에 가비지 컬렉션 수행을 요청하는 메서드입니다.
>
> JVM 구현과 설정에 따라 요청이 무시되거나 다르게 처리될 수 있으며, 특정 객체의 즉각적인 메모리 회수를 보장하지 않습니다.

**핵심 요약:** System.gc()는 GC 수행을 요청하지만 즉각적인 실행을 보장하지 않는다.

<a name="q2"></a>
### Q2. GC는 어떤 기준으로 객체를 제거하나요?

> GC는 일반적으로 Reachability, 즉 GC Root에서 객체에 도달할 수 있는지를 기준으로 회수 대상을 판단합니다.
>
> GC Root에서 참조 관계를 따라 접근할 수 있는 객체는 Reachable 상태이고, 도달할 수 없는 객체는 Unreachable 상태입니다.
>
> Unreachable 객체는 GC의 회수 대상이 될 수 있습니다.

**핵심 요약:** GC는 GC Root에서 객체에 도달할 수 있는지를 기준으로 회수 대상을 판단한다.

<a name="q2-1"></a>
#### ↳ Q2-1. GC Root에는 어떤 것들이 있나요?

> 대표적으로 실행 중인 스레드의 Stack Frame에서 참조하는 객체, 클래스의 static 필드를 통해 참조되는 객체, JNI 참조 등이 있습니다.
>
> GC는 이러한 참조들을 시작점으로 객체의 참조 관계를 탐색합니다.

**핵심 요약:** GC Root는 객체의 도달 가능성을 판단하기 위한 참조 탐색의 출발점이다.

<a name="q2-2"></a>
#### ↳ Q2-2. 두 객체가 서로 참조하고 있어도 GC 대상이 될 수 있나요?

> 네. 두 객체가 서로 참조하고 있더라도 GC Root에서 두 객체에 도달할 수 없다면 GC 대상이 될 수 있습니다.
>
> 따라서 객체 사이에 참조가 존재하는지보다 GC Root에서 접근 가능한지가 중요합니다.

**핵심 요약:** 객체끼리 서로 참조하더라도 GC Root에서 도달할 수 없다면 회수 대상이 된다.

<a name="q2-3"></a>
#### ↳ Q2-3. [심화 질문] 참조 변수를 null로 만들면 객체가 즉시 삭제되나요?

> 아닙니다.
>
> 참조 변수를 null로 변경하면 해당 변수를 통한 참조가 제거됩니다.
>
> 하지만 다른 경로에서 객체를 참조하고 있을 수 있으며, 모든 경로가 끊어져 GC 대상이 되더라도 실제 메모리 회수는 즉시 이루어진다고 보장할 수 없습니다.

**핵심 요약:** 참조를 제거하는 것과 실제 객체 메모리가 회수되는 것은 다르다.

<a name="q3"></a>
### Q3. Mark-Sweep-Compact 알고리즘에 대해 설명해 주세요.

> Mark-Sweep-Compact는 GC에서 객체를 식별하고 불필요한 메모리를 회수하며 메모리 공간을 정리하는 과정을 설명하는 방식입니다.
>
> Mark 단계에서는 GC Root에서 도달 가능한 객체를 탐색하여 표시합니다.
>
> Sweep 단계에서는 도달할 수 없는 객체가 차지하는 메모리를 회수합니다.
>
> Compact 단계에서는 살아 있는 객체를 이동시켜 메모리 단편화를 줄입니다.
>
> 다만 모든 GC가 이 세 단계를 동일하게 수행하는 것은 아닙니다.

**핵심 요약:** Mark는 살아 있는 객체 표시, Sweep은 불필요한 객체 회수, Compact는 메모리 정리이다.

<a name="q3-1"></a>
#### ↳ Q3-1. 메모리 단편화란 무엇인가요?

> 메모리 단편화는 사용 가능한 메모리 공간이 여러 작은 영역으로 나뉘어 있는 현상입니다.
>
> 전체 여유 메모리가 충분하더라도 연속된 메모리 공간이 부족하면 큰 객체를 할당하기 어려울 수 있습니다.
>
> Compact는 살아 있는 객체를 이동시켜 연속된 여유 공간을 확보함으로써 이러한 문제를 줄입니다.

**핵심 요약:** 메모리 단편화는 여유 공간이 흩어져 연속된 공간을 확보하기 어려워지는 현상이다.

<a name="q3-2"></a>
#### ↳ Q3-2. Compact를 수행하면 단점은 없나요?

> Compact 과정에서는 살아 있는 객체를 이동시키고 관련 참조를 갱신해야 하므로 추가적인 처리 비용이 발생할 수 있습니다.
>
> GC 구현에 따라 이러한 과정에서 CPU 자원이 사용되거나 애플리케이션 실행이 일시적으로 중단될 수 있습니다.

**핵심 요약:** Compact는 단편화를 줄이지만 객체 이동과 참조 갱신에 비용이 발생한다.

<a name="q3-3"></a>
#### ↳ Q3-3. [심화 질문] Mark-Sweep와 Mark-Compact의 차이는 무엇인가요?

> Mark-Sweep는 살아 있는 객체를 표시하고 도달할 수 없는 객체의 메모리를 회수합니다.
>
> 하지만 살아 있는 객체를 반드시 이동시키지는 않으므로 메모리 단편화가 남을 수 있습니다.
>
> Mark-Compact는 살아 있는 객체를 이동시켜 공간을 정리하는 방식으로 단편화를 줄일 수 있습니다.

**핵심 요약:** Mark-Sweep는 메모리를 회수하고 Mark-Compact는 살아 있는 객체를 이동시켜 공간을 정리한다.

<a name="q4"></a>
### Q4. Young Generation과 Old Generation의 차이는 무엇인가요?

> 전통적인 세대별 GC에서는 객체의 생존 기간에 따른 특성을 활용하기 위해 Heap을 Young Generation과 Old Generation으로 구분합니다.
>
> Young Generation에는 새로 생성된 객체가 주로 할당되며, Old Generation에는 여러 번의 GC를 거쳐 오래 살아남은 객체 등이 저장됩니다.
>
> 이러한 구조는 대부분의 객체가 비교적 짧은 시간 안에 사용되지 않게 된다는 특성을 활용하여 GC 효율을 높이기 위한 것입니다.

**핵심 요약:** Young은 새 객체를, Old는 오래 살아남은 객체를 주로 관리한다.

<a name="q4-1"></a>
#### ↳ Q4-1. Eden과 Survivor 영역은 무엇인가요?

> 전통적인 Young Generation 구조에서 Eden은 새로운 객체가 주로 생성되는 공간입니다.
>
> Survivor는 Young GC 이후 살아남은 객체를 관리하는 공간으로, 일반적으로 S0와 S1으로 설명합니다.
>
> 객체가 여러 번 GC에서 살아남으면 일정 조건에 따라 Old Generation으로 승격될 수 있습니다.

**핵심 요약:** Eden은 새 객체가 생성되는 공간이고 Survivor는 GC에서 살아남은 객체를 관리하는 공간이다.

<a name="q4-2"></a>
#### ↳ Q4-2. 모든 객체가 Eden에서 생성되나요?

> 아닙니다.
>
> 일반적으로 새 객체는 Eden 영역에 생성된다고 설명하지만, GC 알고리즘이나 객체 크기, JVM 최적화에 따라 다른 방식으로 할당될 수도 있습니다.
>
> 예를 들어 G1 GC에서는 매우 큰 객체를 Humongous Region에 할당할 수 있습니다.

**핵심 요약:** 새 객체는 주로 Eden에 생성되지만 크기와 GC 방식에 따라 예외가 있다.

<a name="q4-3"></a>
#### ↳ Q4-3. [심화 질문] 객체가 Old Generation으로 이동하는 이유는 무엇인가요?

> 오래 살아남은 객체를 새로 생성된 객체와 구분하여 관리하기 위해서입니다.
>
> 세대별 GC에서는 Young 영역의 객체를 상대적으로 자주 수집하고, 오래 살아남은 객체는 Old 영역에서 관리하여 수집 효율을 높일 수 있습니다.

**핵심 요약:** 오래 살아남은 객체를 Old 영역으로 관리하여 세대별 GC 효율을 높인다.

<a name="q5"></a>
### Q5. Minor GC, Major GC, Full GC의 차이는 무엇인가요?

> Minor GC는 일반적으로 Young Generation을 대상으로 수행되는 GC입니다.
>
> Major GC는 보통 Old Generation과 관련된 수집을 의미하지만, 구체적인 정의는 GC 구현에 따라 달라질 수 있습니다.
>
> Full GC는 일반적으로 Heap의 광범위한 영역을 수집하는 작업을 의미합니다.
>
> 따라서 세 용어의 정확한 범위는 사용하는 GC 알고리즘에 따라 확인해야 합니다.

**핵심 요약:** Minor는 주로 Young 영역을 수집하고 Major와 Full GC의 범위는 구현에 따라 달라질 수 있다.

<a name="q5-1"></a>
#### ↳ Q5-1. Full GC가 발생하면 반드시 애플리케이션이 오래 멈추나요?

> 반드시 그렇지는 않습니다.
>
> Full GC는 애플리케이션 성능에 큰 영향을 줄 수 있지만 정지 시간은 Heap 크기, 살아 있는 객체의 양, GC 알고리즘 등에 따라 달라집니다.
>
> 따라서 Full GC가 발생했다는 사실만으로 정지 시간이 반드시 길다고 단정할 수는 없습니다.

**핵심 요약:** Full GC의 정지 시간은 Heap 크기와 GC 알고리즘 등에 따라 달라진다.

<a name="q5-2"></a>
#### ↳ Q5-2. Old Generation의 GC는 왜 중요하나요?

> Old Generation에는 상대적으로 오래 살아남은 객체가 포함됩니다.
>
> 살아 있는 객체가 많으면 객체를 추적하고 처리하는 비용이 증가할 수 있으며, 메모리 사용량이 지속적으로 증가하면 메모리 압박이 발생할 수 있습니다.
>
> 따라서 Old 영역의 메모리 사용량과 GC 동작을 모니터링하는 것이 중요합니다.

**핵심 요약:** Old 영역의 객체와 메모리 사용량은 GC 비용과 메모리 압박에 영향을 줄 수 있다.

<a name="q6"></a>
### Q6. Stop-The-World란 무엇인가요?

> Stop-The-World(STW)는 GC 등의 작업을 수행하기 위해 JVM이 애플리케이션 스레드의 실행을 일시적으로 중단하는 현상입니다.
>
> GC는 객체의 참조 관계를 분석하거나 메모리를 정리하는 과정에서 일부 작업을 위해 애플리케이션 실행을 중단할 수 있습니다.
>
> 이로 인해 웹 서버의 요청 처리 시간이 지연될 수 있습니다.

**핵심 요약:** Stop-The-World는 GC 등을 위해 애플리케이션 실행을 일시적으로 중단하는 현상이다.

<a name="q6-1"></a>
#### ↳ Q6-1. GC가 발생하면 항상 STW가 발생하나요?

> 모든 GC 작업이 STW 상태에서 수행되는 것은 아닙니다.
>
> G1 GC나 ZGC 등은 일부 작업을 애플리케이션과 동시에 수행하도록 설계되어 있습니다.
>
> 다만 GC 종류와 작업 단계에 따라 짧은 STW가 발생할 수 있습니다.

**핵심 요약:** 모든 GC 작업이 STW로 진행되지는 않으며 일부 작업은 애플리케이션과 동시에 수행된다.

<a name="q6-2"></a>
#### ↳ Q6-2. GC로 인한 성능 문제는 어떻게 확인할 수 있나요?

> GC 로그와 JVM 모니터링 지표를 확인할 수 있습니다.
>
> GC 발생 횟수, 정지 시간, Heap 사용량 등을 분석하여 응답 지연과 GC 사이의 연관성을 확인합니다.
>
> Spring Boot에서는 Actuator와 Micrometer 등을 활용하고, Prometheus와 Grafana 등으로 지표를 관찰할 수도 있습니다.

**핵심 요약:** GC 로그와 Heap 사용량, GC 정지 시간을 분석하여 성능 문제를 확인한다.

<a name="q6-3"></a>
#### ↳ Q6-3. [심화 질문] G1 GC와 ZGC는 어떤 차이가 있나요?

> G1 GC는 Heap을 여러 Region으로 나누어 관리하며, 처리량과 GC 정지 시간의 균형을 고려하는 GC입니다.
>
> ZGC는 매우 짧은 정지 시간을 목표로 설계된 GC로, 많은 수집 작업을 애플리케이션과 동시에 수행합니다.
>
> 두 GC는 목표와 구현 방식이 다르므로 애플리케이션의 Heap 크기, 응답 시간 요구사항, 처리량 등을 고려해 선택합니다.

**핵심 요약:** G1은 처리량과 정지 시간의 균형을 고려하고 ZGC는 짧은 정지 시간에 초점을 맞춘다.

---

<a name="q7"></a>
### Q7. Java에서 메모리 누수를 방지하려면 어떻게 해야 하나요?

> 불필요한 객체 참조를 제거하고 캐시의 크기와 만료 정책을 적절하게 설정해야 합니다.
>
> 또한 파일, 네트워크 연결 등의 리소스는 사용 후 적절히 종료해야 합니다.
>
> 메모리 사용량이 비정상적으로 증가하면 Heap Dump나 메모리 프로파일러를 사용하여 어떤 객체가 계속 참조되고 있는지 분석할 수 있습니다.

**핵심 요약:** 불필요한 객체 참조를 제거하고 캐시와 리소스의 생명주기를 관리해야 한다.

<a name="q7-1"></a>
#### ↳ Q7-1. [심화 질문] GC가 있는데도 OutOfMemoryError가 발생하는 이유는 무엇인가요?

> GC는 도달할 수 없는 객체를 회수하지만, 여전히 참조되고 있는 객체는 필요하지 않더라도 일반적으로 회수할 수 없습니다.
>
> 또한 실제로 필요한 객체가 너무 많거나 JVM의 메모리 한도가 부족한 경우에도 OutOfMemoryError가 발생할 수 있습니다.

**핵심 요약:** GC가 있어도 객체 참조가 유지되거나 필요한 메모리를 확보하지 못하면 OOM이 발생할 수 있다.

<a name="q7-2"></a>
#### ↳ Q7-2. [심화 질문] 메모리 사용량이 높으면 무조건 메모리 누수인가요?

> 아닙니다.
>
> 트래픽 증가나 정상적인 캐시 사용으로도 메모리 사용량이 높아질 수 있습니다.
>
> 메모리 누수 여부를 판단하려면 GC 이후에도 불필요한 객체가 계속 유지되는지, 객체 수와 참조 관계가 어떻게 변하는지 확인해야 합니다.

**핵심 요약:** 높은 메모리 사용량이 반드시 누수는 아니며 불필요한 객체의 참조 유지 여부를 확인해야 한다.
