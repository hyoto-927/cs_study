<a name="section-01"></a>
## 기본 개념

<a name="q1"></a>
### Q1. REST API란 무엇인가요?

**답변**

> "REST API는 서버의 리소스를 URI로 식별하고, HTTP Method를 사용해 해당 리소스에 수행할 작업의 의미를 표현하는 API 설계 방식입니다.
>
> 예를 들어 `/users/1`은 1번 회원이라는 리소스를 나타내고, `GET /users/1`은 조회, `DELETE /users/1`은 삭제를 요청하는 의미가 됩니다."

**핵심 요약**

**REST API는 URI로 리소스를 표현하고 HTTP Method로 행위를 표현하는 API 설계 방식입니다.**

<a name="q1-1"></a>
#### ↳ Q1-1. REST API에서 URI와 HTTP Method는 각각 무엇을 나타내나요?

> "URI는 어떤 리소스를 대상으로 하는지 나타내고, HTTP Method는 그 리소스에 어떤 작업을 요청하는지를 나타냅니다."

**핵심 요약**

**URI = 무엇을 / HTTP Method = 어떻게 할지를 표현한다.**

---

<a name="q1-2"></a>
#### ↳ Q1-2. REST에서 Resource란 무엇인가요?

> "Resource는 서버가 관리하고 클라이언트가 접근하려는 대상을 의미합니다. 회원, 상품, 주문, 게시글 등이 리소스가 될 수 있습니다."

**핵심 요약**

**Resource는 API가 다루는 대상이다.**

---

<a name="q1-3"></a>
#### ↳ Q1-3. REST에서는 왜 URI에 동사보다 명사를 사용하나요?

> "URI가 리소스를 표현하고 행위는 HTTP Method가 표현하도록 역할을 나누기 위해서입니다.
>
> 따라서 `/getUser`, `/deleteUser`보다는 `/users/1`에 GET이나 DELETE를 사용하는 것이 REST의 의미에 더 잘 맞습니다."

**핵심 요약**

**URI는 명사로 리소스를 표현하고 행위는 HTTP Method로 표현한다.**

---

<a name="section-02"></a>
## HTTP Method란 무엇인가?

<a name="q2"></a>
### Q2. HTTP Method란 무엇이며 어떤 역할을 하나요?

**답변**

> "HTTP Method는 클라이언트가 서버의 리소스에 대해 어떤 작업을 수행하고 싶은지를 나타내는 HTTP 요청의 구성 요소입니다.
>
> 같은 URI라도 GET, POST, PUT, PATCH, DELETE 등의 Method에 따라 요청의 의미를 다르게 표현할 수 있습니다."

**핵심 요약**

**HTTP Method는 리소스에 어떤 작업을 요청하는지 나타냅니다.**

---

<a name="q3"></a>
### Q3. HTTP Method의 종류와 각각의 용도를 설명해주세요.

**답변**

> "GET은 리소스 조회, POST는 데이터 처리나 생성 요청, PUT은 리소스 전체 대체, PATCH는 부분 변경, DELETE는 삭제에 사용합니다.
>
> HEAD는 Response Body 없이 Header 정보만 확인하고, OPTIONS는 서버가 지원하는 통신 방식이나 Method를 확인할 때 사용합니다."

**핵심 요약**

**GET 조회 / POST 처리·생성 / PUT 전체 대체 / PATCH 부분 수정 / DELETE 삭제**

<a name="q3-1"></a>
#### ↳ Q3-1. HEAD는 GET과 어떤 차이가 있나요?

> "HEAD는 GET과 같은 리소스를 대상으로 하지만 Response Body를 반환하지 않고 Header 정보만 확인하는 데 사용합니다."

**핵심 요약**

**HEAD는 Body 없이 Header만 확인하는 GET과 비슷한 Method이다.**

---

<a name="q3-2"></a>
#### ↳ Q3-2. OPTIONS는 언제 사용하나요?

> "서버나 특정 리소스가 어떤 HTTP Method나 통신 옵션을 지원하는지 확인할 때 사용합니다. 브라우저의 CORS Preflight 요청에서도 사용됩니다."

**핵심 요약**

**OPTIONS는 서버가 허용하는 통신 방법을 확인한다.**

---

<a name="q4"></a>
### Q4. GET과 POST의 차이는 무엇인가요?

**답변**

> "GET은 서버의 리소스를 조회하기 위한 Method이고, POST는 서버에 데이터를 전달하여 대상 리소스의 규칙에 따라 처리하도록 요청하는 Method입니다.
>
> GET은 Safe하고 Idempotent하지만, POST는 일반적으로 Safe하지 않고 멱등성도 보장되지 않습니다."

**핵심 요약**

**GET은 조회, POST는 생성이나 서버 처리를 요청하는 Method입니다.**

<a name="q4-1"></a>
#### ↳ Q4-1. POST는 반드시 리소스를 생성할 때만 사용하나요?

> "아닙니다. POST는 서버에 데이터를 전달하여 처리를 요청하는 Method이므로 리소스 생성뿐 아니라 결제, 명령 실행 등 다양한 처리에 사용할 수 있습니다."

**핵심 요약**

**POST는 생성 전용이 아니라 서버에 처리를 요청하는 Method이다.**

---

<a name="q5"></a>
### Q5. PUT과 PATCH의 차이는 무엇인가요?

같은 질문의 다른 회차 답변 · [methods-and-status](http/methods-and-status.md#q7)

**답변**

> "PUT은 대상 리소스를 요청에서 전달한 표현으로 전체 대체하는 의미이고, PATCH는 리소스의 일부에 변경을 적용하는 Method입니다.
>
> 또한 PUT은 멱등성이 보장되지만 PATCH는 변경 방식에 따라 멱등할 수도 있고 아닐 수도 있습니다."

**핵심 요약**

**PUT은 전체 대체, PATCH는 부분 변경입니다.**

<a name="q5-1"></a>
#### ↳ Q5-1. PATCH는 왜 PUT과 달리 멱등성이 보장되지 않나요?

> "PATCH는 부분 변경의 구체적인 방식에 따라 반복 요청의 효과가 달라질 수 있기 때문입니다.
>
> `name을 Kim으로 변경`은 반복해도 결과가 같지만, `재고를 1 증가`는 반복할수록 결과가 달라집니다."

**핵심 요약**

**PATCH는 변경 방식에 따라 반복 효과가 달라질 수 있어 멱등성이 보장되지 않는다.**

---

<a name="q6"></a>
### Q6. POST와 PUT은 둘 다 리소스를 생성할 수 있는데 차이가 무엇인가요?

**답변**

> "POST는 일반적으로 서버에게 새로운 리소스의 생성이나 처리를 요청하고 서버가 새 리소스의 URI를 결정합니다.
>
> PUT은 클라이언트가 지정한 URI의 리소스를 요청 내용으로 생성하거나 전체 대체합니다.
>
> 또한 PUT은 멱등하지만 POST는 일반적으로 멱등하지 않습니다."

**핵심 요약**

**POST는 서버에 생성을 요청하고, PUT은 지정된 URI를 원하는 상태로 만든다.**

---

<a name="q7"></a>
### Q7. GET 요청에 Body를 담을 수 있나요?

**답변**

> "GET 요청에 Body가 존재할 수는 있지만 일반적인 의미가 정의되어 있지 않고 서버, 프록시, 프레임워크 등이 제대로 지원하지 않을 수 있기 때문에 보통 사용하지 않습니다.
>
> 조회 조건은 일반적으로 Query Parameter를 사용합니다."

**핵심 요약**

**GET Body는 일반적으로 사용하지 않고 조회 조건은 Query Parameter로 전달합니다.**

---

<a name="q8"></a>
### Q8. PUT으로 존재하지 않는 리소스를 요청하면 어떻게 되나요?

**답변**

> "PUT은 지정한 URI의 리소스를 생성하거나 대체할 수 있기 때문에 서버가 해당 URI에 새로운 리소스 생성을 허용한다면 생성할 수 있습니다.
>
> 새로 생성한 경우 일반적으로 `201 Created`를 사용할 수 있습니다."

**핵심 요약**

**PUT 대상이 없다면 서버 정책에 따라 지정한 URI에 새 리소스를 생성할 수 있습니다.**

---

<a name="q9"></a>
### Q9. PATCH에서 null로 비우는 것과 필드를 생략하는 것은 어떻게 구분하나요?

**답변**

> "PATCH에서 null과 필드 생략의 의미는 사용하는 Patch 형식과 API 규칙으로 명확하게 정의해야 합니다.
>
> 예를 들어 JSON Merge Patch에서는 필드를 생략하면 변경하지 않고, `null`을 전달하면 해당 멤버를 제거한다는 의미입니다."

**핵심 요약**

**PATCH의 null과 생략은 API 규칙으로 구분해야 합니다.**

---

<a name="q10"></a>
### Q10. HEAD와 OPTIONS는 언제 사용하나요?

**답변**

> "HEAD는 Response Body를 받지 않고 리소스의 Header 정보만 확인할 때 사용하고, OPTIONS는 서버가 허용하는 HTTP Method나 통신 옵션을 확인할 때 사용합니다."

**핵심 요약**

**HEAD는 메타데이터 확인, OPTIONS는 지원하는 통신 방식 확인에 사용합니다.**

---

<a name="q10-1"></a>
#### ↳ Q10-1. DELETE Method는 어떤 작업을 요청할 때 사용하나요?

> "DELETE는 특정 리소스를 제거하도록 서버에 요청하는 Method입니다.
>
> DELETE가 반드시 DB 데이터를 물리적으로 삭제한다는 뜻은 아니며, 서버 구현에 따라 Soft Delete로 처리할 수도 있습니다."

**핵심 요약**

**DELETE는 리소스를 제거하라는 의미이며 실제 삭제 방식은 서버 구현에 따라 다를 수 있다.**

---

<a name="q10-2"></a>
#### ↳ Q10-2. HTTP Method가 Unsafe하면 실제 데이터가 반드시 변경되나요?

> "아닙니다. Safe 여부는 실제 실행 결과가 아니라 Method가 정의한 의미를 기준으로 판단합니다.
>
> 존재하지 않는 리소스에 DELETE를 요청해 실제 데이터가 변경되지 않더라도 DELETE는 삭제를 의도하므로 Unsafe합니다."

**핵심 요약**

**Unsafe는 실제 변경 여부가 아니라 Method가 상태 변경을 의도하는지를 의미한다.**

---

<a name="q10-3"></a>
#### ↳ Q10-3. GET으로 회원 계정을 비활성화하면 여러 번 호출해도 결과가 같으니 괜찮나요?

> "아닙니다. 멱등하더라도 GET은 Safe해야 합니다.
>
> 회원 비활성화는 서버 상태 변경을 의도하므로 GET을 사용하면 HTTP Method의 의미를 위반합니다."

**핵심 요약**

**멱등하다고 해서 GET으로 상태 변경 작업을 하면 되는 것은 아니다.**

---

<a name="section-03"></a>
## Safe란 무엇인가?

<a name="q11"></a>
### Q11. Safe란 무엇이고 왜 중요한가요?

**답변**

> "Safe란 HTTP 요청이 서버 리소스의 상태 변경을 의도하지 않는 특성을 의미합니다.
>
> 대표적으로 GET, HEAD, OPTIONS가 Safe Method이며, 조회 요청을 브라우저나 프록시 등이 안전하게 다룰 수 있게 해줍니다."

**핵심 요약**

**Safe는 클라이언트가 리소스 상태 변경을 의도하지 않는다는 의미입니다.**

---

<a name="q12"></a>
### Q12. Safe하면 서버에서 아무 일도 일어나지 않는 건가요?

**답변**

> "아닙니다.
>
> Safe는 서버 내부에서 아무 변화도 발생하지 않는다는 의미가 아니라 클라이언트가 요청한 주된 목적이 리소스 변경이 아니라는 의미입니다.
>
> 로그 기록이나 통계 수집 같은 부수 효과는 발생할 수 있습니다."

**핵심 요약**

**Safe는 아무 작업도 하지 않는다는 뜻이 아니라 상태 변경을 목적으로 하지 않는다는 뜻입니다.**

<a name="q12-1"></a>
#### ↳ Q12-1. GET 요청을 처리하면서 로그를 저장하거나 조회수를 증가시키면 Safe하지 않은 건가요?

> "일반적인 로그나 통계 기록처럼 요청 처리 과정에서 발생하는 부수 효과는 GET의 Safe 특성을 깨는 것으로 보지 않습니다.
>
> 하지만 결제나 재고 차감처럼 요청의 핵심 비즈니스 효과가 상태 변경이라면 Safe하다고 볼 수 없습니다."

**핵심 요약**

**로그 같은 부수 효과는 가능하지만 핵심 업무 상태를 변경하면 Safe하지 않다.**

---

<a name="q13"></a>
### Q13. GET으로 데이터를 변경하면 어떤 문제가 생기나요?

**답변**

> "GET은 Safe한 조회 요청이라고 가정되기 때문에 브라우저, 검색엔진, 프록시 등이 자동으로 호출할 수 있습니다.
>
> GET 요청이 서버 상태를 변경하도록 구현되면 사용자가 의도하지 않은 데이터 변경이 발생할 수 있습니다."

**핵심 요약**

**GET으로 상태를 변경하면 HTTP의 Safe 의미가 깨지고 예상하지 못한 변경이 발생할 수 있습니다.**

<a name="q13-1"></a>
#### ↳ Q13-1. GET 요청마다 상품 재고가 1개씩 감소한다면 어떤 문제가 있나요?

> "재고 감소는 명백한 서버 상태 변경이므로 GET의 Safe 의미를 위반합니다.
>
> 크롤러나 브라우저의 자동 요청만으로도 재고가 감소할 수 있기 때문에 적절한 상태 변경 Method를 사용해야 합니다."

**핵심 요약**

**GET은 재고 차감 같은 비즈니스 상태 변경에 사용하면 안 된다.**

---

<a name="q14"></a>
### Q14. Safe와 Idempotent의 관계는 무엇인가요?

**답변**

> "Safe는 요청이 서버 상태 변경을 의도하는지를 판단하는 개념이고, Idempotent는 동일한 요청을 반복했을 때 서버에 미치는 의도된 효과가 같은지를 판단하는 개념입니다.
>
> 모든 Safe Method는 멱등하지만 모든 멱등 Method가 Safe한 것은 아닙니다."

**핵심 요약**

**Safe는 상태 변경 의도, Idempotent는 반복 요청의 효과를 판단합니다.**

<a name="q14-1"></a>
#### ↳ Q14-1. GET은 왜 Safe하면서 Idempotent한가요?

> "GET은 리소스 조회를 목적으로 하므로 상태 변경을 의도하지 않아 Safe하고, 동일한 조회 요청을 반복해도 요청 자체가 리소스 변경을 일으키지 않기 때문에 멱등합니다."

**핵심 요약**

**GET은 조회만 의도하므로 Safe하면서 Idempotent하다.**

---

<a name="q14-2"></a>
#### ↳ Q14-2. GET 응답 값이 매번 달라져도 멱등한가요?

> "네. 다른 사용자가 데이터를 수정하거나 시간이 지나면서 조회 결과는 달라질 수 있습니다.
>
> 멱등성은 응답 데이터가 동일한지를 의미하는 것이 아니라 동일한 요청 자체의 의도된 효과를 판단합니다."

**핵심 요약**

**GET의 멱등성은 응답 값이 항상 동일하다는 뜻이 아니다.**

---

<a name="q15"></a>
### Q15. GET은 왜 캐싱할 수 있나요?

**답변**

> "GET은 조회를 위한 Safe Method이므로 동일한 리소스의 이전 응답을 재사용하기 적합합니다.
>
> 실제 캐싱 여부는 `Cache-Control`, `ETag` 등의 HTTP 캐시 정책에 따라 결정됩니다."

**핵심 요약**

**GET은 조회 요청이므로 응답을 재사용하기 쉬워 캐싱에 적합합니다.**

---

<a name="q16"></a>
### Q16. POST는 캐싱할 수 없나요?

**답변**

> "POST도 HTTP 캐시 규칙과 명시적인 캐시 설정에 따라 캐싱할 수 있습니다.
>
> 다만 POST는 주로 상태 변경이나 처리 요청에 사용되기 때문에 GET처럼 일반적으로 캐싱하지는 않습니다."

**핵심 요약**

**POST도 캐싱할 수 있지만 일반적인 방식은 아닙니다.**

---

<a name="q17"></a>
### Q17. 검색 API는 GET과 POST 중 무엇으로 설계하나요?

**답변**

> "일반적인 조회 조건은 GET으로 설계하는 것이 자연스럽습니다.
>
> 검색 조건이 매우 복잡하거나 URL에 표현하기 어려울 정도로 크다면 POST 기반 검색 API를 사용할 수도 있습니다."

**핵심 요약**

**단순 검색은 GET, 매우 복잡한 검색은 POST도 고려할 수 있습니다.**

---

<a name="section-04"></a>
## Idempotent(멱등성)란 무엇인가?

<a name="q18"></a>
### Q18. 멱등성이란 무엇인가요?

**답변**

> "멱등성이란 동일한 요청을 한 번 실행하든 여러 번 실행하든 서버에 미치는 의도된 효과가 동일한 성질입니다."

**핵심 요약**

**같은 요청을 여러 번 수행해도 의도된 최종 효과가 같으면 멱등합니다.**

---

<a name="q19"></a>
### Q19. 멱등성은 응답이 같다는 뜻인가요?

**답변**

> "아닙니다.
>
> 멱등성은 응답 내용이나 HTTP 상태 코드가 항상 동일하다는 뜻이 아니라 서버에 미치는 의도된 효과가 동일하다는 의미입니다."

**핵심 요약**

**멱등성은 응답의 동일성이 아니라 요청의 의도된 효과를 기준으로 판단합니다.**

---

<a name="q20"></a>
### Q20. PUT은 왜 멱등하고 POST는 왜 일반적으로 멱등하지 않나요?

**답변**

> "PUT은 같은 URI를 같은 상태로 반복해서 대체해도 최종 효과가 같기 때문에 멱등합니다.
>
> POST는 동일한 요청을 반복하면 새로운 주문이나 리소스가 여러 번 생성될 수 있기 때문에 일반적으로 멱등하지 않습니다."

**핵심 요약**

**PUT은 반복 적용해도 같은 상태, POST는 반복할 때 새로운 결과가 생길 수 있습니다.**

<a name="q20-1"></a>
#### ↳ Q20-1. PUT은 데이터를 변경하는데 왜 멱등한가요?

> "멱등성은 데이터가 변경되는지 자체가 아니라 동일한 요청을 반복했을 때 효과가 추가로 달라지는지를 판단하기 때문입니다."

**핵심 요약**

**상태를 변경해도 반복 결과가 같다면 멱등할 수 있다.**

---

<a name="q20-2"></a>
#### ↳ Q20-2. PUT을 사용하면서 요청마다 재고를 1씩 증가시키면 멱등한가요?

> "아닙니다.
>
> PUT은 HTTP 표준에서 멱등한 의미를 가지므로 요청할 때마다 재고가 증가하도록 구현하면 PUT의 의미를 위반한 것입니다.
>
> PUT이라면 재고를 특정 값으로 설정하는 방식이 더 적절합니다."

**핵심 요약**

**Method 이름이 PUT이라고 자동으로 멱등한 것이 아니라 실제 구현도 멱등성을 지켜야 한다.**

---

<a name="q21"></a>
### Q21. PATCH는 멱등한가요?

**답변**

> "PATCH는 Method 자체에서 멱등성이 보장되지 않습니다.
>
> 값을 특정 값으로 설정하는 PATCH는 멱등할 수 있지만, 값을 증가시키거나 배열에 항목을 추가하는 방식은 반복할수록 효과가 누적되어 멱등하지 않습니다."

**핵심 요약**

**PATCH의 멱등성은 실제 변경 방식에 따라 달라집니다.**

---

<a name="q22"></a>
### Q22. DELETE 두 번째 요청이 404라면 멱등성이 깨지는 것 아닌가요?

**답변**

> "아닙니다.
>
> 첫 번째 DELETE가 204이고 두 번째가 404더라도 두 요청 후 모두 해당 리소스가 존재하지 않는다는 의도된 효과는 동일하므로 멱등성이 유지됩니다."

**핵심 요약**

**DELETE는 응답이 달라도 리소스가 제거된 효과가 같기 때문에 멱등합니다.**

<a name="q22-1"></a>
#### ↳ Q22-1. DELETE는 데이터를 삭제하는데 왜 멱등한가요?

> "삭제는 상태를 변경하므로 Safe하지 않지만, 동일한 삭제 요청을 여러 번 수행해도 결국 리소스가 존재하지 않는다는 효과가 같기 때문에 멱등합니다."

**핵심 요약**

**DELETE는 Safe하지 않지만 반복 삭제의 최종 효과가 같아 멱등하다.**

---

<a name="q22-2"></a>
#### ↳ Q22-2. DELETE 요청마다 삭제 알림이 계속 발송되면 멱등하다고 볼 수 있나요?

> "삭제 리소스 자체의 상태만 보면 같을 수 있지만, 삭제 알림이 중요한 업무 효과이고 요청할 때마다 반복 발송된다면 전체 비즈니스 효과가 누적됩니다.
>
> 따라서 실제 삭제와 관련 알림도 중복 처리되지 않도록 설계하는 것이 좋습니다."

**핵심 요약**

**중요한 업무적 부수 효과도 반복되지 않도록 설계해야 한다.**

---

<a name="q23"></a>
### Q23. 멱등하지 않은 POST를 안전하게 재시도하려면 어떻게 하나요?

**답변**

> "대표적으로 Idempotency Key를 사용할 수 있습니다.
>
> 클라이언트가 요청마다 고유한 Key를 보내고 서버가 이미 처리된 요청인지 확인하여 같은 요청의 중복 처리를 막습니다."

**핵심 요약**

**Idempotency Key를 이용하면 POST의 중복 실행을 방지할 수 있습니다.**

<a name="q23-1"></a>
#### ↳ Q23-1. POST도 멱등하게 구현할 수 있나요?

> "가능합니다.
>
> HTTP 표준상 POST 자체는 멱등성이 보장되지 않지만 서버가 Idempotency Key나 고유 거래 번호 등을 이용해 중복 처리를 방지하면 애플리케이션 수준에서 멱등하게 동작하도록 만들 수 있습니다."

**핵심 요약**

**POST 자체는 멱등하지 않지만 서버 설계로 중복 처리를 막을 수 있다.**

---

<a name="q24"></a>
### Q24. Idempotency Key로 처리 중인 요청이 다시 들어오면 어떻게 하나요?

**답변**

> "동일한 Key의 요청이 이미 처리 중이라면 서버는 같은 작업을 새로 실행하지 않아야 합니다.
>
> 처리 중임을 반환하거나 기존 요청의 완료를 기다리게 하고, 완료된 요청이라면 기존 처리 결과를 반환할 수 있습니다."

**핵심 요약**

**동일한 Idempotency Key는 하나의 실제 작업만 수행하도록 관리합니다.**

<a name="q24-1"></a>
#### ↳ Q24-1. 같은 Idempotency Key에 다른 요청 데이터가 들어오면 어떻게 해야 하나요?

> "같은 Key는 같은 요청을 의미해야 하므로 기존 요청과 다른 데이터가 전달되었다면 잘못된 Key 재사용으로 판단해 거부하는 것이 안전합니다."

**핵심 요약**

**같은 Idempotency Key에는 동일한 요청 내용이 와야 한다.**

---

<a name="q25"></a>
### Q25. Redis에 장애가 나면 중복 결제를 어떻게 막나요?

**답변**

> "중복 결제 방지를 Redis 하나에만 의존하면 안 됩니다.
>
> DB의 Unique Constraint, 고유한 결제 요청 ID, 트랜잭션 및 결제 상태 관리 등을 함께 사용해 영속적인 중복 방지 장치를 만들어야 합니다."

**핵심 요약**

**중요한 중복 방지는 Redis뿐 아니라 DB 수준에서도 보장해야 합니다.**

---

<a name="q26"></a>
### Q26. 낙관적 락과 비관적 락 중 멱등성 보장에는 무엇이 유리한가요?

**답변**

> "낙관적 락과 비관적 락은 멱등성을 직접 보장하는 방법이 아니라 동시에 여러 요청이 같은 데이터를 수정할 때 충돌을 제어하는 방법입니다.
>
> 멱등성은 Idempotency Key나 Unique Constraint 등의 별도 설계로 보장해야 합니다."

**핵심 요약**

**락은 동시성 제어이고 멱등성 보장과는 별개의 문제입니다.**

---

<a name="q27"></a>
### Q27. 자동 재시도해도 되는 HTTP Method는 무엇인가요?

**답변**

> "GET, HEAD, PUT, DELETE처럼 멱등한 Method는 동일한 요청을 재시도해도 의도된 효과가 같기 때문에 상대적으로 재시도에 유리합니다.
>
> POST처럼 멱등성이 보장되지 않는 요청은 중복 처리 방지 장치 없이 재시도하면 위험할 수 있습니다."

**핵심 요약**

**자동 재시도는 멱등한 요청에서 상대적으로 안전합니다.**

<a name="q27-1"></a>
#### ↳ Q27-1. 멱등한 API라면 네트워크 오류가 발생했을 때 무조건 재시도해도 안전한가요?

> "아닙니다.
>
> 멱등성은 동일 요청의 의도된 효과가 같다는 의미일 뿐, 다른 사용자의 동시 수정, 서버의 부수 효과, 타임아웃과 재시도 폭주 같은 문제까지 해결하지는 않습니다."

**핵심 요약**

**멱등성은 재시도를 유리하게 만들지만 무조건 안전함을 보장하지 않는다.**

---

<a name="q27-2"></a>
#### ↳ Q27-2. PUT 응답이 유실되었다면 같은 요청을 재시도할 수 있는 이유는 무엇인가요?

> "PUT은 멱등하기 때문에 서버가 첫 요청을 이미 처리했더라도 같은 요청을 다시 보내면 대상 리소스를 같은 상태로 설정하게 됩니다."

**핵심 요약**

**PUT은 반복 효과가 같기 때문에 응답 유실 시 재시도하기에 상대적으로 안전하다.**

---

<a name="q28"></a>
### Q28. 멱등한 요청에도 Lost Update가 발생할 수 있나요?

**답변**

> "네.
>
> 멱등성과 동시성 제어는 다른 개념입니다. 같은 PUT 자체는 멱등하더라도 여러 사용자가 동시에 같은 리소스를 수정하면 한 사용자의 변경이 다른 요청에 의해 덮어써지는 Lost Update가 발생할 수 있습니다."

**핵심 요약**

**멱등성은 중복 요청 문제이고 Lost Update는 동시 수정 문제입니다.**

<a name="q28-1"></a>
#### ↳ Q28-1. Lost Update는 어떻게 방지할 수 있나요?

> "ETag와 `If-Match`를 이용한 조건부 요청이나 버전 값을 사용하는 낙관적 락 등을 활용해 다른 사용자가 중간에 수정했는지 확인할 수 있습니다."

**핵심 요약**

**Lost Update는 버전 검증이나 조건부 요청으로 방지할 수 있다.**

---

<a name="section-05"></a>
## 연관 종합 질문

<a name="q29"></a>
### Q29. Safe, Idempotent, 캐싱 가능 여부를 한 번에 정리해주세요.

**답변**

> "Safe는 상태 변경을 의도하는지를 의미하고, Idempotent는 같은 요청을 반복했을 때 의도된 효과가 같은지를 의미하며, Cache는 이전 응답을 저장해 다시 사용할 수 있는지를 의미합니다."

**핵심 요약**

**Safe = 상태 변경 의도 / Idempotent = 반복 효과 / Cache = 응답 재사용**

| Method | Safe | Idempotent | 대표 용도 |
| --- | --- | --- | --- |
| GET | O | O | 조회 |
| HEAD | O | O | Header 조회 |
| OPTIONS | O | O | 지원 옵션 확인 |
| TRACE | O | O | 진단용 요청 |
| POST | X | 보장 X | 생성·처리 |
| PUT | X | O | 전체 대체 |
| PATCH | X | 보장 X | 부분 변경 |
| DELETE | X | O | 삭제 |

<a name="q29-1"></a>
#### ↳ Q29-1. 모든 Safe Method는 멱등한가요?

> "네. Safe Method는 상태 변경을 의도하지 않기 때문에 같은 요청을 반복해도 요청의 의도된 효과가 동일합니다."

**핵심 요약**

**Safe이면 Idempotent하다.**

---

<a name="q29-2"></a>
#### ↳ Q29-2. 모든 Idempotent Method는 Safe한가요?

> "아닙니다. PUT과 DELETE는 서버 상태를 변경하기 때문에 Safe하지 않지만 동일한 요청의 반복 효과는 같아 멱등합니다."

**핵심 요약**

**Idempotent라고 반드시 Safe한 것은 아니다.**

---

<a name="q30"></a>
### Q30. 200, 201, 204의 차이는 무엇인가요?

**답변**

> "`200 OK`는 요청이 정상적으로 처리되었다는 의미이고, `201 Created`는 새로운 리소스가 생성되었다는 의미입니다.
>
> `204 No Content`는 요청은 성공했지만 응답 Body가 없다는 의미입니다."

**핵심 요약**

**200 성공 / 201 생성 성공 / 204 성공했지만 Body 없음**

---

<a name="q31"></a>
### Q31. 400, 401, 403, 404의 차이는 무엇인가요?

**답변**

> "`400 Bad Request`는 잘못된 요청, `401 Unauthorized`는 인증이 필요하거나 인증 실패, `403 Forbidden`은 요청을 이해했으나 처리를 거부함(인증 성공을 전제하지 않음), `404 Not Found`는 리소스를 찾지 못했다는 의미입니다."

**핵심 요약**

**400 요청 오류 / 401 인증 필요 / 403 권한 없음 / 404 리소스 없음**

---

<a name="q32"></a>
### Q32. 409 Conflict는 언제 사용하나요?

**답변**

> "`409 Conflict`는 요청 자체는 이해했지만 현재 리소스 상태와 충돌하여 처리할 수 없는 경우 사용합니다.
>
> 예를 들어 버전 충돌이나 현재 상태상 허용되지 않는 변경 요청 등에 사용할 수 있습니다."

**핵심 요약**

**409는 요청이 현재 리소스 상태와 충돌한 경우입니다.**

---

<a name="section-06"></a>
## REST API 설계 종합

<a name="q33"></a>
### Q33. REST API 설계 시 HTTP Method · Safe · Idempotent는 어떤 순서로 고려해야 하나요?

**답변**

> "먼저 어떤 리소스에 어떤 작업을 수행하는 API인지 정의하고 그 의미에 맞는 HTTP Method를 선택합니다.
>
> 조회라면 GET, 생성이나 처리라면 POST, 전체 대체라면 PUT, 부분 변경이라면 PATCH, 삭제라면 DELETE를 고려합니다.
>
> 그다음 선택한 Method의 Safe와 Idempotent 특성을 실제 서버 로직도 지키도록 구현하고, 네트워크 재시도나 동시성 문제가 있다면 Idempotency Key나 동시성 제어 방법을 추가합니다."

**핵심 요약**

**작업 의미에 맞는 Method를 먼저 고르고, 그 Method의 Safe·Idempotent 특성을 실제 구현도 지키게 해야 합니다.**

<a name="q33-1"></a>
#### ↳ Q33-1. HTTP Method만 올바르게 선택하면 Safe와 멱등성이 자동으로 보장되나요?

> "아닙니다.
>
> PUT을 사용하면서 요청할 때마다 값을 증가시키거나, GET으로 데이터를 삭제하도록 구현하면 Method가 가진 표준적 의미를 실제 서버 로직이 위반하게 됩니다."

**핵심 요약**

**HTTP Method의 이름뿐 아니라 실제 서버 동작도 Method의 의미와 일치해야 한다.**
