## 대표 질문과 답변

<a name="q1"></a>
### Q1. 메시지 큐를 사용하는 이유와 장단점

**답변**

> "메시지 큐는 비동기 처리용 중간 저장소.
>
> **결합도를 낮춰** 한쪽이 죽어도 다른 쪽에 즉시 영향이 없고, 트래픽이 몰려도 큐에 쌓아두고 처리 가능한 속도로 소화하는 **버퍼 역할**을 하며, 무거운 작업을 큐에 위임하고 바로 응답해서 **응답 속도를 높일** 수 있습니다.
>
> 단점은 구조가 복잡해지고, 순서 보장·중복 처리·유실 방지 같은 추가 고민이 필요하다는 것입니다."

<a name="q2"></a>
### Q2. 동기 방식과 메시지 큐(비동기) 방식은 언제 각각 선택하나요?

> "즉시 결과가 필요한 경우는 동기, 결과를 바로 몰라도 되는 경우는 비동기가 적합합니다."

<a name="q3"></a>
### Q3. Kafka와 RabbitMQ의 핵심적인 아키텍처 차이는?

> "RabbitMQ는 처리가 끝나면 삭제되는 큐 중심이고, Kafka는 데이터를 디스크에 쌓아두고 다시 읽을 수 있는 로그 중심입니다. 따라서 RabbitMQ는 복잡한 라우팅과 일반적인 비동기 작업 처리에 적합하고 Kafka는 대용량 실시간 처리에 특화되어있습니다.

<a name="q4"></a>
### Q4. 메시지가 중복으로 처리되면 어떻게 방지하나요?

> 같은 메시지가 재전달되어도 업무 결과가 한 번만 반영되도록 설계합니다. 예를 들어 메시지 ID에 고유 제약을 두고 처리 이력 저장과 주문 상태 변경을 같은 DB 트랜잭션에서 수행한 뒤 ACK합니다. 단순 조회 후 처리만 하면 두 소비자가 동시에 통과할 수 있습니다.

<a name="q5"></a>
### Q5. Consumer가 죽으면 메시지는 어떻게 되나요?

> " RabbitMQ 일반 큐의 수동 확인 모드에서는 Consumer가 메시지를 처리하고 ACK를 보내기 전까지는 메시지가 큐에서 제거되지 않습니다. 그래서 Consumer가 죽으면 ACK를 못 보냈으므로, 큐가 그 메시지를 다시 다른 Consumer에게 전달합니다. 재시도 제한과 데드레터 라우팅을 구성하면 반복 실패 메시지를 별도 큐로 보낼 수 있습니다."

<a name="q6"></a>
### Q6. 메시지 소비 중 컨슈머에서 예외가 발생해 처리가 계속 실패하면 어떻게 대응하나요?

> "일정 횟수 재시도 후에도 실패하면 DLQ(Dead Letter Queue)로 격리합니다."

<a name="q7"></a>
### Q7. 메시지 큐가 다운되면 어떻게 되나요? 유실을 어떻게 막나요?

> "디스크에 영속화하거나 여러 브로커에 복제해둡니다. 또한 RabbitMQ의 소비자 수동 ACK는 처리 중 재전달을 지원합니다. 발행 단계의 수신 확인은 publisher confirm으로 별도로 처리합니다. Kafka 소비자의 오프셋 커밋은 소비 위치를 기록하며 레코드 삭제는 로그 보관 정책을 따릅니다."

<a name="q8"></a>
### Q8. 메시지 큐를 사용하면 DB Transaction과 메시지 발행의 원자성은 어떻게 보장하나요?

> "해결하는 방법으로 Transactional Outbox Pattern이 있습니다. 메시지를 큐에 바로 발행하는 대신, 같은 DB 트랜잭션 안에서 'Outbox'라는 별도 테이블에 발행할 메시지를 함께 저장합니다. 이렇게 하면 DB 저장과 메시지 기록이 하나의 트랜잭션으로 원자성이 보장되고, 이후 별도의 프로세스가 Outbox 테이블을 읽어서 실제 메시지 큐에 발행합니다."

<a name="q9"></a>
### Q9. 백엔드에서 메시지 큐를 실제로 어디에 활용하나요?

> "주문 시 결제·재고·알림을 각각 다른 서비스가 큐로 비동기 처리하는 이벤트 기반 아키텍처, 대량 발송, 로그 수집 및 실시간 분석 파이프라인, MSA 간 서비스 디커플링 등에 활용됩니다."
