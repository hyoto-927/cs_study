## Spring Boot · 실무 응용 질문

<a name="q1"></a>
### Q1. Spring Boot 서버에서 메모리 사용량이 계속 증가한다면 어떻게 분석하시겠습니까?

> 먼저 Heap 사용량과 GC 발생 횟수, GC 이후에도 유지되는 메모리 사용량을 확인하겠습니다.
>
> GC 이후에도 사용 중인 Heap이 지속적으로 증가한다면 불필요한 객체 참조가 유지되고 있는지 의심할 수 있습니다.
>
> 이후 Heap Dump를 분석하여 메모리를 많이 차지하는 객체와 참조 관계를 확인하고, static 컬렉션이나 캐시 등에서 불필요한 객체가 유지되는지 점검하겠습니다.
>
> 또한 정상적인 캐시 증가나 트래픽 변화도 함께 고려하겠습니다.

**핵심 요약:** Heap 사용량과 GC 지표를 확인하고 Heap Dump로 객체의 참조 관계를 분석한다.

<a name="q1-1"></a>
#### ↳ Q1-1. Heap Dump란 무엇인가요?

> Heap Dump는 특정 시점의 Heap에 존재하는 객체와 참조 관계 등을 분석할 수 있도록 저장한 데이터입니다.
>
> Eclipse MAT 등의 도구를 이용하면 메모리를 많이 점유하는 객체와 객체가 회수되지 못하는 원인을 분석할 수 있습니다.

**핵심 요약:** Heap Dump는 특정 시점의 객체와 참조 관계를 분석하기 위한 메모리 정보이다.

<a name="q1-2"></a>
#### ↳ Q1-2. [심화 질문] Heap Dump 분석 시 어떤 정보를 중점적으로 확인해야 하나요?

> 메모리를 많이 차지하는 객체의 종류와 개수, 객체가 유지되는 참조 경로, GC Root와의 관계 등을 확인할 수 있습니다.
>
> 특히 Retained Heap을 분석하면 특정 객체 때문에 함께 회수되지 못하는 메모리 규모를 추정하는 데 도움이 됩니다.
>
> 다만 Heap Dump에는 민감한 데이터가 포함될 수 있으므로 보관과 접근 권한에 주의해야 합니다.

**핵심 요약:** Heap Dump에서는 객체 수, Retained Heap, GC Root 참조 경로 등을 확인한다.

<a name="q2"></a>
### Q2. API 응답 시간이 갑자기 느려졌다면 GC가 원인인지 어떻게 확인하겠습니까?

> API 응답 시간이 증가한 시점과 GC 발생 시점 및 정지 시간을 비교하겠습니다.
>
> GC 로그를 통해 긴 Stop-The-World가 발생했는지 확인하고, Heap 사용량과 GC 발생 빈도도 함께 분석하겠습니다.
>
> 응답 지연과 GC 정지 시간이 일치한다면 GC를 원인 후보로 고려할 수 있습니다.
>
> 다만 DB 쿼리 지연, 외부 API 응답 지연, 스레드 풀 포화 등의 가능성도 함께 확인하겠습니다.

**핵심 요약:** 응답 지연 시점과 GC 로그 및 정지 시간을 비교해 원인을 분석한다.

<a name="q2-1"></a>
#### ↳ Q2-1. GC 문제를 해결하기 위해 Heap 크기만 늘리면 되나요?

> 아닙니다.
>
> Heap 크기를 늘리면 일부 환경에서는 GC 발생 빈도를 줄이는 데 도움이 될 수 있습니다.
>
> 하지만 메모리 누수나 과도한 객체 생성이 원인이라면 근본적인 해결이 되지 않으며, 일부 GC에서는 수집 비용이 커질 수도 있습니다.
>
> 따라서 객체 생성량과 메모리 사용 패턴을 먼저 분석한 후 Heap 크기와 GC 설정을 조정해야 합니다.

**핵심 요약:** GC 문제는 Heap 크기만 늘리기보다 객체 생성량과 메모리 사용 패턴을 분석해야 한다.

<a name="q2-2"></a>
#### ↳ Q2-2. [심화 질문] GC를 줄이면 항상 애플리케이션 성능이 좋아지나요?

> 반드시 그렇지는 않습니다.
>
> GC 횟수가 줄어들더라도 한 번의 GC에서 처리해야 할 작업량이 커지면 정지 시간이 증가할 수 있습니다.
>
> 또한 GC 빈도뿐 아니라 전체 처리량, 응답 지연, 메모리 사용량을 함께 고려해야 합니다.

**핵심 요약:** GC 성능은 발생 횟수뿐 아니라 정지 시간과 애플리케이션 처리량을 함께 평가해야 한다.

<a name="q3"></a>
### Q3. Spring의 Singleton Bean은 Heap과 어떤 관계가 있나요?

> Spring의 Singleton Bean은 기본적으로 Spring IoC 컨테이너가 Bean 정의당 하나의 인스턴스를 생성하고 공유하도록 관리하는 객체입니다.
>
> 일반적인 Java 객체처럼 Bean 인스턴스는 주로 JVM Heap에 생성됩니다.
>
> Spring 컨테이너가 Bean을 계속 참조하고 있다면 해당 객체는 일반적으로 GC Root에서 도달 가능한 상태로 유지되어 GC 대상이 되지 않습니다.

**핵심 요약:** Spring Singleton Bean은 컨테이너가 공유하고 관리하는 Java 객체이며 일반적으로 Heap에 생성된다.

<a name="q3-1"></a>
#### ↳ Q3-1. Singleton Bean은 여러 스레드가 공유하나요?

> 네. Spring의 Singleton Bean은 여러 요청 처리 스레드에서 공유하여 사용될 수 있습니다.
>
> 따라서 Singleton Bean에 변경 가능한 인스턴스 필드를 저장하고 여러 스레드가 동시에 수정하면 Race Condition이 발생할 수 있습니다.
>
> 이러한 이유로 Service Bean은 가능하면 상태를 가지지 않는 Stateless 구조로 설계하는 것이 좋습니다.

**핵심 요약:** Singleton Bean은 여러 스레드가 공유할 수 있으므로 변경 가능한 상태를 주의해야 한다.

<a name="q3-2"></a>
#### ↳ Q3-2. Spring Singleton Bean과 static 변수의 차이는 무엇인가요?

> static 변수는 Java 언어 차원에서 클래스에 속하는 필드입니다.
>
> 반면 Spring Singleton Bean은 Spring 컨테이너가 인스턴스의 생성과 생명주기를 관리하는 객체입니다.
>
> Spring의 Singleton은 JVM 전체에서 무조건 하나라는 의미가 아니라 일반적으로 하나의 컨테이너에서 Bean 정의당 하나의 인스턴스를 관리한다는 의미입니다.

**핵심 요약:** static은 클래스 수준의 필드이고 Spring Singleton은 컨테이너가 관리하는 객체 범위이다.

<a name="q3-3"></a>
#### ↳ Q3-3. [심화 질문] Spring Bean도 GC 대상이 될 수 있나요?

> 네. Spring Bean도 Java 객체이므로 더 이상 GC Root에서 도달할 수 없다면 GC 대상이 될 수 있습니다.
>
> 다만 일반적인 Singleton Bean은 Spring 컨테이너가 참조를 유지하므로 컨테이너가 살아 있는 동안에는 대개 회수되지 않습니다.
>
> Bean의 스코프와 생명주기, 참조 관계에 따라 달라질 수 있습니다.

**핵심 요약:** Spring Bean도 Java 객체이므로 참조가 사라지면 GC 대상이 될 수 있다.

<a name="q4"></a>
### Q4. [심화 질문] Spring의 @Transactional이나 AOP Proxy도 JVM 메모리를 사용하나요?

> 네. Spring이 생성하는 프록시도 Java 객체이므로 JVM의 메모리 관리 대상입니다.
>
> 클래스 기반 프록시를 생성할 때는 프록시 클래스의 메타데이터가 필요하고, 프록시 인스턴스도 생성됩니다.
>
> 일반적인 경우 프록시 객체는 Heap에서 관리되며, 클래스 메타데이터는 JVM 구현에 맞는 메모리 영역에서 관리됩니다.
>
> 따라서 Spring AOP 역시 JVM의 클래스 로딩과 객체 생성, 메모리 관리 기능을 활용합니다.

**핵심 요약:** Spring AOP 프록시도 JVM에서 생성하고 관리하는 Java 객체이다.

<a name="q4-1"></a>
#### ↳ Q4-1. [심화 질문] Spring이 동적으로 생성한 프록시 클래스도 ClassLoader가 로딩하나요?

> 네. 동적으로 생성한 프록시 클래스도 JVM에서 사용하려면 적절한 ClassLoader를 통해 정의되어야 합니다.
>
> Spring은 JDK 동적 프록시나 클래스 기반 프록시 기술 등을 활용하며, 프록시 클래스도 JVM의 클래스 관리 대상이 됩니다.

**핵심 요약:** 동적으로 생성한 프록시 클래스도 JVM의 클래스 로딩 및 관리 대상이다.

---

<a name="q5"></a>
### Q5. [심화 질문] JVM에서 클래스 언로딩(Class Unloading)이란 무엇인가요?

> 클래스 언로딩은 더 이상 필요하지 않은 클래스의 메타데이터를 회수하는 과정입니다.
>
> 특정 클래스를 정의한 ClassLoader와 관련 객체 등이 더 이상 도달 가능하지 않은 등 필요한 조건이 충족되면 클래스 언로딩이 가능해질 수 있습니다.
>
> 실제 수행 여부는 JVM 구현과 GC 설정 등에 따라 달라집니다.

**핵심 요약:** 클래스 언로딩은 사용하지 않는 클래스의 메타데이터를 회수하는 과정이다.

<a name="q5-1"></a>
#### ↳ Q5-1. [심화 질문] ClassLoader가 메모리 누수의 원인이 될 수도 있나요?

> 네. 더 이상 필요하지 않은 ClassLoader가 참조 상태로 계속 유지된다면 해당 ClassLoader가 정의한 클래스와 관련 메타데이터도 회수되지 못할 수 있습니다.
>
> 특히 애플리케이션을 반복 배포하거나 플러그인을 동적으로 로딩하는 환경에서는 ClassLoader의 참조 관계를 확인할 필요가 있습니다.

**핵심 요약:** 불필요한 ClassLoader의 참조가 유지되면 클래스 메타데이터 회수를 방해할 수 있다.

<a name="section-02"></a>
## 최종 통합 질문

<a name="q6"></a>
### Q6. JVM에서 객체가 생성되고 사라지는 전체 과정을 설명해 주세요.

> 객체를 생성할 때 JVM은 해당 클래스가 필요한 만큼 로딩 및 초기화되어 있는지 확인합니다.
>
> 이후 일반적으로 Heap에 객체의 메모리를 할당하고 필드를 기본값으로 설정한 뒤 초기화 코드와 생성자를 실행합니다.
>
> 객체는 참조를 통해 사용되며, 더 이상 GC Root에서 도달할 수 없게 되면 GC의 회수 대상이 됩니다.
>
> 실제 메모리 회수 시점은 JVM의 GC 동작에 따라 결정됩니다.

**핵심 요약:** 클래스 준비 → 객체 생성 및 초기화 → 사용 → 도달 불가능 → GC 회수 대상.

<a name="q6-1"></a>
#### ↳ Q6-1. [심화 질문] 객체를 생성할 때마다 클래스 로딩과 초기화가 다시 발생하나요?

> 아닙니다.
>
> 동일한 정의 ClassLoader에서 클래스가 이미 로딩되고 초기화되었다면 새로운 객체를 생성할 때마다 클래스 로딩과 초기화를 반복하지 않습니다.
>
> 객체 생성은 클래스 정보의 준비와 구분되는 과정입니다.

**핵심 요약:** 같은 클래스의 객체를 여러 번 만들어도 클래스 로딩과 초기화를 매번 반복하지 않는다.

<a name="q7"></a>
### Q7. ClassLoader와 GC는 어떤 관계가 있나요?

> ClassLoader는 JVM이 사용할 클래스를 로딩하는 역할을 하고, GC는 더 이상 필요하지 않은 객체의 메모리를 회수합니다.
>
> 클래스 언로딩도 GC와 관련되며, 특정 클래스와 이를 정의한 ClassLoader 등이 더 이상 필요한 참조를 유지하지 않는 조건이 충족되면 클래스 메타데이터가 회수될 수 있습니다.

**핵심 요약:** ClassLoader는 클래스 로딩을 담당하고 GC는 객체와 불필요한 클래스 메타데이터 회수에 관여한다.

---

<a name="q8"></a>
### Q8. [심화 질문] JVM의 메모리 구조를 이해하는 것이 백엔드 개발자에게 중요한 이유는 무엇인가요?

> Java 백엔드 서버에서는 여러 요청을 처리하면서 많은 객체가 생성되고, 다양한 스레드가 메모리를 사용합니다.
>
> JVM 메모리 구조를 이해하면 메모리 누수, OutOfMemoryError, GC 지연, 동시성 문제 등을 분석하는 데 도움이 됩니다.
>
> 또한 적절한 객체 생명주기 관리와 JVM 모니터링을 통해 애플리케이션의 안정성과 성능을 개선할 수 있습니다.

**핵심 요약:** JVM 메모리 구조 이해는 백엔드 서버의 성능 문제와 메모리 장애를 분석하는 데 중요하다.

<a name="q9"></a>
### Q9. [심화 질문] Java 프로그램의 실행 과정에서 JVM, ClassLoader, Memory, GC는 어떻게 연결되나요?

> Java 소스 코드는 컴파일을 통해 바이트코드로 변환됩니다.
>
> ClassLoader는 필요한 클래스를 로딩하고, JVM의 Runtime Data Area는 객체와 메서드 실행 정보 등을 관리합니다.
>
> Execution Engine은 바이트코드를 실행하며, 실행 과정에서 더 이상 도달할 수 없게 된 객체는 GC의 회수 대상이 됩니다.
>
> 따라서 클래스 로딩, 메모리 관리, 코드 실행, GC는 Java 프로그램 실행을 구성하는 서로 연결된 과정입니다.

**핵심 요약:** 클래스 로딩 → 메모리 관리 → 코드 실행 → GC는 JVM에서 Java 프로그램이 실행되는 주요 과정이다.
