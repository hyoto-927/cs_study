<a name="section-01"></a>
## 동시성(Concurrency)

<a name="q1"></a>
### Q1. [대표 질문] 동시성이란 무엇이고, 병렬성과 어떻게 다른가요?

> "동시성은 여러 작업이 같은 시간 구간에 진행되는 것이고, 병렬성은 여러 작업이 실제로 같은 시점에 실행되는 것입니다.
>
> 단일 코어에서도 컨텍스트 스위칭으로 여러 작업을 번갈아 실행하여 동시성을 구현할 수 있지만, 병렬성은 일반적으로 여러 코어와 같은 복수의 실행 자원이 필요합니다."

**핵심 요약**

**동시성은 여러 작업을 함께 진행하는 것이고, 병렬성은 여러 작업을 실제로 동시에 실행하는 것이다.**

<a name="q2"></a>
### Q2. 동시성이 필요한 이유는 무엇인가요?

> "CPU 자원을 효율적으로 활용하고 여러 요청에 대한 응답성과 처리량을 높이기 위해서입니다.
>
> 특히 DB나 네트워크 응답을 기다리는 동안 다른 작업을 처리하면 CPU가 불필요하게 대기하는 시간을 줄일 수 있습니다."

**핵심 요약**

**동시성은 작업의 대기 시간에 다른 작업을 처리하여 자원 활용도와 처리량을 높인다.**

<a name="q3"></a>
### Q3. 동시성 프로그래밍이 어려운 이유는 무엇인가요?

> "여러 스레드의 실행 순서를 예측하거나 통제하기 어렵고, 공유 자원에 접근하는 순서에 따라 결과가 달라질 수 있기 때문입니다.
>
> 대표적으로 Race Condition, Deadlock, 가시성 문제 등이 발생할 수 있습니다."

**핵심 요약**

**동시성 프로그래밍은 실행 순서가 일정하지 않아 공유 자원 관련 문제가 발생하기 쉽다.**

<a name="q4"></a>
### Q4. 병렬성 없이 동시성만 있어도 성능이 좋아지나요?

> "I/O 바운드 작업에서는 대기 시간 동안 다른 작업을 처리할 수 있어 응답성과 처리량이 개선될 수 있습니다.
>
> 반면 CPU 바운드 작업은 단일 코어에서 번갈아 실행하므로 컨텍스트 스위칭 비용 때문에 오히려 느려질 수 있습니다."

**핵심 요약**

**동시성만으로도 I/O 대기 시간을 활용할 수 있지만 CPU 연산 자체가 빨라지는 것은 아니다.**

<a name="q5"></a>
### Q5. 스레드가 많을수록 동시성이 좋아지나요?

> "아닙니다. 스레드가 지나치게 많으면 컨텍스트 스위칭 비용, 메모리 사용량, 락 경합이 증가하여 성능이 저하될 수 있습니다.
>
> CPU 바운드 작업은 코어 수를 고려하고, I/O 바운드 작업은 대기 비율을 고려해 적절한 동시 작업 수를 결정해야 합니다."

**핵심 요약**

**스레드는 많을수록 좋은 것이 아니라 작업 특성에 맞게 조절해야 한다.**

<a name="q6"></a>
### Q6. 동시성을 다루는 방식에는 어떤 것이 있나요?

> "멀티스레드, 이벤트 루프 기반 비동기 처리, 코루틴, Java의 Virtual Thread 등이 있습니다.
>
> 또한 불변 객체나 메시지 전달 방식으로 공유 가변 상태를 최소화하면 동시성 문제를 줄일 수 있습니다."

**핵심 요약**

**동시성은 멀티스레드, 비동기 처리, 경량 스레드 등을 활용하며 공유 상태를 줄이는 것이 중요하다.**

<a name="q7"></a>
### Q7. 동기/비동기, 블로킹/논블로킹은 동시성과 어떤 관계인가요?

> "동기와 비동기는 작업 완료와 결과를 처리하는 방식에 관한 개념이고, 블로킹과 논블로킹은 호출한 스레드가 작업을 기다리며 멈추는지에 관한 개념입니다.
>
> 비동기 또는 논블로킹 방식을 적절히 활용하면 I/O 대기 중인 작업을 효율적으로 관리할 수 있습니다."

**핵심 요약**

**동기/비동기는 결과 처리 방식, 블로킹/논블로킹은 호출 시 대기 여부의 차이다.**

<a name="q8"></a>
### Q8. 동시성 문제가 백엔드 서버에서 발생하는 이유는 무엇인가요?

> "Spring MVC 기반 서버에서는 여러 HTTP 요청을 서로 다른 스레드가 동시에 처리할 수 있습니다.
>
> 이때 여러 스레드가 동일한 공유 가변 데이터를 수정하면 Race Condition이 발생할 수 있습니다.
>
> 예를 들어 여러 사용자가 동시에 재고를 차감하거나 조회수를 증가시키는 상황에서 원자성이 보장되지 않으면 데이터 불일치가 발생할 수 있습니다."

**핵심 요약**

**백엔드에서는 여러 요청 스레드가 공유 데이터를 동시에 수정할 수 있기 때문에 동시성 문제가 발생한다.**

<a name="q8-1"></a>
#### ↳ Q8-1. 모든 동시 요청에 동기화가 필요한가요?

> "아닙니다. 여러 스레드가 동시에 실행되더라도 공유 가변 데이터가 없다면 일반적으로 별도의 동기화가 필요하지 않습니다.
>
> 예를 들어 요청 별 지역 변수를 사용하거나 불변 객체를 읽는 경우에는 공유 상태로 인한 Race Condition 위험이 낮습니다.
>
> 따라서 실제로 공유되는 가변 상태가 있는지 먼저 확인해야 합니다."

**핵심 요약**

**모든 동시 요청에 동기화가 필요한 것은 아니며 공유 가변 상태가 있는지 확인해야 한다.**

<a name="q9"></a>
### Q9. 동시성과 병렬성의 차이를 예시로 설명해 주세요.

> "동시성은 요리사 한 명이 파스타를 삶는 동안 샐러드를 만드는 것처럼 여러 작업을 번갈아 진행하는 것입니다.
>
> 병렬성은 요리사 두 명이 각각 파스타와 샐러드를 실제로 동시에 만드는 것입니다."

**핵심 요약**

**동시성은 번갈아 처리할 수 있고, 병렬성은 실제로 동시에 처리한다.**

<a name="q10"></a>
### Q10. [핵심 질문] Context Switching(컨텍스트 스위칭)이란 무엇인가요?

> "CPU가 실행 중인 스레드나 프로세스를 다른 작업으로 전환하면서 현재 실행 상태를 저장하고 다음 작업의 상태를 복원하는 과정입니다.
>
> 여러 작업을 번갈아 실행할 수 있게 하지만 전환 과정에서 오버헤드가 발생합니다."

**핵심 요약**

**컨텍스트 스위칭은 CPU가 실행 대상을 변경하면서 작업 상태를 저장하고 복원하는 과정이다.**

<a name="q11"></a>
### Q11. [핵심 질문] CPU Bound와 I/O Bound의 차이는 무엇인가요?

> "CPU Bound는 계산 작업이 실행 시간의 대부분을 차지하는 경우이고, I/O Bound는 DB, 파일, 네트워크 등 외부 작업의 대기 시간이 큰 비중을 차지하는 경우입니다."

**핵심 요약**

**CPU Bound는 계산 중심, I/O Bound는 입출력 대기 중심 작업이다.**

<a name="q11-1"></a>
#### ↳ Q11-1. [핵심 질문] 동시성과 병렬성은 동시에 존재할 수 있나요?

> "가능합니다. 여러 코어에서 작업들이 병렬로 실행되는 동시에 각 코어에서도 여러 작업이 번갈아 실행될 수 있습니다.
>
> 따라서 동시성과 병렬성은 서로 배타적인 개념이 아닙니다."

**핵심 요약**

**동시성과 병렬성은 서로 다른 개념이지만 함께 나타날 수 있다.**

<a name="section-02"></a>
## Race Condition

<a name="q12"></a>
### Q12. [대표 질문] Race Condition이란 무엇이고 왜 발생하나요?

> "Race Condition은 여러 작업의 실행 순서나 타이밍에 따라 프로그램의 결과가 달라지는 문제입니다.
>
> 특히 여러 스레드가 공유 자원에 접근하면서 읽기, 수정, 쓰기 과정이 원자적으로 처리되지 않으면 발생할 수 있습니다."

**핵심 요약**

**Race Condition은 여러 작업의 실행 순서에 따라 결과가 달라지는 문제이다.**

<a name="q13"></a>
### Q13. Race Condition의 구체적인 예시를 들어주세요.

> "`count++`는 값을 읽고, 1을 더하고, 다시 저장하는 복합 연산입니다.
>
> 두 스레드가 동시에 10을 읽고 각각 11을 저장하면 두 번 증가했지만 최종 결과는 11이 될 수 있습니다."

**핵심 요약**

**count++는 원자적 연산이 아니므로 여러 스레드가 동시에 실행하면 증가 결과가 누락될 수 있다.**

<a name="q13-1"></a>
#### ↳ Q13-1. count++는 왜 원자적이지 않나요?

> "count++는 하나의 코드처럼 보이지만 실제로는 값을 읽고, 증가시키고, 저장하는 여러 단계로 이루어져 있습니다.
>
> 여러 스레드가 같은 값을 읽은 뒤 각각 수정하면 한 스레드의 증가 결과가 다른 스레드의 저장으로 덮어써질 수 있습니다."

**핵심 요약**

**count++는 읽기·수정·쓰기가 하나의 원자적 연산이 아니기 때문에 경쟁 상태가 발생할 수 있다.**

<a name="q14"></a>
### Q14. Critical Section(임계 영역)이란 무엇인가요?

> "임계 영역은 여러 스레드가 공유 자원에 접근하는 코드 중 동시에 실행하면 문제가 발생할 수 있어 보호가 필요한 구간입니다.
>
> 일반적으로 Mutex나 synchronized 등으로 상호 배제를 구현하여 보호합니다."

**핵심 요약**

**임계 영역은 공유 자원의 안전한 접근을 위해 보호해야 하는 코드 구간이다.**

<a name="q14-1"></a>
#### ↳ Q14-1. Race Condition과 임계 영역은 어떤 관계인가요?

> "임계 영역은 여러 스레드가 동시에 실행할 경우 공유 데이터의 일관성이 깨질 수 있는 코드 영역입니다.
>
> Race Condition을 방지하려면 해당 임계 영역에 대한 접근을 적절하게 동기화해야 합니다."

**핵심 요약**

**Race Condition을 막기 위해 공유 자원에 접근하는 임계 영역을 보호해야 한다.**

<a name="q15"></a>
### Q15. 임계 영역 문제를 해결하려면 어떤 조건을 만족해야 하나요?

> "상호 배제, 진행, 한정 대기라는 세 가지 조건을 만족해야 합니다.
>
> 상호 배제는 동시에 하나만 임계 영역에 들어가는 것이고, 진행은 진입 가능한 스레드의 선택을 불필요하게 미루지 않는 것이며, 한정 대기는 특정 스레드가 무한정 기다리지 않도록 하는 것입니다."

**핵심 요약**

**임계 영역의 세 가지 조건은 상호 배제, 진행, 한정 대기이다.**

<a name="q16"></a>
### Q16. Race Condition을 막는 방법에는 어떤 것이 있나요?

> "synchronized나 ReentrantLock으로 임계 영역을 보호하거나 AtomicInteger 같은 원자 연산을 사용할 수 있습니다.
>
> 불변 객체와 ThreadLocal로 공유 상태를 줄일 수도 있으며, DB에서는 원자적 UPDATE, 낙관적 락, 비관적 락 등을 활용합니다."

**핵심 요약**

**Race Condition은 동기화, 원자 연산, 공유 상태 최소화 등으로 해결한다.**

<a name="q17"></a>
### Q17. Race Condition과 Data Race는 같은 건가요?

> "다릅니다. Data Race는 적절한 동기화 없이 동일한 메모리에 충돌하는 접근이 발생하는 현상이고, Race Condition은 실행 순서나 타이밍에 따라 결과가 달라지는 더 넓은 개념입니다.
>
> Data Race가 없어도 확인 후 실행하는 Check-Then-Act 과정에서 Race Condition이 발생할 수 있습니다."

**핵심 요약**

**Data Race는 메모리 접근 충돌이고, Race Condition은 실행 순서에 따른 결과 문제이다.**

<a name="q18"></a>
### Q18. volatile만 붙이면 Race Condition이 해결되나요?

> "아닙니다. volatile은 가시성과 메모리 순서 보장을 제공하지만, count++처럼 여러 단계로 이루어진 연산의 원자성을 보장하지 않습니다.
>
> 원자성이 필요하면 synchronized나 AtomicInteger 등을 사용해야 합니다."

**핵심 요약**

**volatile은 가시성을 보장하지만 count++의 원자성까지 보장하지는 않는다.**

<a name="q19"></a>
### Q19. volatile과 AtomicInteger의 차이는 무엇이며, 각각 언제 사용하나요?

> "volatile은 여러 스레드 사이에서 변수의 변경 사항을 올바르게 관찰할 수 있도록 가시성을 보장하지만 복합 연산의 원자성은 보장하지 않습니다.
>
> 반면 AtomicInteger는 CAS 등의 원자적 연산을 활용하여 여러 스레드가 동시에 값을 증가시키더라도 갱신 손실을 방지할 수 있습니다.
>
> 따라서 실행 상태 플래그처럼 가시성이 필요한 경우에는 volatile을, 공유 카운터의 증가 연산에는 AtomicInteger를 선택합니다."

**핵심 요약**

**volatile은 가시성, AtomicInteger는 원자적 정수 연산이 필요할 때 사용한다.**

<a name="q19-1"></a>
#### ↳ Q19-1. AtomicInteger와 synchronized 중 어떤 것을 선택하나요?

> "단순한 정수 증가나 감소처럼 하나의 값에 대한 원자적 연산이 필요하다면 AtomicInteger를 선택할 수 있습니다.
>
> 반면 여러 변수의 상태를 함께 변경하거나 여러 연산을 하나의 임계 영역으로 보호해야 한다면 synchronized가 적합합니다.
>
> 따라서 보호해야 하는 연산의 범위와 동시성 요구사항에 따라 선택합니다."

**핵심 요약**

**단일 값의 원자적 변경은 AtomicInteger, 여러 연산을 함께 보호할 때는 synchronized를 고려한다.**

<a name="q20"></a>
### Q20. 백엔드에서 Race Condition이 발생하는 사례는 무엇인가요?

> "상품 재고 차감, 좌석 예약, 쿠폰 중복 발급, 계좌 잔액 변경 등이 대표적입니다.
>
> 여러 요청이 동일한 데이터를 조회한 뒤 수정하면 데이터가 잘못 반영될 수 있으므로 DB의 원자적 연산이나 락 등을 사용해야 합니다."

**핵심 요약**

**백엔드에서는 여러 요청이 같은 데이터를 조회하고 수정할 때 Race Condition이 발생할 수 있다.**

<a name="q21"></a>
### Q21. 싱글톤 Bean에서 Race Condition이 생기는 경우는 무엇인가요?

> "싱글톤 Bean에 여러 요청이 함께 수정하는 가변 인스턴스 필드가 있으면 Race Condition이 발생할 수 있습니다.
>
> 따라서 Controller와 Service는 가능한 한 무상태로 설계하고, 요청별 데이터는 지역 변수나 적절한 범위의 객체로 관리하는 것이 좋습니다."

**핵심 요약**

**싱글톤 Bean은 여러 스레드가 공유하므로 가변 인스턴스 필드를 주의해야 한다.**

<a name="q22"></a>
### Q22. Race Condition과 Lost Update의 차이는 무엇인가요?

> "Race Condition은 실행 순서에 따라 결과가 달라지는 문제 전체를 의미합니다.
>
> Lost Update는 여러 작업이 동일한 데이터를 수정하면서 한 작업의 변경 결과가 다른 작업에 덮어써져 사라지는 현상입니다."

**핵심 요약**

**Race Condition은 넓은 개념이고, Lost Update는 변경 결과가 덮어써지는 구체적인 문제이다.**

<a name="q23"></a>
### Q23. [핵심 질문] 원자성(Atomicity)이란 무엇인가요?

> "작업이 다른 스레드의 관점에서 중간 상태 없이 하나의 단위로 수행되는 성질입니다.
>
> 예를 들어 AtomicInteger의 incrementAndGet()은 증가 연산을 원자적으로 수행합니다."

**핵심 요약**

**원자성은 작업이 중간에 끼어들 수 없는 하나의 단위로 수행되는 성질이다.**

<a name="q24"></a>
### Q24. [핵심 질문] 가시성(Visibility)이란 무엇인가요?

> "한 스레드가 변경한 값을 다른 스레드가 올바르게 관찰할 수 있는 성질입니다.
>
> Java에서는 volatile, synchronized, Atomic 클래스 등을 통해 필요한 가시성을 보장할 수 있습니다."

**핵심 요약**

**가시성은 한 스레드의 변경 결과를 다른 스레드가 올바르게 볼 수 있는 성질이다.**

<a name="q25"></a>
### Q25. [핵심 질문] Check-Then-Act 문제란 무엇인가요?

> "조건을 확인한 뒤 실제 작업을 수행하기 전에 다른 스레드가 상태를 변경하여 잘못된 결과가 발생하는 문제입니다.
>
> 예를 들어 좌석이 비었는지 확인한 뒤 예약하는 사이 다른 요청이 같은 좌석을 예약하면 중복 예약이 발생할 수 있습니다."

**핵심 요약**

**Check-Then-Act는 확인과 실행 사이에 상태가 변경되어 발생하는 경쟁 상태이다.**

<a name="section-03"></a>
## Mutex

<a name="q26"></a>
### Q26. [대표 질문] Mutex란 무엇이고 어떻게 동작하나요?

락을 획득한 스레드가 임계 영역을 실행하고 작업이 끝나면 락을 해제하며, 다른 스레드는 락을 획득할 수 있을 때까지 대기합니다."

> "Mutex는 Mutual Exclusion의 약자로, 공유 자원에 한 번에 하나의 스레드만 접근하도록 하는 상호 배제 잠금 장치입니다.

**핵심 요약**

**Mutex는 공유 자원에 한 번에 하나의 스레드만 접근하도록 하는 잠금 장치이다.**

<a name="q27"></a>
### Q27. Mutex에는 소유권이 있다는 게 무슨 뜻인가요?

> "락을 획득한 스레드가 해당 락의 소유자가 되며, 일반적으로 그 스레드만 락을 해제할 수 있다는 의미입니다.
>
> 이는 소유권이 없는 Semaphore와의 중요한 차이입니다."

**핵심 요약**

**Mutex는 락을 획득한 스레드가 소유권을 가지며 직접 해제해야 한다.**

<a name="q28"></a>
### Q28. Java에서 Mutex는 어떻게 사용하나요?

> "Java에서는 synchronized 또는 ReentrantLock으로 상호 배제를 구현할 수 있습니다.
>
> synchronized는 간단하고 자동으로 락을 해제하며, ReentrantLock은 타임아웃과 공정성 설정 등 세밀한 제어를 지원합니다."

**핵심 요약**

**Java에서는 synchronized와 ReentrantLock으로 Mutex와 같은 상호 배제를 구현한다.**

<a name="q29"></a>
### Q29. synchronized를 사용하면 항상 하나의 스레드만 실행되나요?

> "아닙니다. synchronized는 동일한 모니터 락을 획득하려는 스레드 사이에서만 상호 배제를 보장합니다.
>
> 서로 다른 객체의 락을 사용하거나 동기화되지 않은 코드를 실행하는 스레드들은 동시에 실행될 수 있습니다.
>
> 따라서 같은 공유 자원을 보호하려면 동일한 락을 사용하도록 설계해야 합니다."

**핵심 요약**

**synchronized는 모든 스레드를 막는 것이 아니라 동일한 락을 사용하는 스레드 사이에서 상호 배제를 보장한다.**

<a name="q30"></a>
### Q30. synchronized와 ReentrantLock의 차이는 무엇인가요?

> "synchronized는 Java 언어에 내장된 동기화 기능으로 락 해제가 자동으로 이루어집니다.
>
> ReentrantLock은 개발자가 명시적으로 락을 관리하며 tryLock(), 타임아웃, 공정성, 인터럽트 가능한 락 획득 등을 지원합니다.
>
> 따라서 단순한 동기화에는 synchronized를 우선 고려하고, 락 획득을 세밀하게 제어해야 한다면 ReentrantLock을 선택할 수 있습니다."

**핵심 요약**

**synchronized는 간단한 자동 락 관리, ReentrantLock은 세밀한 수동 락 제어가 특징이다.**

<a name="q31"></a>
### Q31. ReentrantLock에서 unlock()을 finally에 넣어야 하는 이유는 무엇인가요?

> "임계 영역에서 예외가 발생하더라도 락을 반드시 해제하기 위해서입니다.
>
> unlock()이 실행되지 않으면 다른 스레드가 계속 대기할 수 있으므로 락을 획득한 뒤에는 try-finally로 해제를 보장해야 합니다."

**핵심 요약**

**unlock()을 finally에 넣는 이유는 예외가 발생해도 락을 반드시 해제하기 위해서이다.**

<a name="q32"></a>
### Q32. 재진입 가능(Reentrant)이란 무엇인가요?

> "이미 락을 보유한 스레드가 같은 락을 다시 획득할 수 있는 성질입니다.
>
> Java의 synchronized와 ReentrantLock은 모두 재진입을 지원합니다."

**핵심 요약**

**재진입 가능은 락을 보유한 스레드가 같은 락을 다시 획득할 수 있다는 뜻이다.**

<a name="q33"></a>
### Q33. Mutex를 사용하면 어떤 단점이 있나요?

> "락 경합으로 인해 대기 시간이 증가하고 처리량이 감소할 수 있습니다.
>
> 특히 임계 영역 안에서 DB 조회나 외부 API 호출처럼 오래 걸리는 작업을 수행하면 락 점유 시간이 길어집니다.
>
> 또한 락을 잘못 사용하면 Deadlock이나 Starvation이 발생할 수 있으므로 임계 영역을 가능한 한 짧게 유지하는 것이 좋습니다."

**핵심 요약**

**Mutex는 안전성을 높이지만 락 경합과 대기 비용, Deadlock 위험이 있다.**

<a name="q34"></a>
### Q34. Spin Lock과 Mutex의 차이는 무엇인가요?

> "Spin Lock은 락을 획득할 때까지 CPU를 사용하며 반복적으로 확인하는 방식입니다.
>
> 반면 일반적인 대기 기반 Mutex는 락을 획득하지 못하면 스레드를 대기시켜 CPU 사용을 줄일 수 있습니다. 락 점유 시간이 매우 짧을 때는 Spin Lock이 유리할 수 있습니다."

**핵심 요약**

**Spin Lock은 계속 확인하며 기다리고, 대기 기반 Mutex는 스레드를 대기시켜 기다린다.**

<a name="q35"></a>
### Q35. 분산 환경에서도 Mutex로 충분한가요?

> "아닙니다. synchronized와 ReentrantLock은 하나의 JVM 내부에서만 동작합니다.
>
> 여러 서버가 같은 데이터를 수정하는 환경에서는 DB 락이나 Redis 기반 분산 락 등 서버 간 동시성 제어가 필요할 수 있습니다."

**핵심 요약**

**JVM 내부 락만으로는 여러 서버의 공유 자원 접근을 제어할 수 없다.**

<a name="q36"></a>
### Q36. 동시성 문제를 해결할 때 synchronized만 사용하지 않는 이유는 무엇인가요?

> "synchronized는 JVM 내부에서 공유 자원에 대한 상호 배제를 구현하는 데 유용하지만 모든 동시성 문제에 적합한 것은 아닙니다.
>
> 단순 카운터 갱신에는 AtomicInteger를 사용할 수 있고, 동시 실행 수를 제한해야 한다면 Semaphore가 더 적합합니다.
>
> 또한 여러 서버에서 공유하는 DB 데이터를 수정하는 경우 synchronized만으로는 서버 간 동시성 문제를 해결할 수 없습니다.
>
> 따라서 보호할 자원의 특성과 동시성 제어가 필요한 범위에 따라 적절한 방법을 선택해야 합니다."

**핵심 요약**

**synchronized만 사용하는 것이 아니라 문제의 특성에 따라 적절한 동시성 제어 방법을 선택해야 한다.**

<a name="q37"></a>
### Q37. [핵심 질문] Mutex와 synchronized는 같은 개념인가요?

> "Mutex는 상호 배제를 위한 잠금 개념이고, synchronized는 Java에서 객체 모니터를 이용해 상호 배제를 구현하는 언어 기능입니다.
>
> 동일한 용어는 아니지만 synchronized로 Mutex와 같은 상호 배제를 구현할 수 있습니다."

**핵심 요약**

**Mutex는 상호 배제 개념이고, synchronized는 이를 구현하는 Java의 동기화 기능이다.**

<a name="q38"></a>
### Q38. [핵심 질문] tryLock()은 언제 사용하나요?

> "락을 즉시 획득할 수 있는지 확인하거나 정해진 시간 동안만 기다리고 싶을 때 사용합니다.
>
> 락 획득에 실패하면 다른 작업을 수행하거나 재시도하도록 설계할 수 있습니다."

**핵심 요약**

**tryLock()은 락 획득을 시도하고 실패 시 다른 처리를 할 수 있도록 하는 메서드이다.**

<a name="section-04"></a>
## Semaphore

<a name="q39"></a>
### Q39. [대표 질문] Semaphore란 무엇이고 Mutex와 어떻게 다른가요?

> "Semaphore는 허가증(Permit)의 개수를 관리하여 동시에 접근할 수 있는 작업 수를 제한하는 동기화 도구입니다.
>
> Mutex는 일반적으로 하나의 스레드만 접근하도록 하고 소유권이 있지만, Semaphore는 여러 허가증을 제공할 수 있고 스레드 소유권이 없습니다."

**핵심 요약**

**Mutex는 한 번에 하나만 접근시키고, Semaphore는 허가증 개수만큼 접근을 허용한다.**

<a name="q40"></a>
### Q40. Binary Semaphore와 Counting Semaphore의 차이는 무엇인가요?

> "Binary Semaphore는 허가증을 0개 또는 1개로 관리하는 방식이고, Counting Semaphore는 여러 개의 허가증을 관리하는 방식입니다.
>
> Binary Semaphore는 상호 배제에 사용할 수 있지만 Mutex와 달리 소유권이 없습니다."

**핵심 요약**

**Binary Semaphore는 1개, Counting Semaphore는 여러 개의 허가증을 관리한다.**

<a name="q40-1"></a>
#### ↳ Q40-1. Semaphore를 1로 설정하면 Mutex 대신 사용할 수 있나요?

> "동시에 하나의 작업만 접근하도록 제한하는 용도로 사용할 수 있습니다.
>
> 다만 Mutex는 일반적으로 락을 획득한 스레드가 해제해야 하는 소유권 개념이 있는 반면, Semaphore는 허가증을 획득한 스레드와 반환하는 스레드가 달라도 됩니다.
>
> 따라서 단순한 상호 배제가 목적이라면 소유권을 통한 안전한 락 관리가 가능한 Mutex 계열 동기화 기법을 우선 고려할 수 있습니다."

**핵심 요약**

**Semaphore를 1로 설정하면 상호 배제에 사용할 수 있지만 Mutex와 소유권이 다르다.**

<a name="q41"></a>
### Q41. Semaphore의 P 연산과 V 연산은 무엇인가요?

> "P 연산은 허가증을 획득하는 동작이고, V 연산은 허가증을 반환하는 동작입니다.
>
> Java에서는 acquire()와 release()를 사용하며, 허가증이 없으면 acquire()를 호출한 스레드는 대기합니다."

**핵심 요약**

**P는 허가증 획득, V는 허가증 반환이며 Java에서는 acquire()와 release()를 사용한다.**

<a name="q42"></a>
### Q42. Semaphore는 어디에 사용하나요?

> "DB 연결 사용량 제한, 외부 API 동시 호출 수 제한, 한정된 리소스에 대한 접근 제어 등에 사용합니다.
>
> 예를 들어 외부 API에 대한 동시 호출을 최대 5개로 제한해야 한다면 허가증이 5개인 Semaphore를 사용할 수 있습니다."

**핵심 요약**

**Semaphore는 제한된 자원을 동시에 사용할 수 있는 작업 수를 관리할 때 사용한다.**

<a name="q43"></a>
### Q43. 서버가 여러 대라면 Semaphore가 전체 요청 수를 제한하나요?

> "아닙니다. 일반적인 Java Semaphore는 해당 JVM 내부에서만 허가증 개수를 관리합니다.
>
> 예를 들어 서버가 3대이고 각 서버에서 허가증을 5개씩 설정했다면 전체적으로 최대 15개의 작업이 동시에 허가증을 획득할 수 있습니다.
>
> 따라서 여러 서버 전체에 걸쳐 동시 실행 수를 제한하려면 공통 저장소 등을 활용한 분산 제어 방식이 필요합니다."

**핵심 요약**

**Java Semaphore는 JVM 단위로 동작하므로 여러 서버 전체의 동시 실행 수를 제한하려면 분산 제어가 필요하다.**

<a name="q44"></a>
### Q44. Semaphore로 스레드 실행 순서를 제어할 수 있나요?

> "가능합니다. 허가증이 0개인 Semaphore에서 스레드 B가 acquire()로 대기하고, 스레드 A가 작업을 마친 뒤 release()하면 B가 이후 작업을 진행하도록 만들 수 있습니다."

**핵심 요약**

**Semaphore는 허가증 획득과 반환을 이용해 스레드 간 실행 순서를 조정할 수 있다.**

<a name="q45"></a>
### Q45. 생산자-소비자 문제를 Semaphore로 어떻게 해결하나요?

> "일반적으로 empty, full, mutex라는 세 가지 동기화 수단을 사용합니다.
>
> empty는 빈 버퍼 칸 수, full은 채워진 칸 수를 나타내고, mutex는 버퍼에 대한 상호 배제를 담당합니다.
>
> 생산자는 빈 칸이 있을 때 데이터를 넣고, 소비자는 데이터가 있을 때 꺼내도록 제어합니다."

**핵심 요약**

**생산자-소비자 문제는 빈 칸과 채워진 칸을 관리하고 버퍼 접근을 보호하여 해결한다.**

<a name="q46"></a>
### Q46. Semaphore를 잘못 사용하면 어떤 문제가 생기나요?

> "release()를 누락하면 허가증이 반환되지 않아 다른 스레드가 계속 대기할 수 있습니다.
>
> 반대로 release()를 잘못 중복 호출하면 허가증 수가 의도한 제한을 초과할 수 있으며, 획득 순서를 잘못 설계하면 Deadlock도 발생할 수 있습니다."

**핵심 요약**

**Semaphore는 acquire()와 release()를 올바르게 관리하지 않으면 대기나 접근 제한 오류가 발생한다.**

<a name="q47"></a>
### Q47. 커넥션 풀과 Semaphore의 차이는 무엇인가요?

> "커넥션 풀은 DB 연결 객체의 생성, 재사용, 검증, 반환 등을 관리합니다.
>
> 반면 Semaphore는 동시에 접근할 수 있는 허가증의 개수만 관리합니다.
>
> 따라서 Semaphore는 커넥션 풀의 동시 사용량 제어에 활용될 수 있지만 커넥션 풀 자체를 대체하지는 않습니다."

**핵심 요약**

**커넥션 풀은 연결 객체를 관리하고, Semaphore는 동시 접근 수를 관리한다.**

<a name="q48"></a>
### Q48. [핵심 질문] Semaphore는 공정성을 보장하나요?

> "항상 보장하지는 않습니다. Java의 Semaphore는 생성할 때 공정성 옵션을 설정할 수 있습니다.
>
> 공정 모드는 대기 순서를 고려하여 허가증을 제공하지만 모든 상황에서 엄격한 작업 완료 순서까지 보장하지는 않습니다."

**핵심 요약**

**Java Semaphore는 공정성 옵션을 지원하지만 모든 실행 순서를 보장하는 것은 아니다.**

<a name="q49"></a>
### Q49. [핵심 질문] Semaphore의 허가증이 0개가 되면 어떻게 되나요?

> "새로운 acquire() 호출은 허가증이 반환될 때까지 대기합니다.
>
> tryAcquire()를 사용하면 허가증을 즉시 획득할 수 있는지 확인하고 실패 시 대기하지 않고 다른 작업을 수행할 수 있습니다."

**핵심 요약**

**Semaphore의 허가증이 없으면 acquire()는 대기하고, tryAcquire()는 즉시 실패할 수 있다.**

<a name="section-05"></a>
## 연관 종합 질문

<a name="q50"></a>
### Q50. 동시성, Race Condition, Mutex, Semaphore를 한 문장으로 연결하면?

> "동시성 환경에서 여러 스레드가 공유 자원에 접근하면 Race Condition이 발생할 수 있고, 이를 방지하기 위해 Mutex로 상호 배제를 구현하거나 Semaphore로 동시 접근 수를 제한할 수 있습니다.
>
> 단, 허가증이 여러 개인 Semaphore만으로 동일한 데이터의 동시 수정이 자동으로 안전해지는 것은 아닙니다."

**핵심 요약**

**동시성 환경의 공유 자원 문제를 해결하기 위해 Mutex와 Semaphore 같은 동기화 도구를 사용한다.**

<a name="q51"></a>
### Q51. Mutex와 Semaphore 중 무엇을 사용해야 하나요?

> "하나의 공유 자원에 대해 상호 배제가 필요하면 Mutex를 사용하고, 여러 개의 제한된 자원에 대한 동시 접근 수를 관리하거나 스레드 간 신호 전달이 필요하면 Semaphore를 사용합니다."

**핵심 요약**

**단독 접근이 필요하면 Mutex, 접근 개수 제한이나 신호 전달이 필요하면 Semaphore이다.**

<a name="q52"></a>
### Q52. 락을 사용하지 않고 Race Condition을 해결할 수 있나요?

> "가능합니다. Atomic 클래스의 원자 연산, 불변 객체, ThreadLocal, 메시지 전달, DB 원자적 UPDATE 등을 활용할 수 있습니다.
>
> 다만 여러 단계로 이루어진 복잡한 작업에서는 추가적인 동시성 제어가 필요할 수 있습니다."

**핵심 요약**

**Race Condition은 락 외에도 원자 연산과 공유 상태 제거 등으로 해결할 수 있다.**

<a name="q53"></a>
### Q53. Race Condition과 Deadlock의 관계는 무엇인가요?

> "Race Condition은 작업 실행 순서에 따라 결과가 달라지는 문제이고, Deadlock은 작업들이 서로가 보유한 자원을 기다리며 진행하지 못하는 상태입니다.
>
> 락은 Race Condition을 방지할 수 있지만 잘못 설계하면 Deadlock이 발생할 수 있습니다."

**핵심 요약**

**Race Condition은 결과가 달라지는 문제이고, Deadlock은 서로 기다리며 멈추는 문제이다.**

<a name="q54"></a>
### Q54. Monitor(모니터)란 무엇인가요?

> "Monitor는 공유 데이터에 대한 상호 배제와 조건 대기를 지원하는 동기화 구조입니다.
>
> Java에서는 객체 모니터를 기반으로 synchronized를 사용하며, wait(), notify(), notifyAll()을 통해 조건 대기와 알림을 구현할 수 있습니다."

**핵심 요약**

**Monitor는 상호 배제와 조건 대기를 제공하는 동기화 구조이다.**

<a name="section-06"></a>
## 추가로 알아두면 좋은 질문

<a name="q55"></a>
### Q55. [핵심 질문] Deadlock(교착 상태)이란 무엇인가요?

> "두 개 이상의 스레드가 서로 상대방이 보유한 자원을 기다리면서 어떤 스레드도 진행하지 못하는 상태입니다."

**핵심 요약**

**Deadlock은 서로가 가진 자원을 기다리며 모든 관련 작업이 멈추는 상태이다.**

<a name="q55-1"></a>
#### ↳ Q55-1. [핵심 질문] Deadlock의 발생 조건 네 가지는 무엇인가요?

> "상호 배제, 점유와 대기, 비선점, 순환 대기입니다.
>
> 이 네 가지 조건이 동시에 성립해야 Deadlock이 발생할 수 있습니다."

**핵심 요약**

**Deadlock의 네 조건은 상호 배제, 점유와 대기, 비선점, 순환 대기이다.**

<a name="q55-2"></a>
#### ↳ Q55-2. [핵심 질문] Deadlock을 예방하는 방법은 무엇인가요?

> "락 획득 순서를 일관되게 유지하고, 불필요한 중첩 락을 줄이며, tryLock()과 타임아웃 등을 활용할 수 있습니다."

**핵심 요약**

**Deadlock은 락 순서 통일과 중첩 락 최소화 등으로 예방할 수 있다.**

<a name="q56"></a>
### Q56. [핵심 질문] Starvation(기아 상태)이란 무엇인가요?

> "특정 스레드가 자원이나 실행 기회를 계속 얻지 못해 무한정 대기하는 현상입니다.
>
> 우선순위나 불공정한 락 획득 정책 등이 원인이 될 수 있습니다."

**핵심 요약**

**Starvation은 특정 스레드가 계속 실행 기회를 얻지 못하는 상태이다.**

<a name="q56-1"></a>
#### ↳ Q56-1. [핵심 질문] Deadlock과 Starvation의 차이는 무엇인가요?

> "Deadlock은 작업들이 서로를 기다리며 진행하지 못하는 상태이고, Starvation은 다른 작업들은 진행하지만 특정 작업만 계속 기회를 얻지 못하는 상태입니다."

**핵심 요약**

**Deadlock은 서로 기다리는 문제, Starvation은 특정 작업만 계속 기다리는 문제이다.**

<a name="q57"></a>
### Q57. [핵심 질문] 원자성, 가시성, 순서 보장의 차이는 무엇인가요?

> "원자성은 작업이 중간에 끼어들 수 없는 단위로 수행되는 성질이고, 가시성은 다른 스레드의 변경 결과를 올바르게 관찰하는 성질입니다.
>
> 순서 보장은 메모리 모델에서 요구하는 작업 간 실행·관찰 순서가 유지되는 성질입니다."

**핵심 요약**

**원자성은 작업 단위, 가시성은 변경 결과의 관찰, 순서 보장은 작업 간 순서에 관한 성질이다.**

<a name="q58"></a>
### Q58. [핵심 질문] CAS(Compare-And-Swap)란 무엇인가요?

> "CAS는 현재 값이 예상한 값과 같을 때만 새로운 값으로 변경하는 원자적 연산입니다.
>
> Java의 AtomicInteger 등에서 활용되며 락을 사용하지 않는 동시성 알고리즘의 중요한 구성 요소입니다."

**핵심 요약**

**CAS는 현재 값이 예상값과 일치할 때만 원자적으로 변경하는 연산이다.**

<a name="q58-1"></a>
#### ↳ Q58-1. [핵심 질문] CAS의 단점은 무엇인가요?

> "경쟁이 심하면 반복적인 재시도로 CPU 자원을 낭비할 수 있고, 값이 A에서 B로 바뀌었다가 다시 A로 돌아오는 ABA 문제도 발생할 수 있습니다."

**핵심 요약**

**CAS는 재시도 비용과 ABA 문제를 고려해야 한다.**

<a name="q59"></a>
### Q59. [핵심 질문] synchronized와 volatile의 차이는 무엇인가요?

> "synchronized는 임계 영역의 상호 배제와 가시성을 보장하지만, volatile은 상호 배제 없이 변수의 가시성과 메모리 순서를 보장합니다.
>
> 따라서 공유 카운터의 증가 연산에는 volatile만으로 충분하지 않습니다."

**핵심 요약**

**synchronized는 상호 배제와 가시성, volatile은 가시성과 메모리 순서를 보장한다.**

<a name="q60"></a>
### Q60. [핵심 질문] ThreadLocal은 무엇인가요?

> "ThreadLocal은 스레드마다 독립적인 변수 값을 저장할 수 있도록 하는 Java 클래스입니다.
>
> 스레드 간 데이터 공유를 줄일 수 있지만, 스레드 풀 환경에서는 사용 후 remove()로 정리하지 않으면 이전 작업의 데이터가 남을 수 있습니다."

**핵심 요약**

**ThreadLocal은 스레드마다 독립적인 데이터를 보관하는 기능이다.**

<a name="q61"></a>
### Q61. [핵심 질문] Java에서 스레드 안전한 컬렉션에는 무엇이 있나요?

> "ConcurrentHashMap, CopyOnWriteArrayList, BlockingQueue 등이 있습니다.
>
> 각각 동시성 제어 방식과 성능 특성이 다르므로 읽기·쓰기 비율과 사용 목적에 따라 선택해야 합니다."

**핵심 요약**

**Java는 ConcurrentHashMap 등 여러 스레드 안전 컬렉션을 제공한다.**

<a name="q61-1"></a>
#### ↳ Q61-1. [핵심 질문] HashMap과 ConcurrentHashMap의 차이는 무엇인가요?

> "HashMap은 기본적으로 스레드 안전하지 않지만, ConcurrentHashMap은 여러 스레드가 안전하게 접근할 수 있도록 설계되어 있습니다.
>
> 다만 여러 연산을 조합한 로직에서는 compute(), putIfAbsent() 같은 원자적 메서드가 필요할 수 있습니다."

**핵심 요약**

**HashMap은 기본적으로 스레드 안전하지 않고, ConcurrentHashMap은 동시 접근을 지원한다.**

<a name="q62"></a>
### Q62. [핵심 질문] DB 트랜잭션을 사용하면 Race Condition이 모두 해결되나요?

> "아닙니다. 트랜잭션을 사용하더라도 격리 수준과 쿼리 패턴에 따라 Lost Update나 동시 수정 문제가 발생할 수 있습니다.
>
> 필요에 따라 원자적 UPDATE, 낙관적 락, 비관적 락 등을 사용해야 합니다."

**핵심 요약**

**트랜잭션만으로 모든 동시성 문제가 해결되는 것은 아니며 적절한 격리와 락이 필요하다.**

<a name="q62-1"></a>
#### ↳ Q62-1. [핵심 질문] 낙관적 락과 비관적 락의 차이는 무엇인가요?

> "낙관적 락은 충돌이 적다고 가정하고 버전 정보 등을 이용해 수정 시 충돌을 감지합니다.
>
> 비관적 락은 충돌 가능성을 고려해 데이터를 잠그고 다른 트랜잭션의 접근을 제어합니다."

**핵심 요약**

**낙관적 락은 충돌을 감지하고, 비관적 락은 미리 잠금으로 충돌을 제어한다.**

<a name="q63"></a>
### Q63. [핵심 질문] Java의 Virtual Thread는 Race Condition을 없애주나요?

> "아닙니다. Virtual Thread는 많은 동시 작업을 효율적으로 처리하기 위한 경량 스레드이지만 공유 가변 상태에 대한 Race Condition은 여전히 발생할 수 있습니다."

**핵심 요약**

**Virtual Thread는 동시 작업의 효율성을 높이지만 공유 데이터의 경쟁 문제를 자동으로 해결하지는 않는다.**
