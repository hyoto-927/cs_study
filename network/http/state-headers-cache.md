## Stateless, Stateful, 쿠키와 세션

<a name="q1"></a>
### Q1. [대표 질문] HTTP의 Stateless 특성은 무엇이고 장단점은 무엇인가요?

> "Stateless(스테이트리스)는 HTTP가 이전 요청의 대화 상태를 프로토콜 차원에서 자동으로 유지하지 않는 특성입니다.
>
> 장점은 각 요청을 독립적으로 처리할 수 있어 서버 확장과 장애 대응에 유리하다는 점입니다.
>
> 단점은 요청마다 필요한 인증 정보 등을 전달하거나 별도의 상태 저장소에서 조회해야 할 수 있다는 점입니다."

**핵심 요약**

Stateless는 요청을 독립적으로 처리해 확장에 유리하지만 별도의 상태 관리가 필요할 수 있다.

<a name="q2"></a>
### Q2. Stateless가 서버 확장에 유리한 이유는 무엇인가요?

> "특정 서버가 이전 요청의 상태를 기억하지 않아도 요청을 처리할 수 있도록 설계하면 로드 밸런서가 여러 서버로 요청을 분산하기 쉽습니다.
>
> 예를 들어 첫 요청은 서버 A, 다음 요청은 서버 B가 처리하더라도 필요한 인증 정보를 요청이나 공통 저장소에서 확인할 수 있다면 정상 처리할 수 있습니다."

**핵심 요약**

Stateless는 특정 서버에 대한 상태 의존성을 줄여 수평 확장에 유리하다.

<a name="q3"></a>
### Q3. Stateful과 Stateless의 차이는 무엇인가요?

> "Stateful은 이전 상호작용의 상태를 유지하여 이후 요청 처리에 활용하는 방식이고, Stateless는 각 요청을 이전 요청의 대화 상태에 의존하지 않고 처리하는 방식입니다.
>
> Stateful은 연속적인 작업에 편리할 수 있지만 특정 서버에만 상태가 존재하면 확장과 장애 복구가 복잡해질 수 있습니다."

**핵심 요약**

Stateful은 이전 상태에 의존하고 Stateless는 요청을 독립적으로 처리한다.

<a name="q3-1"></a>
#### ↳ Q3-1. Stateful 방식이 필요한 상황도 있나요?

> "그렇습니다. 실시간 게임의 진행 상태나 장시간 유지되는 대화형 세션 등에서는 이전 상태를 계속 관리해야 할 수 있습니다.
>
> 다만 상태를 유지하는 서비스라고 해서 반드시 한 서버의 메모리에만 저장해야 하는 것은 아니며, 외부 저장소를 사용해 확장성을 확보할 수 있습니다."

**핵심 요약**

연속적인 작업에서는 Stateful 방식이 유용할 수 있고, 상태 저장 위치를 분리해 확장할 수도 있다.

<a name="q4"></a>
### Q4. Stateless인데 로그인 상태는 어떻게 유지하나요?

> "세션 기반 인증이나 토큰 기반 인증을 활용합니다.
>
> 세션 방식에서는 서버가 로그인 정보를 저장하고 클라이언트가 세션 ID를 전달하며, 토큰 방식에서는 클라이언트가 JWT 등의 인증 토큰을 전달하고 서버가 이를 검증할 수 있습니다."

**핵심 요약**

HTTP가 Stateless하더라도 세션 ID나 인증 토큰을 매 요청에 전달해 로그인 상태를 관리할 수 있다.

<a name="q4-1"></a>
#### ↳ Q4-1. 서버가 여러 대라면 세션은 어떻게 관리하나요?

> "서버별 메모리에만 세션이 있으면 요청이 다른 서버로 전달되었을 때 해당 세션을 찾지 못할 수 있습니다.
>
> Redis 같은 공유 세션 저장소를 사용하면 여러 서버가 동일한 세션 정보에 접근할 수 있습니다.
>
> 로드 밸런서의 Sticky Session을 사용할 수도 있지만 특정 서버에 대한 의존성이 생길 수 있습니다."

**핵심 요약**

여러 서버에서는 공유 세션 저장소나 Sticky Session으로 세션 접근 문제를 해결할 수 있다.

<a name="q4-2"></a>
#### ↳ Q4-2. JWT를 사용하면 무조건 Stateless한 구조가 되나요?

> "아닙니다. JWT의 서명과 만료 시간 등을 검증해 별도 세션 조회 없이 인증할 수는 있습니다.
>
> 하지만 로그아웃을 위한 토큰 차단 목록이나 Refresh Token 관리 등에 서버 저장소를 사용한다면 상태 관리가 여전히 필요할 수 있습니다.
>
> 따라서 JWT를 사용한다는 사실만으로 전체 시스템이 완전히 Stateless하다고 할 수는 없습니다."

**핵심 요약**

JWT를 사용하더라도 토큰 무효화나 갱신 관리에 서버 상태가 필요할 수 있다.

<a name="q5"></a>
### Q5. 쿠키와 세션의 차이는 무엇인가요?

> "쿠키와 세션의 가장 큰 차이는 데이터를 저장하고 관리하는 위치입니다.
>
> 쿠키는 클라이언트인 브라우저에 데이터를 저장하는 방식이고, 세션은 일반적으로 서버에서 사용자별 상태 정보를 저장하고 관리하는 방식입니다.
>
> 세션 방식에서는 서버가 사용자에게 세션 ID를 발급하고, 브라우저는 이를 쿠키에 저장해 요청마다 전달합니다. 서버는 전달받은 세션 ID로 사용자를 식별하고 세션 정보를 조회합니다.
>
> 따라서 쿠키는 클라이언트에 정보를 저장하고 전달하는 수단이고, 세션은 서버에서 사용자 상태를 유지하는 방식이라는 차이가 있습니다."

| 구분 | 쿠키 | 서버 측 세션 |
| --- | --- | --- |
| 저장 위치 | 클라이언트 | 서버 또는 공유 저장소 |
| 역할 | 데이터 저장·전송 | 사용자 상태 관리 |
| 대표 값 | 세션 ID, 사용자 설정 | 로그인 사용자 정보 |
| 관계 | 세션 ID 전달 가능 | 전달받은 ID로 상태 조회 |

**핵심 요약**

쿠키는 클라이언트에 저장되는 데이터이고 서버 측 세션은 사용자 상태를 서버에서 관리하는 방식이다.

<a name="q5-1"></a>
#### ↳ Q5-1. 쿠키에 비밀번호를 저장해도 되나요?

> "권장되지 않습니다. 쿠키는 클라이언트에 저장되므로 사용자나 공격자가 내용을 확인하거나 탈취할 위험이 있습니다.
>
> 비밀번호 자체를 저장하기보다는 적절히 보호된 세션 ID 등의 식별자를 사용하고, HttpOnly, Secure, SameSite와 같은 속성을 활용해야 합니다."

**핵심 요약**

쿠키에 비밀번호를 직접 저장하지 말고 안전한 세션 식별과 쿠키 보안 속성을 활용해야 한다.

<a name="q5-2"></a>
#### ↳ Q5-2. HttpOnly와 Secure의 차이는 무엇인가요?

> "HttpOnly는 브라우저 JavaScript가 해당 쿠키에 직접 접근하는 것을 제한하는 속성입니다.
>
> Secure는 쿠키가 일반적으로 HTTPS 같은 보안 연결에서만 전송되도록 제한하는 속성입니다.
>
> 두 속성은 목적이 다르므로 함께 사용하는 경우가 많습니다."

**핵심 요약**

HttpOnly는 JavaScript 접근 제한, Secure는 보안 연결을 통한 쿠키 전송 제한이다.

<a name="q5-3"></a>
#### ↳ Q5-3. [핵심 질문] SameSite는 무엇인가요?

> "SameSite(세임사이트)는 교차 사이트 요청에서 쿠키를 전송할지 제어하는 속성입니다.
>
> Strict, Lax, None 등의 값이 있으며 CSRF 위험을 줄이는 데 도움이 됩니다.
>
> 다만 SameSite만으로 모든 CSRF 위험이 해결되는 것은 아닙니다."

**핵심 요약**

SameSite는 교차 사이트 요청에서 쿠키 전송 범위를 제어한다.

<a name="section-02"></a>
## HTTP 헤더

<a name="q6"></a>
### Q6. [대표 질문] HTTP 헤더란 무엇인가요?

> "HTTP 헤더는 요청과 응답에 포함되는 메타데이터로, 콘텐츠 형식, 인증 정보, 캐시 정책, 요청 출처 등을 전달합니다.
>
> 대표적으로 Content-Type, Accept, Authorization, Cookie, Cache-Control, ETag, Location 등이 있습니다."

**핵심 요약**

HTTP 헤더는 요청과 응답을 처리하는 데 필요한 부가 정보를 전달한다.

<a name="q7"></a>
### Q7. Content-Type에는 어떤 값이 있나요?

> "대표적으로 JSON은 `application/json`, HTML은 `text/html`, 일반적인 HTML 폼 전송은 `application/x-www-form-urlencoded`, 파일을 포함하는 폼 전송은 `multipart/form-data`를 사용합니다."

| Content-Type | 사용 상황 |
| --- | --- |
| `application/json` | JSON API |
| `text/html` | HTML 문서 |
| `application/x-www-form-urlencoded` | 일반 폼 전송 |
| `multipart/form-data` | 파일 업로드 |
| `text/plain` | 텍스트 데이터 |

**핵심 요약**

Content-Type은 전송하는 메시지 본문의 형식을 나타낸다.

<a name="q8"></a>
### Q8. Content-Type과 Accept의 차이는 무엇인가요?

> "Content-Type은 현재 전송하는 본문의 미디어 타입을 나타내고, Accept는 클라이언트가 받아들일 수 있는 응답 미디어 타입을 나타냅니다.
>
> 즉, Content-Type은 보내는 데이터의 형식이고 Accept는 원하는 응답 형식입니다."

**핵심 요약**

Content-Type은 보내는 형식, Accept는 받고 싶은 형식이다.

<a name="q9"></a>
### Q9. Authorization 헤더에는 어떤 정보가 들어가나요?

> "Authorization 헤더에는 서버가 요청의 인증 정보를 확인하는 데 사용하는 자격 정보가 들어갑니다.
>
> 예를 들어 JWT 기반 인증에서는 `Authorization: Bearer <token>` 형태로 접근 토큰을 전송하고, 서버는 토큰의 서명과 만료 시간 등을 검증할 수 있습니다."

**핵심 요약**

Authorization 헤더는 요청자의 인증을 위한 자격 정보를 전달한다.

<a name="q10"></a>
### Q10. Host 헤더는 왜 필요한가요?

> "같은 IP 주소에서 여러 도메인을 서비스할 때 요청이 어떤 호스트를 대상으로 하는지 구분하기 위해 필요합니다.
>
> HTTP/1.1에서 Host 헤더는 필수이며 HTTP/2와 HTTP/3에서는 일반적으로 `:authority`를 사용합니다."

**핵심 요약**

Host는 요청 대상 도메인을 구분하는 데 사용된다.

<a name="q11"></a>
### Q11. Location 헤더는 언제 사용하나요?

> "Location 헤더는 3xx 응답에서 이동할 주소를 알려주거나 201 Created 응답에서 새로 생성된 자원의 주소를 알려줄 때 사용합니다."

**핵심 요약**

Location은 이동할 주소나 생성된 자원의 주소를 전달한다.

<a name="q12"></a>
### Q12. [핵심 질문] Cookie와 Set-Cookie의 차이는 무엇인가요?

> "Set-Cookie는 서버가 클라이언트에게 쿠키를 설정하도록 전달하는 응답 헤더이고, Cookie는 클라이언트가 저장된 쿠키를 서버에 전송하는 요청 헤더입니다."

**핵심 요약**

Set-Cookie는 쿠키 설정, Cookie는 쿠키 전송에 사용한다.

<a name="q13"></a>
### Q13. [핵심 질문] Origin 헤더는 무엇인가요?

> "Origin은 요청을 발생시킨 출처를 나타내는 헤더이며, 출처는 스킴, 호스트, 포트의 조합으로 구분합니다.
>
> 브라우저가 교차 출처 요청에 대한 접근을 제어하는 CORS에서 중요하게 사용됩니다."

**핵심 요약**

Origin은 요청 출처를 나타내며 CORS 처리에 활용된다.

<a name="section-03"></a>
## HTTP 캐시

<a name="q14"></a>
### Q14. [대표 질문] HTTP 캐시란 무엇이고 어떻게 동작하나요?

> "HTTP 캐시는 이전 HTTP 응답을 브라우저나 중간 캐시 등에 저장한 뒤 재사용하는 메커니즘입니다.
>
> Cache-Control 등의 정책에 따라 신선한 캐시를 재사용하거나, 만료된 캐시를 ETag 또는 Last-Modified로 재검증할 수 있습니다.
>
> 이를 통해 네트워크 요청과 데이터 전송 비용을 줄일 수 있습니다."

**핵심 요약**

HTTP 캐시는 이전 응답을 저장하고 재사용해 네트워크 비용과 응답 지연을 줄인다.

<a name="q15"></a>
### Q15. Cache-Control과 ETag의 차이는 무엇인가요?

> "Cache-Control은 캐시를 언제, 어떤 조건에서 저장하거나 재사용할지 지정하는 헤더입니다.
>
> ETag는 자원 표현의 버전을 식별하는 값으로, 클라이언트가 서버에 변경 여부를 재검증할 때 사용할 수 있습니다."

```
HTTP/1.1 200 OK
Cache-Control: max-age=60
ETag: "v1"
```

이후 재검증:

```
GET /products/10 HTTP/1.1
If-None-Match: "v1"
```

**핵심 요약**

Cache-Control은 캐시 정책, ETag는 변경 여부 검증에 사용한다.

<a name="q16"></a>
### Q16. 304 Not Modified는 캐시와 어떤 관계인가요?

> "클라이언트가 If-None-Match 등으로 조건부 요청을 보냈을 때 캐시된 자원이 변경되지 않았다면 서버가 304 Not Modified를 반환할 수 있습니다.
>
> 이때 본문을 새로 받지 않고 기존 캐시를 재사용할 수 있습니다."

**핵심 요약**

304는 자원이 변경되지 않았으므로 기존 캐시를 재사용할 수 있다는 의미이다.

<a name="q17"></a>
### Q17. no-cache와 no-store의 차이는 무엇인가요?

> "`no-cache`는 저장된 응답을 재사용하기 전에 서버에 재검증하도록 요구합니다.
>
> `no-store`는 캐시에 응답을 저장하지 않도록 요구합니다."

**핵심 요약**

no-cache는 재검증, no-store는 저장 금지이다.

<a name="q18"></a>
### Q18. [핵심 질문] 캐시의 Freshness란 무엇인가요?

> "Freshness(프레시니스, 신선도)는 캐시된 응답을 서버에 다시 확인하지 않고 재사용할 수 있는 상태를 의미합니다.
>
> `Cache-Control: max-age=60`처럼 신선도 유지 시간을 설정할 수 있습니다."

**핵심 요약**

Freshness는 캐시된 응답을 재검증 없이 사용해도 되는 상태이다.

<a name="q19"></a>
### Q19. [핵심 질문] ETag와 Last-Modified의 차이는 무엇인가요?

> "ETag는 자원 표현의 버전 식별자를 사용하고 Last-Modified는 마지막 수정 시간을 사용합니다.
>
> 각각 If-None-Match와 If-Modified-Since를 통해 조건부 재검증을 수행할 수 있습니다."

**핵심 요약**

ETag는 버전 식별자, Last-Modified는 수정 시간을 사용해 캐시를 검증한다.

<a name="q20"></a>
### Q20. HTTP 캐시와 Redis 캐시의 차이는 무엇인가요?

> "HTTP 캐시는 브라우저나 CDN 등에서 HTTP 응답을 저장하고 재사용하는 방식입니다.
>
> Redis 캐시는 애플리케이션이 자주 사용하는 데이터나 조회 결과를 Redis 저장소에 보관하는 방식입니다.
>
> HTTP 캐시는 네트워크 요청 및 전송 비용을 줄이는 데, Redis 캐시는 DB 조회나 반복 계산 등 서버 내부 처리 비용을 줄이는 데 주로 활용됩니다."

| 구분 | HTTP 캐시 | Redis 캐시 |
| --- | --- | --- |
| 저장 대상 | HTTP 응답 | 애플리케이션 데이터·조회 결과 등 |
| 위치 | 브라우저, 프록시, CDN | Redis 서버 |
| 주요 목적 | 네트워크 요청·전송 비용 감소 | DB 조회·계산 비용 감소 |
| 관리 방식 | HTTP 캐시 헤더 | 애플리케이션 로직, TTL 등 |

**핵심 요약**

HTTP 캐시는 응답 전송 비용을 줄이고 Redis 캐시는 서버 내부 데이터 처리 비용을 줄이는 데 주로 사용한다.

<a name="q21"></a>
### Q21. [핵심 질문] 캐시를 사용하면 항상 좋은가요?

> "아닙니다. 오래된 데이터를 반환할 수 있고, 민감한 정보를 부적절하게 캐시하면 정보 노출 위험이 있습니다.
>
> 따라서 데이터의 변경 빈도와 민감도, 캐시 만료와 재검증 정책을 함께 고려해야 합니다."

**핵심 요약**

캐시는 성능에 도움이 되지만 데이터 최신성과 보안을 고려해야 한다.
