<a name="section-01"></a>
## JVM (Java Virtual Machine)

<a name="q1"></a>
### Q1. JVM이란 무엇이며, 어떤 역할을 하나요?

> JVM은 Java 바이트 코드를 실행하는 가상 머신입니다.
>
> Java 소스 코드는 컴파일러에 의해 바이트 코드로 변환되고, JVM은 이를 인터프리터나 JIT 컴파일러를 통해 실행합니다.
>
> 또한 클래스 로딩, 메모리 관리, 가비지 컬렉션 등의 기능을 제공하며, 운영체제별 JVM을 통해 동일한 바이트코드를 여러 플랫폼에서 실행할 수 있게 합니다.

**핵심 요약:** JVM은 Java 바이트코드를 실행하고 런타임 환경을 관리하는 가상 머신이다.

<a name="q1-1"></a>
#### ↳ Q1-1. Java는 왜 플랫폼 독립적이라고 하나요?

> Java 소스 코드는 특정 운영체제의 기계어가 아니라 JVM이 이해할 수 있는 바이트 코드로 컴파일 됩니다.
>
> 각 운영체제에 맞는 JVM이 동일한 바이트코드를 실행할 수 있기 때문에 플랫폼 독립성을 가집니다.
>
> 다만 JVM 구현체 자체는 운영체제와 하드웨어 환경에 종속적입니다.

**핵심 요약:** Java 바이트 코드는 플랫폼 독립적이지만 JVM 구현체는 플랫폼에 종속적이다.

<a name="q1-2"></a>
#### ↳ Q1-2. JVM은 Java 언어만 실행할 수 있나요?

> 아닙니다. JVM은 Java 언어 자체가 아니라 JVM 바이트코드를 실행합니다.
>
> 따라서 Kotlin이나 Scala처럼 JVM 바이트코드로 컴파일되는 다른 프로그래밍 언어도 JVM에서 실행할 수 있습니다.

**핵심 요약:** JVM은 Java뿐 아니라 JVM 바이트코드로 컴파일되는 다른 언어도 실행할 수 있다.

<a name="q1-3"></a>
#### ↳ Q1-3. [심화 질문] JVM 없이 Java 프로그램을 실행할 수 있나요?

> 일반적인 Java 프로그램은 JVM을 통해 바이트코드를 실행합니다.
>
> 하지만 GraalVM Native Image와 같은 AOT 컴파일 기술을 사용하면 Java 애플리케이션을 네이티브 실행 파일로 변환할 수 있습니다.
>
> 이렇게 생성한 프로그램은 전통적인 JVM의 바이트코드 실행 방식 없이 실행할 수 있습니다.

**핵심 요약:** AOT 컴파일을 통해 Java 프로그램을 네이티브 실행 파일로 변환할 수 있다.

<a name="q2"></a>
### Q2. JDK, JRE, JVM의 차이는 무엇인가요?

> JVM은 Java 바이트코드를 실행하는 가상 머신입니다.
>
> JRE는 JVM과 Java 프로그램 실행에 필요한 라이브러리 등을 포함하는 런타임 환경입니다.
>
> JDK는 Java 프로그램의 개발과 실행에 필요한 컴파일러, 디버거 등의 개발 도구까지 포함하는 개발 키트입니다.
>
> 최신 Java 배포판에서는 별도의 JRE가 제공되지 않을 수도 있습니다.

**핵심 요약:** JVM은 바이트코드 실행을 위한 가상 머신, JRE는 실행 환경, JDK는 개발 도구까지 포함한 환경이다.

<a name="q2-1"></a>
#### ↳ Q2-1. Java 프로그램을 실행하려면 반드시 JDK가 필요한가요?

> 반드시 그렇지는 않습니다.
>
> Java 프로그램을 실행하려면 적절한 JVM과 런타임 라이브러리가 필요합니다.
>
> JDK는 컴파일과 디버깅 등의 개발 도구를 제공하지만, 실행 환경에서는 필요한 구성 요소만 포함한 런타임 이미지를 사용할 수도 있습니다.

**핵심 요약:** Java 프로그램 실행에는 적절한 런타임 환경이 필요하지만 전체 JDK가 반드시 필요한 것은 아니다.

<a name="q3"></a>
### Q3. Java 프로그램이 실행되는 과정을 설명해 주세요.

> Java 소스 코드는 javac 컴파일러를 통해 .class 바이트코드로 변환됩니다.
>
> 이후 JVM의 ClassLoader가 필요한 클래스를 로딩하고, Linking과 Initialization을 통해 실행할 수 있도록 준비합니다.
>
> Execution Engine은 바이트코드를 인터프리터로 실행하거나 JIT 컴파일러를 통해 네이티브 기계어로 변환하여 실행합니다.
>
> 실행 중 생성되는 객체는 주로 Heap에서 관리되며, 더 이상 도달할 수 없는 객체는 GC의 회수 대상이 됩니다.

**핵심 요약:** Java 소스 코드 → 바이트코드 → 클래스 로딩 → JVM 실행 엔진을 통한 실행.

<a name="q3-1"></a>
#### ↳ Q3-1. Java는 컴파일 언어인가요, 인터프리터 언어인가요?

> Java는 컴파일과 인터프리터 방식의 특성을 모두 가지고 있습니다.
>
> 먼저 Java 소스 코드를 바이트코드로 컴파일합니다.
>
> 이후 JVM은 인터프리터 방식으로 바이트코드를 실행할 수 있고, JIT 컴파일러를 통해 일부 코드를 네이티브 기계어로 변환하여 실행할 수도 있습니다.

**핵심 요약:** Java는 바이트코드로 컴파일한 뒤 JVM에서 인터프리터와 JIT 컴파일 방식으로 실행된다.

<a name="q3-2"></a>
#### ↳ Q3-2. Java 프로그램은 실행할 때마다 모든 코드를 기계어로 컴파일하나요?

> 아닙니다. JVM은 바이트코드를 인터프리터 방식으로 실행할 수 있으며, 자주 실행되는 코드 등을 JIT 컴파일러가 네이티브 기계어로 변환할 수 있습니다.
>
> 따라서 모든 메서드를 프로그램 시작 시점에 기계어로 컴파일하지는 않습니다.

**핵심 요약:** JVM은 모든 코드를 처음부터 기계어로 컴파일하는 것이 아니라 필요에 따라 JIT 컴파일을 수행한다.

<a name="q4"></a>
### Q4. JVM의 내부 구조에 대해 설명해 주세요.

> JVM은 크게 ClassLoader, Runtime Data Area, Execution Engine으로 구성됩니다.
>
> ClassLoader는 필요한 클래스를 로딩하고, Runtime Data Area는 객체와 메서드 실행 정보 등을 관리합니다.
>
> Execution Engine은 바이트코드를 해석하거나 JIT 컴파일을 통해 실행합니다.
>
> 또한 JVM은 GC를 통해 더 이상 필요하지 않은 객체의 메모리를 회수합니다.

**핵심 요약:** JVM은 클래스 로딩, 실행 데이터 관리, 바이트코드 실행을 담당하는 구성 요소로 이루어진다.

<a name="q5"></a>
### Q5. 인터프리터와 JIT 컴파일러의 차이는 무엇인가요?

> 인터프리터는 바이트코드 명령어를 실행하면서 해석하는 방식입니다.
>
> JIT 컴파일러는 실행 중 자주 사용되는 코드를 네이티브 기계어로 컴파일하여 이후 실행에서 재사용합니다.
>
> 인터프리터는 별도의 기계어 컴파일 과정 없이 실행을 시작할 수 있지만, 반복 실행 시 해석 비용이 발생할 수 있습니다.
>
> 반면 JIT는 컴파일 비용이 발생하지만 반복 실행 성능을 개선할 수 있습니다.

**핵심 요약:** 인터프리터는 실행하며 해석하고 JIT는 자주 실행되는 코드를 기계어로 컴파일한다.

<a name="q5-1"></a>
#### ↳ Q5-1. JIT 컴파일러가 있는데 인터프리터도 사용하는 이유는 무엇인가요?

> 모든 코드를 처음부터 기계어로 컴파일하면 컴파일에 많은 시간과 자원이 필요합니다.
>
> 따라서 인터프리터를 이용해 실행을 시작하고, 실행 빈도 등의 정보를 수집한 뒤 성능상 중요한 코드를 JIT 컴파일하여 최적화할 수 있습니다.

**핵심 요약:** 인터프리터는 초기 실행을 돕고 JIT는 반복 실행 성능을 최적화한다.

<a name="q5-2"></a>
#### ↳ Q5-2. JIT 컴파일러가 생성한 기계어는 어디에 저장되나요?

> HotSpot JVM에서는 JIT 컴파일러가 생성한 네이티브 기계어를 주로 Code Cache에 저장합니다.
>
> Code Cache는 컴파일된 코드가 재사용될 수 있도록 관리하는 메모리 영역입니다.
>
> Native Method Stack은 네이티브 메서드의 실행을 지원하는 영역이므로 Code Cache와 구분해야 합니다.

**핵심 요약:** HotSpot JVM의 JIT 컴파일 결과는 주로 Code Cache에 저장된다.

<a name="q5-3"></a>
#### ↳ Q5-3. [심화 질문] JVM은 왜 실행 초기에 느리고 시간이 지나면 빨라질 수 있나요?

> JVM은 실행 초기에 클래스 로딩, 검증, 초기화 등의 작업을 수행합니다.
>
> 또한 JIT 컴파일러가 실행 정보를 수집하고 코드를 최적화하는 데 비용이 발생합니다.
>
> 이후 최적화된 네이티브 코드가 사용되면 반복 실행 성능이 개선될 수 있습니다.

**핵심 요약:** JVM은 초기 준비 비용이 발생하지만 JIT 최적화로 반복 실행 성능이 개선될 수 있다.

<a name="q5-4"></a>
#### ↳ Q5-4. [심화 질문] JIT 컴파일러는 모든 코드를 최적화하나요?

> 반드시 그렇지는 않습니다.
>
> JIT 컴파일러는 실행 빈도와 성능 정보 등을 바탕으로 컴파일 및 최적화할 코드를 선택합니다.
>
> 실행 빈도가 낮은 코드는 인터프리터로 실행될 수 있으며, 이미 최적화한 코드도 실행 조건이 달라지면 최적화가 취소될 수 있습니다.

**핵심 요약:** JIT는 실행 정보를 바탕으로 성능상 중요한 코드를 선택적으로 최적화한다.

<a name="q5-5"></a>
#### ↳ Q5-5. [심화 질문] JIT 컴파일러와 AOT 컴파일러의 차이는 무엇인가요?

> JIT는 프로그램 실행 중 코드를 네이티브 기계어로 컴파일합니다.
>
> AOT는 프로그램을 실행하기 전에 미리 네이티브 코드로 컴파일합니다.
>
> JIT는 실제 실행 정보를 활용한 동적 최적화가 가능하고, AOT는 실행 시점의 컴파일 부담을 줄일 수 있다는 특징이 있습니다.

**핵심 요약:** JIT는 실행 중 컴파일하고 AOT는 실행 전에 컴파일한다.
