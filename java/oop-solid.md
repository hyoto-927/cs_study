<a name="section-01"></a>
## OOP (객체지향 기본과 4대 특성)

<a name="q1"></a>
### Q1. [핵심 질문] 객체지향 프로그래밍이란 무엇인가요?

> 객체지향 프로그래밍은 프로그램을 여러 객체의 협력으로 구성하는 프로그래밍 방식입니다. 각 객체는 자신의 상태와 그 상태를 다루는 행위를 가지며, 맡은 책임에 따라 다른 객체와 메시지를 주고받으며 전체 기능을 수행합니다. 이를 통해 관련된 데이터와 로직을 하나의 객체에 모으고, 객체 간 역할을 분리하여 변경에 유연한 구조를 만들 수 있습니다.

<a name="q1-1"></a>
#### ↳ Q1-1. 객체와 클래스의 차이는 무엇인가요?

> "클래스는 객체를 만들기 위한 설계도이고, 객체는 그 설계도로 메모리에 실제로 만들어진 실체(인스턴스)입니다. 클래스는 하나지만 그로부터 만들어진 객체는 각자 다른 상태값을 가질 수 있습니다."

<a name="q1-2"></a>
#### ↳ Q1-2. [핵심 질문] 객체지향의 4대 특성은 무엇인가요?

> 객체지향의 4대 특성은 캡슐화, 상속, 추상화, 다형성입니다.
> 캡슐화는 객체의 상태와 행위를 하나로 묶고 외부의 직접 접근을 제한해 객체 스스로 상태를 관리하도록 하는 것이고, 상속은 상위 클래스의 속성과 기능을 하위 클래스가 재사용하거나 확장하는 것입니다.
> 추상화는 복잡한 내부 구현은 숨기고 외부에 필요한 핵심 역할과 규약만 제공하는 것이며, 다형성은 하나의 상위 타입이나 인터페이스로 여러 실제 구현 객체를 동일한 방식으로 다룰 수 있게 하는 것입니다.

<a name="q1-3"></a>
#### ↳ Q1-3. 객체지향에서 가장 중요하다고 생각하는 특징은?

> "다형성이라고 생각합니다. 다른 특성들은 코드를 잘 정리하는 데 기여하지만, 변경에 유연한 구조를 실제로 만들어주는 것은 다형성입니다. 클라이언트가 구현이 아니라 추상 타입에 의존하게 되어, 새 구현을 추가해도 기존 코드를 고치지 않아도 됩니다."

<a name="q1-4"></a>
#### ↳ Q1-4. 객체지향적으로 설계한다는 것을 한 문장으로 설명한다면?

> 객체지향적으로 설계한다는 것은 객체마다 적절한 책임을 부여하고, 자신의 상태와 관련된 로직은 객체 내부에 캡슐화하며, 객체 간에는 구체 구현에 직접 의존하기보다 역할과 인터페이스를 통해 협력하도록 만들어 변경의 영향을 줄이는 것입니다.

<a name="q1-5"></a>
#### ↳ Q1-5. 객체 지향이 항상 좋은가요?

> "아닙니다. 간단한 스크립트나 데이터 파이프라인처럼 흐름이 선형적인 작업에서는 절차지향이 더 직관적이고 빠릅니다. 문제에 맞는 패러다임을 선택하는 것이 중요합니다."

<a name="q1-6"></a>
#### ↳ Q1-6. 결합도와 응집도를 설명해주세요.

> "결합도는 서로 다른 클래스나 모듈이 얼마나 강하게 의존하는지, 응집도는 한 클래스 내부 요소들이 하나의 책임을 중심으로 얼마나 밀접하게 모여 있는지를 의미합니다. 좋은 설계는 높은 응집도와 낮은 결합도를 지향합니다. 다만 의존성 자체를 없애는 것이 목표는 아니고, 필요한 역할과 계약에만 의존하도록 만드는 것이 핵심입니다."

<a name="section-02"></a>
### 캡슐화

<a name="q2"></a>
#### Q2. [핵심 질문] 캡슐화와 정보 은닉이 중요한 이유와, Java에서 어떻게 구현하나요?

> "외부에서 내부 데이터에 직접 접근해 값을 바꾸면 객체가 스스로 정합성을 보장할 수 없기 때문입니다. Java에서는 필드를 private으로 선언해 직접 접근을 차단하고, 비즈니스 규칙이 담긴 public 메서드를 통해서만 상태를 변경하게 합니다. 단순히 필드를 숨기는 것을 넘어, 객체가 자신의 상태 변경 규칙을 직접 관리하게 만드는 것이 캡슐화의 본질입니다."

<a name="q2-1"></a>
##### ↳ Q2-1. [핵심 질문] private 필드에 getter/setter를 만들면 캡슐화가 된 것인가요?

> "반드시 그렇지는 않습니다. 모든 상태를 setter로 자유롭게 바꿀 수 있다면 외부가 사실상 직접 제어하는 것과 다르지 않습니다. 핵심은 상태를 숨기는 것보다 상태 변경의 책임을 객체가 갖는 것입니다. `setBalance()`보다 검증 규칙이 포함된 `deposit()`, `withdraw()`를 제공하는 것이 적절합니다."

<a name="q2-2"></a>
##### ↳ Q2-2. 캡슐화와 추상화의 차이는?

> "캡슐화는 '어떻게 구현했는지를 감추는 것'(정보 은닉)이고, 추상화는 '무엇을 할 수 있는지를 정의하는 것'(인터페이스 설계)입니다. 캡슐화는 구현 쪽, 추상화는 설계 쪽의 관심사입니다."

<a name="section-03"></a>
### 상속과 합성

<a name="q3"></a>
#### Q3. 상속을 사용하는 이유는 무엇인가요?

> "부모와 자식 사이에 타입 관계를 만들고 공통 상태나 동작을 공유하기 위해서입니다. 다만 단순한 코드 재사용만을 위해 상속하면 자식이 부모 구현에 강하게 결합되므로, 자식이 부모 타입으로 자연스럽게 대체될 수 있는 is-a 관계가 실제로 존재하는지 먼저 판단해야 합니다."

<a name="q3-1"></a>
##### ↳ Q3-1. [핵심 질문] 상속보다 합성(Composition)을 권장하는 이유는?

> 상속은 부모와 자식의 관계가 강하게 결합되어 부모의 구현 변경이 자식에게 영향을 줄 수 있고, 계층이 깊어질수록 구조를 이해하고 변경하기 어려워질 수 있습니다. 반면 합성은 다른 객체를 필드로 가지고 필요한 기능만 위임하므로 결합도를 낮출 수 있고, 인터페이스와 함께 사용하면 구현체를 쉽게 교체할 수 있습니다. 그래서 명확한 is-a 관계가 아니라면 상속보다 합성을 우선하는 것이 일반적인 설계 원칙입니다.

<a name="q3-2"></a>
##### ↳ Q3-2. 상속을 쓰면 안 되는 상황을 구체적으로 들어주세요.

> "단순히 코드를 재사용하고 싶어서 상속하는 경우입니다. Stack이 ArrayList를 상속하면 Stack에 어울리지 않는 `get(index)`나 `add(index, item)`까지 노출되어 LIFO 규칙이 깨질 수 있습니다."

LIFO 마지막에 들어온 것이 가장 먼저 나온다

<a name="q3-3"></a>
##### ↳ Q3-3. 합성을 쓰면 상속의 장점을 잃는 것 아닌가요?

> "코드 재사용은 위임으로 동일하게 달성할 수 있습니다. 상속의 고유한 장점은 다형성인데, 이는 인터페이스 구현으로 대체 가능합니다. '인터페이스로 타입을 정의하고 구현은 합성으로 재사용'하는 조합이 실무의 기본 패턴입니다."

<a name="section-04"></a>
### 추상 클래스와 인터페이스

<a name="q4"></a>
#### Q4. [핵심 질문] 추상 클래스와 인터페이스의 차이를 설명해주세요.

> 추상 클래스는 관련 있는 클래스들이 공통 상태와 공통 구현을 공유하는 타입 계층을 만들 때 적합하고, 일반 필드와 생성자, 구현 메서드를 가질 수 있습니다. 반면 인터페이스는 객체가 어떤 역할과 기능을 제공해야 하는지에 대한 규약을 정의하는 데 적합하며, 서로 다른 클래스 계층에서도 같은 인터페이스를 구현할 수 있고 여러 인터페이스를 동시에 구현할 수도 있습니다. 따라서 공통 상태와 기본 구현의 공유가 중요하면 추상 클래스를, 구현체 간 결합도를 낮추고 동일한 역할로 다루는 것이 중요하면 인터페이스를 선택합니다.

**추상 클래스 = “같은 계열끼리 공통된 것 공유”**

**인터페이스 = “어떤 역할을 할 수 있는지 약속”**

<a name="q4-1"></a>
##### ↳ Q4-1. [핵심 질문] 인터페이스를 사용하면 왜 결합도가 낮아지나요?

> 인터페이스를 사용하면 사용하는 쪽이 역할과 계약에 의존할 수 있기 때문에 결합도를 낮출 수 있습니다. 예를 들어 Service가 특정 Repository 구현체를 직접 참조하면 구현체가 변경될 때 Service도 영향을 받을 수 있지만, Repository 인터페이스에 의존하면 같은 계약을 구현한 다른 구현체로 교체해도 Service 코드는 변경하지 않아도 됩니다.

<a name="q4-2"></a>
##### ↳ Q4-2. 모든 클래스에 인터페이스를 만드는 것이 좋은 설계인가요?

> "아닙니다. 인터페이스도 추상화라 비용이 있습니다. 구현체가 하나뿐이고 교체 가능성도 낮다면 오히려 구조만 복잡해집니다. 여러 구현체가 존재하거나, 구현 교체 가능성이 높거나, 외부 시스템과의 경계를 분리해야 할 때 사용하는 것이 의미 있습니다."

<a name="section-05"></a>
## 다형성

<a name="q5"></a>
### Q5. [핵심 질문] 다형성이란 무엇이며, '구현의 분리'는 어떤 이점이 있나요?

> "다형성은 하나의 상위 타입이나 인터페이스를 통해 여러 종류의 실제 객체를 동일한 방식으로 다룰 수 있는 성질입니다.  이렇게 역할과 구현을 분리하면 새로운 구현체를 추가하거나 교체할 때 기존 코드에 미치는 영향을 줄일 수 있습니다."

<a name="q5-1"></a>
#### ↳ Q5-1. [핵심 질문] 객체지향 설계에서 다형성이 왜 중요한가요?

> "사용하는 코드와 구체 구현을 분리할 수 있게 해주기 때문입니다. 이를 통해 구현체의 추가나 교체에 유연한 구조를 만들 수 있으며, OCP와 DIP 같은 객체지향 설계 원칙을 적용하는 중요한 기반이 됩니다. DI 역시 이러한 구조에서 구현체를 외부에서 주입하는 방식으로 활용할 수 있습니다.”

<a name="q6"></a>
### Q6. 다형성이 없으면 어떤 문제가 생기나요?

> "구현 타입마다 `if-else`나 `switch`로 분기하는 코드가 늘어날 수 있고, 새로운 타입이 추가될 때 기존 분기 코드를 계속 수정해야 할 수 있습니다. 그 결과 코드의 결합도가 높아지고 복잡성이 증가하며, 확장과 테스트, 유지보수가 어려워질 수 있습니다."

<a name="q7"></a>
### Q7. [핵심 질문] 오버로딩과 오버라이딩의 차이는?

> "오버로딩은 같은 이름의 메서드를 매개변수의 타입, 개수, 순서를 다르게 정의하는 것으로 어떤 메서드를 호출할지가 컴파일 시점에 결정됩니다. 오버라이딩은 상속이나 인터페이스 구현 관계에서 상위 타입의 메서드를 하위 타입이 재정의하는 것이며, 실제 호출할 구현은 런타임의 객체 타입에 따라 결정될 수 있습니다. 런타임 다형성과 직접 연결되는 것은 오버라이딩입니다.”

<a name="q7-1"></a>
#### ↳ Q7-1. 오버라이딩할 때 지켜야 할 규칙이 있나요?

> "메서드 이름과 매개변수 목록이 같아야 하며, 반환 타입은 같거나 부모 메서드보다 더 구체적인 참조 타입인 공변 반환 타입을 사용할 수 있습니다. 접근 제어자는 부모보다 좁아질 수 없고, Checked Exception은 부모가 선언한 범위보다 더 넓게 선언할 수 없습니다.”

<a name="q7-2"></a>
#### ↳ Q7-2. static 메서드도 오버라이딩이 되나요?

> "아닙니다. `static` 메서드는 객체가 아니라 클래스에 속하므로 런타임 다형성의 대상이 아닙니다. 자식 클래스에 같은 형태의 `static` 메서드를 선언하면 오버라이딩이 아니라 메서드 숨김(method hiding)이 발생하며, 참조 변수의 선언 타입을 기준으로 호출될 메서드가 결정됩니다."

<a name="q8"></a>
### Q8. [핵심 질문] `Animal animal = new Dog()`에서 Animal과 Dog는 각각 무엇인가요?

> "`Animal`은 참조 변수의 선언 타입이고, `Dog`는 실제 생성된 객체의 타입입니다. 컴파일 시점에는 `Animal` 타입을 기준으로 접근 가능한 멤버를 검사하고, 오버라이딩된 인스턴스 메서드는 런타임에 실제 객체인 `Dog`의 구현이 실행됩니다. 선언 타입과 실제 객체 타입을 다르게 둘 수 있다는 점이 Java 다형성의 핵심입니다."

<a name="q8-1"></a>
#### ↳ Q8-1. [핵심 질문] 동적 바인딩(동적 디스패치)이란?

> ""오버라이딩된 인스턴스 메서드를 호출할 때 어떤 구현을 실행할지를 컴파일 시점이 아니라 런타임의 실제 객체 타입을 기준으로 결정하는 것입니다. 이를 통해 같은 상위 타입의 참조로 서로 다른 객체의 동작을 실행할 수 있습니다.”

<a name="q9"></a>
### Q9. [핵심 질문] 업캐스팅이란 무엇이고, 왜 안전한가요?

> "업캐스팅은 하위 클래스 객체를 상위 클래스나 인터페이스 타입의 참조로 다루는 것입니다. 하위 타입의 객체는 상위 타입이 정의한 기능을 만족하므로 상위 타입의 관점에서 사용하는 것은 타입상 안전하며, Java에서는 명시적인 형 변환 없이 자동으로 허용됩니다.”

<a name="q9-1"></a>
#### ↳ Q9-1. [핵심 질문] 다운캐스팅은 무엇이고 왜 위험한가요?

> "다운캐스팅은 상위 타입의 참조를 더 구체적인 하위 타입으로 변환하는 것입니다. 명시적 캐스팅이 필요하며, 참조하고 있는 실제 객체가 해당 하위 타입과 호환되지 않으면 `ClassCastException`이 발생합니다. 따라서 필요한 경우 `instanceof` 등을 통해 실제 타입을 확인해야 합니다."

<a name="q9-2"></a>
#### ↳ Q9-2. [핵심 질문] 다운캐스팅을 자주 쓰는 구조에는 어떤 문제가 있나요?

> "상위 타입으로 객체를 받은 뒤 계속 실제 타입을 확인하고 다운캐스팅해야 한다면, 상위 타입의 공통 계약이 충분하지 않거나 다형성을 제대로 활용하지 못하고 있다는 신호일 수 있습니다. 가능하다면 필요한 행위를 상위 타입이나 인터페이스의 메서드로 정의하고 각 구현체가 오버라이딩하도록 만들어 사용하는 코드가 구체 타입을 알지 않아도 동작하도록 설계하는 것이 더 유연합니다.”

<a name="q10"></a>
### Q10. [핵심 질문] 상속을 통한 다형성과 인터페이스를 통한 다형성 중 왜 인터페이스를 권장하나요?

> "클래스 상속은 부모의 상태와 구현을 함께 물려받기 때문에 부모와 자식 사이의 결합이 강해질 수 있고 Java에서는 단일 클래스 상속만 가능합니다. 반면 인터페이스는 주로 역할과 계약을 정의하므로 구현 세부사항과의 의존을 줄일 수 있고, 하나의 클래스가 여러 인터페이스를 구현할 수도 있습니다. 따라서 공통 구현을 물려받는 것이 목적이 아니라 역할을 추상화하고 여러 구현체를 교체 가능하게 만들고 싶을 때 인터페이스가 더 적합한 경우가 많습니다.”

<a name="q11"></a>
### Q11. [핵심 질문] 다형성이 개방폐쇄 원칙을 만족시키는 방법은?

> "클라이언트 코드가 구체 클래스가 아니라 인터페이스나 추상 타입에 의존하도록 만들면, 새로운 기능이 필요할 때 기존 클라이언트의 분기 로직을 계속 수정하기보다 새로운 구현체를 추가하는 방식으로 확장할 수 있습니다. 이를 통해 기존 코드의 변경 범위를 줄이면서 기능을 확장할 수 있습니다.”

---

<a name="section-06"></a>
## SOLID

<a name="q12"></a>
### Q12. [핵심 질문] SOLID의 5가지 원칙을 설명해주세요.

> "객체지향 시스템에서 변경의 영향 범위를 줄이고 의존성을 안정적으로 관리하기 위한 다섯 가지 설계 원칙입니다. SRP는 책임을 나누고, OCP는 기존 코드를 덜 고치면서 확장하고, LSP는 자식이 부모의 약속을 지키고, ISP는 인터페이스를 필요한 만큼만 나누고, DIP는 구현이 아니라 추상화에 의존하는 원칙입니다.

<a name="q12-1"></a>
#### ↳ Q12-1. SOLID 중 가장 중요한 원칙은?

> "하나만 고르면 OCP입니다. '확장에 열려있고 수정에 닫혀있다'가 유지보수 가능한 설계의 핵심 목표이고, 나머지 원칙은 OCP를 지키기 위한 수단이라고 볼 수 있습니다."

<a name="q12-2"></a>
#### ↳ Q12-2. SOLID 원칙들은 서로 어떤 관계인가요?

> "OCP가 목표이고 나머지가 수단입니다. SRP로 변경 이유를 분리하고, ISP로 인터페이스를 잘게 나누고, DIP로 추상화에 의존하게 만들면 결과적으로 확장에 열리고 수정에 닫힌 구조가 됩니다. LSP는 그 다형성이 안전하게 동작하도록 보장하는 전제 조건입니다."

<a name="q12-3"></a>
#### ↳ Q12-3. 실무에서 SOLID를 전부 지켜야 하나요?

> "원칙을 알되 상황에 맞게 적용해야 합니다. 소규모 프로젝트에서 모든 원칙을 엄격히 지키면 오히려 과도한 추상화로 복잡해집니다. 코드가 커지고 변경이 잦아지는 시점에 점진적으로 적용하는 것이 현실적입니다."

---

<a name="section-07"></a>
### SRP (단일 책임 원칙)

<a name="q13"></a>
#### Q13. [핵심 질문] SRP에서 말하는 '책임'이란 무엇이며, 책임이 너무 많으면 어떤 문제가 생기나요?

> "'변경의 이유가 하나'라는 뜻입니다. 한 클래스가 주문 정책 계산, DB 저장, 이메일 전송을 모두 담당한다면 각각 다른 이유로 변경되므로 책임이 섞여 있는 것입니다. 책임이 많아지면 서로 다른 이유로 같은 클래스를 자주 수정하게 되어 변경 충돌이 잦아지고, 한 부분을 고쳤는데 무관한 기능이 깨지며, 테스트 범위도 불필요하게 커집니다."

<a name="q13-1"></a>
##### ↳ Q13-1. [핵심 질문] 책임을 무조건 '하나의 기능'이라고 보면 될까요?

> "아닙니다. 기능 단위로 쪼개면 메서드 하나짜리 클래스가 양산되어 오히려 복잡해집니다. 기준은 기능 개수가 아니라 '변경을 요구하는 주체(액터)가 누구인가'입니다. 회계팀 요구로 바뀌는 로직과 인사팀 요구로 바뀌는 로직이 한 클래스에 있다면 기능이 하나처럼 보여도 분리 대상입니다."

<a name="q13-2"></a>
##### ↳ Q13-2. Controller, Service, Repository를 나누는 이유는?

> "각 계층이 서로 다른 책임과 변경 이유를 갖기 때문입니다. Controller는 HTTP 요청·응답, Service는 비즈니스 흐름과 객체 간 협력 조정, Repository는 데이터 저장·조회를 담당합니다. 변경 이유를 분리하면 특정 계층의 변경이 다른 계층으로 번지는 것을 줄일 수 있습니다."

<a name="q13-3"></a>
##### ↳ Q13-3. 모든 비즈니스 로직을 Service에 작성하는 것이 좋은가요?

> "아닙니다. 개별 객체가 자신의 상태로 판단할 수 있는 규칙은 그 객체가 책임지는 것이 자연스럽고, 여러 도메인 객체나 외부 시스템을 조합하는 유스케이스는 Service가 담당합니다. 모든 로직을 Service에 모으면 Service가 비대해지고 도메인 객체는 단순 데이터 저장소로 전락합니다."

---

<a name="section-08"></a>
### OCP (개방-폐쇄 원칙)

<a name="q14"></a>
#### Q14. [핵심 질문] OCP는 실제로 어떻게 구현하나요?

> "추상화와 다형성을 이용합니다. 결제 수단이 늘어날 때마다 Service의 조건문을 고치는 대신 `Payment` 인터페이스를 두고, 새 결제 방식은 구현체를 추가하기만 하면 기존 코드는 수정하지 않습니다."

<a name="q14-1"></a>
##### ↳ Q14-1. OCP를 만족하려면 무조건 인터페이스를 써야 하나요?

> "아닙니다. 핵심은 인터페이스 자체가 아니라 변경되는 부분과 안정적인 부분을 적절히 분리하는 것입니다. 인터페이스가 있어도 기능 추가 때마다 기존 조건문을 수정해야 한다면 실질적으로 OCP의 이점을 얻지 못합니다."

<a name="q14-2"></a>
##### ↳ Q14-2. 템플릿 메서드 패턴은 상속 구조를 어떻게 활용해 OCP를 달성하나요?

> "상위 추상 클래스가 전체 알고리즘의 뼈대를 final 메서드로 고정하고, 변하는 부분만 추상 메서드로 남깁니다. 하위 클래스는 그 부분만 구현하면 되므로, 새 변형이 필요할 때 상위 클래스는 전혀 수정하지 않고 하위 클래스만 추가하면 됩니다. 뼈대는 수정에 닫히고 세부 단계는 확장에 열리는 구조입니다."

---

<a name="section-09"></a>
### LSP (리스코프 치환 원칙)

<a name="q15"></a>
#### Q15. LSP를 설명해주세요.

> "하위 타입 객체가 상위 타입이 사용되는 위치를 대체하더라도 프로그램이 기대하던 동작이 깨지지 않아야 한다는 원칙입니다. 문법적으로 대입이 가능한 것만으로는 부족하고, 하위 타입도 상위 타입이 보장하는 의미와 계약을 유지해야 합니다."

<a name="q15-1"></a>
##### ↳ Q15-1. LSP를 위반하는 대표적 예시는?

> "정사각형-직사각형 문제입니다. `Rectangle`을 상속한 `Square`에서 `setWidth()`를 호출하면 height도 같이 바뀌어, `Rectangle` 타입으로 사용할 때 예상과 다르게 동작합니다."

<a name="q15-2"></a>
##### ↳ Q15-2. LSP를 위반하면 구체적으로 무슨 문제가 생기나요?

> "사용하는 코드가 특정 자식 타입을 별도로 검사하거나 예외 처리해야 합니다. 결국 다형성의 이점이 사라지면서 OCP도 함께 무너집니다."

---

<a name="section-10"></a>
### ISP (인터페이스 분리 원칙)

<a name="q16"></a>
#### Q16. ISP를 설명해주세요.

> "하나의 거대한 인터페이스에 모든 기능을 넣기보다, 클라이언트가 실제로 필요한 기능만 의존하도록 인터페이스를 분리하자는 원칙입니다. 인터페이스는 제공자 관점이 아니라 사용하는 클라이언트의 요구를 기준으로 적절한 크기로 나누는 것이 중요합니다."

<a name="q16-1"></a>
##### ↳ Q16-1. ISP를 위반한 인터페이스의 예를 들어주세요.

> "하나의 `Worker` 인터페이스에 `work()`와 `eat()`이 함께 있으면, 식사가 필요 없는 로봇 구현체도 `eat()`을 강제로 구현해야 합니다. 쓰지 않는 메서드를 빈 구현이나 예외 던지기로 채우게 되면 ISP 위반 신호입니다."

<a name="q16-2"></a>
##### ↳ Q16-2. ISP와 SRP의 차이는?

> "SRP는 클래스가 하나의 책임만 가지라는 것(구현 쪽)이고, ISP는 인터페이스가 사용하지 않는 메서드를 강제하지 말라는 것(인터페이스 쪽)입니다. SRP는 클래스 분리, ISP는 인터페이스 분리에 초점이 있습니다."

---

<a name="section-11"></a>
### DIP (의존성 역전 원칙)

<a name="q17"></a>
#### Q17. [핵심 질문] DIP를 설명해주세요.

> DIP는 구체적인 구현 클래스에 직접 의존하지 않고 인터페이스 같은 추상화에 의존하도록 설계하는 원칙입니다. 예를 들어 Service가 특정 Repository 구현체를 직접 사용하지 않고 Repository 인터페이스에 의존하면, 실제 구현체가 바뀌어도 Service에 미치는 영향을 줄일 수 있습니다.

<a name="q17-1"></a>
##### ↳ Q17-1. [핵심 질문] 왜 '역전'이라고 하나요?

> "일반적인 의존 방향은 상위 모듈이 하위 모듈을 직접 호출하는 형태입니다. DIP를 적용하면 상위 모듈이 인터페이스를 정의하고 하위 모듈이 그것을 구현하게 되어, 하위가 상위의 규약에 맞추게 됩니다. '상위가 하위에 맞추던' 방향이 '하위가 상위에 맞추는' 방향으로 뒤집히기 때문에 역전이라고 합니다."

<a name="q17-2"></a>
##### ↳ Q17-2. OCP와 DIP는 어떤 관계인가요?

> "DIP로 구체 구현 대신 추상화에 의존하게 되면 구현체 교체와 추가가 쉬워지고, 그 결과 새 구현을 추가할 때 기존 고수준 코드를 수정할 필요가 줄어듭니다. 즉 DIP가 의존 방향을 바꾸고, OCP는 그 구조를 이용해 변경 없는 확장을 실현합니다."

---

<a name="section-12"></a>
## IoC / DI / Spring 적용

<a name="q18"></a>
### Q18. [핵심 질문] IoC와 DI란 무엇인가요?

> "IoC는 객체 생성과 의존 관계를 제어하는 주체가 객체 자신에서 외부(컨테이너)로 이동하는 것입니다. DI는 객체가 사용할 의존 객체를 직접 생성하지 않고 외부에서 전달받는 방식으로, IoC를 구현하는 대표적인 방법입니다. 핵심은 객체 생성 책임과 사용 책임을 분리하는 것입니다."

<a name="q18-1"></a>
#### ↳ Q18-1. [핵심 질문] Spring Bean이란 무엇인가요?

> "Spring IoC Container가 생성하고 관리하는 Java 객체입니다. 특별한 객체가 아니라 일반 Java 객체지만, 개발자 대신 Container가 생성·의존성 연결·생명주기 관리를 담당한다는 차이가 있습니다."

<a name="q19"></a>
### Q19. [핵심 질문] DIP와 DI의 차이는 무엇인가요?

> "DIP는 '무엇에 의존해야 하는가'에 대한 설계 원칙이고, DI는 '그 의존 객체를 어떻게 전달할 것인가'에 대한 구현 방식입니다. 관련은 있지만 같은 개념은 아닙니다."

<a name="q19-1"></a>
#### ↳ Q19-1. [핵심 질문] DI를 사용하면 무조건 DIP를 만족하나요?

> "아닙니다. 구체 클래스끼리 직접 의존하는 상태에서도 생성자 주입은 쓸 수 있습니다. 또한 인터페이스를 쓰더라도 그 인터페이스를 하위 모듈이 소유하고 있다면 진정한 역전으로 보기 어렵습니다. 상위 모듈이 필요로 하는 규약을 상위 쪽에서 정의할 때 DIP가 제대로 성립합니다."

<a name="q20"></a>
### Q20. [핵심 질문] 생성자 주입을 선호하는 이유는 무엇인가요?

> "객체 생성 시점에 필요한 의존성을 모두 전달받으므로 필수 의존성이 명확히 드러나고, 불완전한 상태의 객체가 만들어질 가능성이 줄어듭니다. 참조 필드를 final로 선언하면 초기화 후 참조를 재할당할 수 없습니다. 참조하는 객체의 상태는 바뀔 수 있고, 테스트에서도 Spring Container 없이 원하는 구현체를 직접 전달할 수 있습니다."

<a name="q21"></a>
### Q21. Spring에서 SOLID가 적용된 사례를 들어주세요.

> "Service와 Repository를 인터페이스로 선언하고 구현체를 주입받는 구조가 DIP와 OCP의 실현입니다. 구현체를 교체해도 상위 계층 코드는 전혀 바뀌지 않고, 테스트 시에는 Mock 구현체를 주입할 수 있습니다."
