<a name="section-01"></a>
## Transaction(트랜잭션)

<a name="q1"></a>
### Q1. [대표 질문] 트랜잭션이란 무엇인가요?

> "여러 DB 작업을 하나의 논리적 단위로 묶어서 전부 성공(Commit)하거나 전부 취소(Rollback)되게 보장하는 작업 단위입니다. 계좌이체에서 출금과 입금은 반드시 함께 성공하거나 함께 실패해야 하는데, 트랜잭션이 이런 불완전한 중간 상태를 원천적으로 방지합니다."

<a name="q1-1"></a>
#### ↳ Q1-1. Commit과 Rollback의 차이는?

> "Commit은 트랜잭션에서 수행한 변경을 최종 확정하는 것이고, Rollback은 변경을 취소해 이전 상태로 되돌리는 것입니다. 여러 SQL이 묶여 있어도 Commit 전까지는 하나의 작업 단위로 관리됩니다."

<a name="q2"></a>
### Q2. 트랜잭션 중간에 장애가 나면 어떻게 되나요?

> "커밋 전에 DB가 중단되면 복구 후 해당 트랜잭션의 일부 변경만 커밋된 상태로 노출되지 않습니다. InnoDB는 미완료 트랜잭션을 되돌리는 데 undo를 사용합니다. 문장 하나의 실패가 전체 트랜잭션을 중단시키는지는 오류 종류와 DBMS에 따라 달라집니다."

<a name="q3"></a>
### Q3. Commit된 트랜잭션도 복구할 수 있나요?

> Commit이 끝난 트랜잭션을 나중에 Rollback할 수는 없습니다. 하지만 Commit 직후 DB가 다운되어 실제 데이터 파일에 변경 내용이 완전히 반영되지 않았더라도, DB는 Redo Log를 이용해 그 Commit 결과를 다시 적용할 수 있습니다. 이것이 지속성(Durability)입니다.

<a name="q4"></a>
### Q4. Savepoint는 무엇이고 언제 쓰나요?

> "트랜잭션 내부에 중간 지점을 표시해두고, 문제가 생기면 트랜잭션 전체가 아니라 그 지점까지만 부분 롤백할 수 있게 하는 기능입니다. 여러 단계로 이루어진 배치 작업에서 일부만 되돌리고 싶을 때 유용합니다."

<a name="q4-1"></a>
#### ↳ Q4-1. MVCC와 Savepoint의 차이는?

> "목적이 완전히 다릅니다. Savepoint는 한 트랜잭션 '안에서' 부분 롤백을 하기 위한 되돌리기 지점이고, MVCC는 '여러 트랜잭션 사이'에서 읽기와 쓰기가 충돌하지 않도록 데이터의 여러 버전을 유지하는 동시성 제어 기법입니다."

<a name="q5"></a>
### Q5. [핵심 질문] 트랜잭션 범위를 어떻게 잡아야 하나요?

> "반드시 함께 성공하거나 실패해야 하는 작업까지만 묶는 것이 기준입니다. 너무 작으면 부분 Commit으로 정합성이 깨지고, 너무 크면 Connection과 Lock 점유 시간이 늘어나 동시성이 떨어집니다. 특히 외부 API 호출이나 파일 I/O는 트랜잭션 밖으로 빼는 것이 원칙입니다."

<a name="q5-1"></a>
#### ↳ Q5-1. [핵심 질문] 트랜잭션을 짧게 유지해야 하는 이유는? (Long Transaction의 문제)

> "Connection과 Lock을 오래 점유해서 다른 트랜잭션의 대기가 늘어나고, Connection Pool이 고갈될 수 있습니다. MVCC 환경에서는 오래된 데이터 버전을 계속 유지해야 해서 정리(VACUUM/Purge)가 밀리고 용량도 부풀 수 있습니다."

<a name="q5-2"></a>
#### ↳ Q5-2. 트랜잭션 안에서 외부 API를 호출하면 왜 문제가 되나요?

> "외부 응답이 늦으면 그동안 DB Connection과 Lock이 계속 유지됩니다. 또한 DB가 Rollback되어도 이미 외부 시스템에서 처리된 작업은 되돌아가지 않기 때문에, 하나의 로컬 트랜잭션만으로 두 시스템의 원자성을 보장할 수 없습니다."

<a name="q6"></a>
### Q6. [핵심 질문] Spring에서 @Transactional의 Rollback 기준은?

> "기본적으로 RuntimeException(Unchecked)과 Error만 자동 Rollback되고, 기본 규칙에서 체크 예외 자체는 롤백 사유가 되지 않습니다. 이미 rollback-only인 경우 등에는 커밋되지 않습니다. 변경하려면 `rollbackFor = Exception.class`로 명시해야 합니다."

<a name="q6-1"></a>
#### ↳ Q6-1. 트랜잭션 메서드 안에서 예외를 catch하면 어떤 문제가 생기나요?

> "예외를 내부에서 처리하고 정상 반환하면 해당 예외는 Spring의 경계까지 전파되지 않습니다. 트랜잭션이 rollback-only로 표시되지 않았다면 커밋될 수 있습니다. 비즈니스적으로는 실패했는데 데이터는 반영되는 상황이 생기므로, 예외 처리 위치와 Rollback 정책을 함께 고려해야 합니다."

<a name="q7"></a>
### Q7. 읽기 전용 트랜잭션(readOnly=true)은 왜 쓰나요?

> Spring의 readOnly는 트랜잭션 매니저와 드라이버에 전달하는 읽기 전용 힌트입니다. Hibernate는 자동 플러시나 변경 감지 비용을 줄일 수 있습니다. 쓰기 차단 여부는 DB 및 설정에 달려 있으므로 권한 통제 수단으로 사용하지 않습니다.

<a name="q8"></a>
### Q8. 트랜잭션 전파(Propagation)란 무엇인가요?

같은 질문의 다른 회차 답변 · [aop-proxy-transactional](../spring/aop-proxy-transactional.md#q23)

> "트랜잭션 안에서 또 다른 `@Transactional` 메서드를 호출했을 때, 그 메서드는 기존 트랜잭션을 같이 쓸지, 자기만의 새 트랜잭션을 만들지 정하는 것을 의미”

기본값 REQUIRED는 있으면 참여하고 없으면 새로 시작하며, REQUIRES_NEW는 항상 독립된 새 트랜잭션을 시작합니다."

<a name="q9"></a>
### Q9. @Transactional은 어떻게 동작하나요?

> "Spring이 Proxy로 메서드 호출을 가로채서, 시작 시 트랜잭션을 열고 정상 종료되면 Commit, Rollback 조건 예외가 나면 Rollback합니다. 실제 트랜잭션 기능 자체는 DB와 JDBC Connection이 제공하고, Spring은 그 시작과 종료를 대신 관리하는 것입니다."

<a name="q9-1"></a>
#### ↳ Q9-1. @Transactional이 붙은 메서드를 같은 객체 내부에서 호출하면?

> 기본 프록시 모드에서 같은 객체 내부로 직접 호출하면 내부 메서드의 트랜잭션 속성이 새로 적용되지 않습니다. 외부 메서드가 이미 연 트랜잭션에는 그대로 참여합니다. 독립된 경계가 필요하다면 별도 Bean의 프록시를 통해 호출할 수 있습니다.

<a name="q9-2"></a>
#### ↳ Q9-2. @Transactional은 보통 왜 Service 계층에 적용하나요?

같은 질문의 다른 회차 답변 · [aop-proxy-transactional](../spring/aop-proxy-transactional.md#q27)

> "트랜잭션 경계는 개별 SQL이 아니라 하나의 비즈니스 작업 단위로 잡아야 하기 때문입니다. 여러 Repository 작업을 조합하는 Service 계층이 그 경계를 두기에 적절합니다."

<a name="q10"></a>
### Q10. Spring Transaction과 DB Connection, Connection Pool은 어떤 관계인가요?

> "하나의 DB 트랜잭션은 하나의 Connection을 기준으로 진행됩니다. 트랜잭션이 시작되면 Pool에서 Connection을 빌려 쓰고 종료 시 반환하므로, 트랜잭션이 길어지면 Connection도 오래 점유되어 Pool이 고갈될 수 있습니다."

<a name="q11"></a>
### Q11. JPA의 Flush와 Commit은 같은 것인가요?

> "다릅니다. Flush는 영속성 컨텍스트의 변경 내용을 SQL로 DB에 반영하는 과정이고, Commit은 DB 트랜잭션을 최종 확정하는 것입니다. Flush가 일어났다고 Commit된 것은 아닙니다."

<a name="q12"></a>
### Q12. 트랜잭션 실패 시 무조건 재시도하면 되나요?

> "아닙니다. Deadlock이나 낙관적 Lock 충돌 같은 일시적 문제는 재시도로 해결되지만, 트랜잭션 안에 외부 API 호출이나 메시지 전송처럼 중복 실행에 민감한 작업이 있으면 재시도가 새 문제를 만듭니다. 멱등성을 함께 고려해야 합니다."

<a name="q13"></a>
### Q13. 분산 환경에서 트랜잭션은 어떻게 처리하나요?

> "여러 서비스나 DB에 걸친 작업은 단일 트랜잭션으로 묶을 수 없습니다. 2PC로 묶는 방법이 있지만 성능과 가용성 문제가 커서, 실무에서는 각 단계를 독립 트랜잭션으로 처리하고 실패 시 보상 트랜잭션으로 되돌리는 Saga 패턴을 많이 씁니다."

<a name="section-02"></a>
## ACID

<a name="q14"></a>
### Q14. [대표 질문] ACID란 무엇이고 왜 필요한가요?

> "트랜잭션이 지켜야 할 네 가지 속성입니다. 원자성은 전부 성공하거나 전부 취소되는 것, 일관성은 전후 데이터 무결성이 유지되는 것, 격리성은 동시 트랜잭션끼리 간섭하지 않는 것, 지속성은 Commit된 결과가 장애에도 보존되는 것입니다. 이 네 가지가 모두 지켜져야 '믿을 수 있는 트랜잭션'이 됩니다."
- **원자성** = 작업이 **전부 성공했는가**
- **일관성** = 결과가 **규칙에 맞는가**
- **격리성** = 동시에 실행될 때 **서로 방해하지 않는가**

| 속성 | 계좌이체로 설명 |
| --- | --- |
| **Atomicity 원자성** | A 출금과 B 입금은 **둘 다 성공하거나 둘 다 실패**해야 함 |
| **Consistency 일관성** | 송금 후에도 잔액, 계좌 규칙 등 **시스템 규칙이 깨지면 안 됨** |
| **Isolation 격리성** | 여러 사람이 동시에 송금해도 **서로의 트랜잭션 때문에 이상한 결과가 생기면 안 됨** |
| **Durability 지속성** | 송금이 Commit됐다면 **정전이나 장애가 나도 결과가 사라지면 안 됨** |

<a name="q15"></a>
### Q15. ACID 중 가장 중요한 것은 무엇인가요?

> 계좌이체에서 부분 성공을 막는 목적에는 원자성이 중요합니다. 동시에 들어온 이체의 충돌에는 격리성이, 장애 이후 커밋을 유지하는 데에는 지속성이 중요합니다. 네 속성에는 고정된 우선순위가 없습니다.

<a name="q16"></a>
### Q16. [핵심 질문] 원자성과 일관성은 뭐가 다른가요?

> "원자성은 '실행 여부'로, 일부 작업만 반영되는 것을 막습니다. 일관성은 '결과 상태'로, 트랜잭션이 끝난 뒤 데이터가 규칙을 만족하는지를 봅니다. 출금과 입금이 둘 다 수행됐다면 원자성은 만족하지만, 로직 오류로 금액이 다르게 저장됐다면 일관성은 깨진 것입니다."

<a name="q16-1"></a>
#### ↳ Q16-1. 일관성은 DB가 모든 비즈니스 규칙을 보장한다는 뜻인가요?

> "아닙니다. DB는 NOT NULL, UNIQUE, FK 같은 자신이 아는 제약 조건만 보장합니다. 애플리케이션만 아는 비즈니스 규칙은 판단하지 못하므로, 일관성은 DB 제약과 올바른 애플리케이션 로직이 함께 유지해야 합니다."

<a name="q17"></a>
### Q17. [핵심 질문] Undo Log와 Redo Log는 각각 어떻게 동작하나요?

> "Undo Log는 변경 전의 값을 기록해두어, 롤백 시 그 값으로 되돌려 원자성을 보장합니다. Redo Log는 변경 내용을 기록해두어, 장애 후 재시작할 때 Commit된 작업을 다시 적용해 지속성을 보장합니다. Undo는 과거로 되돌리는 로그, Redo는 다시 앞으로 진행시키는 로그입니다."

<a name="q17-1"></a>
#### ↳ Q17-1. DB 엔진은 작업 실패 시 Undo Log를 구체적으로 어떻게 활용하나요?

> "데이터를 수정하기 직전에 원래 값을 Undo Log에 먼저 기록합니다. 트랜잭션이 실패하면 이 로그를 역순으로 읽으며 각 변경을 원래 값으로 되돌립니다. 또한 MVCC에서 다른 트랜잭션이 '변경 이전 버전'을 읽어야 할 때도 이 Undo Log를 참조합니다."

<a name="q18"></a>
### Q18. [핵심 질문] WAL(Write-Ahead Logging)이란 무엇인가요?

> "변경된 데이터 페이지를 영구 저장소에 쓰기 전에 그 변경을 설명하는 로그를 먼저 영속화하는 방식입니다. 장애가 나도 로그를 기반으로 복구할 수 있어 지속성을 보장합니다. InnoDB와 PostgreSQL이 사용합니다."

<a name="q18-1"></a>
#### ↳ Q18-1. [핵심 질문] 왜 데이터 파일에 직접 쓰지 않고 로그를 먼저 작성하나요?

> "데이터 파일은 디스크 여기저기에 흩어져 있어 임의 접근(Random I/O)이 필요해 느립니다. 반면 로그는 파일 끝에 순차적으로 덧붙이는 Sequential I/O라 훨씬 빠릅니다. 빠른 로그 기록만 먼저 확정해두면 Commit을 즉시 응답할 수 있고, 실제 데이터 파일 반영은 나중에 몰아서 처리해도 장애 시 로그로 복구할 수 있습니다."

<a name="q18-2"></a>
#### ↳ Q18-2. Commit했는데 데이터 파일에 아직 안 써졌으면 지속성이 깨진 것 아닌가요?

> 동기식 내구성 설정에서는 커밋을 성공으로 알리기 전에 복구에 필요한 로그를 영구 저장소에 기록합니다. 변경된 데이터 페이지는 나중에 기록할 수 있습니다. 비동기 커밋이나 완화된 플러시 설정에서는 장애 직전의 커밋이 유실될 수 있습니다.

<a name="q19"></a>
### Q19. NoSQL은 ACID를 보장 안 하나요?

> ACID 지원 범위는 제품·버전·배포 구성에 따라 다릅니다. 예를 들어 MongoDB는 복제 세트와 샤딩된 클러스터에서 다중 문서 트랜잭션을 지원합니다. 실제 보장은 읽기·쓰기 옵션과 트랜잭션 경계를 확인해야 합니다.

| 개념 | 핵심 |
| --- | --- |
| **ACID** | 트랜잭션의 강한 정합성·안전성 중시 |
| **BASE** | 분산 환경에서 가용성과 최종적 일관성을 중시 |
| **RDB** | 관계형 데이터베이스라는 DB 종류 |
| **NoSQL** | 관계형 모델에 한정되지 않는 DB 계열 |

<a name="section-03"></a>
## Isolation(격리성)

<a name="q20"></a>
### Q20. [대표 질문] 격리성이란 무엇이고, 왜 완벽한 격리성을 일괄 적용하지 않나요?

> "격리성은 동시 실행되는 트랜잭션들이 서로 간섭하지 않고 독립적으로 실행되는 것처럼 보이게 하는 속성입니다. Serializable은 커밋 결과가 어떤 직렬 순서와 같도록 보장합니다. 동시 실행 중 충돌이 많으면 대기나 재시도로 처리량이 줄 수 있어, 격리 수준을 여러 단계로 나누어 정합성과 동시성 사이에서 필요한 만큼만 선택하도록 한 것입니다."

<a name="q21"></a>
### Q21. 격리 수준에는 어떤 것들이 있나요?

> "낮은 순서대로 Read Uncommitted, Read Committed, Repeatable Read, Serializable이 있습니다. 높은 수준은 더 많은 이상 현상을 방지합니다. 대기나 재시도 비용은 DB 구현과 작업 패턴에 따라 달라집니다. MySQL 기본값은 Repeatable Read입니다."

<a name="q21-1"></a>
#### ↳ Q21-1. [핵심 질문] Isolation Level을 무조건 높게 설정하면 안 되나요?

> 더 높은 격리 수준은 허용하는 이상 현상을 줄입니다. 대신 작업에 따라 대기, 충돌 감지, 재시도 비용이 늘 수 있습니다. 비즈니스 규칙과 실제 충돌 빈도를 함께 보고 결정합니다.

<a name="q21-2"></a>
#### ↳ Q21-2. 격리성을 극단적으로 높이면 어떤 시스템적 문제가 생기고, 타협안은?

> "직렬화 가능한 격리에서도 여러 트랜잭션은 동시에 실행될 수 있습니다. 예를 들어 PostgreSQL은 충돌 관계를 추적하고 직렬 실행과 양립할 수 없는 결과라면 트랜잭션 하나를 중단하므로 애플리케이션이 전체 작업을 재시도해야 할 수 있습니다. 현실적인 타협안은 격리 수준은 Read Committed나 Repeatable Read로 두고, 정말 정합성이 중요한 특정 지점에만 비관적 락이나 낙관적 락을 국소적으로 적용하는 것입니다."

<a name="q21-3"></a>
#### ↳ Q21-3. Read Uncommitted는 왜 존재하나요?

> "정합성이 중요하지 않고 속도만 필요한 경우를 위한 것입니다. 대략적인 통계나 모니터링 조회처럼 값이 조금 틀려도 되는 상황입니다. 실무 대부분의 서비스에서는 사용하지 않습니다."

<a name="q22"></a>
### Q22. [핵심 질문] 격리 수준이 낮을 때 발생하는 3대 동시성 이상 현상을 설명해주세요.

> “Dirty Read는 다른 트랜잭션이 아직 Commit하지 않은 값을 읽는 현상입니다. Non-Repeatable Read는 같은 행을 두 번 읽었는데 다른 트랜잭션의 수정·Commit 때문에 값이 달라지는 현상이고, Phantom Read는 같은 조건으로 다시 조회했을 때 INSERT나 DELETE 때문에 조회되는 행의 집합 자체가 달라지는 현상입니다.”

<a name="q22-1"></a>
#### ↳ Q22-1. Non-Repeatable Read와 Phantom Read의 차이는?

> "Non-Repeatable Read는 기존에 있던 '같은 행의 값'이 바뀌는 문제이고, Phantom Read는 조건에 해당하는 '행의 집합 자체'가 바뀌는 문제입니다."

<a name="q22-2"></a>
#### ↳ Q22-2. [핵심 질문] Lost Update(갱신 손실)란 무엇인가요?

> "**두 트랜잭션이 같은 값을 읽고 수정하다가 한쪽 수정 결과가 덮어써져 사라지는 현상**

 재고 10개를 둘 다 읽고 각각 1개씩 차감해 둘 다 9를 저장하면, 실제로는 2개가 팔렸는데 재고는 9로 남습니다."

<a name="q22-3"></a>
#### ↳ Q22-3. [핵심 질문] 격리 수준을 Repeatable Read로 설정했는데도 갱신 손실이 발생하는 이유는?

> 갱신 손실은 DB 구현과 SQL에 따라 달라집니다. InnoDB에서 이전에 읽은 값을 애플리케이션에서 계산해 상수로 덮어쓰는 패턴은 주의해야 합니다. PostgreSQL의 Repeatable Read는 스냅샷 이후 다른 트랜잭션이 변경한 행을 갱신하려 하면 직렬화 실패가 발생할 수 있어 전체 트랜잭션을 재시도해야 합니다.

<a name="q22-4"></a>
#### ↳ Q22-4. Isolation Level만 높이면 동시성 문제를 전부 해결할 수 있나요?

> 한 트랜잭션 안에서 수행한 읽기·수정·쓰기라면 Serializable도 갱신 손실을 막는 방법입니다. 충돌로 중단되면 전체 트랜잭션을 재시도합니다. 원자적 UPDATE, 버전 비교, 행 잠금도 선택할 수 있습니다. 사용자가 읽고 한참 뒤 별도 요청으로 수정한다면 버전 검사가 특히 유용합니다.

<a name="q23"></a>
### Q23. MySQL의 Repeatable Read에서 Phantom Read가 발생하나요?

> "SQL 표준 기준으로는 발생할 수 있지만, MySQL InnoDB는 MVCC와 Next-Key Lock으로 대부분 방지합니다. 실제 동작은 DBMS 구현마다 다르므로 표준 표만으로 단정하면 안 됩니다."

<a name="q23-1"></a>
#### ↳ Q23-1. Next-Key Lock이란 무엇인가요?

> "행 자체에 거는 Record Lock과, 행 사이 빈 구간에 거는 Gap Lock을 합친 잠금입니다. 특정 범위에 새 행이 끼어드는 것까지 막아 Phantom Read를 방지합니다."

<a name="q24"></a>
### Q24. [핵심 질문] MVCC란 무엇이고 왜 쓰나요?

> "Multi-Version Concurrency Control로, 데이터를 수정할 때 기존 버전을 유지하고 새 버전을 만드는 방식입니다. 읽기 트랜잭션은 자신의 시점에 맞는 버전을 읽으므로, 읽기가 쓰기의 Lock 해제를 기다리지 않아도 되어 읽기 동시성이 크게 높아집니다. InnoDB는 Undo Log에 이전 버전을 저장합니다."

<a name="q24-1"></a>
#### ↳ Q24-1. [핵심 질문] MVCC와 Lock의 차이는?

> 잠금은 서로 호환되지 않는 접근을 조정합니다. MVCC는 읽는 쪽에 보이는 버전을 선택합니다. InnoDB에서 일반 스냅샷 조회는 행 쓰기 잠금과 함께 진행할 수 있지만, 잠금 읽기와 쓰기 사이에는 여전히 경합이 발생합니다.

<a name="q24-2"></a>
#### ↳ Q24-2. [핵심 질문] 현대 RDB는 비관적 락의 블로킹 한계를 어떻게 극복하나요?

> "MVCC를 도입해서 극복합니다. InnoDB의 일반 일관 읽기는 스냅샷에 보이는 버전을 읽으므로 다른 트랜잭션의 행 쓰기 락을 기다리는 경우를 줄입니다. SELECT ... FOR UPDATE 같은 잠금 읽기는 같은 행의 락을 기다릴 수 있고, 메타데이터 락도 별도로 작동합니다."

<a name="q24-3"></a>
#### ↳ Q24-3. MVCC를 쓰면 Lock이 필요 없나요?

> "아닙니다. MVCC는 읽기-쓰기 충돌을 줄이는 데 효과적이지만, 여러 트랜잭션이 같은 데이터를 동시에 수정할 때는 여전히 Lock이나 충돌 감지가 필요합니다. 실제 DB는 둘을 함께 사용합니다."

<a name="q24-4"></a>
#### ↳ Q24-4. Snapshot이란 무엇인가요?

> "MVCC에서 특정 트랜잭션이 어떤 버전을 볼 수 있는지 판단하는 기준입니다. 데이터를 통째로 복사한다기보다, 현재 트랜잭션에게 어떤 변경이 보이는지를 결정하는 가시성 정보에 가깝습니다."

<a name="q24-5"></a>
#### ↳ Q24-5. Read Committed와 Repeatable Read를 MVCC 관점에서 설명해주세요.

> "Read Committed는 조회할 때마다 최신 Commit 상태를 반영해서 같은 트랜잭션 안에서도 결과가 달라질 수 있습니다. InnoDB의 Repeatable Read에서 일반 SELECT는 기본적으로 최초 일관 읽기 때 만든 스냅샷을 재사용해서, 다른 트랜잭션이 중간에 Commit해도 기존 버전을 계속 읽습니다."

<a name="q24-6"></a>
#### ↳ Q24-6. MVCC는 오래된 버전이 쌓이면 용량이 늘지 않나요?

> "늘어납니다. 더 이상 참조되지 않는 버전은 PostgreSQL의 VACUUM, MySQL InnoDB의 Purge 스레드가 정리합니다. 긴 트랜잭션이 열려 있으면 그 시점 버전을 계속 유지해야 해서 정리가 밀리고 용량이 부풀 수 있습니다."

<a name="q25"></a>
### Q25. Lock은 왜 필요하고, Shared Lock과 Exclusive Lock은 어떻게 다른가요?

> "여러 트랜잭션이 같은 데이터를 동시에 수정할 때 충돌을 막기 위해 필요합니다. Shared Lock은 읽기용으로 여러 트랜잭션이 동시에 가질 수 있고, Exclusive Lock은 수정용으로 다른 어떤 락과도 충돌합니다. 읽기끼리는 동시에 되지만 수정이 끼면 강하게 제한됩니다."

<a name="q25-1"></a>
#### ↳ Q25-1. SELECT FOR UPDATE는 왜 사용하고 어떻게 동작하나요?

> SELECT ... FOR UPDATE는 읽은 행을 트랜잭션 안에서 이어서 수정할 때 사용합니다. 같은 행에 충돌하는 잠금을 요청하는 작업은 대기할 수 있습니다. 일반 MVCC 조회는 이전 커밋 버전을 읽을 수 있습니다.

<a name="q25-2"></a>
#### ↳ Q25-2. 읽기 작업도 잠금이 필요한 경우가 있나요?

> "있습니다. `SELECT ... FOR SHARE`를 쓰면 다른 트랜잭션의 읽기는 허용하되 수정은 막을 수 있습니다. 조회한 값으로 검증하는 동안 그 값이 바뀌면 안 될 때 사용합니다."

<a name="q26"></a>
### Q26. [핵심 질문] 비관적 Lock과 낙관적 Lock의 차이와 선택 기준은?

> "비관적 Lock은 충돌이 날 것이라 보고 데이터 사용 시점부터 락을 걸어 사전에 막는 방식이고, 낙관적 Lock은 일단 진행시킨 뒤 수정 시점에 version을 비교해 충돌을 사후 감지하는 방식입니다. 재고나 좌석처럼 충돌이 빈번하면 비관적, 프로필 수정처럼 드물면 낙관적이 적합합니다."

<a name="q26-1"></a>
#### ↳ Q26-1. [핵심 질문] 갱신 손실을 방지하기 위한 비관적 락은 어떻게 적용하며, 장단점은?

> 모든 갱신 경로가 같은 행을 SELECT ... FOR UPDATE로 먼저 잠그고, 같은 트랜잭션에서 현재 값을 읽어 계산하고 쓰면 갱신 손실을 막을 수 있습니다. 일반 스냅샷 읽기까지 차단한다는 뜻은 아닙니다.

<a name="q26-2"></a>
#### ↳ Q26-2. 비관적 Lock의 Deadlock은 어떻게 방지하나요?

> "모든 트랜잭션이 자원에 동일한 순서로 접근하도록 규칙을 정하면 순환 대기가 생기지 않습니다. 또한 락 타임아웃을 설정하고, 트랜잭션을 짧게 유지해 락 점유 시간을 줄이는 것도 방법입니다."

<a name="q26-3"></a>
#### ↳ Q26-3. Lock Wait와 Deadlock의 차이는?

> "Lock Wait는 다른 트랜잭션의 락이 풀리기를 기다리는 정상적인 대기 상태입니다. Deadlock은 서로가 가진 락을 기다리는 순환 대기가 생겨 그대로는 진행 불가능한 상태이며, DBMS가 감지해서 한쪽을 강제 Rollback시킵니다."

<a name="q26-4"></a>
#### ↳ Q26-4. 낙관적 Lock에서 충돌이 나면 어떻게 처리하나요?

> 충돌한 트랜잭션을 종료하고 최신 데이터를 다시 읽습니다. 자동 병합이 안전한 작업만 새 트랜잭션에서 제한적으로 재시도합니다. 사용자가 편집한 값을 덮어쓸 위험이 있으면 충돌을 알리고 선택하게 합니다.

<a name="q26-5"></a>
#### ↳ Q26-5. JPA에서 낙관적 Lock은 어떻게 구현하나요?

> "엔티티에 `@Version` 필드를 추가하면 JPA가 UPDATE 시 `WHERE version = ?` 조건을 자동으로 붙입니다. 다른 트랜잭션이 먼저 수정해 version이 불일치하면 OptimisticLockException이 발생합니다."

*Deadlock(교착상태)**은 두 개 이상의 트랜잭션이 서로가 보유한 Lock을 기다리면서 영원히 진행하지 못하는 상태입니다.

예를 들어 트랜잭션 A가 자원 1을 잠근 뒤 자원 2를 기다리고, 트랜잭션 B가 자원 2를 잠근 뒤 자원 1을 기다리면 서로 기다리는 순환 구조가 만들어집니다.

방지 방법으로는 여러 트랜잭션이 **항상 같은 순서로 자원에 접근하도록 규칙을 정하는 것**이 가장 중요합니다. 또한 트랜잭션을 짧게 유지하고, 불필요하게 넓은 범위를 Lock하지 않으며, 적절한 인덱스를 사용해 Lock 범위를 줄이는 것도 도움이 됩니다. 추가로 Lock Timeout이나 Deadlock 감지 후 재시도 로직을 두어 문제가 발생했을 때 복구할 수 있도록 설계합니다.
