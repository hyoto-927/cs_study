<a name="section-01"></a>
## TCP

<a name="q1"></a>
### Q1. [대표 질문] TCP란 무엇인가요?

> "TCP는 연결 지향적인 전송 계층 프로토콜로, 데이터를 보내기 전에 연결을 수립하고 Sequence Number, ACK, 재전송 등을 이용해 신뢰성 있는 데이터 전달을 제공합니다.
>
> 네트워크에서는 데이터가 유실되거나 순서가 바뀔 수 있는데, TCP는 이런 문제를 프로토콜 차원에서 처리해 애플리케이션에 순서가 보장된 바이트 스트림을 제공합니다."

**핵심 요약**

**TCP = 연결을 맺고 순서와 신뢰성을 제공하는 전송 계층 프로토콜**

---

<a name="q2"></a>
### Q2. 흐름 제어와 혼잡 제어의 차이는 무엇인가요?

**연관 질문:** "흐름 제어와 혼잡 제어의 본질적인 차이"

> "흐름 제어는 송신자가 수신자의 처리 속도보다 너무 빠르게 데이터를 보내지 않도록 조절하는 기능입니다.
>
> 반면 혼잡 제어는 네트워크 자체에 너무 많은 데이터가 몰리지 않도록 송신 속도를 조절하는 기능입니다.
>
> 즉 흐름 제어는 수신자를 보호하고, 혼잡 제어는 네트워크 전체를 보호한다고 볼 수 있습니다."

**핵심 요약**

**흐름 제어 = 수신자 보호 / 혼잡 제어 = 네트워크 보호**

---

<a name="q2-1"></a>
#### ↳ Q2-1. 흐름 제어는 구체적으로 어떻게 동작하나요?

> "TCP는 Sliding Window 방식을 이용합니다.
>
> 수신자는 ACK을 보낼 때 자신이 추가로 받을 수 있는 버퍼 공간을 Window Size로 알려주고, 송신자는 그 범위를 고려해 데이터를 보냅니다.
>
> 수신 버퍼의 여유 공간이 없어 Window Size가 0이 되면 송신자는 새로운 데이터 전송을 제한하고, 이후 다시 여유 공간이 생겼는지 확인합니다."

**핵심 요약**

**수신자가 Window Size를 알려주고 송신자는 그 범위에 맞춰 전송한다**

---

<a name="q2-2"></a>
#### ↳ Q2-2. Sliding Window는 왜 Stop-and-Wait보다 효율적인가요?

> "Stop-and-Wait은 데이터를 하나 보내고 ACK을 받을 때까지 기다린 뒤 다음 데이터를 보내기 때문에 왕복 시간 동안 전송 효율이 떨어질 수 있습니다.
>
> Sliding Window는 허용된 범위 안에서 여러 데이터를 연속으로 전송할 수 있고, ACK이 도착하면 Window를 앞으로 이동시켜 새로운 데이터를 계속 보낼 수 있습니다.
>
> 따라서 ACK을 기다리는 동안에도 전송을 이어갈 수 있어 네트워크를 더 효율적으로 활용할 수 있습니다."

**핵심 요약**

**Stop-and-Wait은 하나씩 / Sliding Window는 여러 개를 연속 전송**

---

<a name="q2-3"></a>
#### ↳ Q2-3. 혼잡 제어에는 어떤 방식이 있나요?

> "대표적으로 Slow Start, Congestion Avoidance, Fast Retransmit, Fast Recovery 등이 있습니다.
>
> Slow Start는 처음에는 작은 전송량으로 시작해서 혼잡이 없으면 빠르게 전송량을 증가시키는 방식입니다.
>
> 이후 혼잡 가능성이 높아지면 Congestion Avoidance 단계에서 증가 폭을 줄이고, 손실이 감지되면 전송량을 조절합니다."

**핵심 요약**

**혼잡 제어 = 처음에는 조심스럽게 늘리고, 혼잡이 보이면 속도를 줄인다**

---

<a name="q3"></a>
### Q3. Head-of-Line Blocking이란 무엇인가요?

> "TCP는 데이터를 순서대로 애플리케이션에 전달해야 합니다.
>
> 그래서 앞쪽 데이터가 유실되면 뒤쪽 데이터가 이미 도착했더라도 유실된 데이터가 재전송될 때까지 기다려야 할 수 있습니다.
>
> 이렇게 앞의 데이터 때문에 뒤의 데이터까지 전달이 지연되는 현상을 Head-of-Line Blocking이라고 합니다."

**핵심 요약**

**앞 데이터가 빠지면 뒤 데이터도 기다려야 하는 현상**

---

<a name="q3-1"></a>
#### ↳ Q3-1. 이 문제는 어떻게 개선할 수 있나요?

> "HTTP/3에서는 UDP 위에서 동작하는 QUIC을 사용합니다.
>
> QUIC은 하나의 연결 안에서 여러 독립적인 Stream을 제공하기 때문에 한 Stream에서 데이터 손실이 발생하더라도 다른 Stream은 계속 처리할 수 있습니다.
>
> 따라서 TCP 연결 전체에서 발생할 수 있는 Head-of-Line Blocking 문제를 줄일 수 있습니다."

**핵심 요약**

**QUIC = 한 Stream이 막혀도 다른 Stream은 계속 진행**

---

<a name="q4"></a>
### Q4. TCP는 왜 상대적으로 오버헤드가 큰가요?

> "TCP는 신뢰성을 제공하기 위해 추가적인 작업을 수행하기 때문입니다.
>
> 연결을 만들기 위한 Handshake가 필요하고, Sequence Number와 ACK을 이용해 데이터를 관리하며, 손실된 데이터는 재전송합니다.
>
> 또한 흐름 제어와 혼잡 제어를 통해 전송 속도도 조절합니다.
>
> 따라서 UDP보다 프로토콜 자체가 수행해야 하는 일이 많아 상대적으로 오버헤드가 큽니다."

**핵심 요약**

**TCP는 신뢰성을 얻는 대신 더 많은 관리 비용이 든다**

---

<a name="q5"></a>
### Q5. TCP 연결은 어떻게 식별하나요?

> "일반적으로 TCP 연결은 출발지 IP, 출발지 Port, 목적지 IP, 목적지 Port의 네 가지 조합인 4-tuple로 구분합니다.
>
> 그래서 같은 서버에 여러 Client가 접속하거나 하나의 Client가 여러 TCP 연결을 만들더라도 각각의 연결을 구분할 수 있습니다."

**핵심 요약**

**TCP 연결 = 출발 IP + 출발 Port + 목적 IP + 목적 Port**

---

<a name="q6"></a>
### Q6. TCP는 데이터 오류를 어떻게 검출하나요?

> "TCP Header에는 Checksum이 있습니다.
>
> 송신 측이 Header와 Data 등을 이용해 Checksum을 계산하고, 수신 측도 다시 계산해서 데이터가 전송 과정에서 손상됐는지 검사합니다.
>
> 손상된 Segment는 정상 데이터로 처리되지 않으며, 해당 데이터가 정상적으로 확인되지 않으면 결국 송신 측의 재전송으로 이어질 수 있습니다."

**핵심 요약**

**Checksum = 전송 중 데이터가 손상됐는지 검사**

---

<a name="q7"></a>
### Q7. TCP는 언제 재전송하나요?

> "대표적으로 재전송 타이머인 RTO가 만료됐는데도 필요한 ACK을 받지 못하면 손실로 판단해 재전송할 수 있습니다.
>
> 또한 같은 ACK 번호의 Duplicate ACK을 반복해서 받으면 중간 데이터가 유실된 것으로 추정할 수 있습니다.
>
> 전통적인 Fast Retransmit에서는 Duplicate ACK을 3번 받으면 타임아웃을 기다리지 않고 해당 데이터를 빠르게 재전송합니다."

**핵심 요약**

**RTO 만료 또는 중복 ACK 3번 → 재전송**

---

<a name="q8"></a>
### Q8. HTTP Keep-Alive는 왜 사용하나요?

> "HTTP 요청마다 새로운 TCP 연결을 만들면 매번 TCP Handshake 비용이 발생합니다.
>
> HTTP Keep-Alive나 Persistent Connection을 이용해 이미 생성된 TCP 연결을 여러 요청에 재사용하면 연결 설정 비용을 줄이고 성능을 개선할 수 있습니다.
>
> 참고로 TCP 자체의 Keepalive는 죽은 연결을 탐지하기 위한 별도의 기능이므로 HTTP Keep-Alive와는 구분하는 것이 좋습니다."

**핵심 요약**

**HTTP Keep-Alive = TCP 연결을 재사용해 연결 비용을 줄인다**

---

<a name="q8-1"></a>
#### ↳ Q8-1. 매 API 호출마다 TCP/TLS Handshake를 반복하면 어떤 병목이 생기나요?

> "매 요청마다 TCP 연결과 TLS 연결을 새로 만들면 각각의 Handshake에 필요한 RTT가 반복되고, TLS 인증과 키 교환 비용도 계속 발생합니다.
>
> 요청 자체는 짧은데 연결을 만드는 데 더 많은 시간이 들 수 있어 전체 응답 시간이 증가합니다.
>
> 그래서 HTTP Keep-Alive로 TCP 연결을 재사용하고, TLS Session Resumption을 이용해 TLS 협상 비용도 줄일 수 있습니다."

**핵심 요약**

**매번 새 연결을 만들면 RTT가 반복되므로 연결을 재사용한다**

---

<a name="section-02"></a>
## UDP

<a name="q9"></a>
### Q9. [대표 질문] UDP란 무엇인가요?

> "UDP는 연결을 먼저 수립하지 않고 Datagram 단위로 데이터를 전송하는 비연결형 전송 계층 프로토콜입니다.
>
> UDP 자체는 데이터의 도착, 순서, 재전송을 보장하지 않습니다.
>
> 대신 TCP보다 Header가 단순하고 연결 관리나 재전송 등의 기능이 없어 프로토콜 오버헤드가 작습니다."

**핵심 요약**

**UDP = 연결·순서·재전송을 기본 제공하지 않는 가벼운 프로토콜**

---

<a name="q9-1"></a>
#### ↳ Q9-1. UDP가 비연결형 프로토콜이라고 불리는 이유는?

> "데이터 전송 전에 TCP처럼 Handshake를 통해 연결 상태를 만들지 않기 때문입니다.
>
> 각 Datagram은 독립적으로 전송되고 UDP 자체는 상대방과의 지속적인 연결 상태를 관리하지 않습니다."

**핵심 요약**

**UDP = 연결 상태를 만들지 않고 Datagram을 바로 보낸다**

---

<a name="q10"></a>
### Q10. UDP는 신뢰성이 낮은데 왜 사용하나요?

**연관 질문:** "실시간 화상 회의, 음성 통화, FPS 게임에서 UDP를 쓰는 이유"

> "실시간 서비스에서는 모든 데이터를 반드시 다시 받는 것보다 최신 데이터를 빠르게 전달하는 것이 더 중요할 수 있기 때문입니다.
>
> 예를 들어 음성 통화에서 과거 음성 패킷 하나를 다시 받기 위해 기다리면 오히려 대화가 끊길 수 있습니다.
>
> FPS 게임에서도 과거 위치를 늦게 재전송받는 것보다 현재 위치 정보를 빠르게 받는 것이 더 중요할 수 있습니다."

**핵심 요약**

**실시간 서비스는 과거 데이터의 완벽한 복구보다 최신 데이터의 빠른 전달이 중요할 수 있다**

---

<a name="q11"></a>
### Q11. HTTP/3는 왜 UDP 기반 QUIC을 사용하나요?

같은 질문의 다른 회차 답변 · [versions-tls-cors](http/versions-tls-cors.md#q5)

> "HTTP/3는 UDP 위에서 동작하는 QUIC을 사용합니다.
>
> QUIC은 여러 독립적인 Stream을 제공하기 때문에 한 Stream에서 데이터 손실이 발생해도 다른 Stream까지 함께 대기할 필요가 없습니다.
>
> 또한 연결 설정과 암호화 협상을 효율적으로 통합해 연결 지연을 줄일 수 있다는 장점도 있습니다."

**핵심 요약**

**HTTP/3 = QUIC을 사용해 Stream 간 Blocking과 연결 지연을 줄인다**

---

<a name="q11-1"></a>
#### ↳ Q11-1. QUIC은 UDP인데 어떻게 신뢰성을 제공하나요?

> "UDP 자체에는 재전송이나 순서 보장 같은 기능이 없지만 QUIC이 그 위에서 필요한 기능을 직접 제공합니다.
>
> QUIC은 신뢰성 있는 데이터 전달, 손실 복구, 흐름 제어, 혼잡 제어, 여러 Stream 관리 등을 구현합니다.
>
> 즉 UDP는 하부의 Datagram 전달 기능을 제공하고 QUIC이 그 위에서 신뢰성과 연결 관리 기능을 구현한다고 볼 수 있습니다."

**핵심 요약**

**UDP는 바닥을 제공하고 QUIC이 위에서 신뢰성을 구현한다**

---

<a name="q12"></a>
### Q12. UDP에서 신뢰성이 필요하면 어떻게 하나요?

> "UDP 자체가 신뢰성을 제공하지 않기 때문에 필요한 경우 상위 프로토콜이나 애플리케이션에서 직접 구현해야 합니다.
>
> 예를 들어 Sequence Number를 추가하거나 ACK과 재전송, 타임아웃 등의 기능을 별도로 만들 수 있습니다.
>
> QUIC이 UDP 위에서 이러한 기능들을 체계적으로 제공하는 대표적인 예입니다."

**핵심 요약**

**UDP에서 신뢰성이 필요하면 상위 계층에서 직접 구현한다**

---

<a name="q13"></a>
### Q13. DNS는 왜 UDP를 많이 사용하나요?

**연관 질문:** "DNS 쿼리에서 TCP가 아닌 UDP를 사용하는 결정적인 이유"

> "일반적인 DNS 질의와 응답은 비교적 짧고 빠른 응답이 중요하기 때문에 연결 설정이 필요 없는 UDP가 효율적입니다.
>
> 다만 DNS가 항상 UDP만 사용하는 것은 아닙니다.
>
> 응답의 크기나 상황에 따라 TCP를 사용할 수 있고, Zone Transfer처럼 신뢰성 있는 전송이 필요한 경우에는 TCP를 사용합니다.
>
> 현대 DNS는 UDP와 TCP를 모두 지원합니다."

**핵심 요약**

**일반 DNS 질의는 UDP가 흔하지만 필요하면 TCP도 사용한다**

---

<a name="q14"></a>
### Q14. UDP Header에는 무엇이 들어있나요?

> "UDP Header에는 Source Port, Destination Port, Length, Checksum의 네 필드가 있습니다.
>
> 기본 Header 크기는 총 8Byte로, TCP 기본 Header보다 단순하고 작습니다.
>
> UDP에는 Sequence Number나 ACK Number 같은 TCP의 신뢰성 관련 필드가 없습니다."

**핵심 요약**

**UDP Header = 출발 Port + 목적 Port + Length + Checksum = 8Byte**

---

<a name="q14-1"></a>
#### ↳ Q14-1. UDP Checksum은 무엇을 검증하나요?

> "UDP Header와 Data가 전송 중 손상되지 않았는지 확인하는 데 사용합니다.
>
> Checksum 오류가 발견된 Datagram은 정상 데이터로 전달되지 않고 폐기될 수 있습니다.
>
> UDP 자체는 TCP처럼 해당 Datagram을 자동으로 재전송하지 않기 때문에 필요하다면 상위 계층에서 다시 요청해야 합니다."

**핵심 요약**

**UDP는 오류를 확인할 수 있지만 자체 재전송은 하지 않는다**

---

<a name="q15"></a>
### Q15. UDP는 왜 Broadcast와 Multicast에 사용할 수 있나요?

> "UDP는 특정 상대와 연결 상태를 유지하지 않고 Datagram을 전송하기 때문에 하나의 데이터를 여러 대상에게 보내는 Broadcast나 Multicast 형태의 통신에 사용할 수 있습니다.
>
> 반면 TCP는 두 Endpoint 사이에 연결 상태를 유지하는 1:1 연결 지향 방식입니다."

**핵심 요약**

**UDP는 연결 상태가 없어 1:N 전송 형태에도 활용할 수 있다**

---

<a name="q16"></a>
### Q16. UDP는 항상 TCP보다 빠른가요?

> "항상 그렇다고 할 수는 없습니다.
>
> UDP 자체는 연결 설정, 순서 보장, 재전송 등의 기능이 없기 때문에 기본적인 프로토콜 오버헤드는 TCP보다 작습니다.
>
> 하지만 애플리케이션에서 TCP와 비슷한 신뢰성 기능을 직접 구현한다면 추가 비용이 발생할 수 있기 때문에 실제 성능은 사용 방식에 따라 달라집니다."

**핵심 요약**

**UDP는 기본 오버헤드는 작지만 항상 TCP보다 빠른 것은 아니다**

---

<a name="q16-1"></a>
#### ↳ Q16-1. UDP에 흐름 제어와 혼잡 제어가 없다는 것은 어떤 의미인가요?

> "UDP 자체는 수신자의 처리 능력이나 네트워크 혼잡 상태를 확인해서 송신 속도를 자동으로 조절하지 않습니다.
>
> 따라서 송신자가 너무 빠르게 데이터를 보내면 수신 버퍼가 넘쳐 Datagram이 손실되거나 네트워크 혼잡을 악화시킬 수 있습니다.
>
> 이런 제어가 필요하다면 상위 프로토콜이나 애플리케이션에서 구현해야 합니다."

**핵심 요약**

**UDP는 스스로 속도를 조절하지 않으므로 필요하면 상위 계층이 제어한다**

---

<a name="section-03"></a>
## Handshake

<a name="q17"></a>
### Q17. [대표 질문] Handshake란 무엇인가요?

**연관 질문:** "Handshake란 무엇이며 데이터 송수신 전에 반드시 거쳐야 하는 본질적 이유"

> "Handshake는 연결 지향 통신 등에서 본격적인 데이터 통신을 시작하기 전에 양쪽이 서로의 상태와 필요한 정보를 확인하거나 협상하는 과정입니다.
>
> TCP에서는 연결을 만들 때 3-Way Handshake를 사용하고, 연결을 종료할 때는 일반적으로 FIN과 ACK을 교환하는 종료 절차를 수행합니다.
>
> 이를 통해 상대방과 통신할 수 있는지 확인하고 Sequence Number 같은 연결 상태를 맞출 수 있습니다."

**핵심 요약**

**Handshake = 본격적인 통신 전에 서로 상태와 정보를 맞추는 과정**

---

<a name="q18"></a>
### Q18. 왜 TCP 연결은 2-Way가 아니라 3-Way인가요?

> "TCP에서는 양쪽이 서로의 연결 요청과 초기 Sequence Number를 정상적으로 받았다는 사실을 확인해야 합니다.
>
> Client가 SYN을 보내고 Server가 SYN+ACK으로 응답하면 Client는 Server의 응답을 확인할 수 있습니다.
>
> 마지막으로 Client가 ACK을 보내야 Server도 자신의 SYN이 Client에게 정상적으로 전달됐다는 사실을 확인할 수 있습니다.
>
> 그래서 안정적인 양방향 연결 상태를 확인하려면 세 단계가 필요합니다."

**핵심 요약**

**3-Way = 서로의 연결 의사와 초기 Sequence Number를 양쪽 모두 확인**

---

<a name="q18-1"></a>
#### ↳ Q18-1. 그럼 4-Way로 연결하면 더 확실하지 않나요?

> "3단계에서 연결에 필요한 확인이 완료되므로 추가 단계는 불필요한 통신 비용만 증가시킵니다.
>
> 따라서 TCP 연결 수립에서는 필요한 확인을 수행할 수 있는 3-Way Handshake를 사용합니다."

**핵심 요약**

**3번이면 필요한 확인이 끝나므로 4번째는 불필요하다**

---

<a name="q18-2"></a>
#### ↳ Q18-2. 3-Way Handshake 중 Packet이 손실되면 어떻게 되나요?

> "SYN이나 SYN+ACK 같은 Handshake Segment가 손실되면 송신 측은 일정 시간 동안 응답을 기다렸다가 타임아웃이 발생하면 다시 전송합니다.
>
> 재전송이 반복되면 일반적으로 재전송 간격도 늘어나도록 동작해 네트워크가 불안정한 상황에서 너무 짧은 간격으로 계속 전송하는 것을 방지합니다.
>
> 정해진 재시도 한계를 넘어서도 연결이 성립하지 않으면 결국 연결 시도는 실패합니다."

**핵심 요약**

**Handshake 손실 → Timeout → 재전송 → 계속 실패하면 연결 실패**

---

<a name="q19"></a>
### Q19. TCP 연결 종료는 왜 흔히 4단계로 설명하나요?

> "TCP는 양방향 데이터 흐름을 각각 독립적으로 종료할 수 있습니다.
>
> 한쪽이 FIN을 보내더라도 상대방에게 아직 보낼 데이터가 남아 있을 수 있기 때문에 먼저 ACK만 보낸 뒤 남은 작업을 끝내고 자신의 FIN을 별도로 보낼 수 있습니다.
>
> 그래서 연결 수립에서는 SYN과 ACK을 함께 보낼 수 있지만 종료에서는 FIN과 ACK의 시점이 달라져 흔히 네 단계로 나타납니다."

**핵심 요약**

**종료는 양쪽의 전송 종료 시점이 다를 수 있어 FIN과 ACK이 분리된다**

---

<a name="q20"></a>
### Q20. TIME_WAIT은 왜 필요한가요?

> "연결 종료 시 마지막 ACK을 보낸 측이 즉시 연결 정보를 완전히 없애지 않고 일정 시간 기다리는 상태입니다.
>
> 첫째, 마지막 ACK이 유실되어 상대방이 FIN을 다시 보내면 ACK을 다시 전송할 수 있어야 합니다.
>
> 둘째, 이전 연결에서 늦게 도착한 Segment가 같은 주소와 Port를 사용하는 새로운 연결에 섞이는 위험을 줄이기 위해 일정 시간 기다립니다."

**핵심 요약**

**TIME_WAIT = 마지막 ACK 재전송 대비 + 옛 패킷이 사라질 시간 확보**

---

<a name="q20-1"></a>
#### ↳ Q20-1. TIME_WAIT이 많으면 어떤 문제가 생길 수 있나요?

> "TIME_WAIT 연결도 일정 기간 동안 연결 관련 자원을 사용합니다.
>
> 특히 짧은 outbound TCP 연결을 매우 많이 반복하면 사용할 수 있는 ephemeral port가 부족해지는 문제가 발생할 수 있습니다.
>
> 이런 상황은 연결 재사용이나 Connection Pool 등을 통해 완화할 수 있고, 필요하면 운영체제 설정을 함께 검토할 수 있습니다."

**핵심 요약**

**짧은 연결을 너무 많이 만들면 TIME_WAIT과 Port 사용량이 증가할 수 있다**

---

<a name="q21"></a>
### Q21. SYN Flood 공격이란 무엇인가요?

> "공격자가 Server에 SYN을 대량으로 보내고 마지막 ACK을 정상적으로 보내지 않는 공격입니다.
>
> Server는 SYN+ACK을 보낸 뒤 Client의 ACK을 기다리는 반쯤 열린 연결 상태를 일정 시간 유지해야 합니다.
>
> 공격으로 이런 상태가 대량으로 쌓이면 연결 대기 자원이 소모되어 정상 사용자의 접속이 어려워질 수 있습니다."

**핵심 요약**

**SYN만 대량 전송해 반쪽 연결 자원을 고갈시키는 공격**

---

<a name="q21-1"></a>
#### ↳ Q21-1. SYN Cookie는 어떻게 SYN Flood를 완화하나요?

> "Server가 SYN을 받았을 때 연결 상태를 바로 메모리에 모두 저장하는 대신, 필요한 정보를 기반으로 계산한 값을 SYN+ACK의 Sequence Number에 담아 Client에게 보냅니다.
>
> 이후 정상적인 ACK이 돌아오면 그 값을 검증한 뒤 연결 상태를 생성할 수 있습니다.
>
> 따라서 ACK이 오지 않는 가짜 SYN 요청 때문에 Server가 많은 연결 상태를 미리 저장하는 것을 줄일 수 있습니다."

**핵심 요약**

**SYN Cookie = ACK이 돌아오기 전까지 연결 상태 저장을 최소화**

---

<a name="q22"></a>
### Q22. TLS Handshake란 무엇인가요?

같은 질문의 다른 회차 답변 · [versions-tls-cors](http/versions-tls-cors.md#q10)

> "TLS Handshake는 Client와 Server가 안전한 암호화 통신을 시작하기 위해 필요한 정보를 협상하는 과정입니다.
>
> 서로 사용할 TLS 버전과 암호 알고리즘 등을 결정하고, 일반적인 HTTPS에서는 Server가 인증서를 제공해 자신의 신원을 증명합니다.
>
> 이후 Key Exchange를 통해 양쪽이 이후 통신에 사용할 Session Key를 생성하고, 실제 Application Data는 효율적인 대칭키 암호화 방식으로 보호합니다."

**핵심 요약**

**TLS Handshake = 인증 + 암호 방식 협상 + Session Key 생성**

---

<a name="q22-1"></a>
#### ↳ Q22-1. TCP Handshake와 TLS Handshake의 차이는?

> "TCP Handshake는 통신할 수 있는 전송 연결을 만드는 과정이고, TLS Handshake는 그 연결 위에서 안전하게 통신하기 위한 보안 정보를 협상하는 과정입니다.
>
> 일반적인 HTTPS over TCP에서는 먼저 TCP 연결을 만들고, 그 위에서 TLS Handshake를 수행한 뒤 HTTP 데이터를 주고받습니다."

**핵심 요약**

**TCP Handshake = 연결 / TLS Handshake = 보안**

---

<a name="q22-2"></a>
#### ↳ Q22-2. TLS는 왜 비대칭키와 대칭키 암호화를 함께 사용하나요?

> "두 방식의 장점을 함께 사용하기 위해서입니다.
>
> 비대칭키 방식은 공개키와 개인키를 이용하기 때문에 인증과 안전한 키 합의에 유리하지만 계산 비용이 큽니다.
>
> 반면 대칭키 방식은 동일한 Session Key를 이용해 암호화와 복호화를 수행하므로 속도가 훨씬 빠르지만, 처음에 이 키를 안전하게 공유하는 문제가 있습니다.
>
> 그래서 TLS에서는 비대칭키 기반의 인증과 키 교환 방식을 이용해 안전하게 Session Key를 만들고, 실제 대량의 데이터 통신에서는 빠른 대칭키 암호화를 사용합니다."

**핵심 요약**

**비대칭키 = 안전한 인증·키 합의 / 대칭키 = 빠른 실제 데이터 암호화**

---

<a name="q22-3"></a>
#### ↳ Q22-3. TLS 1.2와 TLS 1.3 Handshake의 차이는?

> "TLS 1.3은 이전 버전에 비해 Handshake 과정을 단순화해 새로운 연결에서 Application Data를 보내기까지 필요한 왕복 횟수를 줄였습니다.
>
> 일반적인 TLS 1.3 Full Handshake는 1-RTT로 수행할 수 있습니다.
>
> 이전 연결에서 얻은 Session 정보를 재사용하는 경우에는 조건에 따라 0-RTT Early Data도 사용할 수 있습니다.
>
> 다만 0-RTT는 Replay 위험 등을 고려해야 하기 때문에 아무 요청에나 사용할 수 있는 것은 아닙니다."

**핵심 요약**

**TLS 1.3 = 일반 1-RTT, 재접속에서는 조건에 따라 0-RTT 가능**

---

<a name="q23"></a>
### Q23. 3-Way Handshake에서 Sequence Number는 왜 교환하나요?

> "TCP는 각 방향의 데이터에 Sequence Number를 사용합니다.
>
> 3-Way Handshake 과정에서 Client와 Server가 각각 자신의 Initial Sequence Number인 ISN을 알려주고 서로 확인합니다.
>
> 이후 이 값을 기준으로 데이터 순서를 관리하고 어떤 데이터가 정상적으로 도착했는지 확인할 수 있습니다."

**핵심 요약**

**ISN을 서로 알려주고 그 번호를 기준으로 데이터 순서를 관리한다**

---

<a name="q23-1"></a>
#### ↳ Q23-1. 초기 Sequence Number를 왜 항상 0으로 시작하지 않나요?

> "매 연결마다 적절한 ISN을 선택하면 과거 연결의 지연된 Segment를 새로운 연결의 데이터와 구분하는 데 도움이 됩니다.
>
> 또한 Sequence Number가 쉽게 예측되면 공격자가 유효한 번호를 추측해서 위조 Segment를 만들어낼 위험이 커질 수 있기 때문에 보안 측면에서도 예측하기 어렵게 만드는 것이 중요합니다."

**핵심 요약**

**ISN은 옛 연결과 구분하고 Sequence Number 예측 공격을 어렵게 하기 위해 예측하기 어렵게 선택**

---

<a name="q24"></a>
### Q24. Handshake 비용을 줄이는 방법에는 무엇이 있나요?

> "가장 기본적인 방법은 이미 생성한 연결을 재사용하는 것입니다.
>
> HTTP Persistent Connection이나 Connection Pool을 사용하면 TCP 연결을 반복해서 생성하는 비용을 줄일 수 있습니다.
>
> TLS에서는 Session Resumption을 이용해 이전 연결 정보를 재활용할 수 있고, TLS 1.3이나 QUIC에서는 재접속 시 더 적은 왕복으로 통신을 시작할 수 있는 방식도 제공합니다."

**핵심 요약**

**연결을 재사용하고 이전 Session 정보를 활용해 Handshake 횟수와 RTT를 줄인다**

---

<a name="section-04"></a>
## 연관 종합 질문

<a name="q25"></a>
### Q25. TCP와 UDP의 가장 큰 차이는 무엇인가요?

> "TCP는 연결을 수립하고 순서 제어, 재전송, 흐름 제어, 혼잡 제어 등을 제공해 신뢰성 있는 데이터 전달을 지원합니다.
>
> UDP는 이러한 기능을 기본 제공하지 않는 대신 Header와 처리 구조가 단순하고 프로토콜 오버헤드가 작습니다."

**핵심 요약**

**TCP = 신뢰성 / UDP = 가벼움**

---

<a name="q26"></a>
### Q26. TCP는 왜 신뢰성이 있고 UDP는 왜 신뢰성이 없다고 하나요?

> "TCP에는 Sequence Number, ACK, 재전송, 흐름 제어 등 데이터 전달 상태를 추적하고 복구하기 위한 기능이 포함되어 있습니다.
>
> UDP에는 이런 기능이 기본적으로 없고 Datagram을 독립적으로 전달하기 때문입니다."

**핵심 요약**

**TCP는 전달 상태를 관리하지만 UDP는 기본적으로 관리하지 않는다**

---

<a name="q27"></a>
### Q27. TCP와 QUIC의 차이는 무엇인가요?

> "TCP는 운영체제에서 널리 제공되는 연결 지향 전송 프로토콜이고 하나의 연결에서 순서가 보장된 Byte Stream을 제공합니다.
>
> QUIC은 UDP 위에서 동작하면서 자체적으로 신뢰성, 혼잡 제어, 암호화, 여러 독립 Stream 등을 제공합니다.
>
> 특히 Stream을 독립적으로 관리할 수 있어 한 Stream의 손실이 다른 Stream까지 막는 문제를 줄일 수 있습니다."

**핵심 요약**

**TCP = 하나의 신뢰성 있는 Byte Stream / QUIC = UDP 위의 여러 독립 Stream + 신뢰성 + 보안**

---

<a name="section-05"></a>
## 추가 질문

<a name="q28"></a>
### Q28. IP가 있는데 왜 TCP/UDP 같은 전송 계층이 필요한가요?

> "IP는 기본적으로 패킷을 목적지 컴퓨터, 즉 호스트까지 전달하는 역할을 합니다.
>
> 하지만 하나의 서버에는 웹 서버, DB, SSH처럼 여러 애플리케이션이 동시에 실행될 수 있기 때문에, 패킷이 서버에 도착했다는 것만으로는 어느 프로그램에 전달해야 하는지 알 수 없습니다.
>
> 그래서 전송 계층에서는 Port Number를 사용해 데이터를 올바른 애플리케이션 프로세스에 전달합니다. 또한 TCP는 필요에 따라 순서 보장, 재전송, 흐름 제어 같은 기능도 제공합니다."

**핵심 요약**

**IP = 컴퓨터 찾기 / Port = 컴퓨터 안의 애플리케이션 찾기**

---

<a name="q29"></a>
### Q29. TCP의 Byte Stream과 UDP의 Datagram 방식은 어떻게 다른가요?

> "TCP는 데이터를 메시지 단위가 아니라 연속된 Byte Stream으로 제공합니다.
>
> 그래서 송신 측에서 `send()`를 두 번 호출했다고 해서 수신 측에서도 반드시 두 번에 나눠서 읽히는 것은 아닙니다. 합쳐지거나 더 잘게 나뉘어 들어올 수 있습니다.
>
> 반면 UDP는 Datagram 단위를 유지하기 때문에 하나의 Datagram으로 보낸 데이터는 하나의 Datagram이라는 경계를 가진 채 전달됩니다."

**핵심 요약**

**TCP = 바이트 흐름 / UDP = 메시지 단위 유지**

---

<a name="q30"></a>
### Q30. TCP의 ACK 번호는 정확히 무엇을 의미하나요?

> "TCP의 ACK 번호는 다음에 받고 싶은 Byte 번호를 의미합니다.
>
> 예를 들어 `ACK = 1500`이라면 일반적인 누적 ACK 기준으로 1499번 Byte까지 정상적으로 받았고, 다음에는 1500번부터 보내달라는 뜻입니다.
>
> 따라서 ACK은 특정 패킷 하나만 받았다는 의미라기보다, 그 이전 범위의 데이터까지 정상적으로 받았다는 누적 확인의 의미를 가집니다."

**핵심 요약**

**ACK N = N-1까지 받았고 다음은 N부터 보내달라는 뜻**

---

<a name="q31"></a>
### Q31. RTO와 RTT는 어떤 관계인가요?

> "RTT는 데이터를 보내고 응답이 돌아오기까지 걸리는 왕복 시간이고, RTO는 ACK이 오지 않았을 때 재전송하기까지 기다리는 시간입니다.
>
> RTO를 너무 짧게 잡으면 네트워크가 단순히 조금 느린 상황에서도 불필요한 재전송이 발생할 수 있고, 너무 길게 잡으면 실제 손실이 발생했을 때 복구가 늦어집니다.
>
> 그래서 TCP는 통신 과정에서 관찰한 RTT를 바탕으로 적절한 RTO를 계산합니다."

**핵심 요약**

**RTT를 관찰해서 적절한 재전송 시간 RTO를 정한다**

---

<a name="q32"></a>
### Q32. 흐름 제어와 혼잡 제어는 실제 전송량에 어떻게 함께 적용되나요?

> "흐름 제어는 수신자가 얼마나 받을 수 있는지를 나타내는 `rwnd`를 기준으로 하고, 혼잡 제어는 네트워크가 얼마나 감당할 수 있는지를 나타내는 `cwnd`를 기준으로 합니다.
>
> 실제 송신자는 두 조건을 모두 만족해야 하기 때문에 개념적으로 한 번에 전송할 수 있는 양은 `min(rwnd, cwnd)`의 제한을 받습니다.
>
> 즉 수신자는 충분히 받을 수 있어도 네트워크가 혼잡하면 적게 보내야 하고, 네트워크가 여유로워도 수신 버퍼가 작으면 그에 맞춰 줄여야 합니다."

**핵심 요약**

**실제 전송량 = 수신자 여유와 네트워크 여유 중 더 작은 쪽**

---

<a name="q33"></a>
### Q33. TCP의 Half-Close란 무엇인가요?

> "TCP는 Full Duplex 통신이기 때문에 양방향 데이터 흐름을 독립적으로 종료할 수 있습니다.
>
> 한쪽이 FIN을 보냈다는 것은 자신은 더 이상 보낼 데이터가 없다는 뜻이지, 상대방도 즉시 전송을 멈춰야 한다는 뜻은 아닙니다.
>
> 따라서 한 방향의 송신은 종료됐지만 반대 방향에서는 아직 데이터를 보낼 수 있는 상태가 존재하며, 이를 Half-Close라고 합니다."

**핵심 요약**

**Half-Close = 한쪽 송신은 끝났지만 반대 방향 통신은 계속 가능**

---

<a name="q34"></a>
### Q34. CLOSE_WAIT이 계속 증가하면 어떤 문제를 의심해야 하나요?

> "CLOSE_WAIT은 상대방이 FIN을 보내 연결 종료를 요청했고, 운영체제가 이를 ACK했지만 애플리케이션이 아직 자신의 소켓을 닫지 않은 상태입니다.
>
> 따라서 CLOSE_WAIT이 계속 증가한다면 애플리케이션에서 `close()` 처리를 제대로 하지 않거나 네트워크 연결 자원을 적절히 정리하지 않는 문제를 의심할 수 있습니다.
>
> TIME_WAIT은 정상적인 연결 종료 과정에서도 많이 나타날 수 있지만, CLOSE_WAIT이 지속적으로 쌓이는 것은 애플리케이션의 연결 종료 처리 문제일 가능성이 큽니다."

**핵심 요약**

**CLOSE_WAIT 누적 = 애플리케이션의 소켓 close 누락 의심**

---

<a name="q35"></a>
### Q35. TCP Keep-Alive와 HTTP Keep-Alive는 같은 개념인가요?

> "아닙니다.
>
> TCP Keepalive는 일정 시간 동안 통신이 없는 TCP 연결이 실제로 살아 있는지 확인하기 위한 기능입니다.
>
> 반면 HTTP Keep-Alive는 HTTP 요청마다 새로운 TCP 연결을 만들지 않고 기존 TCP 연결을 여러 요청에 재사용하는 개념입니다.
>
> 따라서 둘 다 '연결을 유지한다'는 표현을 쓰지만 목적은 다릅니다."

**핵심 요약**

**TCP Keepalive = 연결 생존 확인 / HTTP Keep-Alive = 연결 재사용**

---

<a name="q36"></a>
### Q36. TCP의 Sequence Number는 왜 세그먼트 번호가 아니라 Byte 번호인가요?

> "TCP는 애플리케이션에 메시지나 Segment 단위가 아니라 연속된 Byte Stream을 제공하기 때문입니다.
>
> 따라서 TCP는 각 Segment 자체에 번호를 붙이는 것이 아니라, 전체 Byte Stream에서 데이터가 어느 위치에 있는지를 Sequence Number로 관리합니다.
>
> 이렇게 하면 Segment의 크기가 달라지거나 데이터가 나뉘어 전송되더라도 정확한 Byte 위치를 기준으로 순서와 손실을 관리할 수 있습니다."

**핵심 요약**

**TCP는 Segment가 아니라 Byte Stream을 관리하므로 Sequence Number도 Byte 기준**

---

<a name="q37"></a>
### Q37. HTTP/2는 Multiplexing을 하는데도 왜 TCP의 HOL Blocking 영향을 받나요?

> "HTTP/2는 하나의 TCP 연결 안에서 여러 HTTP Stream을 동시에 처리할 수 있습니다.
>
> 하지만 그 아래 전송 계층은 여전히 하나의 TCP Byte Stream입니다.
>
> 따라서 TCP에서 앞쪽 Byte가 유실되면 뒤쪽 데이터가 도착했더라도 누락된 데이터가 복구될 때까지 애플리케이션으로 전달되지 못할 수 있고, 이 때문에 여러 HTTP/2 Stream이 함께 영향을 받을 수 있습니다.
>
> QUIC은 Stream을 전송 계층 수준에서 독립적으로 관리해 이 문제를 줄입니다."

**핵심 요약**

**HTTP/2는 Stream은 여러 개지만 아래 TCP는 하나의 Byte Stream이라 같이 막힐 수 있다**

---

<a name="q38"></a>
### Q38. QUIC도 신뢰성을 제공하는데 왜 TCP 대신 UDP 위에서 구현했나요?

> "QUIC은 UDP의 Datagram 전달 기능을 기반으로 하면서, 그 위에 신뢰성, 혼잡 제어, 암호화, Stream 관리 등을 자체적으로 구현합니다.
>
> 이렇게 하면 TCP의 기존 연결 관리 방식에 묶이지 않고 여러 독립 Stream을 제공할 수 있고, 사용자 공간에서 프로토콜을 발전시키기도 비교적 유연합니다.
>
> 즉 UDP가 신뢰성이 좋아서 사용하는 것이 아니라, 최소한의 전송 기능만 가진 UDP 위에 QUIC이 필요한 기능을 새롭게 설계한 것입니다."

**핵심 요약**

**UDP의 단순한 바닥 위에 QUIC이 필요한 전송 기능을 새로 설계한다**

---

<a name="q39"></a>
### Q39. TIME_WAIT이 많다고 바로 커널 설정부터 바꾸면 안 되는 이유는 무엇인가요?

> "TIME_WAIT은 TCP의 정상적인 연결 종료 과정에서 필요한 상태이기 때문입니다.
>
> 짧은 연결을 자주 생성하고 종료하는 시스템에서는 TIME_WAIT이 많이 보이는 것이 자연스러울 수 있습니다.
>
> 따라서 단순히 개수가 많다는 이유만으로 문제라고 판단하기보다, 누가 Active Close를 하는지, 연결을 재사용하고 있는지, Ephemeral Port가 실제로 부족한지 등을 함께 확인해야 합니다."

**핵심 요약**

**TIME_WAIT 많음 ≠ 장애, 연결 패턴과 실제 자원 부족 여부를 같이 봐야 한다**

<a name="section-07"></a>
## 핵심 요약

**TCP = 신뢰성을 위해 연결·ACK·재전송·흐름 제어·혼잡 제어를 제공**

**UDP = 이런 기능을 기본 제공하지 않아 단순하고 가볍다**

**Flow Control = 수신자 보호 / Congestion Control = 네트워크 보호**

**3-Way Handshake = 양쪽 연결 상태와 Sequence Number를 확인**

**TCP Handshake = 연결 / TLS Handshake = 보안**

**비대칭키 = 인증·키 합의 / 대칭키 = 빠른 데이터 암호화**

**Handshake 비용은 연결 재사용으로 줄인다**

<a name="section-08"></a>
## 구분해서 이해할 개념

**TCP = 패킷 하나 보낼 때마다 ACK 하나를 기다리는 방식이 아님**

**HTTP Keep-Alive ≠ TCP Keepalive**

**UDP = 무조건 TCP보다 빠른 것은 아님**

**DNS = 항상 UDP가 아님**

**QUIC = 단순히 TCP를 그대로 다시 만든 것이 아님**

**QUIC에서도 같은 Stream 내부 HOL은 존재할 수 있음**

**TIME_WAIT은 서버에만 생기는 상태가 아님**

**TLS에서 대칭키를 그대로 네트워크로 보내는 것이 아님**

**TLS는 비대칭키와 대칭키를 역할에 맞게 조합**

**TLS 1.3의 0-RTT는 모든 연결에서 가능한 것이 아님**

**3-Way Handshake Packet이 손실되면 재전송 타이머가 동작**

**매 요청마다 TCP/TLS 연결을 새로 만들면 RTT 비용이 반복됨**
