## Index (인덱스)

<a name="q1"></a>
### Q1. [대표 질문] 데이터베이스 인덱스란 무엇이고 왜 사용하나요?

> "인덱스는 데이터베이스에서 특정 데이터를 빠르게 검색하기 위한 자료구조입니다.
>
> 적절한 인덱스가 없으면 조건에 맞는 데이터를 찾기 위해 테이블 전체를 탐색해야 할 수 있지만, 인덱스가 있으면 검색 범위를 줄여 효율적으로 접근할 수 있습니다.
>
> 다만 인덱스를 유지하기 위한 저장 공간과 데이터 변경 비용이 발생합니다."

**핵심 요약**

인덱스는 검색 성능을 높이기 위한 자료구조이지만 저장 공간과 쓰기 비용이 발생한다.

<a name="q1-1"></a>
#### ↳ Q1-1. 인덱스는 무조건 생성하는 것이 좋나요?

> "아닙니다. 인덱스가 많아질수록 저장 공간과 INSERT, UPDATE, DELETE 시 유지 비용이 증가할 수 있습니다.
>
> 따라서 조회 빈도, 검색 조건, 데이터 분포, 쓰기 작업의 비율 등을 고려해 필요한 인덱스만 생성해야 합니다."

**핵심 요약**

인덱스는 많을수록 좋은 것이 아니라 조회 이점과 유지 비용을 고려해 생성해야 한다.

<a name="q2"></a>
### Q2. 인덱스가 없으면 데이터베이스는 어떻게 검색하나요?

> "적절한 인덱스가 없다면 데이터베이스는 테이블 데이터를 전체적으로 읽으면서 검색 조건에 맞는 행을 찾을 수 있습니다.
>
> 이를 Full Table Scan이라고 하며, 데이터가 많을수록 읽어야 하는 페이지가 증가할 수 있습니다."

**핵심 요약**

적절한 인덱스가 없으면 테이블 전체를 탐색해야 할 수 있다.

<a name="q2-1"></a>
#### ↳ Q2-1. Full Table Scan과 Index Scan의 차이는 무엇인가요?

> "Full Table Scan은 테이블 전체 데이터를 읽는 방식이고, Index Scan은 인덱스 구조를 읽어 데이터를 탐색하는 방식입니다.
>
> 인덱스를 활용하면 검색 범위를 줄일 수 있지만, 전체 데이터 중 많은 행을 조회한다면 Full Table Scan이 더 효율적일 수 있습니다."

**핵심 요약**

Full Table Scan은 테이블 전체를, Index Scan은 인덱스를 읽는 방식이다.

<a name="q2-2"></a>
#### ↳ Q2-2. [핵심 질문] Index Seek와 Index Scan의 차이는 무엇인가요?

> "Index Seek는 검색 키를 이용해 인덱스의 특정 위치나 범위로 접근하는 방식입니다.
>
> Index Scan은 인덱스의 전체 또는 일부를 순차적으로 읽는 방식입니다.
>
> 구체적인 실행 계획 명칭과 접근 방식은 DBMS마다 다를 수 있습니다."

**핵심 요약**

Index Seek는 특정 위치를 찾아 접근하고 Index Scan은 인덱스를 순차적으로 읽는다.

| 구분 | Index Seek | Index Scan |
| --- | --- | --- |
| 의미 | 키를 이용해 특정 위치로 접근 | 인덱스 항목을 순차적으로 읽음 |
| 접근 범위 | 특정 키 또는 키 범위 | 인덱스 전체 또는 일부 |
| 대표 사례 | `WHERE id = 30` | 전체 ID 목록 조회 |
| 효율적인 상황 | 원하는 데이터가 적을 때 | 많은 데이터를 읽어야 할 때 |

<a name="q3"></a>
### Q3. 인덱스의 장점과 단점은 무엇인가요?

> "장점은 검색 조건에 맞는 데이터에 빠르게 접근할 수 있고, JOIN이나 ORDER BY 등의 처리 성능을 개선할 수 있다는 점입니다.
>
> 단점은 별도의 저장 공간이 필요하고 데이터 삽입, 수정, 삭제 시 관련 인덱스도 관리해야 하므로 쓰기 비용이 증가할 수 있다는 점입니다."

**핵심 요약**

인덱스는 조회 성능 개선에 유리하지만 저장 공간과 쓰기 비용이 증가한다.

<a name="q3-1"></a>
#### ↳ Q3-1. 인덱스는 왜 쓰기 성능을 저하시킬 수 있나요?

> "INSERT, UPDATE, DELETE 시 테이블 데이터뿐 아니라 관련 인덱스 항목도 관리해야 하기 때문입니다.
>
> 특히 B+Tree는 키의 정렬 순서를 유지해야 하므로 삽입 시 페이지 분할이 발생할 수 있고, 키 변경이나 삭제 과정에서도 추가 관리 비용이 발생할 수 있습니다."

**핵심 요약**

데이터 변경 시 인덱스도 함께 유지해야 하므로 쓰기 성능에 부담이 발생할 수 있다.

<a name="q4"></a>
### Q4. 인덱스를 사용하면 무조건 조회 성능이 좋아지나요?

> "아닙니다. 조회 대상이 테이블의 대부분을 차지하거나 테이블 크기가 작다면 전체 스캔이 더 효율적일 수 있습니다.
>
> 또한 인덱스 사용 후 실제 행 데이터를 추가로 읽는 비용이 크면 인덱스를 사용하는 것이 불리할 수 있습니다.
>
> 옵티마이저는 통계 정보와 예상 비용을 바탕으로 접근 방식을 선택합니다."

**핵심 요약**

인덱스의 성능 개선 효과는 조회 범위와 데이터 분포에 따라 달라진다.

<a name="q5"></a>
### Q5. 어떤 컬럼에 인덱스를 생성하는 것이 좋나요?

> "WHERE 조건이나 JOIN에 자주 사용되는 컬럼, 정렬이나 범위 조회에 활용되는 컬럼을 우선 고려합니다.
>
> 검색 조건으로 많은 데이터를 걸러낼 수 있는 컬럼은 인덱스 효율이 높을 수 있습니다.
>
> 다만 데이터 분포와 실제 조회 패턴, 쓰기 비용을 함께 고려해야 합니다."

**핵심 요약**

인덱스는 자주 사용하는 검색·조인·정렬 조건과 데이터 분포를 고려해 생성한다.

<a name="q5-1"></a>
#### ↳ Q5-1. Cardinality란 무엇인가요?

> "Cardinality(카디널리티)는 특정 컬럼에 존재하는 서로 다른 값의 개수를 의미합니다.
>
> 회원 ID처럼 고유값이 많은 컬럼은 카디널리티가 높고, 성별처럼 값의 종류가 적은 컬럼은 낮습니다."

**핵심 요약**

카디널리티는 컬럼에 존재하는 서로 다른 값의 개수이다.

<a name="q5-2"></a>
#### ↳ Q5-2. Selectivity란 무엇인가요?

> "Selectivity(셀렉티비티, 선택도)는 검색 조건이 전체 행 중 얼마나 많은 행을 선택하는지 나타내는 개념입니다.
>
> 검색 대상 행의 비율이 낮으면 일반적으로 인덱스를 활용해 읽을 데이터의 양을 줄이기 유리합니다.
>
> 단, 자료에 따라 고유값 비율을 선택도라고 부르기도 있으므로 정의를 확인해야 합니다."

**핵심 요약**

인덱스 효율은 검색 조건이 전체 데이터에서 얼마나 많은 행을 걸러낼 수 있는지와 관련이 있다.

<a name="q5-3"></a>
#### ↳ Q5-3. [핵심 질문] 카디널리티가 낮은 컬럼에는 인덱스를 생성하면 안 되나요?

> "반드시 그렇지는 않습니다.
>
> 카디널리티가 낮더라도 특정 값의 비율이 매우 적거나, 다른 컬럼과 함께 복합 인덱스를 구성한다면 유용할 수 있습니다.
>
> 따라서 고유값의 개수뿐 아니라 실제 데이터 분포와 검색 조건을 고려해야 합니다."

**핵심 요약**

카디널리티가 낮더라도 데이터 분포와 검색 패턴에 따라 인덱스가 효과적일 수 있다.

<a name="q6"></a>
### Q6. 인덱스에는 어떤 종류가 있나요?

> "자료구조에 따라 B-Tree 계열 인덱스와 Hash 인덱스 등이 있습니다.
>
> 컬럼 구성에 따라 단일 인덱스와 복합 인덱스로, 제약 조건에 따라 Unique Index 등으로 구분할 수 있습니다.
>
> MySQL InnoDB에서는 실제 저장 방식에 따라 Clustered Index와 Secondary Index로도 구분합니다."

**핵심 요약**

인덱스는 자료구조, 컬럼 구성, 제약 조건, 저장 방식에 따라 구분할 수 있다.

<a name="q6-1"></a>
#### ↳ Q6-1. B-Tree 계열 인덱스와 Hash 인덱스의 차이는 무엇인가요?

> "B-Tree 계열 인덱스는 키의 정렬 순서를 유지하므로 동등 검색과 범위 검색에 활용할 수 있습니다.
>
> Hash 인덱스는 해시값을 이용해 동등 검색에 적합하지만 일반적으로 범위 검색이나 정렬에는 적합하지 않습니다."

**핵심 요약**

B-Tree 계열은 동등·범위 검색에 유리하고 Hash는 동등 검색에 특화되어 있다.

<a name="q7"></a>
### Q7. 단일 인덱스와 복합 인덱스의 차이는 무엇인가요?

> "단일 인덱스는 하나의 컬럼으로 구성되고, 복합 인덱스는 여러 컬럼을 정해진 순서로 구성합니다.
>
> 복합 인덱스는 선행 컬럼을 기준으로 키가 정렬되므로 컬럼 순서에 따라 검색 효율이 달라질 수 있습니다."

**핵심 요약**

복합 인덱스는 여러 컬럼을 함께 사용하며 컬럼의 순서가 중요하다.

<a name="q7-1"></a>
#### ↳ Q7-1. 복합 인덱스에서 컬럼 순서가 중요한 이유는 무엇인가요?

> "복합 B+Tree 인덱스는 지정된 컬럼 순서대로 키가 정렬되기 때문입니다.
>
> 선행 컬럼에 적절한 검색 조건이 있으면 탐색 범위를 효과적으로 좁힐 수 있지만, 선행 컬럼이 없으면 일반적인 탐색 효율이 떨어질 수 있습니다."

**핵심 요약**

복합 인덱스는 선행 컬럼부터 정렬되므로 컬럼 순서가 검색 성능에 영향을 준다.

<a name="q7-2"></a>
#### ↳ Q7-2. Leftmost Prefix Rule이란 무엇인가요?

> "Leftmost Prefix Rule(레프트모스트 프리픽스 룰)은 복합 인덱스의 가장 왼쪽 컬럼부터 조건이 주어질 때 일반적으로 효율적인 탐색이 가능하다는 원칙입니다.
>
> 다만 DBMS에 따라 Skip Scan 등의 최적화가 가능하므로 선행 컬럼 조건이 없으면 인덱스를 절대 사용할 수 없다는 뜻은 아닙니다."

**핵심 요약**

복합 인덱스는 왼쪽 선행 컬럼부터 활용하는 것이 일반적으로 유리하다.

<a name="q7-3"></a>
#### ↳ Q7-3. [핵심 질문] 복합 인덱스에서 동등 조건과 범위 조건의 순서가 중요한 이유는 무엇인가요?

> "동등 조건으로 먼저 검색 범위를 좁히고, 이후 범위 조건에 해당하는 구간을 탐색할 수 있도록 구성하면 효율적일 수 있기 때문입니다.
>
> 다만 실제 인덱스 순서는 데이터 분포와 정렬 조건, 다른 쿼리 패턴도 고려해 결정해야 합니다."

**핵심 요약**

복합 인덱스는 동등·범위 조건과 실제 조회 패턴을 고려해 컬럼 순서를 결정한다.

<a name="q8"></a>
### Q8. Covering Index란 무엇인가요?

> "Covering Index(커버링 인덱스)는 쿼리 처리에 필요한 컬럼을 인덱스만으로 모두 얻을 수 있는 경우를 의미합니다.
>
> 실제 행 데이터에 추가로 접근하는 과정을 줄일 수 있어 조회 성능을 개선할 수 있습니다."

**핵심 요약**

커버링 인덱스는 인덱스만으로 필요한 데이터를 얻어 추가 행 조회 비용을 줄인다.

<a name="q8-1"></a>
#### ↳ Q8-1. [핵심 질문] 커버링 인덱스가 항상 좋은가요?

> "아닙니다. 커버링을 위해 인덱스에 많은 컬럼을 포함하면 인덱스 크기와 유지 비용이 증가할 수 있습니다.
>
> 따라서 조회 성능의 이점과 저장 공간, 쓰기 비용을 함께 고려해야 합니다."

**핵심 요약**

커버링 인덱스도 인덱스 크기와 쓰기 비용을 고려해 설계해야 한다.

<a name="q9"></a>
### Q9. 인덱스를 생성했는데도 조회 성능이 개선되지 않는 이유는 무엇인가요?

> "인덱스가 존재하더라도 옵티마이저가 인덱스 사용이 비효율적이라고 판단할 수 있기 때문입니다.
>
> 조회 대상 행이 많거나 인덱스 컬럼에 함수를 적용하거나 복합 인덱스의 컬럼 순서가 검색 조건과 맞지 않으면 효율적으로 활용하지 못할 수 있습니다."

**핵심 요약**

인덱스가 있어도 데이터 분포와 검색 조건에 따라 사용되지 않거나 효과가 작을 수 있다.

<a name="q9-1"></a>
#### ↳ Q9-1. 인덱스의 실제 사용 여부는 어떻게 확인하나요?

> "데이터베이스의 실행 계획을 확인합니다.
>
> MySQL에서는 EXPLAIN을 통해 선택된 인덱스를 나타내는 key, 접근 방식을 나타내는 type, 예상 행 수를 나타내는 rows 등을 확인할 수 있습니다.
>
> 실제 실행 통계도 함께 살펴보면 인덱스 효과를 더 정확하게 판단할 수 있습니다."

**핵심 요약**

인덱스의 사용 여부는 EXPLAIN 실행 계획으로 확인한다.

<a name="q9-2"></a>
#### ↳ Q9-2. LIKE 검색에서도 인덱스를 사용할 수 있나요?

> "일반적인 B-Tree 인덱스에서는 검색어 앞부분이 고정된 패턴이 인덱스 범위 탐색에 유리할 수 있습니다.
>
> 반면 검색어 시작 부분에 와일드카드가 포함되면 일반적인 인덱스 범위 탐색이 어려워질 수 있습니다."

**핵심 요약**

LIKE 검색은 앞부분이 고정된 패턴이 B-Tree 인덱스 활용에 유리하다.

<a name="q9-3"></a>
#### ↳ Q9-3. [핵심 질문] 인덱스 컬럼에 함수를 적용하면 왜 성능이 저하될 수 있나요?

> "일반적인 B-Tree 인덱스는 컬럼의 원래 값을 기준으로 정렬되어 있습니다.
>
> 해당 컬럼에 함수를 적용하면 기존 인덱스의 정렬 순서를 직접 활용하기 어려워질 수 있습니다.
>
> 다만 DBMS가 지원하는 함수 기반 인덱스 등을 이용하면 최적화가 가능합니다."

**핵심 요약**

인덱스 컬럼에 함수를 적용하면 일반적인 인덱스 범위 탐색이 어려워질 수 있다.

<a name="section-02"></a>
## B-Tree / B+Tree

<a name="q10"></a>
### Q10. B-Tree란 무엇인가요?

> "B-Tree(비 트리)는 여러 개의 키를 하나의 노드에 저장하는 균형 잡힌 다진 탐색 트리입니다.
>
> 모든 리프가 같은 깊이에 위치하며, 삽입과 삭제 과정에서도 노드 분할과 병합 등을 통해 균형을 유지합니다.
>
> 일반적으로 탐색, 삽입, 삭제를 O(log N) 시간에 수행할 수 있습니다."

**핵심 요약**

B-Tree는 여러 키를 한 노드에 저장하고 균형을 유지하는 다진 탐색 트리이다.

<a name="q10-1"></a>
#### ↳ Q10-1. B-Tree가 균형을 유지하는 이유는 무엇인가요?

> "트리가 한쪽으로 지나치게 치우치면 특정 데이터를 탐색할 때 많은 노드를 거쳐야 하기 때문입니다.
>
> B-Tree는 모든 리프의 깊이를 동일하게 유지하여 검색 경로가 불균형해지는 것을 방지합니다."

**핵심 요약**

B-Tree는 검색 경로가 지나치게 길어지는 것을 방지하기 위해 균형을 유지한다.

<a name="q11"></a>
### Q11. [대표 질문] B+Tree란 무엇이고 데이터베이스 인덱스에 적합한 이유는 무엇인가요?

> "B+Tree(비 플러스 트리)는 정렬된 키를 관리하는 균형 잡힌 다진 탐색 트리입니다.
>
> 내부 노드는 탐색을 위한 키와 자식 노드 정보를 저장하고, 실제 데이터 항목은 리프 노드에 저장합니다.
>
> 하나의 노드에서 여러 자식으로 분기하여 트리 높이를 낮출 수 있고, 정렬된 리프를 순차적으로 탐색할 수 있어 데이터베이스 인덱스에 적합합니다."

**핵심 요약**

B+Tree는 낮은 트리 높이와 정렬된 리프 구조로 검색과 범위 탐색에 유리하다.

<a name="q12"></a>
### Q12. B+Tree는 어떤 구조로 이루어져 있나요?

> "B+Tree는 Root Node, Internal Node, Leaf Node로 구성됩니다.
>
> Root Node는 탐색 시작점이고, Internal Node는 검색 키를 비교해 다음 경로를 결정합니다.
>
> Leaf Node는 실제 인덱스 항목을 저장하며 모든 리프 노드는 동일한 깊이에 위치합니다."

**핵심 요약**

B+Tree는 Root, Internal, Leaf Node로 구성되며 모든 리프의 깊이가 같다.

<a name="q12-1"></a>
#### ↳ Q12-1. Root Node, Internal Node, Leaf Node의 역할은 무엇인가요?

> "Root Node(루트 노드)는 탐색을 시작하는 노드입니다.
>
> Internal Node(인터널 노드)는 키를 비교하여 다음에 탐색할 자식 노드를 결정합니다.
>
> Leaf Node(리프 노드)는 실제 데이터 항목 또는 행을 찾기 위한 정보를 저장합니다."

**핵심 요약**

Root는 시작점, Internal은 경로 결정, Leaf는 인덱스 항목 저장을 담당한다.

<a name="q12-2"></a>
#### ↳ Q12-2. 모든 리프 노드가 같은 깊이에 있다는 것은 무슨 뜻인가요?

> "Root에서 어떤 리프까지 이동하더라도 거치는 트리의 계층 수가 동일하다는 뜻입니다.
>
> 모든 데이터를 하나의 페이지에 저장하거나 트리 깊이가 항상 일정한 숫자로 고정된다는 뜻은 아닙니다.
>
> 데이터가 증가하면 트리의 높이 자체는 커질 수 있지만 모든 리프는 같은 깊이를 유지합니다."

**핵심 요약**

B+Tree는 데이터량에 따라 높이가 변할 수 있지만 모든 리프는 같은 깊이에 있다.

<a name="q13"></a>
### Q13. B-Tree와 B+Tree의 차이는 무엇인가요?

> "B-Tree는 내부 노드에도 실제 데이터 항목을 저장할 수 있지만, B+Tree는 실제 데이터 항목을 리프 노드에 집중시킵니다.
>
> B+Tree는 내부 노드에 더 많은 탐색 키와 자식 포인터를 저장하기 유리하고, 리프 항목이 순서대로 연결되어 있어 범위 검색에 효율적입니다."

**핵심 요약**

B+Tree는 데이터 항목을 리프에 집중시키고 정렬된 리프를 연결하여 범위 탐색에 유리하다.

<a name="q13-1"></a>
#### ↳ Q13-1. 왜 Hash 자료구조 대신 B+Tree를 사용하나요?

> "Hash 자료구조는 정확히 일치하는 값을 찾는 동등 검색에 적합하지만, 일반적으로 키의 정렬 순서를 유지하지 않아 범위 검색이나 정렬에 적합하지 않습니다.
>
> 반면 B+Tree는 키를 정렬된 상태로 관리하므로 동등 검색뿐 아니라 범위 검색과 정렬에도 활용할 수 있습니다."

**핵심 요약**

B+Tree는 동등 검색뿐 아니라 범위 검색과 정렬까지 지원하기 때문에 범용 인덱스로 적합하다.

<a name="q14"></a>
### Q14. B+Tree가 일반적인 이진 탐색 트리보다 유리한 이유는 무엇인가요?

> "일반적인 이진 탐색 트리는 하나의 노드에서 최대 두 자식으로 분기하고, 균형을 유지하지 않으면 한쪽으로 치우칠 수 있습니다.
>
> B+Tree는 하나의 노드에 여러 키를 저장하고 많은 자식으로 분기하므로 트리 높이를 낮게 유지할 수 있습니다.
>
> 이를 통해 데이터베이스의 페이지 접근 횟수를 줄이는 데 유리합니다."

**핵심 요약**

B+Tree는 높은 분기 수와 균형 구조로 트리 높이를 낮추고 페이지 I/O를 줄인다.

<a name="q14-1"></a>
#### ↳ Q14-1. Fan-out이란 무엇인가요?

> "Fan-out(팬아웃)은 내부 노드 하나에서 연결할 수 있는 자식 노드의 수입니다.
>
> Fan-out이 크면 같은 수의 데이터를 저장하더라도 필요한 트리 높이가 낮아질 수 있으므로 탐색 효율에 유리합니다."

**핵심 요약**

Fan-out은 한 노드의 자식 수이며 클수록 트리 높이를 낮추기 유리하다.

<a name="q14-2"></a>
#### ↳ Q14-2. B+Tree의 시간 복잡도는 어떻게 되나요?

> "B+Tree의 검색, 삽입, 삭제는 일반적으로 트리 높이에 비례하여 O(log N)으로 표현할 수 있습니다.
>
> 다만 실제 데이터베이스 성능은 비교 연산뿐 아니라 디스크 페이지 I/O와 메모리 캐시 적중 여부에도 영향을 받습니다."

**핵심 요약**

B+Tree의 기본 연산은 일반적으로 로그 시간이며 실제 성능은 페이지 I/O의 영향을 받는다.

<a name="q15"></a>
### Q15. B+Tree에서 데이터를 검색하는 과정은 무엇인가요?

> "Root Node에서 검색 키를 비교해 탐색할 자식 노드를 결정합니다.
>
> 이후 Internal Node에서 같은 과정을 반복하여 Leaf Node에 도달한 뒤 해당 키의 인덱스 항목을 찾습니다.
>
> 필요한 데이터가 인덱스에 모두 없다면 추가적으로 실제 행에 접근할 수 있습니다."

**핵심 요약**

B+Tree는 루트부터 탐색 범위를 좁혀 리프에서 인덱스 항목을 찾는다.

<a name="q16"></a>
### Q16. B+Tree가 범위 검색에 유리한 이유는 무엇인가요?

> "B+Tree는 리프 노드의 키가 정렬되어 있고, 리프 사이를 순차적으로 탐색할 수 있는 구조를 가집니다.
>
> 따라서 범위의 시작 키를 찾은 뒤 인접한 리프 항목을 순서대로 읽으면서 필요한 데이터를 탐색할 수 있습니다."

**핵심 요약**

B+Tree는 정렬된 리프를 순차적으로 탐색할 수 있어 범위 검색에 유리하다.

<a name="q17"></a>
### Q17. B+Tree에서 실제 데이터는 어디에 저장되나요?

> "B+Tree의 데이터 항목은 리프 노드에 저장됩니다.
>
> 다만 리프에 무엇이 저장되는지는 인덱스 종류에 따라 다릅니다.
>
> MySQL InnoDB의 Clustered Index 리프에는 실제 행 데이터가 저장되고, Secondary Index 리프에는 보조 인덱스 키와 Primary Key 값 등이 저장됩니다."

**핵심 요약**

B+Tree의 리프에는 데이터 항목이 저장되지만 실제 저장 내용은 인덱스 종류에 따라 다르다.

<a name="q18"></a>
### Q18. B+Tree에 데이터를 삽입하면 어떤 일이 발생하나요?

> "먼저 삽입할 키가 위치할 리프 노드를 탐색합니다.
>
> 대상 페이지에 공간이 있으면 키의 정렬 순서를 유지하면서 항목을 삽입합니다.
>
> 공간이 부족하면 페이지 분할이 발생할 수 있고, 이 과정에서 상위 노드의 키도 변경될 수 있습니다."

**핵심 요약**

B+Tree는 리프의 정렬 순서를 유지하며 삽입하고 공간이 부족하면 페이지를 분할한다.

<a name="q18-1"></a>
#### ↳ Q18-1. B+Tree는 데이터를 삭제할 때 어떻게 동작하나요?

> "삭제할 키가 있는 리프 노드를 찾아 항목을 제거합니다.
>
> 이론적인 B+Tree에서는 노드가 지나치게 비게 되면 다른 노드에서 키를 재분배하거나 노드를 병합해 균형을 유지합니다.
>
> 실제 DBMS에서는 삭제 표시나 페이지 공간 관리 등의 최적화가 추가로 사용될 수 있습니다."

**핵심 요약**

B+Tree는 삭제 후 필요한 경우 재분배나 병합으로 구조를 유지한다.

<a name="q18-2"></a>
#### ↳ Q18-2. Page Split이란 무엇이고 언제 발생하나요?

> "Page Split(페이지 스플릿)은 새로운 항목을 삽입할 때 기존 인덱스 페이지에 공간이 부족하여 페이지를 나누는 작업입니다.
>
> 새 페이지 할당과 항목 재배치, 필요한 경우 부모 노드 갱신이 발생하며 추가적인 인덱스 관리 비용이 생길 수 있습니다."

**핵심 요약**

Page Split은 인덱스 페이지에 새로운 항목을 삽입할 공간이 부족할 때 발생한다.

<a name="q18-3"></a>
#### ↳ Q18-3. Page Split을 줄이려면 어떻게 해야 하나요?

> "InnoDB의 Clustered Index에서는 순차적으로 증가하는 기본 키를 사용하면 무작위 키보다 새 데이터가 인덱스의 끝부분에 삽입되기 쉬워 무작위 위치의 페이지 분할을 줄이는 데 유리합니다.
>
> 다만 순차 키를 사용해도 페이지 공간 확보를 위한 분할이 완전히 사라지는 것은 아닙니다."

**핵심 요약**

순차적으로 증가하는 기본 키는 무작위 위치의 페이지 분할을 줄이는 데 유리하다.

<a name="q18-4"></a>
#### ↳ Q18-4. [핵심 질문] Page Split이 빈번하면 어떤 문제가 발생하나요?

> "페이지 분할 시 데이터 이동과 페이지 할당, 상위 노드 관리 비용이 증가할 수 있습니다.
>
> 또한 페이지 공간 활용률이 낮아지면 저장해야 하는 페이지가 늘어나 조회 성능에도 영향을 줄 수 있습니다."

**핵심 요약**

잦은 Page Split은 추가 I/O와 인덱스 관리 비용을 증가시킬 수 있다.

<a name="q19"></a>
### Q19. 데이터베이스의 Page란 무엇인가요?

> "Page(페이지)는 데이터베이스가 데이터와 인덱스를 관리하는 저장 단위입니다.
>
> MySQL InnoDB의 기본 페이지 크기는 일반적으로 16KB이며, B+Tree의 노드도 페이지 단위로 구성됩니다.
>
> 따라서 인덱스 탐색 성능은 접근해야 하는 페이지 수와 밀접한 관련이 있습니다."

**핵심 요약**

페이지는 데이터베이스의 저장 관리 단위이며 페이지 접근 횟수가 검색 성능에 영향을 준다.

<a name="q19-1"></a>
#### ↳ Q19-1. [핵심 질문] Buffer Pool이란 무엇인가요?

> "Buffer Pool(버퍼 풀)은 MySQL InnoDB가 데이터와 인덱스 페이지를 메모리에 캐싱하는 영역입니다.
>
> 필요한 페이지가 버퍼 풀에 있다면 디스크에서 다시 읽는 비용을 줄일 수 있습니다."

**핵심 요약**

Buffer Pool은 데이터·인덱스 페이지를 메모리에 캐싱해 디스크 I/O를 줄인다.

<a name="q19-2"></a>
#### ↳ Q19-2. [핵심 질문] B+Tree의 높이가 낮으면 왜 성능에 유리한가요?

> "트리의 높이가 낮으면 루트에서 리프까지 탐색할 때 거쳐야 하는 페이지 수가 적어지기 때문입니다.
>
> 특히 필요한 페이지가 메모리에 없을 때 디스크 I/O를 줄이는 데 유리합니다."

**핵심 요약**

B+Tree의 낮은 높이는 검색에 필요한 페이지 접근 횟수를 줄여준다.

<a name="section-03"></a>
## Clustered Index (클러스터형 인덱스)

<a name="q20"></a>
### Q20. [대표 질문] Clustered Index란 무엇인가요?

> "Clustered Index(클러스터드 인덱스)는 실제 행 데이터를 인덱스 키 기준으로 구성하는 인덱스입니다.
>
> MySQL InnoDB에서는 리프 페이지에 실제 행 데이터가 저장되며, Primary Key가 있으면 이를 기준으로 클러스터형 인덱스를 구성합니다.
>
> 따라서 기본 키를 이용한 조회에 효율적이며 한 테이블에 하나만 존재합니다."

**핵심 요약**

InnoDB의 Clustered Index는 Primary Key를 기준으로 실제 행 데이터를 저장하는 인덱스이다.

<a name="q20-1"></a>
#### ↳ Q20-1. Clustered Index가 테이블당 하나만 존재하는 이유는 무엇인가요?

> "Clustered Index는 실제 행 데이터를 하나의 키 순서에 따라 구성하는 저장 구조이기 때문입니다.
>
> 동일한 행 데이터를 서로 다른 키 순서로 하나의 클러스터드 구조에 동시에 저장할 수 없으므로 한 테이블에는 하나만 존재합니다."

**핵심 요약**

실제 행 데이터의 클러스터드 저장 기준은 하나이므로 테이블당 하나만 존재한다.

<a name="q21"></a>
### Q21. Primary Key와 Clustered Index는 같은 개념인가요?

> "아닙니다. Primary Key는 행을 고유하게 식별하는 제약 조건이고, Clustered Index는 실제 행 데이터를 구성하는 저장 구조입니다.
>
> MySQL InnoDB에서는 Primary Key가 있으면 이를 Clustered Index의 기준으로 사용하지만, 모든 DBMS에서 두 개념이 동일한 것은 아닙니다."

**핵심 요약**

Primary Key는 제약 조건이고 Clustered Index는 저장 구조이다.

<a name="q21-1"></a>
#### ↳ Q21-1. InnoDB에서 Clustered Index가 Primary Key를 기준으로 생성되는 이유는 무엇인가요?

> "Primary Key는 중복과 NULL을 허용하지 않아 각 행을 고유하게 식별할 수 있습니다.
>
> InnoDB는 Primary Key가 있으면 이를 Clustered Index의 키로 사용하도록 설계되어 있습니다.
>
> 또한 Secondary Index에도 기본 키 값이 포함되어 실제 행을 찾는 데 사용되므로 작고 변경되지 않는 기본 키가 유리합니다."

**핵심 요약**

InnoDB는 행을 고유하게 식별하는 Primary Key를 클러스터드 키로 사용한다.

<a name="q21-2"></a>
#### ↳ Q21-2. Primary Key가 없는 InnoDB 테이블은 어떻게 되나요?

> "Primary Key가 없다면 InnoDB는 모든 키 컬럼이 NOT NULL인 적절한 UNIQUE 인덱스를 클러스터드 키로 선택할 수 있습니다.
>
> 그런 인덱스도 없다면 내부적으로 숨겨진 행 ID를 생성하여 Clustered Index를 구성합니다."

**핵심 요약**

InnoDB는 PK가 없어도 UNIQUE NOT NULL 키나 내부 행 ID를 이용해 클러스터드 인덱스를 구성한다.

<a name="q22"></a>
### Q22. Clustered Index와 Non-Clustered Index의 차이는 무엇인가요?

> "Clustered Index는 인덱스의 리프에 실제 행 데이터가 저장되는 구조입니다.
>
> 반면 Non-Clustered Index는 별도의 인덱스 구조로 관리되며 실제 행을 찾기 위한 정보를 저장합니다.
>
> MySQL InnoDB에서는 Non-Clustered Index를 보통 Secondary Index라고 부르며, 리프에 보조 인덱스 키와 기본 키 값 등이 저장됩니다."

**핵심 요약**

Clustered Index는 실제 행 데이터를 저장하고 Non-Clustered Index는 별도의 구조로 행을 찾는 정보를 관리한다.

<a name="q23"></a>
### Q23. Clustered Index의 장점과 단점은 무엇인가요?

> "장점은 기본 키로 검색할 때 실제 행 데이터에 직접 접근할 수 있고, 기본 키 범위를 순차적으로 탐색하는 데 유리하다는 것입니다.
>
> 단점은 삽입 위치가 불규칙하면 페이지 분할과 관리 비용이 증가할 수 있으며, 키가 크거나 변경되면 보조 인덱스에도 부담이 발생할 수 있다는 점입니다."

**핵심 요약**

Clustered Index는 기본 키 조회에 유리하지만 키 크기와 삽입·변경 비용을 고려해야 한다.

<a name="q24"></a>
### Q24. Secondary Index는 실제 행을 어떻게 찾나요?

> "먼저 Secondary Index의 B+Tree에서 검색 키를 찾습니다.
>
> 해당 항목에 포함된 기본 키 값을 확인한 후 필요한 데이터가 인덱스에 모두 없다면, Clustered Index를 다시 탐색하여 실제 행을 조회합니다."

**핵심 요약**

Secondary Index는 기본 키를 찾고 필요한 경우 Clustered Index를 추가로 탐색한다.

<a name="q24-1"></a>
#### ↳ Q24-1. Secondary Index를 사용하면 항상 Clustered Index를 다시 조회하나요?

> "아닙니다. 쿼리에서 필요한 데이터가 Secondary Index만으로 모두 충족된다면 추가적인 클러스터드 인덱스 접근을 생략할 수 있습니다.
>
> 이를 커버링 인덱스 활용이라고 합니다."

**핵심 요약**

보조 인덱스만으로 필요한 데이터를 모두 얻을 수 있으면 추가 행 조회가 필요하지 않다.

<a name="q24-2"></a>
#### ↳ Q24-2. [핵심 질문] Secondary Index로 많은 행을 조회하면 왜 느려질 수 있나요?

> "보조 인덱스에서 찾은 각 항목에 대해 실제 행 데이터에 추가로 접근해야 할 수 있기 때문입니다.
>
> 조회할 행이 많다면 클러스터드 인덱스에 반복적으로 접근하는 비용이 커져 전체 테이블 스캔보다 불리할 수 있습니다."

**핵심 요약**

보조 인덱스에서 많은 행을 찾으면 반복적인 추가 행 조회 비용이 증가할 수 있다.

<a name="q25"></a>
### Q25. 기본 키에 AUTO_INCREMENT를 사용하는 것이 유리한 이유는 무엇인가요?

> "증가하는 정수 기본 키는 새로운 행이 일반적으로 클러스터드 인덱스의 끝부분에 삽입되도록 합니다.
>
> 무작위 키보다 삽입 위치가 예측 가능하고, 비교적 작은 키는 보조 인덱스의 저장 공간에도 유리합니다."

**핵심 요약**

증가하는 작은 기본 키는 InnoDB 인덱스의 삽입과 저장 효율에 유리할 수 있다.

<a name="q25-1"></a>
#### ↳ Q25-1. UUID를 Primary Key로 사용하면 어떤 문제가 발생할 수 있나요?

> "무작위 UUID를 사용하면 새로운 행이 클러스터드 인덱스의 다양한 위치에 삽입될 수 있어 페이지 분할과 관리 비용이 증가할 수 있습니다.
>
> 또한 기본 키 크기가 커지면 이를 포함하는 보조 인덱스의 저장 비용도 증가합니다.
>
> 다만 시간순 UUID 등은 이러한 단점을 일부 완화할 수 있습니다."

**핵심 요약**

무작위 UUID 기본 키는 삽입 위치 분산과 큰 키 크기로 인덱스 비용을 높일 수 있다.

<a name="q25-2"></a>
#### ↳ Q25-2. [핵심 질문] AUTO_INCREMENT가 항상 UUID보다 좋은가요?

> "아닙니다. AUTO_INCREMENT는 저장 효율과 순차적인 삽입에 유리하지만 분산 환경에서의 식별자 생성 요구사항도 고려해야 합니다.
>
> 매우 높은 동시 삽입 환경에서는 인덱스 끝부분의 경합이 발생할 수도 있으므로 시스템 특성에 따라 선택해야 합니다."

**핵심 요약**

기본 키는 저장 효율뿐 아니라 분산 환경과 동시성 요구사항까지 고려해 선택한다.

<a name="q26"></a>
### Q26. Clustered Index의 키를 변경하면 왜 비용이 큰가요?

> "클러스터드 키는 실제 행 데이터의 저장 기준이며, InnoDB의 Secondary Index에도 기본 키 값이 포함됩니다.
>
> 따라서 기본 키가 변경되면 클러스터드 인덱스의 행 항목과 관련 보조 인덱스 항목을 변경해야 할 수 있습니다."

**핵심 요약**

InnoDB의 기본 키는 행 저장 구조와 보조 인덱스에 연결되므로 변경 비용이 크다.

<a name="q27"></a>
### Q27. [핵심 질문] Clustered Index는 데이터를 디스크에 물리적으로 연속해서 저장하나요?

> "반드시 그렇지는 않습니다. Clustered Index는 B+Tree의 키 순서로 행 데이터를 관리한다는 의미입니다.
>
> 실제 데이터 페이지가 디스크의 연속된 물리 주소에 저장된다는 뜻은 아니며 페이지 분할과 저장 공간 관리에 따라 배치가 달라질 수 있습니다."

**핵심 요약**

Clustered Index의 키 순서는 논리적 정렬 구조이지 물리적 주소의 연속성을 보장하지 않는다.

<a name="q28"></a>
### Q28. [핵심 질문] Clustered Index와 ORDER BY는 어떤 관계가 있나요?

> "Clustered Index는 키 순서로 데이터를 관리하므로 해당 키를 기준으로 정렬된 데이터를 읽는 데 유리할 수 있습니다.
>
> 하지만 SQL 결과의 출력 순서는 ORDER BY를 명시하지 않으면 보장되지 않습니다."

**핵심 요약**

Clustered Index가 키 순서로 저장되어 있어도 조회 결과의 정렬은 ORDER BY로 명시해야 한다.

<a name="q29"></a>
### Q29. [핵심 질문] InnoDB와 PostgreSQL의 클러스터링 방식은 같은가요?

> "아닙니다. InnoDB는 클러스터드 인덱스 리프에 실제 행 데이터를 저장합니다.
>
> PostgreSQL은 기본적으로 테이블과 인덱스를 별도로 관리하며, CLUSTER 명령으로 특정 인덱스 순서에 맞춰 테이블을 재정렬할 수 있지만 이후 변경에 대해 그 순서를 자동으로 유지하지는 않습니다."

**핵심 요약**

InnoDB의 Clustered Index와 PostgreSQL의 CLUSTER는 저장 방식과 유지 방식이 다르다.

<a name="q30"></a>
### Q30. [핵심 질문] SQL Server에서도 Primary Key가 항상 Clustered Index인가요?

> "아닙니다. SQL Server는 Primary Key에 비클러스터드 인덱스를 사용할 수 있고, 다른 컬럼을 기준으로 Clustered Index를 구성할 수도 있습니다.
>
> 따라서 Primary Key와 Clustered Index가 항상 동일하다는 설명은 모든 DBMS에 적용되지 않습니다."

**핵심 요약**

Primary Key와 Clustered Index의 관계는 DBMS마다 다르다.

<a name="section-04"></a>
## 연관 종합 및 심화 질문

<a name="q31"></a>
### Q31. Index, B+Tree, Clustered Index의 관계를 설명해주세요.

> "Index는 데이터를 효율적으로 검색하기 위한 자료구조이고, B+Tree는 이를 구현하는 대표적인 트리 구조입니다.
>
> Clustered Index는 실제 행 데이터를 인덱스 키 기준으로 구성하는 저장 방식입니다.
>
> MySQL InnoDB에서는 B-Tree 계열의 구조를 사용하며 Primary Key가 있으면 이를 클러스터드 키로 사용합니다."

**핵심 요약**

Index는 검색 목적, B+Tree는 구현 자료구조, Clustered Index는 실제 행 데이터의 저장 방식이다.

<a name="q32"></a>
### Q32. Primary Key 조회와 Secondary Index 조회의 차이는 무엇인가요?

> "InnoDB에서는 Primary Key로 조회할 때 Clustered Index를 탐색하여 실제 행에 직접 접근할 수 있습니다.
>
> Secondary Index로 조회할 때는 보조 인덱스에서 기본 키를 찾고, 필요한 데이터가 인덱스에 없으면 Clustered Index를 추가로 탐색합니다."

**핵심 요약**

PK 조회는 클러스터드 인덱스에 직접 접근하고 보조 인덱스 조회는 추가 탐색이 필요할 수 있다.

<a name="q33"></a>
### Q33. 데이터가 적은 테이블에도 인덱스가 필요한가요?

> "반드시 그렇지는 않습니다. 데이터가 적으면 전체 테이블을 읽는 비용이 크지 않아 인덱스 사용의 이점이 제한적일 수 있습니다.
>
> 따라서 테이블 크기와 실제 조회 패턴, 실행 비용을 고려해야 합니다."

**핵심 요약**

작은 테이블에서는 인덱스보다 Full Table Scan이 효율적일 수도 있다.

<a name="q34"></a>
### Q34. ORDER BY에서도 인덱스를 사용할 수 있나요?

> "그렇습니다. B+Tree 인덱스는 키를 정렬된 상태로 관리하기 때문에 정렬 조건과 인덱스 구성이 일치하면 별도의 정렬 작업을 줄일 수 있습니다.
>
> 다만 검색 조건, 컬럼 순서, 정렬 방향에 따라 실제 활용 여부는 달라집니다."

**핵심 요약**

B+Tree의 정렬된 키 구조를 활용하면 정렬 비용을 줄일 수 있다.

<a name="q35"></a>
### Q35. [핵심 질문] Index Condition Pushdown이란 무엇인가요?

> "Index Condition Pushdown은 인덱스에 포함된 컬럼으로 판단할 수 있는 조건을 스토리지 엔진에서 먼저 검사하는 최적화입니다.
>
> 이를 통해 조건에 맞지 않는 행은 실제 행 데이터에 추가로 접근하지 않도록 하여 불필요한 I/O를 줄일 수 있습니다."

**핵심 요약**

Index Condition Pushdown은 인덱스에서 조건을 먼저 평가해 불필요한 행 조회를 줄인다.

<a name="q35-1"></a>
#### ↳ Q35-1. [핵심 질문] Covering Index와 Index Condition Pushdown의 차이는 무엇인가요?

> "Covering Index는 필요한 데이터를 인덱스만으로 모두 얻어 추가적인 행 조회를 생략하는 방식입니다.
>
> Index Condition Pushdown은 인덱스에서 일부 조건을 먼저 평가해 추가 행 조회가 필요한 대상을 줄이는 최적화입니다."

**핵심 요약**

Covering Index는 추가 조회 자체를 생략하고 Index Condition Pushdown은 추가 조회 대상을 줄인다.

<a name="q36"></a>
### Q36. [핵심 질문] OFFSET 기반 페이지네이션이 느려질 수 있는 이유는 무엇인가요?

> "OFFSET 기반 페이지네이션은 뒤쪽 페이지를 조회할수록 앞의 많은 행을 읽고 건너뛰어야 할 수 있기 때문입니다.
>
> 따라서 데이터가 많을 때는 마지막으로 조회한 정렬 키를 기준으로 다음 데이터를 가져오는 Keyset Pagination을 고려할 수 있습니다."

**핵심 요약**

OFFSET이 커질수록 건너뛰는 행이 증가할 수 있어 Keyset Pagination을 고려한다.

<a name="q37"></a>
### Q37. [핵심 질문] 인덱스를 추가했는데 성능이 오히려 나빠질 수도 있나요?

> "그렇습니다. 불필요한 인덱스는 저장 공간과 쓰기 비용을 증가시키고, 효율이 낮은 인덱스는 조회 성능 개선에 큰 도움이 되지 않을 수 있습니다.
>
> 따라서 인덱스는 실제 조회 성능과 쓰기 비용을 함께 측정하여 유지 여부를 결정해야 합니다."

**핵심 요약**

인덱스는 무조건 많을수록 좋은 것이 아니라 조회와 쓰기 비용을 함께 고려해야 한다.

<a name="q38"></a>
### Q38. [핵심 질문] 데이터베이스 옵티마이저란 무엇인가요?

> "옵티마이저(Optimizer)는 SQL을 실행할 때 사용할 데이터 접근 경로와 연산 순서 등을 결정하는 데이터베이스 구성 요소입니다.
>
> 인덱스 사용 여부, JOIN 방식, 예상 행 수 등을 고려해 비용이 낮을 것으로 예상되는 실행 계획을 선택합니다."

**핵심 요약**

옵티마이저는 SQL의 실행 비용을 고려하여 적절한 실행 계획을 선택한다.

<a name="q38-1"></a>
#### ↳ Q38-1. [핵심 질문] 인덱스가 있는데도 옵티마이저가 Full Table Scan을 선택하는 이유는 무엇인가요?

> "전체 데이터 중 조회 대상이 많거나 인덱스를 통한 추가 행 조회 비용이 큰 경우 전체 테이블 스캔이 더 효율적일 수 있기 때문입니다.
>
> 옵티마이저는 통계 정보와 예상 비용을 바탕으로 이러한 선택을 합니다."

**핵심 요약**

옵티마이저는 인덱스 존재 여부가 아니라 예상 실행 비용에 따라 접근 방식을 선택한다.

<a name="q39"></a>
### Q39. [핵심 질문] 인덱스를 설계할 때 무엇을 먼저 고려해야 하나요?

> "자주 실행되는 검색 조건과 JOIN, 정렬 요구사항을 먼저 파악해야 합니다.
>
> 이후 데이터 크기와 분포를 분석하여 인덱스를 설계하고, 실행 계획과 실제 성능을 확인해 효과를 검증해야 합니다."

**핵심 요약**

인덱스 설계는 조회 패턴 분석, 데이터 분포 확인, 실행 계획 검증을 중심으로 진행한다.
