## AOP (Aspect-Oriented Programming)

<a name="q1"></a>
### Q1. [대표 질문] AOP란 무엇이고 왜 사용하나요?

> "AOP는 관점 지향 프로그래밍으로, 여러 클래스에 반복적으로 필요한 공통 기능을 핵심 비즈니스 로직과 분리하여 관리하는 프로그래밍 방식입니다.
>
> 로깅, 트랜잭션 관리, 실행 시간 측정과 같은 공통 관심사를 별도로 정의하여 코드 중복을 줄이고 유지보수성을 높일 수 있습니다.
>
> Spring AOP는 주로 프록시 기반으로 동작하여 메서드 실행 전후에 공통 기능을 적용합니다."

**핵심 요약**

AOP는 여러 곳에 반복되는 공통 기능을 핵심 비즈니스 로직과 분리하여 관리하는 프로그래밍 방식이다.

<a name="q2"></a>
### Q2. Spring에서 AOP가 필요한 이유는 무엇인가요?

> "트랜잭션 관리나 로깅을 각각의 Service에 직접 작성하면 코드가 중복되고 비즈니스 로직과 섞여 유지보수가 어려워집니다.
>
> AOP를 사용하면 공통 기능을 별도로 관리하고 필요한 메서드에 적용할 수 있어 각 클래스가 핵심 비즈니스 로직에 집중할 수 있습니다."

**핵심 요약**

AOP를 사용하는 이유는 공통 코드의 중복을 줄이고 핵심 비즈니스 로직에 집중하기 위해서이다.

<a name="q3"></a>
### Q3. AOP와 OOP의 차이는 무엇인가요?

> "OOP는 객체의 역할과 책임을 중심으로 기능을 분리하는 방식이고, AOP는 여러 객체에 걸쳐 반복되는 공통 관심사를 분리하는 방식입니다.
>
> 따라서 AOP는 OOP를 대체하는 것이 아니라 OOP에서 발생할 수 있는 공통 로직의 중복을 보완하는 역할을 합니다."

**핵심 요약**

OOP는 객체별 책임을 분리하고, AOP는 여러 객체에 걸친 공통 관심사를 분리한다.

<a name="q4"></a>
### Q4. AOP의 핵심 용어를 설명해주세요.

> "Aspect는 공통 기능을 모아놓은 모듈이고, Advice는 실제로 실행할 부가 기능입니다.
>
> Pointcut은 부가 기능을 적용할 지점을 선택하는 조건이며, Join Point는 부가 기능이 적용될 수 있는 지점입니다.
>
> Target은 부가 기능의 적용 대상 객체이고, Weaving은 공통 기능을 대상 프로그램에 연결하는 과정입니다."

| 용어 | 발음 | 의미 |
| --- | --- | --- |
| Aspect | 애스펙트 | 공통 기능을 모아놓은 모듈 |
| Advice | 어드바이스 | 실행할 부가 기능 |
| Pointcut | 포인트컷 | 부가 기능을 적용할 지점의 선택 조건 |
| Join Point | 조인 포인트 | 부가 기능이 적용될 수 있는 지점 |
| Target | 타깃 | 부가 기능이 적용되는 원본 객체 |
| Weaving | 위빙 | 공통 기능을 대상 코드와 연결하는 과정 |

Spring AOP에서 Join Point는 메서드 실행 지점으로 제한됩니다.

**핵심 요약**

Aspect는 공통 기능, Advice는 실행 코드, Pointcut은 적용 조건, Join Point는 적용 가능한 지점이다.

<a name="q4-1"></a>
#### ↳ Q4-1. Advice에는 어떤 종류가 있나요?

> "Advice에는 메서드 실행 전에 동작하는 `@Before`, 정상 반환 후 실행되는 `@AfterReturning`, 예외 발생 시 실행되는 `@AfterThrowing`, 정상·예외 여부와 관계없이 실행되는 `@After`, 메서드 실행 전체를 감싸는 `@Around`가 있습니다."

| Advice | 실행 시점 |
| --- | --- |
| `@Before` | 메서드 실행 전 |
| `@AfterReturning` | 정상 반환 후 |
| `@AfterThrowing` | 예외 발생 후 |
| `@After` | 메서드 종료 시, finally와 유사 |
| `@Around` | 실행 전후를 감싸며 원본 호출 여부까지 제어 |

**핵심 요약**

Advice는 메서드 실행 전·후·예외 시점 등에 공통 기능을 적용한다.

<a name="q4-2"></a>
#### ↳ Q4-2. @Around가 가장 강력한 이유는 무엇인가요?

> "`@Around`는 원본 메서드의 실행 전후를 모두 감싸고, `proceed()` 호출 여부를 통해 원본 메서드의 실행 자체를 제어할 수 있기 때문입니다.
>
> 반환값과 예외도 다룰 수 있어 실행 시간 측정이나 재시도처럼 전체 호출 과정을 제어해야 하는 기능에 적합합니다."

**핵심 요약**

@Around는 메서드 실행 전후뿐 아니라 실행 여부와 반환값까지 제어할 수 있다.

<a name="q5"></a>
### Q5. 횡단 관심사(Cross-Cutting Concern)란 무엇인가요?

> "횡단 관심사는 여러 클래스와 메서드에 공통적으로 적용되는 기능입니다.
>
> 예를 들어 주문, 회원, 결제 Service 모두에 필요한 로깅, 트랜잭션 관리, 보안 등이 있습니다."

**핵심 요약**

횡단 관심사는 여러 비즈니스 기능에 공통으로 필요한 부가 기능이다.

<a name="q6"></a>
### Q6. AOP는 어디에 사용하나요?

> "AOP는 트랜잭션 관리, 로깅, 실행 시간 측정, 권한 검사, 캐싱, 비동기 처리, 재시도 등에 활용할 수 있습니다.
>
> Spring에서는 `@Transactional`, `@Cacheable`, `@Async` 등의 기능이 프록시 기반 메서드 가로채기를 활용할 수 있습니다."

**핵심 요약**

AOP는 여러 메서드에 공통으로 적용해야 하는 기능을 분리할 때 사용한다.

<a name="q7"></a>
### Q7. Spring AOP는 내부적으로 어떻게 동작하나요?

> "Spring AOP는 일반적으로 프록시 기반으로 동작합니다.
>
> Spring이 AOP 적용 대상 Bean에 대해 프록시 객체를 생성하고, 클라이언트가 메서드를 호출하면 프록시가 먼저 요청을 받습니다.
>
> 프록시는 설정된 Advice를 실행하고 실제 Target 객체의 메서드를 호출하여 공통 기능을 적용합니다."

**핵심 요약**

Spring AOP는 프록시가 원본 객체의 메서드 호출을 가로채 공통 기능을 적용하는 방식이다.

<a name="q8"></a>
### Q8. AOP 사용 시 주의할 점은 무엇인가요?

> "공통 기능을 과도하게 AOP로 분리하면 실제 실행 흐름을 파악하기 어려워집니다.
>
> 특히 핵심 비즈니스 로직까지 AOP에 숨기면 코드의 이해와 디버깅이 어려워질 수 있습니다.
>
> 또한 Spring AOP는 프록시 기반이므로 내부 메서드 호출이나 프록시할 수 없는 메서드에 대한 제약이 있습니다."

**핵심 요약**

AOP는 공통 관심사에 적절히 적용해야 하며 과도하게 사용하면 실행 흐름을 이해하기 어려워진다.

<a name="q8-1"></a>
#### ↳ Q8-1. [핵심 질문] Spring AOP와 AspectJ의 차이는 무엇인가요?

> "Spring AOP는 런타임 프록시 기반으로 동작하며 메서드 실행 지점을 대상으로 합니다.
>
> AspectJ는 컴파일 시점이나 클래스 로딩 시점에 코드를 위빙할 수 있어 메서드 실행뿐 아니라 생성자와 필드 접근 등 더 다양한 지점을 지원합니다.
>
> 다만 AspectJ는 설정과 운영이 더 복잡할 수 있습니다."

**핵심 요약**

Spring AOP는 프록시 기반의 메서드 AOP이고, AspectJ는 바이트코드 위빙을 통한 더 폭넓은 AOP를 지원한다.

<a name="q9"></a>
### Q9. 모든 공통 기능을 AOP로 분리하는 것이 좋은가요?

> "아닙니다. 공통 기능이라도 핵심 비즈니스 로직과 강하게 연결되어 있거나 실행 흐름을 명시적으로 드러내는 것이 중요한 경우에는 일반적인 메서드 호출로 구현하는 편이 좋을 수 있습니다.
>
> 따라서 재사용성, 유지보수성, 비즈니스 로직과의 연관성을 고려해야 합니다."

**핵심 요약**

공통 기능이라고 모두 AOP로 분리하는 것이 아니라 책임과 실행 흐름을 고려해 선택해야 한다.

<a name="section-02"></a>
## Proxy (프록시)

<a name="q10"></a>
### Q10. [대표 질문] Proxy란 무엇이고 AOP와 어떤 관계인가요?

> "Proxy는 실제 객체를 대신하여 요청을 받는 대리 객체입니다.
>
> 클라이언트가 메서드를 호출하면 프록시가 먼저 요청을 받아 공통 기능을 실행한 뒤 실제 객체의 메서드를 호출합니다.
>
> Spring AOP는 이러한 프록시를 활용하여 원본 코드를 수정하지 않고도 트랜잭션 관리나 로깅 같은 부가 기능을 적용합니다."

**핵심 요약**

AOP는 공통 기능을 분리하는 개념이고, Proxy는 Spring AOP에서 그 기능을 구현하는 수단이다.

<a name="q11"></a>
### Q11. Proxy 객체를 사용하는 이유는 무엇인가요?

> "실제 객체의 코드를 수정하지 않고도 메서드 실행 전후에 공통 기능을 추가할 수 있기 때문입니다.
>
> 핵심 비즈니스 로직과 부가 기능을 분리할 수 있어 코드 중복이 줄어들고 유지보수가 쉬워집니다."

**핵심 요약**

Proxy는 원본 객체를 수정하지 않고 부가 기능을 적용하기 위해 사용한다.

<a name="q12"></a>
### Q12. Spring은 프록시를 어떻게 생성하고 주입하나요?

> "Spring은 Bean을 생성하고 초기화하는 과정에서 AOP 적용 여부를 확인하고, 필요한 경우 BeanPostProcessor 등을 통해 프록시를 생성합니다.
>
> 이후 다른 Bean이 해당 객체를 주입받을 때는 일반적으로 원본 객체 대신 프록시를 주입받습니다."

**핵심 요약**

Spring은 AOP 적용 대상 Bean을 프록시로 감싸고 다른 Bean에는 프록시를 주입한다.

<a name="q12-1"></a>
#### ↳ Q12-1. 실제로 프록시가 주입되었는지 어떻게 확인하나요?

> "객체의 `getClass()`를 확인하거나 Spring에서 제공하는 `AopUtils.isAopProxy()`를 사용할 수 있습니다.
>
> CGLIB 프록시인 경우 클래스 이름에 `$$SpringCGLIB$$`와 같은 형태가 나타날 수 있습니다."

```
System.out.println(orderService.getClass());

System.out.println(AopUtils.isAopProxy(orderService));
```

**핵심 요약**

프록시 여부는 객체 타입이나 AopUtils로 확인할 수 있다.

<a name="q13"></a>
### Q13. JDK Dynamic Proxy와 CGLIB Proxy의 차이는 무엇인가요?

> "JDK Dynamic Proxy는 인터페이스를 구현하는 방식으로 프록시를 생성하며 인터페이스에 정의된 메서드를 대상으로 합니다.
>
> CGLIB는 클래스를 상속하여 프록시를 생성하므로 인터페이스가 없어도 사용할 수 있습니다.
>
> 다만 CGLIB는 상속과 메서드 오버라이딩에 의존하기 때문에 final 클래스나 final 메서드에는 적용할 수 없습니다."

| 구분 | JDK Dynamic Proxy | CGLIB |
| --- | --- | --- |
| 발음 | JDK 다이내믹 프록시 | 씨지립 |
| 기반 | 인터페이스 구현 | 클래스 상속 |
| 인터페이스 | 필요 | 없어도 됨 |
| 주요 대상 | 프록시 인터페이스의 메서드 | 오버라이드 가능한 메서드 |
| 주요 제약 | 인터페이스에 없는 메서드의 노출·호출 제약 | final 클래스·메서드, private 메서드 |

**핵심 요약**

JDK Dynamic Proxy는 인터페이스 기반, CGLIB는 클래스 상속 기반 프록시이다.

<a name="q13-1"></a>
#### ↳ Q13-1. Spring Boot는 어떤 프록시를 기본적으로 사용하나요?

> "Spring Boot의 AOP 자동 설정은 기본적으로 CGLIB 클래스 기반 프록시를 사용합니다.
>
> `spring.aop.proxy-target-class=false`로 설정하면 JDK 인터페이스 기반 프록시를 사용하도록 변경할 수 있습니다."

```
spring.aop.proxy-target-class=false
```

이는 Spring Framework를 직접 설정했을 때의 프록시 선택 규칙과 구분해야 합니다.

Home+1

**핵심 요약**

Spring Boot의 AOP 자동 설정은 기본적으로 CGLIB를 사용하며 설정으로 변경할 수 있다.

<a name="q13-2"></a>
#### ↳ Q13-2. [핵심 질문] CGLIB에서 기본 생성자가 필요한 문제는 어떻게 해결되었나요?

> "과거에는 CGLIB 프록시 생성 시 생성자와 관련된 제약이 있었지만, Spring은 Objenesis(옵제네시스 )를 활용하여 프록시 객체 생성 과정에서 원본 클래스의 생성자를 다시 호출하지 않도록 지원합니다.
>
> 따라서 일반적인 Spring 환경에서는 프록시 생성을 위해 반드시 기본 생성자를 작성할 필요가 없습니다."

**핵심 요약**

Spring은 Objenesis를 활용해 CGLIB 프록시 생성 시 기본 생성자 제약을 완화한다.

<a name="q14"></a>
### Q14. Proxy 패턴과 Decorator 패턴의 차이는 무엇인가요?

> "Proxy 패턴은 실제 객체에 대한 접근을 제어하는 데 초점을 두고, Decorator 패턴은 기존 객체의 기능을 변경하지 않으면서 동적으로 기능을 확장하는 데 초점을 둡니다.
>
> 두 패턴 모두 객체를 감싸는 구조를 가질 수 있지만 설계 목적이 다릅니다."

**핵심 요약**

Proxy는 접근 제어, Decorator는 기능 확장에 초점을 둔다.

<a name="q15"></a>
### Q15. Proxy 패턴의 장점은 무엇인가요?

> "클라이언트 코드를 크게 변경하지 않고 원본 객체에 부가 기능을 추가할 수 있습니다.
>
> 또한 접근 제어, 로깅, 캐싱, 트랜잭션 관리 등의 기능을 원본의 비즈니스 로직과 분리할 수 있어 유지보수성과 확장성이 높아집니다."

**핵심 요약**

Proxy는 원본 코드의 변경을 줄이면서 공통 기능을 독립적으로 관리할 수 있게 한다.

<a name="q16"></a>
### Q16. Spring AOP에서 Proxy를 사용하면 어떤 한계가 있나요?

> "프록시 방식은 프록시를 통해 들어오는 메서드 호출을 대상으로 동작합니다.
>
> 따라서 같은 객체 내부에서 자신을 호출하면 프록시를 거치지 않아 Advice가 적용되지 않습니다.
>
> 또한 클래스 기반 프록시는 final 클래스나 final 메서드를 가로챌 수 없으며, Spring이 관리하지 않는 일반 객체에는 자동으로 적용되지 않습니다."

**핵심 요약**

프록시 기반 AOP는 프록시를 거쳐야 동작하며 내부 호출과 메서드 구조에 제약이 있다.

<a name="q17"></a>
### Q17. Self-Invocation(셀프 인보케이션, 자기 호출) 문제란 무엇인가요?

> "같은 클래스 내부에서 `this.method()`처럼 다른 메서드를 호출하면 프록시를 거치지 않고 원본 객체의 메서드가 직접 호출되는 문제입니다.

> 따라서 내부 호출 대상 메서드에 설정된 AOP 기능이 적용되지 않을 수 있습니다.
>
> 일반적으로 해당 메서드를 별도의 Service로 분리하여 외부 호출을 통해 프록시를 거치도록 해결합니다."

**핵심 요약**

자기 호출은 프록시를 거치지 않아 내부 메서드에 선언된 AOP 기능이 적용되지 않는 문제이다.

<a name="q17-1"></a>
#### ↳ Q17-1. [핵심 질문] 내부 호출 문제가 실제로 어떤 버그를 만들 수 있나요?

> "주문 메서드가 같은 클래스의 알림 이력 저장 메서드를 호출하고, 알림 이력 메서드에 `REQUIRES_NEW`를 선언했다고 가정하겠습니다.
>
> 내부 호출로 프록시를 거치지 않으면 새로운 트랜잭션이 시작되지 않습니다.
>
> 따라서 알림 이력을 별도로 커밋하려던 의도와 달리 주문 트랜잭션에 묶여 함께 롤백될 수 있습니다."

자기 호출로 REQUIRES_NEW가 무시되면 독립적인 트랜잭션 처리가 의도대로 동작하지 않을 수 있다.

**핵심 요약**

<a name="q17-2"></a>
#### ↳ Q17-2. [핵심 질문] 자기 호출을 해결하는 방법에는 무엇이 있나요?

> "가장 일반적인 방법은 트랜잭션이나 AOP 기능이 필요한 메서드를 다른 Spring Bean으로 분리하는 것입니다.
>
> 자기 프록시를 주입받거나 AopContext를 사용하는 방식도 있지만, 코드가 Spring AOP에 강하게 의존하므로 구조 분리를 우선 고려하는 것이 좋습니다."

**핵심 요약**

Self-Invocation은 메서드를 별도 Bean으로 분리하여 프록시를 거치도록 해결하는 것이 좋다.

<a name="section-03"></a>
## @Transactional (트랜잭셔널)

<a name="q18"></a>
### Q18. [대표 질문] @Transactional이란 무엇이고 어떻게 동작하나요?

> "`@Transactional`은 Spring에서 선언적 트랜잭션 관리를 제공하는 어노테이션입니다.
>
> 일반적인 프록시 기반 설정에서는 메서드 호출 시 Proxy가 먼저 요청을 받아 TransactionInterceptor를 통해 트랜잭션을 시작하거나 기존 트랜잭션에 참여시킵니다.
>
> 이후 실제 비즈니스 로직을 실행하고, 정상 종료하면 커밋하며 롤백 대상 예외가 발생하면 롤백합니다."

**핵심 요약**

@Transactional은 프록시를 활용하여 비즈니스 메서드의 트랜잭션 시작·커밋·롤백을 관리한다.

<a name="q19"></a>
### Q19. @Transactional의 내부 동작 과정을 단계별로 설명해주세요.

> "먼저 Spring이 트랜잭션 적용 대상 Bean에 대한 Proxy를 생성합니다.
>
> 외부에서 메서드를 호출하면 Proxy의 TransactionInterceptor가 트랜잭션 관리자를 통해 트랜잭션을 시작하거나 기존 트랜잭션에 참여합니다.
>
> 실제 메서드가 실행된 후 정상 종료하면 커밋하고, 롤백 대상 예외가 발생하면 롤백합니다."

Controller

Service 메서드 호출

Proxy / TransactionInterceptor

트랜잭션 시작 또는 기존 트랜잭션 참여

실제 Service 메서드

비즈니스 로직 및 Repository 호출

정상 완료

Commit

롤백 대상 예외

Rollback

실제 커밋·롤백 여부는 전파 설정, 트랜잭션 참여 상태, 예외 규칙 등에 따라 달라질 수 있습니다.

**핵심 요약**

프록시 호출 → 트랜잭션 시작·참여 → 실제 메서드 실행 → 커밋 또는 롤백 순서로 동작한다.

<a name="q19-1"></a>
#### ↳ Q19-1. @Transactional이 없다면 어떤 코드를 직접 작성해야 하나요?

> "JDBC를 직접 사용한다면 커넥션을 얻고 자동 커밋을 해제한 뒤, 비즈니스 로직 실행 결과에 따라 commit 또는 rollback을 호출하고 커넥션을 정리해야 합니다.
>
> Spring의 `@Transactional`은 이러한 트랜잭션 관리 코드를 선언적으로 처리할 수 있도록 도와줍니다."

```
Connection conn = dataSource.getConnection();

try {
    conn.setAutoCommit(false);

    // DB 작업 수행

    conn.commit();
} catch (Exception e) {
    conn.rollback();
    throw e;
} finally {
    conn.close();
}
```

**핵심 요약**

@Transactional은 개발자가 직접 작성해야 할 트랜잭션 관리 코드를 Spring에 위임한다.

<a name="q20"></a>
### Q20. @Transactional에서 예외가 발생하면 무조건 Rollback되나요?

> "아닙니다. 기본 설정에서는 RuntimeException과 Error가 발생하면 롤백하지만, Checked Exception은 기본적으로 롤백하지 않습니다.
>
> Checked Exception도 롤백해야 한다면 `rollbackFor` 속성으로 명시할 수 있습니다."

| 예외 종류 | 기본 롤백 여부 |
| --- | --- |
| RuntimeException | 롤백 |
| Error | 롤백 |
| Checked Exception | 기본적으로 롤백하지 않음 |

```
@Transactional(rollbackFor = Exception.class)
public void saveOrder() throws Exception {
    // 비즈니스 로직
}
```

위 규칙은 기본 설정 기준으로, Spring 버전과 애플리케이션의 전역 롤백 설정에 따라 변경할 수 있습니다.

Home+1

**핵심 요약**

@Transactional은 기본적으로 RuntimeException과 Error에서 롤백하고 Checked Exception에서는 롤백하지 않는다.

<a name="q20-1"></a>
#### ↳ Q20-1. Checked Exception과 Unchecked Exception의 차이는 무엇인가요?

> "Checked Exception은 컴파일러가 예외 처리 또는 예외 선언을 요구하는 예외입니다. IOException과 SQLException 등이 대표적입니다.
>
> Unchecked Exception은 RuntimeException 계열의 예외로, 컴파일러가 예외 처리를 강제하지 않습니다."

**핵심 요약**

Checked Exception은 예외 처리를 강제하고, Unchecked Exception은 강제하지 않는다.

<a name="q20-2"></a>
#### ↳ Q20-2. Checked Exception은 왜 기본적으로 롤백하지 않나요?

> "Spring은 전통적으로 Checked Exception을 애플리케이션이 처리하거나 복구할 수 있는 상황으로 간주하는 기본 정책을 사용해 왔습니다.
>
> 다만 Checked Exception이라고 항상 커밋해야 하는 것은 아니며, 비즈니스 요구사항에 따라 `rollbackFor`를 설정해야 합니다."

**핵심 요약**

Checked Exception의 기본 커밋 정책은 Spring의 기본 규칙일 뿐이며 비즈니스 요구에 따라 변경할 수 있다.

<a name="q20-3"></a>
#### ↳ Q20-3. @Transactional 메서드 내부에서 예외를 try-catch로 처리하면 어떻게 되나요?

> "메서드 내부에서 예외를 잡아 정상 반환하면 일반적으로 트랜잭션 인터셉터는 예외를 전달받지 못하므로 커밋을 시도합니다.
>
> 롤백이 필요하면 예외를 다시 던지거나 트랜잭션을 rollback-only 상태로 지정할 수 있습니다.
>
> 단, 이미 rollback-only로 표시된 트랜잭션은 정상 반환하더라도 최종적으로 롤백될 수 있습니다."

**핵심 요약**

예외를 내부에서 처리하고 정상 반환하면 일반적으로 커밋을 시도하므로 롤백 여부를 명시적으로 고려해야 한다.

<a name="q20-4"></a>
#### ↳ Q20-4. [핵심 질문] rollback-only란 무엇인가요?

> "rollback-only는 현재 트랜잭션을 커밋하지 말고 반드시 롤백해야 한다고 표시하는 상태입니다.
>
> 트랜잭션에 참여하는 내부 작업이 실패하여 이 상태로 변경되면, 외부 메서드가 정상 종료하더라도 최종 커밋이 실패하고 롤백될 수 있습니다."

**핵심 요약**

rollback-only는 현재 트랜잭션을 최종적으로 롤백하도록 표시하는 상태이다.

<a name="q21"></a>
### Q21. @Transactional은 클래스와 메서드 중 어디에 적용하나요?

> "클래스에 선언하면 해당 클래스의 적용 가능한 메서드들에 기본 트랜잭션 설정을 제공하고, 메서드에 선언하면 메서드의 설정이 우선합니다.
>
> 일반적으로 비즈니스 작업의 경계를 관리하는 Service 계층에 적용합니다."

```
@Service
@Transactional(readOnly = true)
public class ProductService {

    public Product findProduct(Long id) {
        // 조회
        return null;
    }

    @Transactional
    public void updateProduct(Long id) {
        // 변경
    }
}
```

**핵심 요약**

클래스 레벨은 기본 트랜잭션 설정, 메서드 레벨은 해당 메서드의 우선 설정이다.

<a name="q21-1"></a>
#### ↳ Q21-1. [핵심 질문] @Transactional은 public 메서드에서만 동작하나요?

> "항상 그렇지는 않습니다.
>
> Spring Framework 6.0 이후에는 클래스 기반 프록시에서 protected와 package-private 메서드도 트랜잭션 대상이 될 수 있습니다.
>
> 반면 JDK 인터페이스 기반 프록시에서는 프록시 인터페이스에 정의된 public 메서드가 대상입니다.
>
> 혼동을 줄이고 일관된 동작을 기대하려면 public 메서드에 사용하는 것이 좋습니다."

**핵심 요약**

@Transactional의 접근 제어자 제약은 프록시 방식과 Spring 버전에 따라 달라진다.

<a name="q21-2"></a>
#### ↳ Q21-2. @Transactional이 적용되지 않는 대표적인 경우는 무엇인가요?

> "같은 클래스 내부의 자기 호출, Spring이 관리하지 않는 객체에 대한 호출, 프록시가 가로챌 수 없는 메서드 호출 등이 대표적입니다.
>
> CGLIB 기반에서는 final 클래스나 final 메서드, private 메서드에 제약이 있습니다."

**핵심 요약**

@Transactional이 적용되지 않는 대표적 이유는 호출이 프록시를 통과하지 못하기 때문이다.

<a name="q22"></a>
### Q22. @Transactional의 주요 옵션을 설명해주세요.

> "readOnly는 읽기 전용 트랜잭션 힌트를 제공하고, rollbackFor는 롤백 대상 예외를 설정합니다.
>
> propagation은 트랜잭션 전파 방식을, isolation은 격리 수준을, timeout은 트랜잭션 제한 시간을 지정합니다."

| 옵션 | 발음 | 역할 |
| --- | --- | --- |
| `readOnly` | 리드 온리 | 읽기 전용 힌트 |
| `rollbackFor` | 롤백 포 | 롤백 대상 예외 지정 |
| `propagation` | 프로퍼게이션 | 트랜잭션 전파 방식 |
| `isolation` | 아이솔레이션 | 트랜잭션 격리 수준 |
| `timeout` | 타임아웃 | 제한 시간 설정 |

**핵심 요약**

@Transactional은 읽기 전용 여부, 롤백 규칙, 전파 방식, 격리 수준, 제한 시간을 설정할 수 있다.

<a name="q22-1"></a>
#### ↳ Q22-1. [핵심 질문] readOnly = true를 설정하면 DB 변경이 완전히 차단되나요?

> "아닙니다. `readOnly = true`는 기본적으로 읽기 전용 트랜잭션이라는 힌트이며, 모든 DB 변경을 강제로 금지하는 설정은 아닙니다.
>
> JPA와 Hibernate 환경에서는 변경 감지 등 일부 처리의 최적화에 도움이 될 수 있지만, 실제 동작은 사용 중인 기술과 설정에 따라 달라집니다."

**핵심 요약**

readOnly는 읽기 전용 힌트이며 변경을 항상 차단하는 것은 아니다.

<a name="q23"></a>
### Q23. 트랜잭션 전파(Propagation)란 무엇인가요?

같은 질문의 다른 회차 답변 · [transaction-acid-isolation](../database/transaction-acid-isolation.md#q8)

> "트랜잭션 전파는 트랜잭션이 이미 존재하는 상황에서 다른 트랜잭션 메서드를 호출했을 때 기존 트랜잭션에 참여할지, 새로 시작할지 등을 결정하는 속성입니다.
>
> 대표적으로 REQUIRED와 REQUIRES_NEW가 있습니다."

**핵심 요약**

트랜잭션 전파는 기존 트랜잭션이 있을 때 새로운 작업을 어떻게 처리할지 결정하는 속성이다.

<a name="q23-1"></a>
#### ↳ Q23-1. REQUIRED와 REQUIRES_NEW의 차이는 무엇인가요?

> "REQUIRED는 기존 트랜잭션이 있으면 참여하고 없으면 새로 생성합니다.
>
> 반면 REQUIRES_NEW는 기존 트랜잭션이 있더라도 이를 일시 중단하고 독립적인 새로운 물리적 트랜잭션을 시작합니다.
>
> 따라서 REQUIRES_NEW는 내부 작업의 커밋과 롤백을 외부 작업과 분리해야 할 때 사용할 수 있습니다."

| 구분 | REQUIRED | REQUIRES_NEW |
| --- | --- | --- |
| 발음 | 리콰이어드 | 리콰이어즈 뉴 |
| 기존 트랜잭션 | 참여 | 일시 중단 |
| 기존 트랜잭션이 없을 때 | 새로 생성 | 새로 생성 |
| 내부 커밋·롤백 | 기존 물리 트랜잭션과 공유 | 독립적으로 처리 |
| 주요 주의점 | rollback-only 전파 | 추가 커넥션과 자원 사용 |

**핵심 요약**

REQUIRED는 기존 트랜잭션에 참여하고, REQUIRES_NEW는 독립적인 새 트랜잭션을 시작한다.

<a name="q23-2"></a>
#### ↳ Q23-2. REQUIRED와 REQUIRES_NEW는 롤백에 어떤 차이가 있나요?

> "REQUIRED는 기존 물리적 트랜잭션에 참여하므로 내부 작업이 트랜잭션을 rollback-only로 표시하면 전체 트랜잭션이 롤백될 수 있습니다.
>
> REQUIRES_NEW는 독립적인 트랜잭션을 사용하므로 내부 작업의 커밋과 롤백을 별도로 처리할 수 있습니다.
>
> 단, 내부 예외가 외부로 전파되면 외부 트랜잭션에도 영향을 줄 수 있습니다."

**핵심 요약**

REQUIRED는 하나의 물리적 트랜잭션을 공유하고, REQUIRES_NEW는 커밋과 롤백을 독립적으로 처리한다.

<a name="q23-3"></a>
#### ↳ Q23-3. [핵심 질문] REQUIRED 내부에서 예외가 발생했는데 외부에서 잡으면 어떻게 되나요?

> "내부 REQUIRED 작업이 기존 트랜잭션에 참여하고, 롤백 대상 예외로 인해 rollback-only를 설정했다면 외부에서 예외를 잡더라도 해당 물리적 트랜잭션은 커밋할 수 없습니다.
>
> 외부에서 커밋을 시도할 때 `UnexpectedRollbackException`이 발생할 수 있습니다."

**핵심 요약**

REQUIRED의 내부 실패로 rollback-only가 설정되면 외부에서 예외를 잡아도 최종 롤백될 수 있다.

<a name="q23-4"></a>
#### ↳ Q23-4. REQUIRES_NEW 사용 시 주의할 점은 무엇인가요?

> "기존 트랜잭션을 유지하면서 독립적인 새 트랜잭션을 시작하므로 DB 커넥션이 추가로 필요할 수 있습니다.
>
> 동시 요청이 많으면 커넥션 풀 고갈이나 락 경합이 발생할 수 있으므로 반드시 필요한 작업에 제한적으로 사용하는 것이 좋습니다."

**핵심 요약**

REQUIRES_NEW는 트랜잭션을 분리할 수 있지만 추가 커넥션과 자원 사용을 고려해야 한다.

<a name="q23-5"></a>
#### ↳ Q23-5. [핵심 질문] 그 밖의 트랜잭션 전파 옵션에는 무엇이 있나요?

> "SUPPORTS는 트랜잭션이 있으면 참여하고 없으면 트랜잭션 없이 실행합니다.
>
> MANDATORY는 기존 트랜잭션이 반드시 필요하며, NOT_SUPPORTED는 기존 트랜잭션을 중단하고 트랜잭션 없이 실행합니다.
>
> NEVER는 기존 트랜잭션이 있으면 예외를 발생시키고, NESTED는 지원되는 환경에서 중첩 트랜잭션을 사용합니다."

**핵심 요약**

전파 옵션은 기존 트랜잭션의 존재 여부에 따라 참여, 생성, 중단, 거부 등을 결정한다.

<a name="q24"></a>
### Q24. 트랜잭션 격리 수준과 관련된 이상 현상에는 무엇이 있나요?

> "트랜잭션의 격리 수준이 충분하지 않거나 동시성 제어가 적절하지 않으면 Dirty Read, Non-Repeatable Read, Phantom Read, Lost Update 등의 이상 현상이 발생할 수 있습니다.
>
> 이들은 다른 트랜잭션의 데이터를 읽거나 수정하는 과정에서 발생하는 문제들입니다."

| 이상 현상 | 발음 | 의미 |
| --- | --- | --- |
| Dirty Read | 더티 리드 | 커밋되지 않은 다른 트랜잭션의 변경값 읽기 |
| Non-Repeatable Read | 논 리피터블 리드 | 같은 행을 두 번 조회했는데 값이 달라짐 |
| Phantom Read | 팬텀 리드 | 같은 조건으로 조회했는데 결과 행 집합이 달라짐 |
| Lost Update | 로스트 업데이트 | 한 트랜잭션의 변경이 다른 변경에 덮어써짐 |

**핵심 요약**

Dirty Read는 미커밋 데이터 읽기, Non-Repeatable Read는 행 값 변화, Phantom Read는 결과 행 집합 변화, Lost Update는 수정 결과 유실이다.

<a name="q24-1"></a>
#### ↳ Q24-1. [핵심 질문] 트랜잭션 격리 수준 네 가지는 무엇인가요?

> "표준적인 트랜잭션 격리 수준은 READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ, SERIALIZABLE입니다.
>
> 일반적으로 격리 수준이 높아질수록 동시 트랜잭션 간 간섭은 줄어들지만, 성능과 동시성 측면에서 비용이 증가할 수 있습니다."

| 격리 수준 | 발음 | 기본 개념 |
| --- | --- | --- |
| READ UNCOMMITTED | 리드 언커미티드 | 커밋되지 않은 변경을 읽을 수 있음 |
| READ COMMITTED | 리드 커미티드 | 커밋된 데이터만 읽음 |
| REPEATABLE READ | 리피터블 리드 | 같은 행의 반복 읽기 일관성을 강화 |
| SERIALIZABLE | 시리얼라이저블 | 직렬 실행과 동등한 결과를 보장하는 격리 수준 |

참고: 실제 이상 현상 차단 방식은 DBMS의 MVCC 및 락 구현에 따라 달라질 수 있습니다. 특히 Lost Update는 격리 수준 이름만 보고 무조건 예방된다고 판단하면 안 됩니다.

**핵심 요약**

격리 수준은 동시 트랜잭션이 서로의 작업 결과를 어느 정도 관찰하고 간섭할 수 있는지 결정한다.

<a name="q25"></a>
### Q25. 같은 클래스 내부에서 @Transactional 메서드를 호출하면 어떻게 되나요?

> "Spring의 일반적인 프록시 기반 트랜잭션 관리에서는 같은 클래스 내부 호출이 Proxy를 거치지 않으므로 내부 호출 대상 메서드에 선언된 `@Transactional`이 적용되지 않습니다.
>
> 이를 Self-Invocation 문제라고 하며, 트랜잭션이 필요한 메서드를 별도의 Service로 분리하는 방법을 주로 사용합니다."

**핵심 요약**

같은 클래스 내부의 메서드 호출은 프록시를 거치지 않아 호출 대상의 @Transactional이 적용되지 않는다.

이 질문은 Q2-⑦ Self-Invocation과 동일하므로 개념 설명은 하나로 통합했습니다. AOP와 `@Transactional` 양쪽에서 모두 중요하게 다루는 질문입니다.

<a name="q26"></a>
### Q26. @Transactional이 붙은 메서드에서 외부 API를 호출하면 어떤 문제가 있나요?

> "외부 API의 응답이 지연되면 DB 트랜잭션이 불필요하게 길어질 수 있습니다.
>
> 이로 인해 DB 커넥션과 이미 획득한 락 등이 오래 유지되어 락 경합, 커넥션 풀 부족, 처리량 저하가 발생할 수 있습니다.
>
> 따라서 외부 API 호출과 DB 트랜잭션의 범위를 가능한 한 분리하는 것이 좋습니다."

**핵심 요약**

트랜잭션 안에서 오래 걸리는 외부 API를 호출하면 DB 자원을 오래 점유하여 성능 문제가 발생할 수 있다.

<a name="q26-1"></a>
#### ↳ Q26-1. [핵심 질문] 외부 API 호출과 DB 작업을 분리하면 데이터 일관성은 어떻게 보장하나요?

> "DB 트랜잭션과 외부 API 호출은 일반적으로 하나의 로컬 트랜잭션으로 함께 롤백할 수 없습니다.
>
> 따라서 상황에 따라 Transactional Outbox, 재시도, 멱등성 처리, 보상 트랜잭션 등을 활용하여 실패 상황을 처리해야 합니다."

**핵심 요약**

DB와 외부 시스템을 함께 처리할 때는 트랜잭션 범위를 분리하고 실패 복구 방식을 별도로 설계해야 한다.

<a name="q27"></a>
### Q27. @Transactional은 보통 왜 Service 계층에 적용하나요?

같은 질문의 다른 회차 답변 · [transaction-acid-isolation](../database/transaction-acid-isolation.md#q9-2)

> "트랜잭션은 여러 DB 작업을 하나의 비즈니스 작업 단위로 묶는 것이 중요하기 때문입니다.
>
> Service 계층은 여러 Repository 호출과 비즈니스 규칙을 조합하므로 트랜잭션의 경계를 설정하기에 적절합니다."

**핵심 요약**

트랜잭션 경계는 개별 SQL보다 비즈니스 작업 단위를 관리하는 Service 계층에 두는 것이 일반적이다.

<a name="q28"></a>
### Q28. [핵심 질문] @Transactional을 테스트 코드에 사용하면 어떻게 되나요?

> "Spring 테스트에서 트랜잭션을 지원하는 환경에서는 테스트 메서드에 `@Transactional`을 적용할 경우 기본적으로 테스트 종료 시 롤백합니다.
>
> 하지만 실제 운영에서는 성공한 트랜잭션이 커밋되므로, 테스트의 자동 롤백이 운영 환경의 동작과 완전히 동일하지는 않습니다."

**핵심 요약**

테스트의 @Transactional은 기본적으로 테스트 종료 시 롤백하므로 운영의 커밋 동작과 구분해야 한다.

<a name="q28-1"></a>
#### ↳ Q28-1. [핵심 질문] 테스트의 자동 롤백 때문에 놓칠 수 있는 문제는 무엇인가요?

> "커밋 시점에만 나타나는 동작이나 실제 DB 반영 결과를 검증하지 못할 수 있습니다.
>
> 또한 테스트 트랜잭션과 분리된 `REQUIRES_NEW` 작업은 별도로 커밋될 수 있으므로 테스트 데이터가 예상과 다르게 남을 수 있습니다.
>
> 따라서 필요에 따라 실제 커밋을 검증하는 테스트도 작성해야 합니다."

**핵심 요약**

테스트의 자동 롤백만으로는 실제 커밋 시점의 동작과 독립 트랜잭션을 충분히 검증하기 어렵다.

<a name="q29"></a>
### Q29. [핵심 질문] Flush와 Commit의 차이는 무엇인가요?

> "Flush는 JPA 영속성 컨텍스트의 변경 내용을 SQL로 DB에 반영하도록 동기화하는 과정이고, Commit은 트랜잭션의 변경 사항을 최종 확정하는 과정입니다.
>
> 따라서 Flush가 실행되었다고 반드시 트랜잭션이 커밋된 것은 아닙니다."

**핵심 요약**

Flush는 SQL 반영, Commit은 트랜잭션 확정이다.

<a name="q30"></a>
### Q30. [핵심 질문] @Transactional과 DB 락은 어떤 관계인가요?

> "`@Transactional`은 DB 작업을 트랜잭션 단위로 묶고 관리하는 기능이지만 모든 동시성 문제를 자동으로 해결하는 것은 아닙니다.
>
> 여러 요청이 같은 데이터를 수정하는 경우에는 원자적 UPDATE, 낙관적 락, 비관적 락 등 적절한 동시성 제어가 추가로 필요할 수 있습니다."

**핵심 요약**

@Transactional은 트랜잭션을 관리하지만 모든 Race Condition을 자동으로 해결하지는 않는다.

<a name="section-04"></a>
## 연관 종합 질문

<a name="q31"></a>
### Q31. AOP, Proxy, @Transactional의 관계를 한 문장으로 설명한다면?

> "AOP는 공통 기능을 핵심 비즈니스 로직과 분리하는 프로그래밍 방식이고, Proxy는 Spring AOP에서 이를 구현하는 수단입니다.
>
> `@Transactional`은 Proxy를 활용하여 메서드 실행 전후에 트랜잭션을 시작하거나 참여하고, 커밋과 롤백을 관리하는 대표적인 사례입니다."

**핵심 요약**

AOP는 개념, Proxy는 구현 수단, @Transactional은 대표적인 활용 사례이다.

<a name="q32"></a>
### Q32. @Transactional이 적용되지 않는 이유를 하나의 원리로 설명한다면?

> "Spring의 기본적인 프록시 기반 트랜잭션 관리에서는 프록시를 통해 메서드가 호출되어야 트랜잭션 인터셉터가 동작합니다.
>
> 따라서 같은 클래스 내부 호출이나 Spring이 관리하지 않는 객체에 대한 직접 호출처럼 프록시를 거치지 않으면 해당 메서드의 트랜잭션 설정이 적용되지 않습니다.
>
> 또한 프록시 종류에 따라 메서드 접근 제어자나 final과 관련된 제약이 있습니다."

**핵심 요약**

프록시 기반 @Transactional은 프록시가 호출을 가로챌 수 있어야 적용된다.

<a name="q33"></a>
### Q33. [핵심 질문] @Transactional과 @Async, @Cacheable을 같은 메서드에 사용하면 무엇을 주의해야 하나요?

> "여러 프록시 기반 기능이 함께 적용되면 Advice의 실행 순서와 각 기능의 동작 범위를 고려해야 합니다.
>
> 특히 `@Async`는 다른 스레드에서 실행되므로 호출한 스레드의 트랜잭션 컨텍스트가 자동으로 전달되지 않습니다.
>
> 또한 `@Cacheable`의 캐시 적중으로 실제 메서드 실행이 생략되는 경우 등도 고려해야 합니다."

**핵심 요약**

여러 AOP 기능을 조합할 때는 Advice 순서와 스레드·트랜잭션 경계를 고려해야 한다.

<a name="q34"></a>
### Q34. [핵심 질문] AOP와 Filter, Interceptor는 어떻게 다른가요?

> "Filter는 서블릿 요청·응답 처리 단계에서 동작하고, Spring MVC Interceptor는 Controller 핸들러 호출 전후를 가로챕니다.
>
> 반면 Spring AOP는 Spring Bean의 메서드 실행을 대상으로 공통 기능을 적용합니다.
>
> 따라서 HTTP 요청 처리 전반에 적용할 기능인지, MVC 핸들러에 적용할 기능인지, 비즈니스 메서드에 적용할 기능인지에 따라 선택합니다."

| 구분 | 주요 적용 지점 | 대표 용도 |
| --- | --- | --- |
| Filter (필터) | 서블릿 요청·응답 처리 | 요청·응답 공통 처리, 보안 필터 체인 |
| Interceptor (인터셉터) | Spring MVC 핸들러 | 인증 관련 검사, 요청 로깅 |
| AOP | Spring Bean 메서드 | 트랜잭션, 메서드 실행 시간 측정 |

**핵심 요약**

Filter는 서블릿 요청, Interceptor는 MVC 핸들러, AOP는 Bean 메서드를 중심으로 동작한다.

<a name="q35"></a>
### Q35. [핵심 질문] DB 트랜잭션과 외부 API 호출을 하나의 @Transactional로 묶을 수 있나요?

> "일반적인 Spring의 로컬 DB 트랜잭션은 DB 작업의 커밋과 롤백을 관리하며, 외부 HTTP API에서 이미 수행된 작업까지 자동으로 롤백하지는 못합니다.
>
> 외부 시스템까지 일관성을 유지하려면 멱등성, 재시도, 이벤트 처리 또는 보상 트랜잭션 같은 별도 설계가 필요합니다."

**핵심 요약**

@Transactional은 외부 HTTP API의 작업까지 자동으로 롤백하지 않는다.
