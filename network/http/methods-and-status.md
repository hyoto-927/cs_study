<a name="section-01"></a>
## HTTP 메서드, Safe, Idempotent

<a name="q1"></a>
### Q1. [대표 질문] HTTP 메서드에는 어떤 것이 있으며 GET과 POST는 어떻게 다른가요?

> "HTTP 메서드는 클라이언트가 서버에 요청하는 작업의 종류를 나타내며, 대표적으로 GET, POST, PUT, PATCH, DELETE, HEAD, OPTIONS 등이 있습니다.
>
> GET은 서버의 자원을 조회할 때 사용하며, POST는 서버에 데이터를 전달하여 생성이나 처리를 요청할 때 사용합니다.
>
> GET은 안전성(Safe)과 멱등성(Idempotent)을 가지지만, POST는 일반적으로 둘 다 보장하지 않습니다.
>
> 또한 GET은 주로 URL의 쿼리 파라미터로 조건을 전달하고, POST는 주로 요청 본문(Body)에 데이터를 담아 전달합니다."

| 메서드 | 주된 의미 |
| --- | --- |
| GET | 자원 조회 |
| POST | 생성 또는 작업 처리 |
| PUT | 자원 표현 교체 |
| PATCH | 부분 변경 |
| DELETE | 자원 삭제 |
| HEAD | 본문 없이 응답 메타데이터 조회 |
| OPTIONS | 지원하는 통신 옵션 확인 |

**핵심 요약**

GET은 조회, POST는 처리·생성, PUT은 교체, PATCH는 부분 변경, DELETE는 삭제이다.

<a name="q2"></a>
### Q2. HTTP의 Safe와 Idempotent는 무엇인가요?

> "Safe(세이프)는 클라이언트가 서버의 자원 상태 변경을 요청하지 않는 메서드의 특성입니다.
>
> Idempotent(아이덤포턴트, 멱등성)는 동일한 요청을 한 번 실행하든 여러 번 실행하든 의도된 최종 효과가 같은 특성입니다.
>
> GET은 Safe하면서 멱등하고, PUT과 DELETE는 Safe하지 않지만 멱등합니다."

**핵심 요약**

Safe는 상태 변경을 요청하지 않는 것, Idempotent는 반복 실행해도 의도된 최종 효과가 같은 것이다.

<a name="q2-1"></a>
#### ↳ Q2-1. GET 요청도 서버에 로그를 남기는데 Safe한가요?

> "그렇습니다. Safe는 서버에서 어떤 변화도 발생하지 않는다는 뜻이 아니라 클라이언트가 요청한 동작 자체가 상태 변경을 목적으로 하지 않는다는 의미입니다.
>
> 따라서 조회 요청에 따라 접근 로그나 모니터링 통계가 기록될 수 있습니다."

**핵심 요약**

GET으로 부수적인 로그가 기록되어도 조회 자체가 상태 변경을 요구하지 않는다면 Safe하다.

<a name="q2-2"></a>
#### ↳ Q2-2. GET으로 데이터를 삭제하도록 구현하면 어떻게 되나요?

> "기술적으로 구현할 수는 있지만 HTTP의 Safe 메서드 의미를 위반하는 설계입니다.
>
> 검색 엔진 크롤러나 링크 미리보기, 자동 요청 등으로 의도하지 않은 삭제가 발생할 수 있으므로 자원 삭제에는 DELETE 같은 적절한 메서드를 사용해야 합니다."

**핵심 요약**

GET에 삭제 동작을 구현하면 Safe 의미를 위반하며 자동 요청으로 예기치 않은 변경이 발생할 수 있다.

<a name="q3"></a>
### Q3. 멱등성이 중요한 이유는 무엇인가요?

> "네트워크 장애로 요청의 처리 결과를 확인하지 못했을 때 안전하게 재시도할 수 있는지를 판단하는 데 중요합니다.
>
> 특히 결제나 주문 생성처럼 중복 실행이 문제가 되는 POST 요청은 멱등성 키 등 별도의 중복 처리 방지 방식을 고려해야 합니다."

**핵심 요약**

멱등성은 네트워크 오류에 따른 요청 재시도와 중복 처리 방지에 중요하다.

<a name="q3-1"></a>
#### ↳ Q3-1. DELETE는 첫 번째와 두 번째 응답이 달라도 왜 멱등한가요?

> "첫 번째 DELETE 요청으로 자원이 삭제되고 두 번째 요청에서 404가 반환되더라도, 자원이 삭제된 최종 상태는 같습니다.
>
> 멱등성은 응답 코드가 동일하다는 뜻이 아니라 서버에 대한 의도된 최종 효과가 같다는 의미입니다."

**핵심 요약**

멱등성은 응답의 동일성이 아니라 최종 효과의 동일성을 의미한다.

<a name="q4"></a>
### Q4. POST는 GET보다 보안에 유리한가요?

> "POST가 GET보다 무조건 안전한 것은 아닙니다.
>
> GET의 쿼리 파라미터는 URL에 포함되어 브라우저 기록이나 서버 로그에 남을 수 있지만, POST의 본문도 HTTP로 전송하면 암호화되지 않습니다.
>
> 민감한 정보의 전송을 보호하려면 HTTPS를 사용해야 하며, 인증과 접근 제어도 별도로 적용해야 합니다."

**핵심 요약**

POST는 데이터를 자동으로 암호화하지 않으며 민감한 정보 전송에는 HTTPS가 필요하다.

<a name="q5"></a>
### Q5. GET 요청에도 Body를 넣을 수 있나요?

> "메시지 형식상 GET 요청에 본문을 포함하는 것이 불가능한 것은 아닙니다.
>
> 하지만 GET 요청 본문의 일반적인 의미는 정의되어 있지 않으며 서버나 중간 프록시가 지원하지 않거나 거부할 수 있으므로 일반적인 API에서는 사용하지 않는 것이 좋습니다."

**핵심 요약**

GET에 Body를 넣을 수는 있지만 일반적인 의미가 정의되지 않아 사용을 피하는 것이 좋다.

<a name="q6"></a>
### Q6. POST와 PUT의 차이는 무엇인가요?

> "POST는 서버에 자원 생성이나 특정 작업 처리를 요청하는 메서드입니다.
>
> PUT은 클라이언트가 지정한 대상 URI에 해당하는 자원의 표현을 생성하거나 교체합니다.
>
> PUT은 의미상 멱등하지만 POST는 일반적으로 멱등성을 보장하지 않습니다."

**핵심 요약**

POST는 서버에 처리를 요청하고 PUT은 지정된 자원의 표현을 교체한다.

<a name="q7"></a>
### Q7. PUT과 PATCH의 차이는 무엇인가요?

같은 질문의 다른 회차 답변 · [rest-api](../rest-api.md#q5)

> "PUT은 대상 자원의 전체 표현을 생성하거나 교체하는 의미이고, PATCH는 자원에 부분적인 변경을 적용하는 의미입니다.
>
> PUT은 멱등하지만 PATCH는 변경 방식에 따라 멱등할 수도 있고 아닐 수도 있습니다."

**핵심 요약**

PUT은 자원 표현의 교체, PATCH는 부분 변경이다.

<a name="q7-1"></a>
#### ↳ Q7-1. PUT 요청에서 일부 필드만 전달하면 어떻게 되나요?

> "PUT은 대상 자원의 표현을 교체한다는 의미이므로 일부 필드를 빠뜨리면 서버의 자원 표현 규칙에 따라 해당 필드가 기본값으로 처리되거나 요청이 거부될 수 있습니다.
>
> 기존 값을 유지하면서 특정 필드만 변경하려는 경우에는 PATCH가 더 적합합니다.
>
> 다만 실제 동작은 API 계약을 확인해야 합니다."

**핵심 요약**

PUT은 전체 표현 교체를 의미하므로 일부 필드 누락 시 결과를 API 명세에 따라 확인해야 한다.

<a name="q7-2"></a>
#### ↳ Q7-2. PATCH가 항상 멱등하지 않은 이유는 무엇인가요?

> "PATCH는 수행하는 변경 작업에 따라 결과가 달라질 수 있기 때문입니다.
>
> 예를 들어 가격을 5만 원으로 설정하는 PATCH는 반복하더라도 결과가 같지만, 현재 가격에 1만 원씩 더하는 PATCH는 실행할 때마다 값이 달라집니다."

```
PATCH: price = 50000
→ 반복해도 50000

PATCH: price = price + 10000
→ 반복할 때마다 증가
```

**핵심 요약**

PATCH의 멱등성은 부분 변경을 어떤 방식으로 구현했는지에 따라 달라진다.

<a name="section-02"></a>
## HTTP 상태 코드

<a name="q8"></a>
### Q8. [대표 질문] HTTP 상태 코드는 무엇이며 어떻게 분류하나요?

> "HTTP 상태 코드는 서버가 요청을 처리한 결과를 전달하는 세 자리 숫자입니다.
>
> 1xx는 정보성 응답, 2xx는 성공, 3xx는 리다이렉션 및 캐시 재검증, 4xx는 요청 측 오류, 5xx는 서버 측 오류를 의미합니다."

| 분류 | 의미 | 대표 예시 |
| --- | --- | --- |
| 1xx | 정보성 응답 | 100 |
| 2xx | 성공 | 200, 201, 204 |
| 3xx | 리다이렉션·재검증 | 301, 302, 304 |
| 4xx | 요청 측 오류 | 400, 401, 403, 404 |
| 5xx | 서버 측 오류 | 500, 502, 503, 504 |

**핵심 요약**

HTTP 상태 코드는 1xx 정보, 2xx 성공, 3xx 리다이렉션, 4xx 요청 오류, 5xx 서버 오류로 구분한다.

<a name="q9"></a>
### Q9. 200 OK, 201 Created, 204 No Content의 차이는 무엇인가요?

> "200 OK는 요청을 성공적으로 처리했음을 나타냅니다.
>
> 201 Created는 새로운 자원이 생성되었음을 의미하고 Location 헤더로 자원 주소를 전달할 수 있습니다.
>
> 204 No Content는 요청은 성공했지만 응답 본문을 보내지 않는 경우입니다."

**핵심 요약**

200은 일반 성공, 201은 자원 생성, 204는 본문 없는 성공이다.

<a name="q10"></a>
### Q10. 401 Unauthorized와 403 Forbidden의 차이는 무엇인가요?

> "401 Unauthorized는 유효한 인증 정보가 없거나 인증이 필요한 상황을 나타냅니다.
>
> 403 Forbidden은 서버가 요청을 이해했지만 처리를 거부하는 상황입니다.
>
> 일반적으로 로그인하지 않은 사용자는 401, 인증되었지만 필요한 권한이 없는 사용자는 403으로 처리합니다."

**핵심 요약**

401은 인증이 필요한 상황, 403은 요청 처리가 거부된 상황이다.

<a name="q10-1"></a>
#### ↳ Q10-1. 로그인한 사용자가 관리자 API에 접근하면 어떤 상태 코드를 반환하나요?

> "로그인은 되어 있지만 관리자 권한이 부족하다면 일반적으로 403 Forbidden을 반환합니다.
>
> 인증 정보가 없거나 유효하지 않은 경우에는 401 Unauthorized를 사용할 수 있습니다."

**핵심 요약**

인증된 일반 사용자의 관리자 권한 부족은 일반적으로 403으로 처리한다.

<a name="q10-2"></a>
#### ↳ Q10-2. Spring Security에서 401과 403은 어떻게 처리하나요?

> "Spring Security에서는 인증이 필요하거나 인증을 시작해야 하는 상황에 AuthenticationEntryPoint를 사용할 수 있습니다.
>
> 접근 권한 부족에 대해서는 AccessDeniedHandler가 403 응답을 처리하도록 구성할 수 있습니다.
>
> 실제 응답은 인증 상태와 Security 설정에 따라 달라질 수 있습니다."

**핵심 요약**

Spring Security는 AuthenticationEntryPoint와 AccessDeniedHandler 등을 통해 인증·인가 오류를 처리한다.

<a name="q11"></a>
### Q11. 301과 302의 차이는 무엇인가요?

> "301 Moved Permanently는 자원이 영구적으로 이동했음을 나타내고, 302 Found는 임시 이동을 나타냅니다.
>
> 일부 클라이언트에서는 POST 요청을 리다이렉션하면서 GET으로 변경할 수 있어, 요청 메서드 보존이 필요할 때는 307이나 308을 고려합니다."

**핵심 요약**

301은 영구 이동, 302는 임시 이동이다.

<a name="q11-1"></a>
#### ↳ Q11-1. 304 Not Modified는 언제 사용하나요?

> "조건부 캐시 재검증 요청에서 자원이 변경되지 않았다면 304 Not Modified를 반환할 수 있습니다.
>
> 이때 응답 본문 없이 기존 캐시를 재사용할 수 있습니다."

**핵심 요약**

304는 기존 캐시를 재사용할 수 있음을 알려주는 조건부 요청 응답이다.

<a name="q11-2"></a>
#### ↳ Q11-2. [핵심 질문] 307과 308의 차이는 무엇인가요?

> "307 Temporary Redirect는 메서드를 보존하는 임시 리다이렉션이고, 308 Permanent Redirect는 메서드를 보존하는 영구 리다이렉션입니다."

**핵심 요약**

<a name="q12"></a>
### Q12. 클라이언트 오류 4xx와 서버 오류 5xx의 차이는 무엇인가요?

307은 임시 이동, 308은 영구 이동이며 둘 다 기존 요청 메서드를 유지한다.

> "4xx는 서버가 요청을 처리할 수 없는 원인이 요청과 관련되어 있음을 나타내고, 5xx는 서버가 요청을 정상적으로 처리하지 못했음을 나타냅니다.
>
> 예를 들어 잘못된 입력값은 400 Bad Request, 예상하지 못한 서버 내부 오류는 500 Internal Server Error가 적절할 수 있습니다."

**핵심 요약**

4xx는 요청 측 오류, 5xx는 서버 처리 측 오류이다.

<a name="q12-1"></a>
#### ↳ Q12-1. 서버 코드에서 예외가 발생하면 무조건 500인가요?

> "아닙니다. Java 예외가 서버 내부에서 발생했다고 해서 무조건 500인 것은 아닙니다.
>
> 예를 들어 요청값 검증 실패는 400이나 상황에 적합한 4xx로 처리할 수 있고, 예상하지 못한 내부 장애는 500으로 처리할 수 있습니다."

**핵심 요약**

예외가 발생한 위치보다 실제 오류의 의미를 기준으로 HTTP 상태 코드를 선택한다.

<a name="q13"></a>
### Q13. 502, 503, 504의 차이는 무엇인가요?

> "502 Bad Gateway는 게이트웨이나 프록시가 상위 서버로부터 유효하지 않은 응답을 받은 경우입니다.
>
> 503 Service Unavailable은 서비스가 일시적으로 요청을 처리할 수 없는 경우이고, 504 Gateway Timeout은 게이트웨이가 상위 서버로부터 제시간에 응답받지 못한 경우입니다."

**핵심 요약**

502는 잘못된 상위 응답, 503은 일시적 서비스 불가, 504는 상위 응답 시간 초과이다.

<a name="q13-1"></a>
#### ↳ Q13-1. 502와 504가 발생하면 어디를 확인하나요?

> "502에서는 프록시와 상위 서버 사이의 연결 상태, 애플리케이션 프로세스, 비정상 응답과 로그를 확인합니다.
>
> 504에서는 느린 DB 쿼리, 외부 API 지연, 응답 처리 시간, 타임아웃 설정 등을 확인합니다."

**핵심 요약**

502는 상위 서버 연결·응답 문제, 504는 처리 지연과 타임아웃을 우선 확인한다.

<a name="q13-2"></a>
#### ↳ Q13-2. 외부 API 호출이 실패하면 어떤 상태 코드를 반환하나요?

> "외부 API 오류를 무조건 하나의 코드로 반환하지 않고 현재 서버의 역할과 실패 원인을 고려해야 합니다.
>
> 게이트웨이로서 잘못된 상위 응답을 받았다면 502, 서비스가 일시적으로 이용 불가능하다면 503, 게이트웨이의 상위 서버 응답 시간이 초과되었다면 504를 고려할 수 있습니다.
>
> 외부 API를 호출하는 일반 애플리케이션에서는 클라이언트에 어떤 오류 의미를 전달할지도 별도로 설계해야 합니다."

**핵심 요약**

외부 API 오류의 상태 코드는 실패 원인과 현재 서버의 역할에 따라 결정한다.

<a name="q14"></a>
### Q14. 405, 409, 429는 언제 사용하나요?

> "405 Method Not Allowed는 대상 자원에서 해당 HTTP 메서드를 지원하지 않는 경우입니다.
>
> 409 Conflict는 현재 자원 상태와 요청이 충돌하는 경우, 429 Too Many Requests는 요청 횟수 제한을 초과한 경우입니다."

**핵심 요약**

405는 메서드 불허, 409는 상태 충돌, 429는 요청 제한 초과이다.

<a name="q15"></a>
### Q15. 모든 오류를 500으로 처리하거나 모든 응답을 200으로 처리하면 어떤 문제가 있나요?

> "모든 오류를 500으로 처리하면 요청값 오류와 실제 서버 장애를 구분하기 어렵습니다.
>
> 반대로 실패까지 모두 200으로 처리하면 HTTP 상태 코드의 의미를 활용하는 클라이언트, 모니터링, 캐시 등의 처리에 혼란이 생길 수 있습니다.
>
> 따라서 오류의 원인과 결과에 맞는 상태 코드를 반환하는 것이 좋습니다."

**핵심 요약**

상태 코드는 클라이언트와 서버가 오류의 원인을 구분할 수 있도록 의미에 맞게 사용해야 한다.

<a name="q16"></a>
### Q16. Spring에서 HTTP 상태 코드는 어떻게 지정하나요?

> "Spring에서는 ResponseEntity로 상태 코드, 헤더, 본문을 지정할 수 있습니다.
>
> 또한 `@ResponseStatus`, `@ExceptionHandler`, `@RestControllerAdvice` 등을 활용하여 예외에 따른 응답을 일관되게 관리할 수 있습니다."

```
@PostMapping("/users")
public ResponseEntity<UserResponse> createUser() {
    UserResponse user = userService.createUser();

    return ResponseEntity
            .created(URI.create("/users/" + user.id()))
            .body(user);
}
```

**핵심 요약**

Spring에서는 ResponseEntity와 예외 처리 기능으로 의미에 맞는 HTTP 응답을 구성한다.

<a name="q17"></a>
### Q17. [핵심 질문] 415와 406의 차이는 무엇인가요?

> "415 Unsupported Media Type은 서버가 요청 본문의 형식을 지원하지 않는 경우이고, 406 Not Acceptable은 클라이언트가 요구한 응답 형식을 서버가 제공할 수 없는 경우입니다."

**핵심 요약**

415는 요청 본문 형식 문제, 406은 응답 형식 협상 문제이다.
