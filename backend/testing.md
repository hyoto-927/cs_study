<a name="section-01"></a>
## 대표 질문과 답변

<a name="q1"></a>
### Q1. 단위 테스트와 통합 테스트의 차이와 각각의 목적

**답변**

> "단위 테스트는 가장 작은 단위를 독립적으로 검증하는 테스트입니다. 필요하면 외부 의존성을 테스트 대역으로 바꿔 해당 단위의 동작을 검증합니다. 통합 테스트는 여러 컴포넌트나 실제 DB, 외부 API 등을 함께 연동해서, 실제로 조합되어 잘 동작하는지 검증합니다.
>
> 단위 테스트의 목적은 개별 로직의 정확성을 빠르게 검증하고 회귀 버그를 조기에 잡는 것이고, 통합 테스트의 목적은 컴포넌트 간 연동, 실제 DB 쿼리, 트랜잭션 동작처럼 단위 테스트로는 잡을 수 없는 문제를 검증하는 것입니다."

<a name="q2"></a>
### Q2. 왜 단위 테스트에서는 Mock을 사용하나요?

> 시간, 외부 API처럼 통제하기 어려운 의존성을 대역으로 바꾸면 성공·실패 조건을 재현할 수 있습니다. 호출 여부가 계약일 때 Mock으로 상호작용을 검증합니다. 순수 함수처럼 대역 없이 검증할 수 있는 단위도 많습니다.

<a name="q3"></a>
### Q3. Mock, Stub, Fake의 차이는 무엇인가요?

> "Stub은 미리 정해진 값을 반환. Mock은 여기에 더해 행위 자체를 검증 가능. Fake는 실제로 동작하는 간이 구현체."

<a name="q4"></a>
### Q4. 단위 테스트에서 Mock을 과도하게 사용하면 어떤 부작용이 있나요?

> "실제 컴포넌트 간 연동 문제를 잡지 못해 '가짜 통과'가 생길 수 있고, 리팩토링할 때마다 테스트가 깨지는 문제가 발생."

<a name="q5"></a>
### Q5. 통합 테스트는 왜 단위 테스트보다 느린가요?

> 여러 컴포넌트를 초기화하거나 DB와 통신하면 추가 비용이 들어 통합 테스트가 느려지는 경우가 많습니다. 테스트 종류는 실제 검증 경계로 나눕니다. 단위 테스트에 Mock이 필수인 것은 아니며 통합 테스트가 항상 전체 Spring 컨텍스트를 띄우는 것도 아닙니다.

<a name="q6"></a>
### Q6. 단위 테스트가 있는데 통합 테스트도 필요한 이유는?

> "각 컴포넌트가 개별적으로 정상이어도, 연결 지점에서 문제가 발생할 수 있기 때문입니다. 단위 테스트는 이런 연결 문제를 잡아내지 못합니다."

<a name="q7"></a>
### Q7. 통합 테스트에서 @Transactional을 붙이면 롤백되는데, 이때 주의점은?

> "커밋 시점의 동작이 재현이 안되는 문제가 있습니다."

<a name="q8"></a>
### Q8. 슬라이스 테스트란 무엇이며 어떤 어노테이션이 있나요?

> "애플리케이션 전체가 아니라 특정 계층만 잘라서 가볍게 테스트하는 방식입니다. @WebMvcTest(Controller), @DataJpaTest(Repository), @JsonTest 등이 있습니다."

<a name="q9"></a>
### Q9. @SpringBootTest와 @WebMvcTest, @DataJpaTest의 차이는?

> "@SpringBootTest는 전체 컨텍스트를 다 띄워 통합 테스트에 씁니다. @WebMvcTest는 Controller 계층만, @DataJpaTest는 JPA 관련 컴포넌트만 슬라이스로 띄워 필요한 계층만 빠르게 테스트합니다."

<a name="q10"></a>
### Q10. 테스트 피라미드란 무엇인가요?

> "단위 테스트는 많이, 통합 테스트는 그보다 적게, E2E 테스트는 가장 적게 작성해야 한다는 가이드입니다. 아래로 갈수록 빠르고 저렴하고, 위로 갈수록 느리고 비싸지만 사용자 흐름에 가깝기 때문입니다."

<a name="q11"></a>
### Q11. 단위 테스트와 통합 테스트 중 어느 것을 더 많이 작성하는 것이 좋을까요?

> "테스트 피라미드에 따르면 단위 테스트를 훨씬 많이 작성하는 것이 좋습니다. 단위 테스트는 빠르고 저렴해서 부담 없이 많이 쌓을 수 있고, 통합 테스트는 느리고 무거우니 핵심 연동 경로 위주로 최소한만 작성하는 것이 효율적입니다."

<a name="q12"></a>
### Q12. E2E 테스트와 통합 테스트의 차이는?

> "통합 테스트보다 E2E가 더 넓은 범위입니다. E2E는 사용자 관점에서 브라우저부터 서버, DB까지 전체 흐름을 테스트합니다."

<a name="q13"></a>
### Q13. 테스트 커버리지가 100%면 버그가 없다고 할 수 있나요?

> "아닙니다. 커버리지는 코드가 실행되었는지만 보여줄 뿐, 결과가 올바른지는 보장하지 않습니다. 테스트 케이스의 품질이 더 중요합니다."

<a name="q14"></a>
### Q14. 테스트가 많으면 무조건 좋은가요?

> "아닙니다. 실행 시간, 유지보수 비용, 변경 시 수정 비용이 늘어나므로, 중요한 비즈니스 로직 중심으로 작성해야 합니다."
